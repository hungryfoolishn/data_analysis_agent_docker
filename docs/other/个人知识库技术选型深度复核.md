3. 你的 SHA-256 文档 ID 怎么落到 RAGFlow？
这里有一个容易踩坑的地方：RAGFlow 的 document_id 与你定义的 SHA-256 文档 ID 不是同一个概念。

建议建立外部映射：
sha256_document_id
    ├── original_path
    ├── extracted_text_path
    ├── ragflow_dataset_id
    ├── ragflow_internal_document_id
    ├── ingestion_status
    └── last_indexed_at


将 SHA-256 放进上传文件的元数据或自定义映射表，不要假设上传文件名、内部 document ID 或文件夹路径天然就是稳定的 SHA-256 主键。

另外，你现有的 3,000 万字符是提取后的文本规模，不是 3,000 万 Token。对成本、切块和上下文窗口进行估算时，要以实际 tokenizer 和分块结果为准。

A4. 槽位 A 的最终结论
明确答案：暂时保留 RAGFlow，不建议现在直接替换。

理由是你已经确定了架构，且需求把引用溯源放在很高的位置。RAGFlow 的文档管理、解析、检索和引用能力比较完整，官方也明确支持 TXT 上传 API。它的主要疑点是资源消耗、解析和索引维护成本，而不是完全缺少自动化接口。

但有两个条件：
- 如果服务器达到官方建议的 4 核、16GB RAM 起步配置，先测完整 Compose 栈，再决定是否继续。
- 如果实际可用内存明显低于 16GB，或者持续维护多个重量级服务违背“维护时间≈0”，应把 LightRAG 作为首个替代 POC，而不是因为它叫 LightRAG 就直接认为一定更省资源。
下一步最值得做的实验： 将同一批 100 篇中文文档导入 RAGFlow 和 LightRAG，统一模型、切块、查询集和硬件，比较检索命中率、引用定位、资源峰值、增量更新耗时。这样能在不推翻现有架构的情况下获得可靠结论。

B2. 可直接验证的 API 调用
以下示例通过思源 Kernel API 创建读书笔记。请先在思源中创建笔记本，并从当前版本获取正确的笔记本 ID 和 API Token。
import requestsBASE_URL = "http://127.0.0.1:6806"TOKEN = "YOUR_SIYUAN_API_TOKEN"NOTEBOOK_ID = "YOUR_NOTEBOOK_ID"session = requests.Session()session.headers.update({    "Authorization": f"Token {TOKEN}",    "Content-Type": "application/json",})def create_book_note(path: str, markdown: str) -> str:    resp = session.post(        f"{BASE_URL}/api/filetree/createDocWithMd",        json={            "notebook": NOTEBOOK_ID,            "path": path,            "markdown": markdown,        },        timeout=30,    )    resp.raise_for_status()    result = resp.json()    if result.get("code") != 0:        raise RuntimeError(result.get("msg", "SiYuan API failed"))    return result["data"]



调用示例：
doc_id = create_book_note(    "/AI读书/机器学习/梯度下降",    """# 梯度下降## 核心论点梯度提供局部变化方向的信息。## 思维模型迭代优化。## 行动启示在实际问题中检查学习率与收敛情况。""")print("创建的思源文档 ID:", doc_id)



这里创建的是思源内部文档，不是直接在 Docker 工作区批量写入 .sy 私有文件。后者涉及内部格式和索引一致性，不应作为首选自动化路径。
B3. 如何存储你的 SHA-256 文档 ID？
建议在笔记的文档块上设置自定义属性：
def set_source_hash(block_id: str, document_hash: str):    resp = session.post(        f"{BASE_URL}/api/attr/setBlockAttrs",        json={            "id": block_id,            "attrs": {                "custom-document-id": document_hash,                "custom-note-type": "ai-book-summary",            },        },        timeout=30,    )    resp.raise_for_status()    result = resp.json()    if result.get("code") != 0:        raise RuntimeError(result.get("msg", "Attribute update failed"))



注意：上面的代码展示的是 API 的调用方式，不是声称已经在你的思源版本上实测通过。block_id 必须是实际存在的块 ID，不能随便传入刚创建文档时返回的 ID 而不核验它所对应的块类型。

建议首次写入后，使用 /api/attr/getBlockAttrs 读回属性，确认 custom-document-id 已成功保存。

B5. 思源还是 Trilium？
我的建议是继续使用思源。

不是因为思源的 Markdown 批量导入没有问题，而是因为你的核心任务不是导入一堆独立 Markdown 文件，而是：
1. 由 Python 调用 Kernel API 创建笔记。
2. 将笔记放入指定的知识目录。
3. 写入 document_id 等自定义属性。
4. 通过块引用建立关联。
5. 人工在 PC 客户端批注和修正。
6. 定期核验笔记、原始文档和外部映射是否一致。
这套流程在思源的 API 能力范围内是可实现的。

替代条件： 如果你实际测试发现思源 API 在批量写入时有难以规避的同步、更新或稳定性问题，再用 TriliumNext 做同一批 100 篇笔记的对照测试。Trilium 的 ETAPI 更适合以外部脚本直接操纵笔记对象，但这还不足以证明它在你的整体使用体验上更优。
B6. 必须实现的幂等写入机制
不能只写一个 create_note() 函数。你需要一个可重试的同步器：
- 写入前查询 document_id 是否已有对应笔记。
- 不存在则创建；存在则按策略更新已有笔记或新建版本。
- 将 document_id、笔记 ID、写入时间和状态保存到外部映射表。
- 写入成功后读回属性，验证内容和回链。
- 网络超时后先查询再重试，避免产生重复笔记。
尤其要记住：SHA-256 是原文内容的身份标识，LLM 生成的笔记内容可能因提示词或模型变化而变化。建议另加 pipeline_version、prompt_version 和 model_id，这样原文不变时也可以追踪笔记生成版本。

C4. 参考实现：自研流水线的最小可行设计
我的建议不是一开始开发多 Agent 系统，而是先实现一个可恢复的批处理程序。
1. 输入清单

document_id · 文本路径 · 标题 · 文档类型


2. 结构识别与章节切分

保留章节标题、页码、段落 ID 和原文位置


3. 分章节摘要与证据提取

调用国产 LLM API，输出符合 JSON Schema 的结果


4. 全书综合与验证

去重、论点综合、引用校验、失败重试


5. 生成 Markdown + 写入思源 API

写入 document_id、版本号、章节和原文引用


结构化输出建议
每本书至少生成以下字段：
{
  "document_id": "sha256-of-original-content",
  "pipeline_version": "1.0",
  "model_id": "your-model-id",
  "title": "书名",
  "summary": "全书主旨",
  "core_arguments": [],
  "mental_models": [],
  "evidence": [
    {
      "claim": "核心论点",
      "source_locator": {
        "chapter": "章节标题",
        "page": 42,
        "paragraph_id": "p-000123"
      },
      "quote": "对应原文摘录"
    }
  ],
  "limitations": [],
  "actionable_insights": [],
  "open_questions": []
}


这只是建议的数据格式。页码和段落 ID 必须来自提取管线的真实定位信息，不能让 LLM 自己编造页码。如果现有纯文本没有页码映射，就应先补建定位索引，再生成可核验的引用。
重要的工程边界
- 不要一次把整本书塞进一个 Prompt。 章节分段、分层摘要和最终综合可以降低上下文溢出风险。
- 不要只保存最终总结。 保留分章节摘要和证据记录，以便发现错误后局部重跑。
- 不要每次都重新生成所有笔记。 用 document_id + pipeline_version + prompt_version + model_id 管理生成任务状态。
- 不要把生成成功当作质量合格。 至少检查 JSON Schema、引用是否存在、引用是否支持对应论点、笔记是否重复。
- 不要把每本书的所有章节都生成独立思源文档。 先生成一篇总笔记，章节摘要和证据作为内部结构或附属文档，避免知识树迅速膨胀。
C5. 自研 200 行脚本是否足够？
可以先用 200 行左右实现原型，但不应把“200 行”当成生产系统的目标。

最小原型只需要：读取清单、分段调用 LLM、校验结构化输出、合并总结、调用思源 API。

生产版通常还需要持久化任务状态、速率限制、超时、重试、断点续跑、版本追踪、日志、引用验证和失败告警。它可能超过 200 行，但这部分代码比部署一个功能庞大的文档分析平台更贴合你的目标。
C6. 槽位 C 的明确结论
用自研 Python 流水线作为核心，借鉴 ChatPaper 的分段总结、PapersGPT 的阅读后沉淀，以及 DocsGPT 的 API 化设计。

暂时不建议部署一个新的完整 AI 笔记平台。你已经有 RAGFlow、思源和 FTS5，再增加一个完整文档问答平台，反而会带来重复索引、重复数据和维护负担。

你的增量更新流程比较简单：

发现新文件 → 提取文本 → 计算 SHA-256 → 入 RAGFlow → 生成读书笔记（可选）→ 写入思源 → 验证 → 通知

D2. 为什么当前不建议引入 n8n？
你的主要流程由 Python 脚本完成，且任务状态、文档 ID 和笔记映射都已经有明确的设计方向。

引入 n8n 后，还需要管理：
- 工作流平台的数据库与配置备份。
- 工作流升级后的兼容性。
- API 凭证和访问权限。
- Python 脚本调用与工作流状态之间的一致性。
- 重试时如何避免重复入库、重复生成笔记。
- 当 n8n 自己故障时，如何恢复尚未执行的任务。
这些并非 n8n 不具备相应能力，而是对于当前只有一个使用者、流程相对固定的系统来说，它带来的管理面可能大于收益。

如果未来你需要几十条不同的工作流、多个通知渠道、复杂条件分支，或者希望通过图形界面随时调整流程，那么 n8n 的价值会明显上升。
D3. 最小可靠方案：cron + Python + 通知
建议将流程分为一个发现任务和一个处理任务。
cron
  ├── scan_files.py
  │     └── 写入待处理任务
  │
  └── process_queue.py
        ├── 提取与校验
        ├── RAGFlow API 入库
        ├── 可选：AI 读书笔记
        ├── 思源 API 写入
        ├── 校验与更新状态
        └── 失败告警


每个任务都应该有状态，例如：

DISCOVERED → EXTRACTED → INDEXED → NOTE_GENERATED → NOTE_PUBLISHED → VERIFIED

失败则记录 FAILED，并附带失败阶段、错误原因、重试次数和下次重试时间。
调度示例
# 每天凌晨 02:00 扫描新增资料
0 2 * * * /opt/knowledge/.venv/bin/python /opt/knowledge/scan_files.py

# 每 15 分钟处理待处理任务
*/15 * * * * /opt/knowledge/.venv/bin/python /opt/knowledge/process_queue.py


这是调度示例，不代表脚本本身已经实现了可靠重试。生产部署前还需要加入：
- 文件锁或数据库任务锁，防止同一批任务被并发执行。
- 失败重试次数上限和退避间隔。
- 任务状态持久化。
- 成功与失败的日志记录。
- 进程退出码检查。
- 备份和恢复测试。
手机通知
优先选择你能长期使用、服务器可访问的通知渠道，例如 Telegram Bot、企业微信机器人或其他已有通知服务。

通知内容应至少包括：
- 批次 ID 和失败阶段。
- 成功、失败、跳过数量。
- 失败文档的 document_id。
- 错误摘要与日志位置。
- 是否已自动重试、是否需要人工介入。
API Key、完整原文和敏感内容不应直接放进通知消息。
D4. 何时再引入 n8n？
满足以下任一条件时，再考虑引入：
- 你希望在浏览器中管理和修改流程，而不是维护 cron 配置。
- 流程出现大量分支，或者需要连接更多外部服务。
- 需要可视化的执行历史和人工审批。
- 多个独立任务之间需要统一调度、重试和告警管理。
在那之前，使用 Python 把幂等性、状态机和通知实现好，比先部署一个工作流平台更有价值。

10.1 document_id 契约应该落在哪里？
建议把文档 ID、任务状态和跨系统映射保存在一个独立的 SQLite 元数据数据库中，而不是让任何一个平台承担全部主数据职责。
数据对象	建议存放位置	作用
document_id	外部元数据数据库	由原始文件内容 SHA-256 计算，跨系统保持一致
原始文件路径与哈希	外部元数据数据库 + 文件清单	追踪来源、去重、检测变更
RAGFlow 内部文档 ID	外部映射表	把外部文档身份映射到 RAGFlow
FTS5 文档主键	FTS5 外部映射表	支持独立重建全文索引
思源文档 ID / 块 ID	外部映射表 + 思源自定义属性	实现笔记回链和幂等更新
AI 笔记生成版本	任务记录 + 笔记元数据	追踪模型、Prompt、模板变化
页码 / 章节 / 段落 ID	提取文本的定位索引、笔记证据	支持引用验证与原文定位

这里有一个很重要的边界：SHA-256 表示文件内容身份，不表示文件路径身份。 同一个文件移动目录后，document_id 应保持不变；文件内容改变后，哈希也会改变。

如果你后续需要识别“同一本书的不同版本”，可以额外增加 work_id 或 book_family_id，把版本归并和原始文件身份分开处理。

十二、建议的执行顺序

2. 验证思源写入闭环。 创建 10 篇测试笔记，设置 custom-document-id，建立引用，执行重复写入和失败重试，确认不会重复生成笔记。
3. 开发 AI 读书原型。 先挑选 20 本有代表性的书和讲义，测试不同类型的模板、分章节总结、引用验证和国产 LLM API 成本。
4. 建立任务状态与告警。 先用 cron + Python；在连续运行稳定之后，再决定是否需要 n8n。
5. 逐步扩大至 5,970 份文档。 按批次运行，保留失败队列和处理记录；先验证质量和成本，再对全量资料启动自动读书。
最终，我建议保留你的四个槽位，不增加第五个核心平台：
- RAGFlow：AI 问答和引用溯源。
- SiYuan：个人知识沉淀和人工修正。
- SQLite FTS5：独立全文检索兜底。
- 自研 Python 流水线：自动阅读、证据提取、结构化总结和跨系统同步。
这套架构最重要的不是把 6,000 本书全部导入 AI，而是建立一个能够持续增量运行、出现错误可以恢复、每条重要结论都能回到原文验证的知识吸取体系。先把这条闭环做好，再扩展 Agent、图谱和更复杂的自动化，长期维护成本会更可控。
