# B1：M2.7.3 AssetResolver / 快照消费

## 1. 阶段目标

让 Runtime 能够根据执行请求中的 `input_asset_ids`：

1. 找到对应的 `DataAsset`；
2. 从 `DataAsset.source_metadata` 解析 SnapshotReference；
3. 通过 SnapshotStore 加载 DataFrame；
4. 将 DataFrame 注入执行请求的输入命名空间；
5. 让现有 Executor 使用这些输入完成分析。

本阶段只消费已存在的快照，**不得重新执行 SQLite SQL 来恢复数据**。

## 2. 实施前检查

先检查当前 HEAD 中以下内容：

- `DataAsset` 模型及 `source_metadata` 结构；
- M2.7.2 SnapshotStore 的公开接口；
- `AnalysisRuntime.register_sqlite_result()` 的注册逻辑；
- Runtime 请求模型及 `input_asset_ids` 的传递路径；
- Python Executor 如何接收 DataFrame / namespace；
- 现有 DataCache、RuntimeArtifact 与资产恢复逻辑；
- 相关测试文件及现有命名约定。

实施前确认 SnapshotReference 的实际字段和序列化格式，**不要在 Resolver 中另造一套快照引用结构**。

## 3. 设计与实现任务

### 3.1 定义 AssetResolver 边界

建议职责：

- 输入：Runtime、资产 ID 列表或已解析的 DataAsset 列表；
- 输出：执行器可消费的输入数据映射；
- 负责资产查找、引用解析、快照加载和错误归一化；
- 不负责 SQL 执行、Planner、报告生成或 Evidence 生成。

Resolver 应尽量依赖抽象接口，而不是直接访问 Runtime 内部持久化文件。

### 3.2 解析输入资产

对每个 `input_asset_id`：

1. 从 Runtime 的资产登记表中查找 DataAsset；
2. 资产不存在时返回明确错误；
3. 读取 `source_metadata`；
4. 判断是否包含受支持的 SnapshotReference；
5. 验证引用结构及版本；
6. 交给 SnapshotStore 加载 DataFrame。

不能把用户提供的路径直接当作快照路径。路径必须由已登记、已验证的 SnapshotReference 提供，并经过 SnapshotStore 的路径边界检查。

### 3.3 注入执行请求

根据现有 Executor 接口选择最小改动方案：

- 将解析结果放入现有 DataFrame namespace；或
- 为 Runtime request 增加明确的 resolved inputs 字段；或
- 通过现有执行上下文传递。

优先复用现有输入机制，不要同时引入新的 Executor 框架。

输入映射应保持稳定、可预测，并避免多个资产同名时静默覆盖。需要定义确定性的命名规则或返回冲突错误。

### 3.4 错误与安全策略

以下情况必须明确失败：

- 输入资产 ID 不存在；
- 资产不支持快照输入；
- SnapshotReference 缺字段或版本不兼容；
- 快照文件不存在；
- 物理哈希或逻辑数据校验失败；
- 路径越界；
- DataFrame 加载失败；
- 输入命名冲突。

禁止：

- 静默跳过无法解析的输入资产；
- 回退为重新执行 SQL；
- 将不可信路径直接交给文件读取函数；
- 在错误信息中泄露敏感的绝对路径或连接信息。

### 3.5 保留资产语义

Resolver 输出或执行上下文应能保留：

- asset_id；
- source type / provenance；
- snapshot reference；
- row / column 信息；
- truncated 状态；
- 输入解析错误信息。

本阶段不要求完成完整 Evidence 系统，但不能丢失后续 M6 所需的来源信息。

## 4. 测试任务

### Unit tests

- 正常解析单个 SQLite QueryResultAsset；
- 正常解析多个输入资产；
- 资产不存在；
- 无 SnapshotReference；
- SnapshotReference 格式错误；
- 快照缺失；
- 哈希校验失败；
- 路径越界；
- 多资产命名冲突；
- 空 DataFrame；
- 含 null、日期、数值类型的 DataFrame；
- truncated 元数据被保留；
- SnapshotStore 异常被转换为稳定的 Runtime 错误。

### Integration tests

- SQLite query result 注册为 DataAsset；
- Resolver 从资产 ID 解析快照；
- DataFrame 注入执行请求；
- Executor 使用 DataFrame 完成简单分析；
- 验证执行结果与预期一致；
- 验证没有重新执行 SQL。

## 5. 验收标准

- Runtime 可通过 `input_asset_ids` 消费 SQLite 查询结果；
- 快照由 SnapshotStore 加载并校验；
- Executor 能实际使用解析后的 DataFrame；
- 失败情况明确、可诊断；
- 无 SQL 重执行；
- 现有文件 Runtime 行为不回归；
- 相关测试通过；
- 文档说明 Resolver 接口、输入命名和错误契约。

## 6. 不在本阶段实施

- 通用 Planner；
- SQLite SQL Tool；
- Evidence 完整链路；
- Runtime V2 默认切换；
- 报告生成；
- 多 Agent。

## 7. 建议提交

- `feat(runtime): resolve sqlite snapshot inputs`
- `test(runtime): cover sqlite asset resolution`

# B2：M2.7.4 Runtime 恢复 E2E

## 2. 实施任务

8. 恢复 DataAsset；
9. 通过 Resolver 加载 DataFrame；
10. 执行分析并验证结果。

测试必须创建新的 Runtime 实例，不能只验证同一实例内的重复读取。

### 2.2 验证恢复契约

检查：

- asset_id 是否稳定；
- SnapshotReference 是否完整恢复；

确保错误明确，不允许静默重新执行 SQL。

### 2.4 验证清理与生命周期

- 临时测试目录使用现有安全清理方式；
- 不删除非测试生成的文件；
- 不因重复恢复而重复创建快照；
- 验证 dedupe 逻辑在重启前后保持一致。

## 3. 测试任务

- restart 后重复注册/dedupe；
- 缺失快照；

- 元数据损坏；

## 4. 验收标准

- Runtime 不依赖旧进程内存；

- 简单趋势分析；
- 基础异常值识别；

具体分析工具应复用现有实现，不在 M3 中引入复杂 Agent 规划。

- 路径与上传目录边界；
- 文件大小限制；
- 行数 / 内存限制；

# B4：M4 通用 Planner

## 1. 阶段目标

将用户的自然语言分析目标转化为**结构化、可校验、可执行的分析计划**。

Planner 负责规划，不负责直接执行 Python 或 SQL。

目标链路：

**User Goal → Planner → Plan Validation → Runtime Execution → Results**

## 2. 设计原则

- Planner 输出结构化计划，不输出任意可执行代码；
- 计划步骤使用已注册的工具和能力；
- 数据计算由确定性工具完成；
- LLM 不直接伪造计算结果；
- 计划必须经过校验；
- 不支持的任务应明确拒绝或要求澄清；
- Planner 不绑定宏观经济或金融语义。

## 3. 实施任务

### 3.1 定义 Plan Schema

建议包含：

- plan_id；
- user_goal；
- selected input asset IDs；
- steps；
- step_id；
- operation / tool name；
- input references；
- parameters；
- expected output type；
- dependency references；
- validation status；
- explanation / rationale；
- error handling policy。

每个步骤必须明确输入、操作、输出及依赖关系。

### 3.2 定义可执行操作集合

优先支持少量通用操作，例如：

- inspect / summarize；
- filter；
- select columns；
- groupby / aggregate；
- sort；
- join（仅在明确支持时）；
- trend；
- anomaly detection；
- chart preparation。

操作名和参数必须来自 allowlist，不能让 Planner 任意创造工具名。

### 3.3 Plan Validator

验证：

- schema 合法；
- 输入资产存在；
- 列名存在；
- 参数类型正确；
- 操作在 allowlist 中；
- 步骤依赖有效；
- 无循环依赖；
- 输入输出类型兼容；
- 资源限制满足；
- 不允许任意文件访问或任意代码执行。

### 3.4 Planner 与 Executor 分离

- Planner 只生成计划；
- Validator 校验计划；
- Runtime 执行已校验计划；
- Executor 返回结构化结果；
- Planner 不直接修改 Runtime 状态；
- 计划失败时返回可诊断错误。

### 3.5 失败处理

明确区分：

- 用户目标不清晰；
- 数据不支持该分析；
- 计划结构错误；
- 工具不支持；
- 执行失败；
- 结果验证失败。

对需要用户补充信息的情况，返回具体澄清问题，而不是生成猜测性计划。

## 4. 测试任务

- 简单统计计划；
- 分组聚合计划；
- 多步骤依赖计划；
- 非法工具名；
- 非法列名；
- 参数类型错误；
- 依赖循环；
- 输入资产不存在；
- 不支持的分析目标；
- Planner 输出不符合 schema；
- Validator 拒绝非法计划；
- 验证通过的计划可被 Runtime 执行。

## 5. 验收标准

- Planner 输出稳定的结构化计划；
- 所有计划执行前经过 Validator；
- 不存在 Planner 直接执行任意代码的路径；
- 计划可追踪、可记录、可复现；
- 至少覆盖常见通用分析问题；
- 不引入领域专属规则；
- Golden Planner tests 通过。

## 6. 建议提交

- `feat(planner): add structured analysis plans`
- `feat(planner): validate executable plans`
- `test(planner): add golden plan validation cases`

# B5：M5a Runtime V2 默认/回退策略收敛

## 1. 阶段目标

解决 Runtime V2 默认路径与 fallback 配置之间的策略冲突，建立明确的 Runtime 选择、回退、观测与切换门禁。

B0 已发现：

`RUNTIME_V2_FALLBACK_ENABLED` 默认 `true`，与 gate 文档中“fallback 必须显式配置”的策略不一致。

本阶段应根据实际 Runtime 行为与测试结果修正，而不是只修改文档。

## 2. 实施任务

### 2.1 梳理 Runtime 路由

明确：

- Runtime V1 / V2 的选择入口；
- 配置优先级；
- fallback 触发条件；
- fallback 是否会改变执行语义；
- fallback 是否可能掩盖 V2 错误；
- API / UI / 测试环境是否使用不同配置。

### 2.2 定义配置契约

明确以下配置的职责和默认值：

- Runtime V2 enabled；
- Runtime V2 default；
- fallback enabled；
- fallback conditions；
- strict mode；
- test override。

配置名称应表达清晰，避免多个配置控制同一行为。

### 2.3 修正默认 fallback 行为

按 gate 决策：

- fallback 默认关闭，或要求显式配置开启；
- strict mode 下，V2 失败必须暴露错误；
- fallback 只能用于明确允许的兼容场景；
- 不允许将数据错误、校验错误或安全错误静默转交 V1；
- fallback 必须记录触发原因和最终 Runtime 版本。

### 2.4 增加可观测性

记录：

- 实际选择的 Runtime；
- fallback 是否发生；
- fallback 原因；
- 原始异常类别；
- 最终执行结果；
- 关联 task / execution ID。

避免日志输出敏感数据或完整用户数据。

### 2.5 更新 gate 文档

明确：

- 默认 Runtime；
- fallback 策略；
- 启用条件；
- 回退条件；
- 禁止回退的错误类型；
- 测试环境如何覆盖配置；
- M8 切换门禁如何验证。

## 3. 测试任务

- V2 正常执行；
- V2 失败且 fallback 关闭；
- V2 失败且 fallback 显式开启；
- 不可回退错误；
- 可回退兼容错误；
- 配置缺失时的默认行为；
- 环境变量覆盖；
- Runtime 选择日志；
- API / UI / CLI（如存在）路由一致性。

## 4. 验收标准

- 默认行为与 gate 文档一致；
- fallback 不会静默掩盖关键错误；
- fallback 开关可明确控制；
- 回退原因可观测；
- 相关 Runtime 路由测试通过；
- V1 保留为兼容路径，但不成为 V2 的隐式执行依赖。

## 5. 建议提交

- `fix(runtime): make fallback policy explicit`
- `test(runtime): cover runtime routing and fallback gates`
- `docs(runtime): clarify runtime v2 default policy`

# B6：M6 SQLite SQL Tool 与 Evidence

## 1. 阶段目标

在现有 SQLite 只读连接、有界查询、QueryResultAsset、SnapshotStore、AssetResolver 基础上，提供可控 SQL 分析工具，并将查询结果与后续报告证据关联。

本阶段不重新实现底层 SQLite 安全能力，应复用 M2 已完成模块。

## 2. 实施任务

### 2.1 SQL Tool 接口

定义工具输入：

- database / source ID；
- SQL；
- 参数；
- 允许的输出限制；
- 需要的 schema context（如适用）。

定义工具输出：

- execution ID；
- SQL fingerprint；
- query metadata；
- result asset ID；
- row count；
- truncation status；
- execution status；
- error information。

工具返回结构化结果，不直接生成自然语言结论。

### 2.2 SQL 安全校验

复用现有只读 SQLite 执行能力，并确保：

- 只允许单条只读 SELECT / CTE；
- 禁止 DDL / DML；
- 使用参数绑定；
- 表和列名来自 schema allowlist；
- 查询超时生效；
- 行数和结果大小限制生效；
- 错误信息不泄露敏感连接信息；
- SQL 执行失败不生成伪成功资产。

### 2.3 查询结果资产注册

SQL Tool 成功执行后：

1. 获取有界查询结果；
2. 保留 truncation metadata；
3. 注册 QueryResultAsset；
4. 持久化快照；
5. 生成 asset ID；
6. 返回可供后续步骤引用的资产。

不允许报告或 Planner 直接读取临时 DataFrame 绕过资产登记。

### 2.4 Evidence 模型

定义最小证据结构，例如：

- evidence_id；
- evidence_type；
- source asset ID；
- execution ID；
- operation / SQL fingerprint；
- input asset IDs；
- output asset ID；
- relevant parameters；
- validation status；
- provenance；
- truncation status。

Evidence 应关联真实执行记录和真实资产，不允许仅由 LLM 自行生成证据。

### 2.5 EvidenceCollector

在工具执行成功后收集：

- 输入资产；
- 执行操作；
- 执行参数；
- 输出资产；
- 关键元数据；
- 结果验证状态。

失败执行应记录失败事件，但不能伪造成功 Evidence。

## 3. 测试任务

- 合法 SELECT；
- 合法 CTE；
- 参数化查询；
- 非法 SQL；
- 多语句；
- DDL / DML；
- 超时；
- 超行数 / 超结果大小；
- 截断结果；
- QueryResultAsset 注册；
- SnapshotStore 持久化；
- Evidence 与 execution / asset 关联；
- 执行失败不生成成功证据；
- Evidence 恢复与序列化。

## 4. 验收标准

- SQL Tool 复用 M2 的安全执行机制；
- SQL 结果成为可持久化、可解析的 DataAsset；
- Evidence 能追溯到输入、操作、执行和输出；
- truncation 信息被保留并可供后续报告使用；
- 不允许 LLM 伪造 SQL 执行结果；
- SQLite SQL Tool Golden tests 通过。

## 5. 不在本阶段实施

- 任意数据库类型的通用 SQL Tool；
- 数据库写入；
- 财务领域 SQL 模板；
- 多 Agent；
- 默认 Runtime 切换决策。

## 6. 建议提交

- `feat(tools): add readonly sqlite sql tool`
- `feat(evidence): collect sql execution evidence`
- `test(tools): add sqlite sql tool golden tests`

# B7：M7 报告与验证能力

## 1. 阶段目标

将 Planner、Runtime、工具执行结果和 Evidence 汇总为结构化分析报告，并验证报告中的关键结论是否有真实数据支持。

核心原则：

**报告可以由 LLM 组织表达，但关键数字和结论必须绑定执行结果与 Evidence。**

## 2. 实施任务

### 2.1 定义 Report Schema

建议包含：

- report_id；
- task_id；
- user_goal；
- executive summary；
- analysis sections；
- findings；
- tables / charts references；
- evidence references；
- limitations；
- validation status；
- generated_at。

每条 Finding 应具有：

- finding_id；
- claim；
- supporting evidence IDs；
- referenced assets；
- calculation / operation reference；
- confidence or validation status；
- limitation notes。

### 2.2 报告生成器

报告生成分为两步：

1. 确定性整理结构化结果和 Evidence；
2. LLM 对已验证内容进行自然语言组织。

LLM 不应自行补充不存在的数字、样本量、时间范围或统计结论。

### 2.3 Report Validator

检查：

- 所有 Evidence ID 是否存在；
- 所有引用资产是否存在；
- Finding 是否有支持证据；
- 报告数字是否与结构化结果一致；
- 是否引用了截断数据；
- 是否声明了数据限制；
- 是否存在无来源关键结论；
- 是否有明显的输入/输出不一致。

验证器应返回结构化错误和警告，而不是只返回一个布尔值。

### 2.4 结果与图表引用

报告引用表格、图表或数据结果时，应使用 RuntimeArtifact / DataAsset ID，而不是复制一份无法追溯的数据。

图表数据必须来自已执行并验证的结果。

### 2.5 失败与部分报告

明确处理：

- Planner 失败；
- 部分工具执行成功；
- Evidence 缺失；
- 报告验证失败；
- 数据截断；
- 某些分析步骤不支持。

不能把部分成功包装成完整成功报告。

## 3. 测试任务

- 正常报告生成；
- Finding 有 Evidence；
- 缺失 Evidence；
- 无效 Evidence ID；
- 报告数字与结果不一致；
- truncation warning；
- unsupported analysis limitation；
- 部分执行成功；
- LLM 输出不符合 schema；
- 报告序列化与恢复；
- 报告引用资产可追溯。

## 4. 验收标准

- 报告结构稳定；
- 每条关键 Finding 可追溯；
- 关键数字来自真实执行结果；
- Validator 能发现缺证据、错误引用和截断风险；
- 报告能区分成功、部分成功和失败；
- 报告 Golden tests 通过。

## 5. 建议提交

- `feat(report): add evidence-backed analysis reports`
- `feat(report): validate findings and evidence`
- `test(report): add report validation golden tests`

# B8：M8 Golden E2E 与默认 Runtime 切换门禁

## 1. 阶段目标

通过文件数据与 SQLite 数据两条 Golden E2E 主链路，验证 DeepAnalyze 的通用分析 MVP 达到默认 Runtime 切换条件。

M8 是验证与决策阶段，不应在此阶段补做大量新功能。

## 2. Golden 数据集与问题集

### 2.1 文件数据 Golden

至少覆盖：

- CSV；
- Excel；
- Parquet；
- 中文列名；
- 日期字段；
- 缺失值；
- 分组聚合；
- 趋势分析；
- 异常值分析；
- 图表准备；
- 数据类型边界；
- 空数据或异常输入。

### 2.2 SQLite Golden

使用现有 Golden SQLite fixture，覆盖：

- schema introspection；
- 只读 SQL 查询；
- 参数化查询；
- join；
- aggregate；
- bounded result；
- truncation；
- QueryResultAsset；
- SnapshotStore；
- AssetResolver；
- Runtime 执行；
- Evidence；
- 报告生成与验证。

### 2.3 Golden Question Set

每个问题定义：

- user question；
- input dataset / asset；
- expected plan constraints；
- expected tool / operation；
- expected result properties；
- expected Evidence requirements；
- expected report properties；
- allowed variance；
- failure criteria。

不要只比较 LLM 最终自然语言文本；应优先比较结构化结果、计划约束、Evidence 和报告 schema。

## 3. E2E 测试链路

文件链路：

**上传文件 → DataSource → DataAsset → Planner → Validator → Runtime → Analysis → Evidence → Report → Report Validator**

SQLite 链路：

**SQLite Source → SQL Tool → QueryResultAsset → SnapshotStore → AssetResolver → Planner/Runtime → Evidence → Report → Report Validator**

每条链路都应覆盖：

- 正常成功；
- 输入错误；
- 工具失败；
- 结果截断；
- 证据缺失；
- Runtime 重启恢复；
- 部分成功；
- 失败报告。

## 4. 默认 Runtime 切换门禁

建议设定以下门禁：

### 功能门禁

- 文件 Golden E2E 全部通过；
- SQLite Golden E2E 全部通过；
- Planner 输出经过校验；
- Evidence 与报告链路可追溯；
- Runtime 重启恢复通过；
- 关键失败路径符合预期。

### 安全门禁

- SQL 只读限制通过；
- 文件路径边界通过；
- 资源限制有效；
- 不存在任意代码执行路径；
- fallback 不会掩盖关键错误；
- 不存在无证据报告成功的路径。

### 稳定性门禁

- 测试可重复运行；
- 无依赖旧进程内存；
- 无临时文件泄漏；
- 资产去重与恢复行为稳定；
- 关键日志和错误可诊断。

### 产品门禁

- Runtime V2 的默认行为明确；
- fallback 策略显式配置；
- V1 兼容路径仍可按策略使用；
- 文档、配置和实际行为一致；
- 已知限制有清晰记录。

## 5. 切换策略

建议分阶段切换：

1. CI / 测试环境使用 Runtime V2；
2. 开发环境默认使用 Runtime V2；
3. 对照运行并记录差异；
4. 满足门禁后调整产品默认值；
5. 保留明确、可观测的兼容回退；
6. 后续再评估 V1 移除时间。

不能仅因 Golden tests 通过就删除 V1；切换决策应同时考虑错误率、兼容性和可回退性。

## 6. 交付物

- 文件 Golden E2E 报告；
- SQLite Golden E2E 报告；
- Golden Question Set；
- Runtime V2 Gate Report；
- 已知限制与风险清单；
- 默认 Runtime 切换决策；
- 对应配置和文档更新。

## 7. 验收标准

- 文件与 SQLite 两条主链路完整通过；
- 重启恢复、Evidence、报告验证均纳入 E2E；
- 关键安全和失败路径有覆盖；
- 测试结果可重复；
- 配置、文档和实际 Runtime 行为一致；
- 明确给出“允许切换 / 暂缓切换”的结论及依据。

## 8. 建议提交

- `test(runtime): add file and sqlite golden e2e`
- `docs(runtime): add runtime v2 gate report`
- `feat(runtime): enable runtime v2 by default`（仅在门禁通过后单独提交）
