你这个判断是对的：项目现在最需要的不是继续修某个财务语义边界，而是重新明确产品目标、系统边界和阶段验收标准。

从仓库最近的提交看，工作已经集中在 Runtime V10.4 的财务期间语义、同比/环比意图识别、冲突阻断和测试上。它们是有价值的正确性工作，但如果没有一个明确的“何时完成、完成后做什么”的总路线，就很容易陷入：
发现边界问题 → 修复 → 增加测试 → 再发现边界问题 → 继续修复

这不是项目最终目标，而是某个分析能力模块的局部打磨。

我建议把 DeepAnalyze 重新定位为：

一个面向通用表格与数据库、以宏观经济和企业财务为首批领域的数据分析 Agent 平台。

它的核心任务不是“回答一个财务问题”，也不是“预测股票涨跌”，而是：

获取可信数据 → 理解数据与口径 → 规划分析 → 调用可验证的分析工具 → 形成证据 → 输出可追溯报告。

其中，金融数据和金融分析是首批领域能力包；通用数据分析 Runtime 才是平台核心。
一、重新定义最终产品：不是“金融 Agent”，而是“数据分析平台 + 金融分析能力包”
建议把产品分成三层：

这三个层次要解耦。

不要把“金融财务分析”写死在通用 Runtime 里。
金融领域的指标定义、报告期语义、宏观指标知识、财报规则，应当属于金融 Domain Pack；文件/数据库接入、任务执行、证据追踪、报告生成，则是通用平台能力。

场景 A：用户上传数据

上传 CSV / Excel / Parquet，或连接 PostgreSQL / MySQL 等数据库：

平台自动完成数据理解、分析计划、计算、图表和报告。

场景 B：用户直接问公开数据

平台识别指标与国家、选择数据源、拉取数据、对齐频率和单位，再执行分析。

场景 C：上市公司财报分析
分析某上市公司近五年收入、利润、现金流和负债变化，识别盈利质量风险。

平台获取财报、统一报表期间和指标口径，执行可审计的财务分析。

场景 D：多源综合研究
分析美国通胀、就业和利率变化，并结合中国出口数据，解释近期宏观环境。

核心设计原则
1. Agent 负责规划和解释，确定性工具负责计算。

例如 GDP 增长率、CPI 同比、财务比率、缺失值处理、统计检验等，都应该由 Python / SQL 工具执行，不让 LLM 直接心算或编造数字。

2. 不要把所有分析都设计成多 Agent。

默认采用一个 Planner + 一组确定性分析工具。只有复杂任务才启用并行分析角色，例如：
- 趋势分析；
- 结构分析；
- 异常分析；
- 归因分析；
- 风险/反例分析。
这能避免简单问题也进入复杂的 Agent 讨论流程。

3. 证据链是平台基础设施，不是某个金融模块的功能。

每个结论都应关联：
- 数据集和来源；
- 采集时间、数据期间；
- 使用的指标和口径；
- 执行的 SQL / Python 工具；
- 计算结果；
- 图表或证据表；
- 验证状态。
4. 数据获取和分析执行必须分离。

采集系统负责获取和整理数据；分析 Runtime 只消费已经注册的数据集。这样未来换数据源，不需要重写分析 Agent。

四、重新制定实施路线：先交付产品闭环，再逐步增强
建议停止以 V10.x 的小版本不断追加功能为主线，改成以可交付里程碑推进。
阶段 0：项目收敛与冻结
目标： 让当前代码回到一个清晰、可维护的基线。
- 暂停继续扩展金融语义边界测试。
- 保留已有的期间解析、财务指标、Evidence、Execution Plan 等能力。
- 把现有功能整理成模块清单：已完成、可复用、待重构、暂不做。
- 明确当前默认执行路径和兼容路径。
- 将“金融期间语义”标记为金融 Domain Pack，而不是通用 Runtime 的核心。
验收： 一份架构现状图、模块职责表、已知问题清单、下一阶段明确范围。

停止条件： 不要求消灭所有潜在边界问题；只修复阻碍后续开发的 P0/P1 问题。

阶段 1：通用数据分析 MVP
目标： 先证明上传文件和数据库可以完成端到端分析。

支持：
- CSV / Excel / Parquet；
- SQLite / PostgreSQL / MySQL 只读连接；
- Schema / 字段类型 / 缺失值 / 数据质量理解；
- 自然语言分析任务规划；
- SQL / pandas / DuckDB 执行；
- 趋势、分组、异常、相关性、描述统计；
- 图表、证据表、报告；
- 多轮追问与会话状态。
建议重点： 研究 DuckDB 作为文件和多数据源查询引擎，避免为每种文件格式写一套分析逻辑。

验收场景：

用户上传一个 Excel，提出“按地区分析近三年销售趋势，找出异常并解释”，系统能完成分析并给出可追溯报告。

阶段完成标准： 至少 10 个固定测试数据集、30 个分析问题，形成可重复的验收集。

阶段 2：数据获取平台 MVP
目标： 从“用户自己上传数据”扩展到“系统能获取公开数据”。

先做数据源注册机制：
DataSource Adapter

  ├── provider
  ├── dataset / series
  ├── parameters
  ├── fetch()
  ├── normalize()
  ├── validate()
  └── provenance


第一批建议只做：
- 中国宏观：GDP、CPI、PPI、失业/就业、货币金融；
- 美国宏观：GDP、CPI、失业率、非农、利率；
- 中国上市公司财报；
- 美国 SEC 财报。
每个数据源要有：
- 数据目录；
- 指标元数据；
- 单位、频率、地区、时间范围；
- 数据发布时间与观察期间；
- 来源 URL / API 参数；
- 缓存、重试、限流；
- 数据质量和更新时间记录。
验收场景：

用户问“中国和美国近十年 CPI 对比”，系统自动获取、标准化、对齐数据并生成分析报告。

阶段完成标准： 至少 4 个数据源 Adapter 稳定运行，支持手动刷新和定时更新。

阶段 3：宏观经济分析 Domain Pack
目标： 让平台真正理解宏观经济指标，而不只是把数据画出来。

加入：
- 指标定义和口径知识；
- 国家、地区、币种、频率、单位处理；
- 同比、环比、年化、累计值等转换；
- GDP、CPI、PPI、就业、利率、货币、贸易等分析模板；
- 多指标联动分析；
- 宏观事件时间线；
- 数据修订与发布滞后说明。
分析能力包括：
- 趋势与周期；
- 指标之间的领先/滞后关系；
- 历史区间比较；
- 异常变化；
- 多种解释假设及反例；
- 结论置信度和局限。
验收场景：

“分析美国近五年通胀与就业变化，比较加息前后差异，并说明哪些结论有数据支持。”

阶段完成标准： 形成宏观指标目录、标准分析模板和可复现的宏观分析报告。

阶段 4：上市公司财报分析 Domain Pack
目标： 把现有财务分析代码整合成一个可用的企业分析能力包。

加入：
- 财报获取与版本管理；
- 三大报表标准化；
- 年报、季报、累计值、单季值语义；
- 财务指标计算；
- 盈利质量、现金流、偿债、营运效率分析；
- 同业对比；
- 财报异常和风险信号；
- 财报证据与原文定位。
现有 V10.4 的期间语义工作放在这里继续完善。

但今后财务语义问题只在以下情况继续修复：
- 已有验收场景失败；
- 真实用户问题导致错误结果；
- 财务口径可能造成重大误导；
- 阻碍下一阶段功能。
不再为了覆盖所有理论上可能出现的自然语言表达而无限扩展。

阶段完成标准： 能完成中国上市公司与美国 SEC 公司基础财报分析，结果有来源、口径和计算证据。

阶段 5：研究型多 Agent 能力
目标： 在前面数据和计算可靠的基础上，引入 TradingAgents 风格的分析协作。

仅针对复杂研究任务启用：
Planner

  ├── Fundamental Analyst
  ├── Trend / Statistical Analyst
  ├── Risk & Counterargument Analyst
  └── Research Synthesizer


各 Agent 必须引用已有数据和工具结果，不允许凭空补充数值。

验收场景：

“分析某公司过去五年的财务变化，并结合宏观环境，给出经营风险、支持证据、反面解释和数据局限。”

阶段完成标准： 多 Agent 只提升复杂研究质量，不破坏确定性计算、证据链和报告可复现性。

六、以后怎么避免再次陷入循环评估？
建立一个明确的“停止规则”。
1. 每个里程碑只围绕验收目标开发
每次实施前必须明确：
- 本阶段要交付什么用户场景；
- 哪些模块会修改；
- 哪些功能明确不做；
- 验收数据和问题是什么；
- 通过标准是什么。
2. 问题分级
等级	处理规则
P0	数据错误、执行安全、系统不可用，立即修复
P1	核心验收场景失败、严重误导性结论，当前阶段修复
P2	边界表达、体验改善，记录到 backlog
P3	理论可能性、未来扩展，暂不处理

P2/P3 不应自动打断当前里程碑。
3. 每个阶段设置冻结点
阶段验收通过后：
- 固定验收集；
- 固定关键架构；
- 只接受新发现的 P0/P1；
- 新需求进入下一阶段；
