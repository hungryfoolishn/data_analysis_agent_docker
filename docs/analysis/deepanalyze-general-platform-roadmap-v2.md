# DeepAnalyze 通用平台优化路线图 v2

> 版本：v2.0
>
> 日期：2026-08-16
>
> 状态：后续优化的主执行文档
>
> 决策：真实 WrenAI HTTP/SDK Adapter 与受治理查询联调暂缓，不进入近期实施队列。

## 1. 为什么需要新路线图

第一版方案解决的是“DeepAnalyze 应该成为什么”的问题。经过十一批实施，项目已经从聊天式分析 Agent 演进为具有以下能力的平台内核：

- DataAsset、Task、Run、Step、Execution、Artifact 等稳定对象；
- Run 历史、步骤重试、暂停、计划修订、确认和恢复；
- Finding 到字段、数据版本、执行代码和产物的证据血缘；
- 不依赖 LLM 的报告重建和可复现分析包；
- 分组比较、时间趋势、贡献拆解、异常检测等正式分析工具；
- API、SSE 和分析工作台；
- 本地文件语义上下文和稳定的外部语义契约。

现在的主要矛盾已经变化。问题不再是“有没有平台对象”，而是：

1. 无法用一套稳定评测回答“这次优化是否真的更好”；
2. Python 执行仍是线程内 `exec`，超时后无法可靠终止，隔离性不足；
3. 数据仍以单文件、整表载入内存为主，面对大文件、多表和 SQL 数据源时能力不足；
4. 初始 Plan 仍主要由实际工具调用动态形成，不是执行前可审查的完整计划；
5. 正式分析方法只有第一组基础工具，复杂分析仍大量依赖自由 Python；
6. Streamlit 请求生命周期与长任务执行耦合，暂停、恢复和并发控制仍不够稳健；
7. JSON 文件持久化适合当前单机验证，但不适合作为多进程、长周期运行的最终状态存储；
8. 缺少面向生产环境的资源预算、权限、脱敏、审计和发布门禁。

因此，v2 路线图不再以 WrenAI 接入为主线，而以“可评测、可扩展、可治理、可运营的通用分析平台”为主线。

## 2. 当前阶段的产品定位

DeepAnalyze 当前定位保持不变：

> 一个领域无关的数据分析执行与证据平台。它负责规划、计算、检查、产物、血缘和交互，不负责定义某个行业的业务真理。

近期输入仍以本地文件、内存数据和受控测试数据为主。将来无论接入 WrenAI、数据库、数据仓库还是企业 API，都应通过 DataAsset 和执行器契约进入平台，而不是侵入 Agent 核心。

## 3. 本路线图明确不做什么

以下事项在 v2 近期批次中冻结：

- 不实现真实 WrenAI HTTP/SDK Adapter；
- 不读取或复制 WrenAI 的本体、语义模型和内部目录；
- 不建设特定行业的指标库、业务规则库或专家结论库；
- 不把相关性分析包装成自动因果推断；
- 不为了演示效果引入复杂微服务、Kubernetes 或分布式计算集群；
- 不在缺少评测样本时继续无边界增加 Agent Prompt 和硬编码报告规则；
- 不用更多自由 Python helper 代替正式工具契约。

WrenAI 的现有 `SemanticResolution` 契约继续保留并维持兼容，但只有在业务知识、接口稳定性、测试数据和联调环境同时具备后才恢复实施。

## 4. v2 的核心方法：先建立鉴赏能力，再扩大能力

后续优化采用以下闭环：

```text
建立基线任务与事实表
        ↓
运行当前版本并记录缺陷
        ↓
只针对可复现缺陷实施一批优化
        ↓
执行单元测试、契约测试、评测集和服务器回归
        ↓
比较质量、稳定性、耗时和成本
        ↓
达到门禁才部署，否则修正或回滚本批设计
```

任何“看起来更智能”的功能，如果不能在评测集、性能测试或操作流程中体现可验证收益，不进入主分支。

## 5. 平台级评价体系

### 5.1 分析正确性

- 数值事实正确率；
- 分组、时间窗口、分母和去重口径正确率；
- 贡献分解对账误差；
- Join 后行数与度量膨胀检测率；
- 异常、缺失和小样本边界披露率；
- Finding 与证据绑定完整率。

### 5.2 分析完整性

- 是否回答用户问题，而非只输出通用 EDA；
- 是否覆盖任务所需的指标、维度和时间窗口；
- 数据不支持时是否明确停止；
- 是否区分事实、相关线索、假设和因果结论；
- 建议强度是否与证据等级一致。

### 5.3 运行可靠性

- Run 完成率；
- 首次报告通过率；
- 无效工具调用率；
- 平均步骤数和无效重复步骤数；
- 暂停、恢复、修订和失败步骤重试成功率；
- 超时后残留进程、悬挂步骤和损坏状态文件数量。

### 5.4 性能与成本

- 各尺寸数据集的加载、画像和核心方法耗时；
- 峰值内存、临时磁盘和产物大小；
- LLM 调用次数、输入/输出 token 和估算成本；
- 缓存命中率以及缓存节省的计算时间；
- 前端首事件时间和最终完成时间。

### 5.5 可复现与治理

- 分析包文件完整率和哈希验证率；
- 删除原报告后确定性重建一致性；
- Finding 血缘完整率；
- 路径逃逸、未授权数据访问和敏感字段泄露测试通过率；
- 同一输入版本和参数是否得到一致的确定性计算产物。

## 6. 目标架构

```text
WebUI / API Client
        |
        v
Task Control API
  create / plan / confirm / pause / resume / cancel / retry
        |
        v
Durable Run Orchestrator
  state / event log / checkpoint / resource budget
        |
        +-----------------------------+
        |                             |
        v                             v
Data Access Layer              Analysis Method Layer
file / table / query           profile / compare / trend
sample / scan / cache          contribution / tests / quality
        |                             |
        +-------------+---------------+
                      v
              Isolated Executors
              Python / DuckDB / statistics
                      |
                      v
Artifact + Evidence + Lineage
                      |
                      v
Report / Analysis Package / Evaluation
```

Agent 的职责收敛为：理解问题、生成计划、选择正式方法、检查结果和组织 Finding。数据读取、计算隔离、缓存、血缘和质量门禁由确定性平台代码负责。

## 8. 第十二批：分析评测基线与发布门禁

### 目标

让项目第一次能够用数字回答“分析质量提高了还是下降了”。

### 实施内容

1. 新建 `evaluation/` 模块，不复用只验证对象存在的旧 benchmark。
2. 定义 `EvaluationCase`：
   - 数据文件与内容哈希；
   - 用户问题；
   - 必须出现的事实；
   - 禁止出现的结论；
   - 必需指标、维度和时间窗口；
   - 允许的数据限制结论；
   - 数值容差；
   - 期望产物和血缘要求。
3. 建立第一组领域无关评测数据：
   - 单表员工或组织数据；
   - 订单与退款数据；
   - 时间序列销售数据；
   - 小样本和高缺失数据；
   - 含重复主键的数据；
   - 多表客户、订单和产品数据；
   - 指标无法回答问题的数据；
   - 含极端值和口径歧义的数据。
4. 将评分拆成确定性评分与 LLM 辅助评分。数值、字段、血缘、章节、运行状态只能由确定性代码评分。
5. 记录每次评测的模型、Prompt 版本、代码提交、数据哈希、耗时、token 和失败原因。
6. 生成可比较的 JSON 和 HTML 报告。
7. 在发布脚本中加入门禁：关键用例失败、正确率下降或出现 P0 回归时不得发布。

### 首期验收

- 至少 12 个数据集、30 个任务和 100 条可确定验证的事实；
- 同一历史结果重复评分完全一致；
- 能区分计算错误、证据缺失、过度结论、流程失败和报告缺陷；
- 输出当前版本基线，而不是预先设定一个没有测量依据的高分；
- 后续每一批都必须附带与该基线的对比。

### 不做

- 不用一个总分掩盖不同类型的问题；
- 不让 LLM 裁判数值是否正确；
- 不把“文字更长”当成质量提高。

## 9. 第十三批：Python 执行进程隔离

### 目标

替换当前线程内 `exec` 的核心风险，使超时、取消和资源限制真正可执行。

### 实施内容

1. 将 Python 执行移动到独立子进程，主进程不直接执行生成代码。
2. 定义 `ExecutorRequest` 和 `ExecutorResult`：代码、输入资产、允许目录、超时、内存预算、stdout、stderr、退出码和产物清单。
3. 超时或取消时终止进程树，不保留后台线程。
4. 工作目录限制在 Session workspace；禁止访问 `.env`、宿主密钥和其他 Session。
5. 使用显式允许的环境变量，不把后端完整环境传入执行器。
6. 对生成产物做二次路径校验、文件类型校验、大小限制和哈希登记。
7. 将 `python_repl` 改造成隔离执行器客户端；需要跨步骤的变量改为显式中间数据资产，而不是依赖不可序列化的进程内 namespace。
8. 保留兼容期，但新分析默认走隔离执行路径。

### 验收

- 无限循环在超时后 5 秒内无残留子进程；
- 取消 Run 能终止正在执行的 Python；
- 路径逃逸和读取其他 Session 文件被拒绝；
- 内存超限产生结构化失败，而不是拖垮 API 容器；
- 现有正式工具和分析包不受影响；
- 评测集质量不下降，运行失败可明确归因。

## 10. 第十四批：DataSource、扫描、采样与缓存

### 目标

把 DataAsset 从“已加载 DataFrame 的元数据”升级为可扫描、可采样、可版本化的数据访问协议。

### 实施内容

1. 定义 `DataSource` 与 Adapter：CSV、Excel、Parquet、内存表和查询结果。
2. 将 `scan_schema`、`preview`、`sample`、`materialize`、`estimate_rows` 变成统一接口。
3. 采样策略显式记录：方法、随机种子、目标行数、分层字段、原始行数和覆盖范围。
4. EDA 明确区分全量统计、抽样估计和近似统计。
5. 对大 CSV 使用分块扫描；Parquet 优先列裁剪和谓词下推。
6. 缓存 key 至少包含：输入内容哈希、Adapter 版本、选取字段、过滤条件、参数和代码版本。
7. 缓存产物进入 Artifact/Execution 血缘，并支持容量和 TTL 清理。
8. 将恢复策略中的临时 `df.sample()` 提示替换为平台采样协议。

### 验收

- CSV、Parquet 和内存表进入正式方法时输出契约一致；
- 大文件画像无需完整复制 DataFrame；
- 抽样结论在报告和 Finding 中自动带有抽样披露；
- 修改源文件后旧缓存绝不命中；
- 相同数据版本和参数可稳定命中缓存；
- 性能测试记录不同规模下的峰值内存和耗时曲线。

## 11. 第十五批：DuckDB 与多表粒度治理

### 目标

建立可靠的 SQL 和多表分析路径，而不是让 Agent 在 Python 中随意 merge。

### 实施内容

1. 使用 DuckDB 作为本地文件和中间表的正式 SQL 执行引擎。
2. 新增 `execute_sql` 正式工具，只允许只读查询和受控 workspace 数据源。
3. SQL Execution 记录查询文本、输入资产、输出 Schema、行数、耗时和查询计划摘要。
4. 引入表粒度声明：主键候选、实体粒度、时间粒度和唯一性状态。
5. 新增 `inspect_join`：连接键空值、左右唯一性、匹配率、未匹配率和预估基数。
6. 新增 Join 膨胀门禁：实际行数、理论关系类型、一对多/多对多识别和指标重复风险。
7. Join 结果必须登记为新的 DataAsset，保留父资产和查询血缘。
8. 多表分析包包含 SQL 和输入表版本。

### 验收

- 至少支持 CSV/Parquet 多表只读查询；
- 多对多 Join 默认需要显式确认，不能静默进入指标计算；
- 对已知测试数据能准确报告匹配率和度量膨胀倍数；
- SQL 结果可被正式分析方法直接消费；
- 非只读语句、外部路径和扩展安装被拒绝。

## 12. 第十六批：执行前结构化 Plan

### 目标

在第一次分析计算前形成可审查计划，而不是等工具调用发生后才得到步骤列表。

### 实施内容

1. 定义 `AnalysisPlan`：目标、成功标准、输入资产、指标、维度、时间字段、步骤、依赖、预算和需要确认的位置。
2. 增加 `propose_plan` 阶段，计划通过 Schema 和任务约束生成。
3. 用确定性检查器验证：
   - 工具是否存在；
   - 字段是否存在；
   - 依赖是否形成 DAG；
   - 输出是否能支持后续步骤；
   - 是否超过步骤、时间或资源预算。
4. 低风险计划可按配置自动确认；存在多表 Join、高基数、全量大数据或语义歧义时必须人工确认。
5. 执行器严格从 Plan 取下一步；临时偏离必须生成 Plan Revision，不能只在模型文本中解释。
6. 将当前动态 RuntimeStep 兼容路径保留给旧 Run，新的 Run 使用 plan-first 协议。

### 验收

- 开始计算前工作台已经显示完整第一版计划；
- 无效字段和不存在的工具在执行前被拒绝；
- 任何新增、删除、换序和改参都有 plan version；
- 实际 Execution 能逐一关联到计划步骤；
- 计划完成后没有未解释的动态步骤。

## 13. 第十七批：第二组正式分析方法

### 目标

覆盖高频通用分析路径，减少自由 Python 的使用比例。

### 方法清单

- `profile_distribution`：分位数、偏度、长尾和缺失；
- `analyze_correlation`：相关系数、样本量、缺失处理和非因果说明；
- `compare_periods`：同比、环比、自定义窗口和可比性检查；
- `calculate_ratio`：显式分子、分母、去重和零分母处理；
- `analyze_funnel`：阶段顺序、实体去重和转化分母；
- `analyze_retention`：队列定义、观察窗口和右删失披露；
- `test_group_difference`：效应量、置信区间、检验假设和多重比较说明；
- `analyze_concentration`：Top-N、HHI 或累计占比；
- `run_sensitivity_check`：去极值、替代窗口、替代聚合和头部组剔除。

### 工具共同要求

- 显式输入资产、字段、过滤、粒度和聚合；
- Pydantic 输出 Schema；
- 结构化失败条件；
- 表格或图表 Artifact；
- Execution 和 Finding 血缘；
- 小样本、缺失、分母、抽样和多重检验披露；
- 不输出未经验证的因果措辞。

### 验收

- 评测集中至少 80% 的常见计算不再需要 `python_repl`；
- 正式工具计算有独立数值金标准测试；
- Agent 使用正式工具后的平均无效步骤下降；
- 工具失败能给出可执行的参数修正建议。

## 14. 第十八批：自动分析质量检查器

### 目标

把质量控制从“检查报告里有没有某些文字”升级为检查数据、计算、Finding 和报告之间是否一致。

### 实施内容

1. 新建 `AnalysisQualityResult`，分为 error、warning 和 disclosure。
2. 检查 Finding 中的数值是否能在绑定 Execution/Artifact 中找到。
3. 检查百分比是否存在分母、统计范围和去重规则。
4. 检查趋势是否包含时间窗口，分组结论是否包含真实比较组。
5. 检查抽样、过滤、缺失和 Join 风险是否进入 Data Context。
6. 检查贡献之和与总变化是否对账。
7. 检查相关性措辞、因果措辞和证据等级是否一致。
8. 报告验证失败返回机器可执行的修订任务，不让模型反复猜测缺失章节。

### 验收

- 人工植入的数值错配、分母遗漏、时间窗遗漏和血缘断裂均能稳定识别；
- 相同错误最多经过一次结构化反馈即可修复；
- `finish_report` 重复拒绝次数明显低于第十二批基线；
- 不适用的领域规则不会污染通用数据集。

## 15. 第十九批：异步 Task API 与可靠控制面

### 目标

让分析任务独立于某个 HTTP 流和 Streamlit 脚本生命周期。

### 实施内容

1. `POST /analysis/tasks` 创建任务并立即返回 task/run ID。
2. 后端 Worker 独立执行 Run，SSE/WebSocket 只订阅事件，不拥有任务生命周期。
3. 增加事件游标和断线续传，客户端重连不取消任务。
4. pause、resume、cancel、confirm、revise 直接操作 Run 控制状态。
5. 明确幂等 key，防止重复提交创建两次分析。
6. 加入队列状态、并发配额、等待时间和取消传播。
7. 旧 `/v1/chat/completions` 保持兼容，但内部转为 Task API 客户端。

### 验收

- 关闭浏览器或 Streamlit rerun 不会取消后台 Run；
- 重新连接可以从事件游标继续；
- 暂停发生在可恢复检查点，不产生悬挂 Step；
- 相同幂等 key 不会重复执行；
- API 重启后未完成任务可以恢复或明确标记不可恢复。

## 16. 第二十批：分析工作台 2.0

### 目标

把工作台从“实时展示运行记录”提升为适合计划、执行、检查和对比的操作界面。

### 核心视图

1. Task 列表：状态、数据、问题、耗时、成本、更新时间；
2. Plan 视图：依赖、预算、确认点、版本 Diff；
3. Data 视图：Schema、样本、质量、粒度和数据版本；
4. Execution 视图：输入、参数、代码/SQL、stdout、错误和重试；
5. Artifact 视图：表格预览、图表、下载和来源；
6. Finding 视图：结论、证据等级、血缘完整性和争议标记；
7. Run 对比：计划、参数、数据版本、Finding 和报告差异；
8. Evaluation 视图：版本之间的质量与性能变化。

### 交互要求

- 表格和长 JSON 不只放在折叠文本中；
- 暂停、确认、修订、重试、取消具有明确状态反馈；
- 危险操作需要确认；
- 页面刷新不丢任务状态；
- 移动端保证查看，桌面端优先支持高密度评审；
- 不在前端复制后端业务状态机。

### 验收

- 用户可在不读服务器日志的情况下定位失败步骤；
- 可从 Finding 一次跳转到数据、计算和产物；
- 可视化 Plan Revision 差异；
- 长任务控制不依赖正在消费的同步请求。

## 17. 第二十一批：持久化与多进程一致性

### 目标

把运行元数据从单文件快照升级为支持并发、查询和恢复的持久化层。

### 实施内容

1. 先以 SQLite + 迁移机制替代 JSON 作为权威元数据存储，保留 JSON 导出。
2. Task、Run、Step、Execution、Artifact、Finding、PlanRevision 和 Event 分表存储。
3. 使用事务保证步骤状态、Execution 和 Artifact 的原子关联。
4. 增加乐观锁或版本号，拒绝旧状态覆盖新状态。
5. Event 使用单调序号，支持流式游标。
6. 提供旧 workspace JSON 的一次性迁移和只读兼容。
7. 文件产物仍存 workspace；数据库只保存元数据和内容哈希。

### 验收

- 两个 Worker 更新不同 Run 不发生丢失；
- 同一 Run 的冲突写入可检测；
- 任意进程中断后数据库保持一致；
- 历史 API 不再扫描全部 workspace JSON；
- 旧 Run 能迁移并保持 ID、哈希和血缘不变。

## 18. 第二十二批：安全、权限与数据治理

### 目标

为未来进入企业内网建立最低安全基线。

### 实施内容

- API 身份认证与 Session/Task 级授权；
- 数据资产访问范围和最小权限；
- 敏感字段分类、预览脱敏和报告泄露检查；
- 上传类型、压缩包、公式注入和恶意文件检查；
- Python/SQL 执行审计；
- 密钥集中管理和日志脱敏；
- Artifact 下载授权与短期链接；
- 审计事件不可由普通用户修改；
- 保留期、删除和导出策略；
- CORS、请求大小、速率限制和安全响应头收敛。

### 验收

- 用户无法访问其他用户的 Task、数据和产物；
- 日志、Run 快照和分析包不包含 API Key；
- 常见路径逃逸、SQL 外部访问和恶意上传测试通过；
- 删除任务能按策略清理数据与产物，并保留允许保留的审计记录。

## 19. 第二十三批：候选版本验收

### 目标

形成一个可以明确评价和持续迭代的通用平台候选版本。

### 验收维度

1. 质量：评测集相对第十二批基线有可解释提升，无 P0 正确性回归；
2. 稳定：连续批量运行无悬挂任务、状态损坏和孤立进程；
3. 性能：各数据规模的耗时、内存和磁盘曲线有记录并满足既定预算；
4. 恢复：暂停、进程退出、API 重启和单步失败均有验证路径；
5. 可复现：分析包、重建报告和数据/代码哈希验证通过；
6. 安全：授权、隔离、脱敏和路径测试通过；
7. 操作：工作台可完成 Task 创建、确认、暂停、修订、恢复、重试和对比；
8. 文档：API、部署、故障处理、评测和升级文档与代码一致。

只有这些条件满足后，才重新评估是否进入真实语义层或业务系统联调。

## 21. 批次停止条件

出现以下任一情况时，本批不得继续扩展功能，应先修正基础问题：

- 关键数值正确性下降；
- Finding 无法追溯到输入与执行；
- 任务无法取消或产生残留执行进程；
- 状态恢复会覆盖已完成步骤；
- 大数据路径退化为隐式全量载入；
- 缓存无法证明数据版本一致；
- 多表 Join 未披露粒度或膨胀风险；
- 新工具只能依赖 Prompt 才保证正确参数；
- 前端状态与后端权威状态不一致；
- 需要真实业务语义才能验证，却没有稳定业务规则和测试数据。

## 23. 最终判断标准

v2 的成功不是“Agent 能写出更像专家的长报告”，而是：

- 能明确证明关键数字是怎么算出来的；
- 能在不同数据规模和数据源下稳定运行；
- 能在执行错误、用户暂停和服务重启后恢复；
- 能在多表场景中控制粒度和重复膨胀；
- 能用评测数据判断每次优化的收益与代价；
- 能让用户在工作台中检查、干预和比较分析过程；
- 在未来获得真实业务语义后，可以通过稳定输入契约快速接入，而不重写平台内核。

这份路线图从现在起替代第一版方案中的“下一批实施顺序”。第一版方案继续作为架构背景和历史设计依据。
