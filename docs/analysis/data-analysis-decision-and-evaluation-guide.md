# 数据分析的本质、决策与 Agent 评审指南

> 面向 DeepAnalyze 的产品负责人、开发者与评审者。目标不是培养统计术语，而是建立一套能判断分析是否有价值、结论是否可信、系统该如何继续投入的思维框架。

## 1. 数据分析究竟在解决什么问题

数据不是答案，数据只是过去发生过的事情留下的痕迹。业务真正要解决的是：**在信息不完整、资源有限且存在风险时，下一步该如何选择。**

因此，数据分析的本质不是“从表中找规律”，而是一个降低决策不确定性的过程：

```text
行动选择
  <- 需要判断什么才敢行动
  <- 需要哪些证据支持该判断
  <- 要把原始数据变成什么可比较的度量
  <- 数据能说明什么，不能说明什么
```

一份分析的价值，不由图表数量、模型复杂度或报告篇幅决定，而由它是否改变了一个本来会做错、会延迟或会过度冒险的决策决定。

例如“本月销售额下降 18%”是一个描述；“下降主要来自华东的老客复购，优先验证库存可得性和复购触达链路”才开始接近决策支持；“先在华东 A 类商品做两周补货加召回实验，以复购率和毛利为成败指标，未达阈值则停止投入”才形成了可执行、可检验的决策。

## 2. 必须分清的五种分析结论

很多低质量报告的问题，不在于数算错，而在于把低层级结论伪装成高层级结论。以下五层不是同义词，越向后，证据要求越高。

| 层级 | 能回答的问题 | 示例 | 最常见误用 |
|---|---|---|---|
| 描述（what） | 发生了什么？ | 7 月销售额环比下降 18%。 | 把事实陈列误称为洞察。 |
| 诊断（where / who） | 变化发生在哪里、涉及谁？ | 华东、老客和 A 类商品贡献了主要降幅。 | 只按方便的维度切分，遗漏真正驱动因素。 |
| 解释假设（why might） | 哪些机制可能造成该现象？ | 缺货、价格变化、触达减少都可能影响复购。 | 把“可能”写成“原因”。 |
| 预测（what next） | 在假设不变时，接下来可能怎样？ | 当前趋势延续时，下月销量可能继续低于基线。 | 把外推当成确定事实。 |
| 因果与决策（what if） | 采取某个动作会带来什么增量？ | 补货是否会提升复购并带来足够毛利？ | 用观察数据直接声称动作一定有效。 |

大多数企业数据分析首先只能稳定做到前两层。第三层应明确称为“待验证假设”；第五层通常需要对照组、实验、准实验或强业务机制证据。诚实地停在证据所允许的层级，不是能力不足，而是专业性。

## 3. 一个好分析的最小单元：可审计的判断

不要把“报告”当成最小交付物。真正的最小交付物是一条可审计的判断（finding）。它至少回答：

1. **主张**：到底发现了什么，是否有明确方向和数量级？
2. **口径**：指标是什么，分子、分母、过滤条件、时间窗口分别是什么？
3. **证据**：用了哪些字段、计算、样本量、对比基线和图表？
4. **推理**：证据如何支持主张，中间有没有跳步？
5. **边界**：哪些结论不能推出，有哪些替代解释、偏差或数据缺失？
6. **后续动作**：应立即行动、优先验证还是持续观察？为什么？

可以把它写成如下结构：

```text
主张：2026-07 华东老客复购率为 26.0%，较 2026-06 的 34.1% 下降 8.1 个百分点。
口径：复购率 = 当月存在至少两笔有效订单的老客数 / 当月有有效订单的老客数；已排除退款订单。
证据：订单表 2026-06 至 2026-07，n=18,421 名老客；按区域和商品类别分组计算，结果见复购明细表。
推理：该分组对总体复购率降幅贡献最大，且不是由样本量骤降造成。
边界：观察数据不能证明缺货或触达减少是原因；价格、节假日和渠道结构变化仍是替代解释。
动作：先检查 A 类商品缺货率和触达频次；在华东执行可回滚的小范围召回实验。
```

其中任何一项缺失，结论都可能看起来合理，却无法经受审查。

## 4. 从“问题”到“行动”的标准链路

好的分析不是从“先跑一遍 EDA”开始，而是从决策开始倒推。推荐使用以下链路：

```text
业务决策 -> 决策标准 -> 分析问题 -> 指标与口径 -> 数据与质量检查
        -> 比较与分解 -> 结论 -> 不确定性 -> 行动 / 实验 -> 结果复盘
```

### 4.1 先写决策，而不是先写需求

“帮我分析销售数据”不是分析问题。应追问到可选择的行动：

| 模糊需求 | 可分析的决策问题 |
|---|---|
| 分析销售数据 | 下月预算应优先投向哪个区域、品类或用户群？ |
| 看看研发效能 | 当前交付变慢是容量不足、需求波动还是流程阻塞？应先改哪一项？ |
| 分析用户流失 | 哪类用户流失风险最高，干预是否值得投入？ |

如果没有潜在行动，分析至多是监控或探索，不能假装成“建议”。

### 4.2 指标是对现实的压缩，不是现实本身

任何指标都包含价值取舍。只看销售额可能牺牲毛利；只看交付速度可能牺牲质量；只看转化率可能诱导骚扰用户。

每个关键指标都要写清：

- **定义**：公式、单位、统计粒度。
- **时间**：事件发生时间还是入账时间；自然月还是滚动 30 天。
- **范围**：包含哪些订单、用户、渠道，排除什么。
- **基线**：和哪个历史时期、目标或对照组比较。
- **反指标**：避免“优化一个数、伤害另一个数”的护栏，例如销售额对应毛利率和退款率。

### 4.3 数据质量不是前置杂务，而是结论强度的上限

错误的时间字段、重复订单、漏采渠道、口径变化、幸存者偏差，都会让后续再精巧的分析失去意义。质量检查必须回答“这个问题是否足以改变决策”，而非只给出缺失值百分比。

例如：订单金额有 0.5% 缺失，若缺失随机且不集中于目标人群，结论可能仍可用；若缺失集中在华东渠道，恰好该渠道是下降最大的区域，则“华东下降”这一结论应降级或暂停。

### 4.4 比较才产生意义

孤立数值很少有业务意义。分析中的“异常”“增长”“好坏”总是相对于某个基线：历史趋势、目标、预算、同类群体、对照组，或合理的外部基准。

评审时必须问：**相对于什么？为什么选这个比较对象？**

## 5. 相关、解释与因果：最重要的专业边界

观察到 A 和 B 同时变化，最多证明它们相关；不能自动证明 A 导致 B。原因可能是：

- B 导致 A；
- 第三个因素同时影响 A 与 B；
- 分组结构改变导致表面关系反转；
- 数据记录或口径发生变化；
- 只是随机波动。

一个常见错误是：“低活跃用户流失率更高，所以增加推送可以降低流失。”真实情况也可能是用户已经准备离开，所以既不活跃也不响应推送。

当结论要支持高成本或不可逆行动时，必须提升证据：

| 证据强度 | 合适表达 | 合适行动 |
|---|---|---|
| 单次描述 / 弱相关 | “发现信号，值得关注” | 监控、补数、排查。 |
| 多维一致的观察证据 | “存在较强关联，建议验证” | 小范围试验、访谈、专项排查。 |
| 对照实验或可信准实验 | “该动作带来估计增量” | 分阶段推广、持续监测反指标。 |

不要要求 Agent 从普通业务表中“找出根因”。更好的要求是：列出候选机制、分别给出支持与反驳证据、指出最小验证动作。

## 6. 行动建议的质量：不是一句“建议优化”

行动建议是一个资源配置主张，必须接受比描述结论更严格的审查。一条合格建议应包括：

```text
谁：由谁负责；
做什么：具体动作，而不是“提升”“优化”；
为什么现在做：它对应哪条证据及其强度；
预期：希望改变的主指标及预期方向；
代价与风险：预算、人力、反指标、潜在副作用；
验证：对照、阈值、观察窗口；
退出条件：何时停止、回滚或扩大。
```

行动强度必须与证据强度匹配。证据弱时，最佳建议往往不是“大力投入”，而是设计一个低成本、可回滚的信息获取动作。分析的一个重要产出是帮助组织知道“下一步需要知道什么”，而不是假装已经知道答案。

## 7. 如何评审一次 Agent 分析

### 7.1 先看结论卡，不要先被长报告说服

要求系统在最终报告前或报告顶部输出 3 至 5 张结论卡。每张卡都固定包含：主张、指标口径、时间和群体、证据链接、置信度、限制、建议类型。

对每张卡执行以下审计：

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 问题与决策 | 无明确问题 | 有问题但无行动对象 | 明确决策、范围和成功标准 |
| 指标口径 | 名词式指标 | 有部分公式或范围 | 公式、过滤、粒度、基线完整 |
| 数值正确性 | 无法复算或错误 | 可复算但未校验 | 独立脚本复算一致 |
| 证据链 | 只有文字 | 有部分表格或图 | 字段、计算、产物和结论可追溯 |
| 推理边界 | 把相关当因果 | 有少量保留 | 明确替代解释与证据等级 |
| 行动质量 | 空泛建议 | 有方向但不可验证 | 具体、可回滚、有阈值和负责人 |

单张卡满分 12 分。低于 8 分不能作为决策依据；8 至 10 分可作为验证性输入；11 分以上才值得进入高影响决策讨论。这个分数不是数学真理，但能迫使评审把“感觉不错”变成具体争议。

### 7.2 使用“反问式审查”识别幻觉

对每个重要结论，连续追问：

1. 这个数的分子、分母、过滤条件和时间窗口是什么？
2. 与哪个基线比较，为什么这个基线合理？
3. 用了哪些字段和哪段计算，能否重新运行？
4. 哪种替代解释最可能推翻结论？系统检查过吗？
5. 把结论改成更谨慎的说法后，是否仍然足以指导下一步？

无法回答前三题，通常是可追溯性失败；无法回答第四题，是推理边界失败；第五题暴露的是“建议是否被证据过度支撑”。

## 8. 对 DeepAnalyze 当前能力的客观定位

项目中已有的 `record_finding`、Evidence、Lineage、报告校验、状态机、Python 分步执行和会话产物追踪，是正确的工程方向。特别是证据绑定和建议强度校验，已经把“结论必须有依据”“弱证据不能给强行动建议”的原则落实到代码层。

但这些能力需要和“分析正确性”严格区分：

- 流式输出、Docker、重试、会话恢复、并发控制解决的是**服务可靠性**。
- 状态机、工具顺序和步数限制解决的是**流程可控性**。
- evidence、lineage、artifact 解决的是**可审计性**。
- 指标复算、数据口径、反事实、基准测试和人工抽查才共同决定**分析可靠性**。

所以，当前系统可以定位为“具备可审计骨架的数据分析 Agent”，不能仅凭它能完成工具链调用就宣称结论可信。

## 9. 下一阶段最值得建设的不是更多功能，而是评测体系

建立一个小而严格的评测集，比继续添加十个工具更有价值。建议从 6 到 10 个数据集开始，每个数据集配一份人工事实表：

1. 业务背景和可执行决策。
2. 字段字典、正确指标口径和允许范围。
3. 已知正确结论及其复算脚本。
4. 故意设置的质量问题，例如重复、漏数、错误日期、口径突变。
5. 一个相关不等于因果的陷阱。
6. 预期的“不应下结论”项。
7. 可接受的建议类型：观察、验证或立即行动。

评测每次运行时记录：

```text
指标数值是否正确
是否发现关键数据质量问题
是否引用了真实证据和正确产物
是否出现无依据的因果断言
是否把建议强度与证据强度匹配
是否在规定成本、时间和工具步数内完成
```

这会让项目从“演示一次很像分析”变成“可持续地测量分析质量”。当基准稳定后，再讨论更复杂的预测、领域技能和多 Agent 协作，投入才有明确的收益判断。

## 10. 一句话原则

**数据分析不是替组织替人下结论，而是让组织在每一步知道：我凭什么相信、还不知道什么、下一步怎样用最小代价获得更多确定性。**
