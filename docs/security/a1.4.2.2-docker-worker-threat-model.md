# A1.4.2.2 — Docker Worker Threat Model

Status: design-phase threat model (no implementation exists yet; Docker backend is a fail-closed stub at HEAD `4d322cc`).

## 1. Assets & Trust Boundaries

| Asset | Trust level |
|---|---|
| User Python code | untrusted |
| Worker container filesystem/network | untrusted |
| Input artifacts | user-controlled data (untrusted) |
| Output artifacts | untrusted until host-side validation |
| Container Manager | trusted (host-side, only socket user) |
| API process | trusted but largest attack surface |
| Session state (namespace) | trusted (produced by previous trusted runs) |

Trust boundaries: user code -> container (hard); container -> host (kernel namespace/cgroups); container -> manager (result files only, validated); manager -> docker engine (local socket, trusted module only).

## 2. Threats & Controls

| ID | Threat | Control (design) | Residual risk |
|---|---|---|---|
| T01 | Untrusted code reads host files / secrets | RO rootfs, job-specific input mount only, no secret env, no sensitive mounts | kernel vulns |
| T02 | Untrusted code modifies originals | input copied to job dir, mounted RO | none if enforced |
| T03 | Path traversal via artifact refs | existing relative-path validation + container path translation manager-side; host-side re-validation on collect | low |
| T04 | Symlink/hardlink escape | symlink rejection + resolve-escape check on collect (mirror `_validate_artifacts`), RO input | low |
| T05 | Network egress (IPv4/IPv6) | `--network none` | none |
| T06 | DNS exfiltration | no network namespace interfaces | none |
| T07 | Proxy/env-based bypass | no proxy env delivered; S08 test | none |
| T08 | Secret leakage via env | allow-list env + secret-marker rejection in contract (`job_contract.py:149-158`) | env values themselves user-supplied |
| T09 | Secret leakage via fork memory | eliminated: per-job container has no parent memory | none |
| T10 | Container escapes to host (kernel) | cap-drop ALL, no-new-privileges, non-root, seccomp default | kernel/container runtime CVEs — patch policy required |
| T11 | Container creates/controls containers | no docker socket in container; S10 test | none if enforced |
| T12 | Resource exhaustion (CPU/mem/PID/disk) | cgroup limits + pids-limit + tmpfs caps + output quotas | none |
| T13 | Fork bomb / child process escape | pids-limit + PID namespace kill semantics | low |
| T14 | Orphan containers after crash/restart | job_id labels + reconciliation scan | low |
| T15 | Artifact tampering post-execution | output dir is job-specific; host validates + hashes before publication | low |
| T16 | Result protocol abuse (oversized/malformed result.json) | size-limited read, schema-strict parse, fail closed | low |
| T17 | Cancellation race (result after cancel) | container stopped before result acceptance; cancel-after-completion keeps succeeded (A1.3 race contract) | documented |
| T18 | Docker unavailable -> degraded security | fail closed FAILED + BACKEND_UNAVAILABLE; **no silent process fallback** (explicit design rule) | none |
| T19 | Pickle trust across boundary | JSON-only envelope between manager/container; pickle only for trusted host-side state handoff if adopted | low |

## 3. Environment-variable cleaning vs container isolation

The process executor clears `os.environ` (`python_executor.py:228-236`) — this is application-level hygiene only. In fork mode, parent memory (including module-level secrets/clients) remains reachable by untrusted code. Container isolation removes that class entirely. Both layers are documented as distinct; only the container layer counts toward sandbox claims.

## 4. Out-of-scope threats (recorded, handled elsewhere or accepted)

- Kernel 0-day container escapes: accepted residual; mitigated by patch cadence + single-tenant host assumption (documented in deployment).
- Malicious input file content (e.g., zip bombs, CSV parser bugs): data-layer concern; artifact size limits cap blast radius inside container; parser vulns are a dependency-management issue (S/CS review at A1.4.2.2.7).
