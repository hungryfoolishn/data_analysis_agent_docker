## 1. 当前架构与问题

### 1.1 真实执行链（基线 a75a459）

1. 计划步骤以 `RuntimePlanStep` 表示，携带 `required_inputs` / `expected_outputs`
   （`langgraph_langchain/runtime/models.py::RuntimePlanStep`）。
2. `analysis_tasks_from_plan()`（`langgraph_langchain/runtime/scheduler.py`）把每个步骤转成
   `AnalysisTask`。所有任务都收到同一个 `plan.input_asset_ids`；
   `required_inputs` / `expected_outputs` 仅作为字符串列表透传，不做解析。
3. `TaskRunner.execute_next()`（`langgraph_langchain/runtime/runner.py`）通过
   `request_factory(task)` 构建请求。`is_ready()` 只依赖任务状态与 `depends_on`。
4. `AnalysisRuntime.build_execution_request()`
   （`langgraph_langchain/runtime/context.py::build_execution_request`）把
   `task.input_asset_ids` 经 `AssetResolver.resolve_many()`（`runtime/asset_resolver.py`）
   解析进 `namespace.runtime_inputs` / `runtime_input_metadata`。
5. `StructuredTaskExecutor.execute()`（`execution/structured_executor.py`）调用工具。
   `run_analysis_operation`（`tools/tool_analysis_operation.py`）用参数中的 `asset_id`
   自行调用 `runtime.asset_resolver.resolve()`，计算后调用 `runtime.register_dataframe()`
   注册输出资产，并执行 `session.current_asset_id = asset.asset_id`。
   `run_sqlite_query`（`tools/tool_sqlite_query.py`）与 `load_data`
   （`tools/tool_load_data.py`）采用相同模式（`load_data` 走
   `register_session_dataframe()`，见 §6.4）。
6. `extract_artifact_ids()`（`execution/task_models.py`）只从工具 JSON 提取 artifact ID；
   `ExecutionResult` 没有 `output_asset_ids` / `output_assets` 字段
   （`runtime/models.py::ExecutionResult`）。
7. `record_execution_result()`（`runtime/context.py:1117`）按 `step_id + tool_name` 幂等
   合并执行记录，并在工具已先记录执行时“收养”工具侧 execution_id
   （`context.py:1139-1146` 重写 `result.execution_id`、verification 与 evidence 的来源 ID）。

### 1.2 已确认的问题

| 问题 | 代码依据 | 优先级 |
| --- | --- | --- |
| `expected_outputs` 只是逻辑名称，未映射真实 DataAsset ID | `models.py::RuntimePlanStep.expected_outputs`；无任何映射代码 | P1 |
| 下游依赖 `session.current_asset_id` 隐式传递 | `tool_analysis_operation.py:120`、`tool_sqlite_query.py:117`、`tool_load_data.py:158` | P1 |
| `ExecutionResult` 不保存输出 DataAsset ID | `runtime/models.py::ExecutionResult` 字段清单 | P1 |
| execution_id 存在两个独立生成点：`SessionExecutionRecorder.__init__`（`context.py:1866` 起，`new_id("exec")`）与 `ExecutionResult.execution_id` 默认工厂（`runtime/models.py`）；`build_execution_result()`（`execution/task_models.py`）不接受也不传递 execution_id，目前依赖 `record_execution_result()` 事后收养（`context.py:1139-1146`） | P1 |
| 无 OutputAssetBinding 权威注册机制 | 全仓库无对应模型/Registry | P1 |
| Retry 无 attempt 级输出隔离 | `context.py::_create_retry_run` 清空 assets/executions 后重建，但无 binding 记录可追溯 | P2 |
| 上游失败后下游保持 pending（未显式 skip） | `runner.py::execute_next` 失败分支只返回 `failed`；`scheduler.py` 无 skip 级联 | P2 |
| `expected_outputs` 命名不统一 | `analysis_workflow.py:75` 用 `{step_id}:output`；`sqlite_workflow.py:189` 用 `query_result_asset`；`plans.py:104` 用 `analysis_output` | P2 |
| `required_inputs` 语义混杂（物理 ID 与逻辑名未区分） | `sqlite_workflow.py:188` 与 `analysis_workflow.py:74` 均填物理 ID；`validate_plan()`（`plans.py:54`）要求全部命中已注册资产 | P2 |
| `TaskExecutionRequest.input_asset_ids` 是 `task.input_asset_ids` 的只读代理（`execution/task_models.py`），而 Scheduler 给所有任务填的是同一个 `plan.input_asset_ids`；下游解析出的真实输入若不显式回写，`ExecutionResult.input_asset_ids` 将继续记录源资产 | P1 |

补充结论（影响设计）：

- `validate_runtime_plan()`（`runtime/plans.py:190`）第一步就调用 `validate_plan()`，
  后者用 `set(step.required_inputs) - assets` 做物理资产校验（`plans.py:70`）。
  因此 `step_abc.grouped_data` 这类逻辑引用今天会被直接拒绝，必须分型处理（见 §7.3）。
- 现有确定性 Planner 生成的多步计划里，每个分析步骤的 `asset_id` 都指向**源资产**
  （`runtime/general_planner.py::DeterministicAnalysisPlanner.plan` 中 `input_refs=[primary_asset]`；
  `runtime/analysis_workflow.py::general_plan_to_runtime_plan` 原样透传），
  即当前计划层还没有“下游消费上游输出”的真实用例，Binding 引入后需要让该用例可表达。
- 工具通过参数接收 `asset_id` 并自行 resolve（`tool_analysis_operation.py`），这意味着
  Binding 解析必须在 request 构建层完成，否则无法保证工具收到的一定是物理 ID。
- `run_analysis_operation` / `run_sqlite_query` 的返回 JSON 已包含 `output_asset_id`
  （单值）；`load_data` 返回的是人类可读文本（`tool_load_data.py`），不含资产 ID，
  其绑定需要独立路径（见 §6.4）。

## 2. 目标架构

### 2.1 目标数据传递链

```
AnalysisRuntime.build_execution_request(task)
  ↓ 生成 canonical execution_id（本执行的唯一权威 ID）
TaskExecutionRequest(execution_id, resolved_inputs=ResolvedTaskInputs)
  ↓ StructuredTaskExecutor（把 request.execution_id 注入工具参数与结果）
Tool（只接收物理 asset_id；只负责注册 DataAsset，不写 Binding）
  ↓ 返回 JSON（output_asset_id / output_assets 命名映射）
AnalysisRuntime.record_execution_result()
  ↓ 单点校验 + all-or-nothing 写入 OutputAssetBinding
ExecutionResult(execution_id=canonical, input_asset_ids=resolved, output_assets=[...])
  ↓ Evidence / Report 沿 binding → execution → step → run/attempt 重建血缘
下游 build_execution_request 再次解析 Binding
```

### 2.2 职责边界（冻结）

| 层 | 职责 | 明确不做 |
| --- | --- | --- |
| `OutputBindingRegistry` | Binding 的注册、查询、冲突校验、持久化结构 | 不执行数据加载、不解析 dataframe、不生成 execution_id |
| `AnalysisRuntime.build_execution_request()` | 生成 canonical execution_id；解析逻辑引用为 `ResolvedTaskInputs` | 不执行工具 |
| `AnalysisRuntime.record_execution_result()` | 校验输出映射与 expected_outputs；单点 all-or-nothing 写入 Binding；用 resolved inputs 覆盖 `result.input_asset_ids` | 不重复注册资产 |
| `TaskScheduler` | 状态调度 + 失败级联 skip | 不做资产/Binding 查询 |
| `TaskRunner` | 传递 request_factory 产物 | 不解析 Binding |
| 结构化工具 | 接收物理 `asset_id` 与注入的 canonical execution_id；注册 DataAsset；在返回 JSON 中给出输出资产（含命名映射） | 不查询 Binding Registry；不解析逻辑引用；不写 Binding |
| `AssetResolver` | 按 asset_id 加载快照 | 不做逻辑名解析 |
| `SessionExecutionRecorder` | 使用注入的 canonical execution_id 记录执行（兼容路径） | 不再自行生成权威 execution_id（仅注入缺失时的兜底，见 §5.2） |

## 3. 数据模型

### 3.1 OutputAssetBinding

新增于 `langgraph_langchain/runtime/models.py`（与既有模型一致采用 Pydantic，便于
snapshot 序列化与校验）：

```python
class OutputAssetBinding(BaseModel):
    model_config = ConfigDict(frozen=True)   # 真正不可变：任何字段赋值抛 ValidationError

    run_id: str
    step_id: str
    output_name: str          # 规范化后的裸名称，如 "output" / "query_result_asset"
    asset_id: str             # 物理 DataAsset ID
    execution_id: str
    attempt: int = Field(ge=1)
    created_at: str = Field(default_factory=utc_now)
```

设计原则：

1. **逻辑名与物理 ID 分离**。逻辑引用语法冻结为 `{step_id}.{output_name}`
   （如 `step_1.grouped_data`）。`required_inputs` 允许两种取值：
   物理 asset ID（现状兼容）或逻辑引用（新增）。
2. **唯一键**：`(run_id, step_id, output_name, attempt)`。同一键重复注册时：
   - 内容完全一致（asset_id、execution_id 相同）→ 幂等返回；
   - 内容不同（如 asset_id 或 execution_id 不同）→ 抛
     `OutputBindingConflictError`，禁止覆盖。
3. **不可变性**：`frozen=True` 落实字段级不可变；Registry 不提供修改/删除单条接口；
   只有删除整个 run 的历史归档时随之失效。
4. **序列化**：`model_dump(mode="json")`；持久化进 run snapshot
   （`context.py::snapshot()`，新增 `output_bindings` 键，快照版本由 1 升至 2，
   旧快照缺省为空列表）。
5. **血缘完整性**：`execution_id` 记录资产的**生产者执行**。SQLite dedup 复用旧物理资产时，
   新 Binding 仍必须记录当前 Attempt 的 canonical execution_id（见 §8.1 第 4 条），
   不得因资产复用指向旧执行。

### 3.2 逻辑引用语法与识别规则（v2 冻结）

- 输出名命名空间：`expected_outputs` 统一为**裸名称**（不含 `step_id:` 前缀）。
  唯一默认输出名冻结为 `output`；SQLite 查询步骤输出名冻结为 `query_result_asset`。
- 兼容迁移：`runtime/analysis_workflow.py:75` 的 `f"{item.step_id}:output"` 改为
  `"output"`（同一批次内完成，属于命名统一，不改变执行行为）。
- **识别规则（权威顺序）**：
  1. 候选形态正则：`^[A-Za-z_][A-Za-z0-9_]*\.[A-Za-z_][A-Za-z0-9_]*$`
     （`{step_id}.{output_name}`，两段均非空）；
  2. 候选命中后，`step_id` 段必须属于**当前计划的已知 Step ID 集合**
     （`plan.steps` 的 `step_id`），才算逻辑引用；否则按物理 asset ID 处理；
  3. **歧义报错**：若一个字符串同时是已注册物理 asset ID、又满足
     “已知 Step ID + `.` + 输出名”形态，视为计划错误，直接失败，
     不允许隐式选择其中一种解释。
- **Step ID 合法格式**：新增计划步骤的 `step_id` 必须匹配
  `^step_[0-9a-f]{32}$`（与 `models.py::new_id("step")` 和
  `general_planner.py` 的 `f"step_{uuid4().hex}"` 一致）；
  `validate_runtime_plan()` 对逻辑引用中的 `step_id` 段强制该校验。
  自定义 Step ID 属于未来扩展，本批次不支持。
- 分类逻辑收敛在 `runtime/output_bindings.py` 的共享函数
  `classify_input_reference(value, known_step_ids) -> Literal["asset_id", "logical_ref"]`，
  计划校验与执行请求构建必须调用同一函数（见 §7.3 / §7.1）。

## 4. Registry 接口

### 4.1 权威归属

- Registry 是 **AnalysisRuntime 的内存内权威 + run snapshot 持久化**，不新建数据库，
  不复用 `self.assets`（资产表保持“存在什么资产”，Registry 记录“哪个步骤的哪个输出
  是哪个资产”）。
- 存放位置：新模块 `langgraph_langchain/runtime/output_bindings.py`；
  `AnalysisRuntime.__init__` 持有 `self.output_bindings: OutputBindingRegistry`；
  `snapshot()` / `_restore()` / `_persist()` 负责落盘与恢复；
  run 归档（`.analysis_runs/{run_id}.json`）天然形成历史 Attempt 的不可变档案。
- **唯一写点**：Binding 只由 `AnalysisRuntime.record_execution_result()` 写入
  （见 §5.4）。工具、executor、Registry 使用方都不得直接注册 Binding。

### 4.2 接口定义（实施冻结）

```python
class OutputBindingConflictError(ValueError): ...

class OutputBindingNotFoundError(KeyError): ...

class OutputBindingRegistry:
    def register(self, binding: OutputAssetBinding) -> OutputAssetBinding:
        """唯一键幂等注册；冲突抛 OutputBindingConflictError。"""

    def register_many(self, bindings: Sequence[OutputAssetBinding]) -> list[OutputAssetBinding]:
        """预校验全部键后一次性注册；任何冲突则整批不落盘（all-or-nothing）。"""

    def resolve(
        self, *, run_id: str, step_id: str, output_name: str, attempt: int
    ) -> OutputAssetBinding:
        """精确匹配 (run_id, step_id, output_name, attempt)；未命中抛
        OutputBindingNotFoundError（下游据此显式失败，不静默回退）。"""

    def resolve_for_step(
        self, *, run_id: str, step_id: str, attempt: int
    ) -> list[OutputAssetBinding]:
        """按 step 聚合（Evidence Lineage / 血缘重建使用）。"""

    def list_for_run(self, *, run_id: str, attempt: Optional[int] = None) -> list[OutputAssetBinding]:
        """审计与测试断言用。"""
```

- **生命周期**：Registry 随 `AnalysisRuntime` 创建；`_create_retry_run()` 中随
  assets/executions 一起清空（见 §8），父 Attempt 的 Binding 只存在于父 run 归档文件中。
- **清理**：不做自动 GC；与现有 `.analysis_runs/` 归档策略保持一致。
  `_restore()` 执行孤儿清理：凡 `execution_id` 在恢复后的 run 中不存在
  `status == "succeeded"` 执行记录的 Binding 一律丢弃（对应进程在
  “工具成功但结果未落盘”窗口崩溃的残留，见 §5.5）。

## 5. ExecutionResult 与 Canonical execution_id

### 5.1 字段

`runtime/models.py::ExecutionResult` 新增：

```python
input_bindings: list[ResolvedLogicalRef] = Field(default_factory=list)    # 本次执行消费的逻辑引用及其 Binding（随 ExecutionResult 持久化）
output_assets: list[ExecutionOutputAsset] = Field(default_factory=list)   # 命名映射：绑定真源
output_asset_ids: list[str] = Field(default_factory=list)                 # 兼容查询字段，由 output_assets 派生
```

- `output_assets` 是唯一绑定依据；`output_asset_ids` 在模型校验时由
  `output_assets` 去重派生，供 Evidence / 报告便捷消费，不参与 Binding 注册。
- `input_bindings` 由 `record_execution_result()` 从 `request.resolved_inputs.logical_refs`
  写入，随 `self.executions` 列表经 `snapshot()` 天然持久化（v3：不再依赖请求级元数据）；
  `ResolvedLogicalRef` 定义移至 `runtime/models.py`（§7.2）。
- 禁止按下标隐式映射：Binding 注册一律按 `output_name`（见 §5.4）。

### 5.2 Canonical execution_id（v2 新增冻结）

**问题确认**（代码依据）：
`SessionExecutionRecorder.__init__`（`context.py:1857-1876`）自行 `new_id("exec")`；
`StructuredTaskExecutor` → `build_execution_result()`（`execution/task_models.py`）
不接受 execution_id，`ExecutionResult.execution_id` 走默认工厂再生成一个；
当前只靠 `record_execution_result()` 的收养逻辑（`context.py:1139-1146`）事后把
result/verification/evidence 改写成工具侧 ID。该收养以 `step_id + tool_name` 匹配，
依赖隐式全局状态，是评审指出的 P1 缺陷。

**冻结规则**：

1. **唯一创建点**：`AnalysisRuntime.build_execution_request()` 在构建
   `TaskExecutionRequest` 时生成 `request.execution_id = new_id("exec")`。
   一个 Step 的一次调度执行只有一个权威 execution_id，全链路传递：

   ```
   TaskExecutionRequest.execution_id
     → StructuredTaskExecutor（注入工具参数 + build_execution_result）
     → 工具参数 execution_id → SessionExecutionRecorder(execution_id=...)
     → DataAsset.source_metadata["execution_id"]
     → ExecutionResult.execution_id
     → OutputAssetBinding.execution_id
     → Evidence
   ```

2. **注入机制**：`TaskExecutionRequest` 新增字段
   `execution_id: Optional[str]`；`StructuredTaskExecutor.execute()` 把
   `request.execution_id` 注入 `arguments["execution_id"]`（保留键）。
   三个结构化工具签名各新增 `execution_id: str = ""` 尾参：
   提供时 `SessionExecutionRecorder(session, ..., execution_id=request_execution_id)`，
   为空（旧链路/手工调用）时保持现状自生成并在返回 JSON 中带上，供对账。
3. **Executor 侧**：`build_execution_result()` 新增 `execution_id` 参数，
   `StructuredTaskExecutor` 传 `request.execution_id`；
   `record_execution_result()` 收到结果时**校验而非收养**：
   - 工具侧已记录的执行 execution_id 必须 == `result.execution_id`；
     不一致 → 结果改判 failed（error: `ExecutionIdMismatch`），不写入 Binding。
   - 原“收养”分支仅对旧快照恢复的兼容路径保留，且日志告警（不新增静默路径）。
4. **禁止**：任何新代码不得调用 `new_id("exec")` 生成第二个权威 ID；
   `SessionExecutionRecorder` 的自生成仅作为无 Runtime 上下文时的兜底并标记 legacy。

### 5.3 工具输出提取（命名映射）

`execution/task_models.py` 新增：

```python
def extract_output_assets(output: Any) -> list[ExecutionOutputAsset]:
    """解析工具返回 JSON 中的输出资产映射。"""
```

解析规则（按优先级）：

1. `output_assets`：`dict[str, str]`（output_name → asset_id），直接映射为
   `ExecutionOutputAsset` 列表（保持 JSON 序列化顺序，仅用于展示，不用于绑定顺序）；
2. `output_asset_id`：单值字符串，产生一个**未命名**输出项
   （`output_name` 由 Runtime 按 §5.4 规则补全）；
3. 两者同时出现且单值不在映射中 → 解析错误（任务失败）；
4. 均不存在 → 空列表（`load_data` 等文本型工具走 §6.4 回退路径）。

### 5.4 Binding 注册（Runtime 单点，all-or-nothing）

`AnalysisRuntime.record_execution_result()` 扩展（对 succeeded 结果执行）：

1. 取该 `step_id` 对应 `run.steps[].expected_outputs`；
2. **名称解析**：
   - `output_assets` 中每一项的 `output_name` 必须属于 `expected_outputs`，
     未知名称 → 结果改判 failed（`UnknownOutputName`），不写任何 Binding；
   - 未命名单值输出：仅当 `len(expected_outputs) == 1` 时补全为该名称；
     `expected_outputs` 为空或多于一个且无命名映射 → 结果改判 failed
     （`UnnamedMultiOutput`），禁止按下标猜名。
3. **一致性预校验**（全部通过才写）：
   - 每个 asset_id 必须已注册于 `runtime.assets`；
   - 目标键 `(run_id, step_id, output_name, self.run.attempt)` 无已存在的**不同**
     Binding（幂等重复允许）；
   - `result.execution_id` 与资产 `source_metadata["execution_id"]` 一致
     （dedup 复用旧资产时例外，见 §8.1 第 4 条）。
4. 预校验通过后调用 `registry.register_many()` 一次性注册（all-or-nothing）；
   任何环节失败 → 结果改判 failed（error 类型 `BindingRegistrationFailed` /
   `OutputBindingConflictError`），**不写部分 Binding**。
5. 用 `resolved_inputs` 覆盖 `result.input_asset_ids`（见 §7.4）。

### 5.5 崩溃一致性

- 工具已注册资产、结果未落盘（进程中断）→ 只留孤儿资产（内容寻址、无引用，无害），
  无 Binding；`_restore()` 孤儿清理兜底（§4.2）。
- 原子性边界（v3 精确表述）：在**同一次 Runtime Snapshot 写入过程**中，Binding 与
  ExecutionResult 必须一起提交或一起回滚——Binding 写入发生在 `record_execution_result()`
  内部、`self._persist()` 之前；若 `_persist()` 失败则 Binding 从内存回滚
  （恢复注册前快照）并向调用方抛错。工具侧 Recorder 的独立记录**不属于**
  该原子提交边界（语义见 §5.6）。

### 5.6 Tool Recorder 与 Runtime 最终判定（v3 冻结）

工具 Recorder 记录与 Runtime `record_execution_result()` 判定是两个独立写操作，
二者状态可以不同。含义冻结如下：

| 记录 | 表达含义 |
| --- | --- |
| Tool Recorder 记录 | 工具本身执行情况（计算是否成功、资产是否注册） |
| `ExecutionResult` | Runtime 对任务执行及输出契约的最终判定（权威状态） |
| `OutputAssetBinding` | 仅对 Runtime 最终判定成功的输出建立绑定 |

对 `ExecutionIdMismatch`、`UnknownOutputName`、`UnnamedMultiOutput`、
`AmbiguousOutputAsset`、`BindingRegistrationFailed` 等契约失败：

1. Tool Recorder 的原始记录不删除、不回写（保留工具层审计事实）；
2. `ExecutionResult` 明确记录最终失败原因（error type / message），状态为 `failed`；
3. 不产生任何可供下游消费的 Binding；
4. 失败执行注册的 DataAsset 保留为未引用资产，是否 GC 不属于本批次。

## 7. 下游输入解析流程

### 7.1 解析位置

统一在 `AnalysisRuntime.build_execution_request()`（`runtime/context.py`）内完成：

1. **物理输入**（现状保留）：`task.input_asset_ids` 经 `asset_resolver.resolve_many()`
   进 `namespace.runtime_inputs`。
2. **逻辑引用解析**：
   - 遍历 `task.required_inputs`，用 §3.2 的共享
     `classify_input_reference()` 分类；逻辑引用按
     `output_bindings.resolve(run_id, step_id, output_name, attempt=self.run.attempt)`
     解析，其 `asset_id` 追加进本次请求的输入集合与 `namespace.runtime_inputs`；
   - 遍历 `task.arguments`：值为逻辑引用时**原地替换为物理 asset_id**，
     工具收到的仍是物理 ID，工具代码不变；
   - 逻辑引用的 `step_id` 必须是当前任务的传递闭包依赖（`task.depends_on` 闭包）
     或本 run 内已成功步骤，否则视为非法引用，直接失败。
3. **失败语义**：`OutputBindingNotFoundError` / `OutputBindingConflictError` /
   非法引用 / 歧义引用 → 记录 `metadata["binding_resolution_error"]` 并使任务失败；
   **禁止**回退到 `session.current_asset_id` 或 `plan.input_asset_ids`。
4. `RuntimeV2Controller._request_factory()` 合并而非覆盖 `request.metadata`
   （修复 B11.2.0 P2-1，Binding 错误需经 metadata 传递）。

### 7.2 ResolvedTaskInputs（v2 新增）

定义于 `execution/task_models.py`：

```python
class ResolvedLogicalRef(BaseModel):
    reference: str              # 原始字符串，如 "step_abc.grouped_data"
    step_id: str
    output_name: str
    binding: OutputAssetBinding

class ResolvedTaskInputs(BaseModel):
    asset_ids: list[str]                      # 实际消费的物理资产（去重，解析顺序）
    logical_refs: list[ResolvedLogicalRef]    # 逻辑引用及其 Binding（血缘审计用）
```

`ResolvedLogicalRef` 定义于 `runtime/models.py`（与 `OutputAssetBinding` 同层，
供 `ExecutionResult.input_bindings` 复用）；`ResolvedTaskInputs` 仍定义于
`execution/task_models.py`。

`TaskExecutionRequest` 新增：

```python
execution_id: Optional[str] = None
resolved_inputs: Optional[ResolvedTaskInputs] = None
```

`input_asset_ids` 属性冻结为：`resolved_inputs.asset_ids` 优先，
缺省时回退 `task.input_asset_ids`（纯旧链路兼容）。

### 7.3 计划期校验分型（v2 修订）

`validate_runtime_plan()`（`runtime/plans.py`）改造：

1. 用共享 `classify_input_reference(value, known_step_ids)` 把每个步骤的
   `required_inputs` **以及 `parameters` / Planner arguments（含解析后的
   `parameters_json` 值）**分为物理 ID 与逻辑引用两类；
2. **物理 ID** 继续走 `validate_plan()` 现有校验——构造过滤后的计划副本
   （逻辑引用已从 `required_inputs` 剔除）传入，保证逻辑引用
   **不会进入** `set(required_inputs) - assets` 的物理校验分支而被误拒；
3. **逻辑引用**（无论来自 `required_inputs` 还是 `parameters` / arguments）统一校验：
   Step ID 格式（§3.2）、生产 Step 存在、属于该 Step 的 `depends_on` 闭包、
   `output_name` 在生产 Step 的 `expected_outputs` 中声明、无歧义（§3.2 第 3 条）。
   例如 Planner 生成 `parameters={"asset_id": "step_a.output"}` 而 `depends_on` 为空时，
   **计划期**即拒绝，不得等到执行请求构建阶段才失败；
4. 计划期与执行期使用同一分类/解析规则（同一函数、同一正则、同一歧义判定），
   避免“计划期通过、执行期失败”。

### 7.4 输入血缘落库

`record_execution_result()` 用 `request.resolved_inputs.asset_ids` 覆盖
`result.input_asset_ids`（§5.4 第 5 步），确保 `ExecutionResult.input_asset_ids`
记录的是**本次执行实际消费的物理资产**，而不是 Scheduler 预填的
`plan.input_asset_ids`；同时把 `request.resolved_inputs.logical_refs` 写入
`result.input_bindings`（§5.1），随 `self.executions` 经 `snapshot()` 天然持久化，
供 B11.2.2 审计
“下游消费资产 == 上游 Binding 资产”。

### 7.5 不改动的层

- `TaskRunner` / `TaskScheduler`：不接触 Binding（Scheduler 仅新增 §9 的 skip 级联）。
- `AssetResolver`：继续只按 asset_id 解析。

## 8. Retry / Attempt 语义

### 8.1 冻结决策

1. **Binding 唯一键包含 attempt**：新 Attempt 产生的 Binding 永不覆盖旧 Attempt。
2. **Retry Run 不继承父 Run 输出**：`_create_retry_run()`
   （`runtime/context.py:1703`）已经清空 `assets` / `executions` / `artifacts`
   / `task.input_asset_ids` 并新建 `run(attempt=parent+1)`；B11.2.1 沿用该语义——
   retry 从头执行计划，父 Attempt 的 Binding 留在
   `.analysis_runs/{parent_run_id}.json` 中只读可审计，但子 Run 的 `resolve()`
   只在子 Run 自身 Registry 内查找。理由：复用父输出需要跨 run 资产快照恢复与
   “哪些步骤可信复用”的判定，属于独立批次的工作量；强行继承会把未验证的旧数据
   混入新 Attempt，违反“缺失 Binding 时明确失败”的原则。
3. **Retry Run 的 Registry 必须清空**：`_create_retry_run()` 中显式重建
   `OutputBindingRegistry`，防止子 Run 复用父 Run 的任何 Binding。
4. **SQLite dedup 语义**：`register_sqlite_result()` 命中 dedup 时返回已有资产 ID；
   该资产仍以**当前** `(run_id, step_id, output_name, attempt)` 注册 Binding，
   且 `binding.execution_id` 必须是当前 Attempt 的 canonical execution_id（`exec_new`），
   不得因资产复用指向父 Attempt 的 `exec_old`；§5.4 第 3 步的
   `source_metadata["execution_id"]` 一致性校验对 dedup 资产豁免
   （以 dedup 判定函数 `_sqlite_provenance_matches` 的命中为准）。
5. **旧 Attempt 输出防误用**：下游解析只查当前 run 的 Registry（当前 attempt 精确匹配）；
   旧 Attempt 的输出在新 Run 中不可达，除非同一步骤重新执行并重新绑定。
6. **同一 run 内同步骤二次执行**（如 needs_revision 后重跑）：同 attempt 内重复执行
   同一输出名且 asset_id 不同 → `OutputBindingConflictError`，执行失败显式暴露，
   不静默覆盖。
7. **Step Revision / 人工修订后的重执行**：需要单独定义新的执行版本语义
   （新键或版本字段），本批次不做，禁止通过覆盖现有 Binding 实现。

## 9. 失败传播规则

### 9.1 状态定义（冻结）

| 状态 | 含义 |
| --- | --- |
| `failed` | 实际执行过且出错（含 Binding 解析失败、输出映射校验失败、冲突失败、execution_id 不一致） |
| `skipped` | 因传递闭包内上游 `failed`/`skipped` 而确定不执行 |
| `blocked` | 上游仍在运行、结果未定（保持现状语义） |

### 9.2 级联规则

1. `TaskScheduler` 新增 `skip_dependents(task_id)`：把 `task_id` 的传递闭包内所有
   `pending` 任务标记为 `skipped`，并写入 `task.error = "upstream_failed"`（或等价标记）。
2. `TaskRunner._finish_step()` 在 `result.status in {"failed", "cancelled"}` 时调用
   `scheduler.skip_dependents(task_id)`，使 scheduler 状态机在失败后立即收敛，
   而不是留下一批永远 pending 的任务。
3. `AnalysisRuntime.execute_next_task()` 中
   `all(... in {"succeeded","failed","skipped","cancelled"})` 的收敛判断
   （`context.py`）已覆盖 `skipped`，无需改动。
4. **本批次只实现 scheduler/runner 级联**；`run.status` 维持现有“失败即 failed”策略，
   partial-success 的 run 级语义留给 Golden E2E 批次验证后决定。

## 13. Golden E2E 验收计划（B11.2.3 的输入）

新增 `tests/test_runtime_golden_e2e.py` 场景（本批次只验收设计，不实施）：

1. **文件链路**：CSV load → group_aggregate → sort → top_n；每个下游步骤的
   `asset_id` 参数在计划里写成逻辑引用，执行后断言：
   - 每步 `ExecutionResult.output_assets` 非空且命名正确；
   - 下游 `input_asset_ids` == 上游 Binding 资产（不是源 CSV）；
   - 全链路 execution_id 单一且 Binding/ExecutionResult/Evidence 一致；
   - `session.current_asset_id` 不参与解析。
2. **多输出**：一个步骤产生 2 个命名输出，两个下游步骤分别按名消费其一
   （乱序 JSON 键序不导致错配）。
3. **失败传播**：中间步骤注入失败 → 下游 skipped，run 收敛为 failed。
4. **Retry**：对中间步骤发起 retry run → 新 attempt 产生新 Binding（新 canonical
   execution_id）；父 run 归档中旧 Binding 保持原值；子 run 下游消费的是新资产。
5. **SQLite 链路**：`run_sqlite_query` → `run_analysis_operation` 消费查询输出资产
   （经 Binding 而非 `current_asset_id`），dedup 命中时断言 Binding 的
   `execution_id` 属于当前 Attempt。

### 15.2 批次验收门槛（B11.2.1 整体）

1. 单个 Step 可产生一个命名 DataAsset；单个 Step 可产生多个命名 DataAsset，
   且名称与资产 ID 的对应关系由命名映射显式表达。
2. 多个下游 Step 可消费同一 Binding；下游可正确解析上游逻辑输出名称。
3. `ExecutionResult` 能记录真实输出 Asset IDs 及其命名映射；
   `input_asset_ids` 反映实际消费的物理资产。
4. execution_id 全链路单一权威来源，Binding / ExecutionResult / Evidence 一致。
5. V2 计划执行不再依赖 `session.current_asset_id` 做权威传递。
6. Retry 不覆盖历史 Attempt 的 Binding；SQLite dedup 不混淆 Execution 血缘。
7. 原有文件分析与 SQLite 单步骤链路不回归。
8. 缺失 Binding 时返回明确错误，不静默使用错误资产；V2 路径 Binding 解析失败时
   不得读取 `session.current_asset_id`（测试强制断言）。
9. `git diff --check` 通过，相关测试通过。
