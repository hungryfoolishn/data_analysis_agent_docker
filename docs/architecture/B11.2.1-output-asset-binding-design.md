## 1. 当前架构与问题

### 1.1 真实执行链（基线 a75a459）

1. 计划步骤以 `RuntimePlanStep` 表示，携带 `required_inputs` / `expected_outputs`
   （`langgraph_langchain/runtime/models.py::RuntimePlanStep`）。
2. `analysis_tasks_from_plan()`（`langgraph_langchain/runtime/scheduler.py`）把每个步骤转成
   `AnalysisTask`。所有任务都收到同一个 `plan.input_asset_ids`；
   `required_inputs` / `expected_outputs` 仅作为字符串列表透传，不做解析。
3. `TaskRunner.execute_next()`（`langgraph_langchain/runtime/runner.py`）通过
   `request_factory(task)` 构建请求。`is_ready()` 只依赖任务状态与 `depends_on`。
4. `AnalysisRuntime.build_execution_request()`
   （`langgraph_langchain/runtime/context.py::build_execution_request`）把
   `task.input_asset_ids` 经 `AssetResolver.resolve_many()`（`runtime/asset_resolver.py`）
   解析进 `namespace.runtime_inputs` / `runtime_input_metadata`。
5. `StructuredTaskExecutor.execute()`（`execution/structured_executor.py`）调用工具。
   `run_analysis_operation`（`tools/tool_analysis_operation.py`）用参数中的 `asset_id`
   自行调用 `runtime.asset_resolver.resolve()`，计算后调用 `runtime.register_dataframe()`
   注册输出资产，并执行 `session.current_asset_id = asset.asset_id`。
   `run_sqlite_query`（`tools/tool_sqlite_query.py`）与 `load_data`
   （`tools/tool_load_data.py`）采用相同模式。
6. `extract_artifact_ids()`（`execution/task_models.py`）只从工具 JSON 提取 artifact ID；
   `ExecutionResult` 没有 `output_asset_ids` 字段（`runtime/models.py::ExecutionResult`）。
7. `record_execution_result()`（`runtime/context.py`）按 `step_id + tool_name` 幂等合并
   执行记录，并回填 artifact 的 `execution_id`，但无法还原数据资产血缘。

### 1.2 已确认的问题

| 问题 | 代码依据 | 优先级 |
| --- | --- | --- |
| `expected_outputs` 只是逻辑名称，未映射真实 DataAsset ID | `models.py::RuntimePlanStep.expected_outputs`；无任何映射代码 | P1 |
| 下游依赖 `session.current_asset_id` 隐式传递 | `tool_analysis_operation.py:120`、`tool_sqlite_query.py:117`、`tool_load_data.py:158` | P1 |
| `ExecutionResult` 不保存 `output_asset_ids` | `runtime/models.py::ExecutionResult` 字段清单 | P1 |
| 无 OutputAssetBinding 权威注册机制 | 全仓库无对应模型/Registry | P1 |
| Retry 无 attempt 级输出隔离 | `context.py::_create_retry_run` 清空 assets/executions 后重建，但无 binding 记录可追溯 | P2 |
| 上游失败后下游保持 pending（未显式 skip） | `runner.py::execute_next` 失败分支只返回 `failed`；`scheduler.py` 无 skip 级联 | P2 |
| `expected_outputs` 命名不统一 | `analysis_workflow.py:75` 用 `{step_id}:output`；`sqlite_workflow.py:189` 用 `query_result_asset`；`plans.py:104` 用 `analysis_output` | P2 |
| `required_inputs` 语义混杂（物理 ID 与逻辑名未区分） | `sqlite_workflow.py:188` 与 `analysis_workflow.py:74` 均填物理 ID；`validate_plan()`（`plans.py:54`）要求全部命中已注册资产 | P2 |

补充结论（B11.2.0 未覆盖、影响设计）：

- `validate_plan()`（`runtime/plans.py`）对 `required_inputs` 做“必须属于已注册资产”校验，
  因此 `step_1.grouped_data` 这类逻辑引用今天会被直接拒绝。
- 现有确定性 Planner 生成的多步计划里，每个分析步骤的 `asset_id` 都指向**源资产**
  （`runtime/general_planner.py::DeterministicAnalysisPlanner.plan` 中 `input_refs=[primary_asset]`；
  `runtime/analysis_workflow.py::general_plan_to_runtime_plan` 原样透传），
  即当前计划层还没有“下游消费上游输出”的真实用例，Binding 引入后需要让该用例可表达。
- 工具通过参数接收 `asset_id` 并自行 resolve（`tool_analysis_operation.py`），这意味着
  Binding 解析必须在 request 构建层完成，否则无法保证工具收到的一定是物理 ID。

## 2. 目标架构

### 2.1 目标数据传递链

```
RuntimePlanStep(expected_outputs=["grouped_data"])
  ↓ AnalysisTask (required_inputs 可能含逻辑引用 "step_1.grouped_data")
TaskRunner.execute_next() → AnalysisRuntime.build_execution_request()
  ↓ OutputBindingRegistry.resolve() 将逻辑引用解析为物理 asset_id
TaskExecutionRequest(arguments.asset_id=<物理 ID>, namespace.runtime_inputs={...})
  ↓ StructuredTaskExecutor → Tool（只接收物理 asset_id，行为不变）
Tool 计算 → AnalysisRuntime.register_output_asset()
  ↓ 注册 DataAsset + 写入 OutputAssetBinding（run_id, step_id, output_name, attempt, execution_id）
ExecutionResult.output_asset_ids 回填
  ↓ Evidence / Report 沿 binding → execution → step → run/attempt 重建血缘
下游 build_execution_request 再次解析 Binding
```

### 2.2 职责边界（冻结）

| 层 | 职责 | 明确不做 |
| --- | --- | --- |
| `OutputBindingRegistry` | Binding 的注册、查询、冲突校验、持久化结构 | 不执行数据加载、不解析 dataframe |
| `AnalysisRuntime` | 持有 Registry；在 `build_execution_request()` 做输入解析；在 `record_execution_result()` 回填输出绑定 | 不让 Scheduler 感知 Binding |
| `TaskScheduler` | 状态调度 + 失败级联 skip | 不做资产/Binding 查询 |
| `TaskRunner` | 传递 request_factory 产物 | 不解析 Binding |
| 工具（`run_analysis_operation` / `run_sqlite_query` / `load_data`） | 接收物理 `asset_id`；通过 Runtime 注册输出资产 | 不查询 Binding Registry；不解析逻辑引用 |
| `AssetResolver` | 按 asset_id 加载快照 | 不做逻辑名解析 |

## 3. 数据模型

### 3.1 OutputAssetBinding

新增于 `langgraph_langchain/runtime/models.py`（与既有模型一致采用 Pydantic，便于
snapshot 序列化与校验）：

```python
class OutputAssetBinding(BaseModel):
    run_id: str
    step_id: str
    output_name: str          # 规范化后的裸名称，如 "output" / "query_result_asset"
    asset_id: str             # 物理 DataAsset ID
    execution_id: str
    attempt: int = Field(ge=1)
    created_at: str = Field(default_factory=utc_now)
```

设计原则：

1. **逻辑名与物理 ID 分离**。逻辑引用语法冻结为 `{step_id}.{output_name}`
   （如 `step_1.grouped_data`）。`required_inputs` 允许两种取值：
   物理 asset ID（现状兼容）或逻辑引用（新增）。
2. **唯一键**：`(run_id, step_id, output_name, attempt)`。同一键重复注册时：
   - 内容完全一致（asset_id、execution_id 相同）→ 幂等返回；
   - 内容不同（如 asset_id 或 execution_id 不同）→ 抛
     `OutputBindingConflictError`，禁止覆盖。
3. **不可变性**：注册成功后不提供修改接口；只有删除整个 run 的历史归档时随之失效。
4. **序列化**：`model_dump(mode="json")`；持久化进 run snapshot
   （`context.py::snapshot()`，新增 `output_bindings` 键，快照版本由 1 升至 2，
   旧快照缺省为空列表）。

### 3.2 逻辑引用语法

- 输出名命名空间：`expected_outputs` 统一为**裸名称**（不含 `step_id:` 前缀）。
  唯一默认输出名冻结为 `output`；SQLite 查询步骤输出名冻结为 `query_result_asset`。
- 兼容迁移：`runtime/analysis_workflow.py:75` 的 `f"{item.step_id}:output"` 改为
  `"output"`（同一批次内完成，属于命名统一，不改变执行行为）。
- 引用解析正则（代码层冻结）：`^(?P<step_id>step_[0-9a-f]+)\.(?P<output_name>[A-Za-z0-9_]+)$`。
  非 `step_*` 前缀的字符串一律按物理 asset ID 处理，避免误伤现有 ID。

## 4. Registry 接口

### 4.1 权威归属

- Registry 是 **AnalysisRuntime 的内存内权威 + run snapshot 持久化**，不新建数据库，
  不复用 `self.assets`（资产表保持“存在什么资产”，Registry 记录“哪个步骤的哪个输出
  是哪个资产”）。
- 存放位置：新模块 `langgraph_langchain/runtime/output_bindings.py`；
  `AnalysisRuntime.__init__` 持有 `self.output_bindings: OutputBindingRegistry`；
  `snapshot()` / `_restore()` / `_persist()` 负责落盘与恢复；
  run 归档（`.analysis_runs/{run_id}.json`）天然形成历史 Attempt 的不可变档案。

### 4.2 接口定义（实施冻结）

```python
class OutputBindingConflictError(ValueError): ...

class OutputBindingNotFoundError(KeyError): ...

class OutputBindingRegistry:
    def register(self, binding: OutputAssetBinding) -> OutputAssetBinding:
        """唯一键幂等注册；冲突抛 OutputBindingConflictError。"""

    def resolve(
        self, *, run_id: str, step_id: str, output_name: str, attempt: int
    ) -> OutputAssetBinding:
        """精确匹配 (run_id, step_id, output_name, attempt)；未命中抛
        OutputBindingNotFoundError（下游据此显式失败，不静默回退）。"""

    def resolve_for_step(
        self, *, run_id: str, step_id: str, attempt: int
    ) -> list[OutputAssetBinding]:
        """按 step 聚合（Evidence Lineage / 血缘重建使用）。"""

    def list_for_run(self, *, run_id: str, attempt: Optional[int] = None) -> list[OutputAssetBinding]:
        """审计与测试断言用。"""
```

- **生命周期**：Registry 随 `AnalysisRuntime` 创建；`_create_retry_run()` 中随
  assets/executions 一起清空（见 §8），父 Attempt 的 Binding 只存在于父 run 归档文件中。
- **清理**：不做自动 GC；与现有 `.analysis_runs/` 归档策略保持一致。

## 5. ExecutionResult 变更

### 5.1 字段

`runtime/models.py::ExecutionResult` 新增：

```python
output_asset_ids: list[str] = Field(default_factory=list)
```

- 顺序约定：与该步骤 `expected_outputs` 顺序一一对应；单输出步骤 `len == 1`。
- 不新增 `output_binding_names`：名字可由 `step_id + expected_outputs` 还原，
  避免双份真源。

### 5.2 传递链（不依赖解析 stdout 文本之外的信息）

1. 工具返回 JSON 中已含 `output_asset_id`（现状）；多输出时新增
   `output_assets: {name: asset_id}` 有序映射（`json.dumps` 的 dict 保序）。
2. `execution/task_models.py` 新增 `extract_output_asset_ids(output)`：解析单值
   `output_asset_id` 与映射 `output_assets`，返回 `(ordered_names, ordered_asset_ids)`。
3. `StructuredTaskExecutor.execute()` 将结果写入
   `build_execution_result(..., output_asset_ids=...)`。
4. `AnalysisRuntime.record_execution_result()` 在收到结果后做 binding 对账：
   - 按 `step_id` 找到 `run.steps` 中对应 `expected_outputs`；
   - 对每个 `output_asset_ids[i]`，若尚无 `(run_id, step_id, expected_outputs[i], attempt)`
     的 Binding，则调用 Registry 注册（execution_id 用结果中的 execution_id，
     attempt 用 `self.run.attempt`）；
   - 已存在且一致 → 幂等跳过；不一致 → 冲突错误，执行结果按失败处理。
5. `PythonTaskExecutor` 路径：本批次仅在 `ExecutionResult` 上保留字段并允许为空；
   python_repl 的命名输出绑定不在 B11.2.1 范围（见 §14）。

### 5.3 校验规则

- `output_asset_ids` 中出现的每个 asset_id 必须已注册于 `runtime.assets`，
  否则 `record_execution_result()` 抛错并判定该步骤失败（资产注册失败属于执行失败）。

## 6. Tool 输出资产注册机制

### 6.1 新入口 `AnalysisRuntime.register_output_asset()`

新增于 `runtime/context.py`：

```python
def register_output_asset(
    self,
    *,
    dataframe_or_result,          # 复用 register_dataframe / register_sqlite_result 语义
    step_id: str,
    execution_id: str,
    output_name: Optional[str] = None,
) -> DataAsset:
```

行为：

1. 按 `output_name is None` 时取该 step `expected_outputs` 的下一个未绑定名
   （单输出步骤即 `expected_outputs[0]`）。
2. 资产创建复用现有 `register_dataframe()` / `register_sqlite_result()`（含 SQLite dedup），
   不复制注册逻辑。
3. 注册成功后写入 Binding：`run_id=self.run.run_id`、`attempt=self.run.attempt`、
   `execution_id`、`step_id`、`output_name`、`asset_id`。
4. 返回 `DataAsset`。工具继续把 `output_asset_id` 写进返回 JSON（现有行为保留，
   供 executor 提取与 evidence 使用）。

### 6.2 工具改动（最小化）

| 工具 | 改动 |
| --- | --- |
| `tools/tool_analysis_operation.py` | `runtime.register_dataframe(...)` → `runtime.register_output_asset(..., step_id=session.current_runtime_step_id, execution_id=recorder.execution_id)`；保留 `session.current_asset_id` 赋值（兼容） |
| `tools/tool_sqlite_query.py` | 同上（经由 `register_sqlite_result` 的包装）；dedup 返回旧资产时**仍然创建当前上下文 Binding** |
| `tools/tool_load_data.py` | `register_session_dataframe` 后调用 `register_output_asset` 绑定 `expected_outputs`（load_data 步骤的输出名同样为 `output`） |

工具不感知 Binding 细节，只负责“把输出交给 Runtime 注册”。

## 7. 下游输入解析流程

### 7.1 解析位置

统一在 `AnalysisRuntime.build_execution_request()`（`runtime/context.py`）内完成，
新增私有步骤 `_resolve_task_inputs(task) -> ResolvedTaskInputs`：

1. **物理输入**（现状保留）：`task.input_asset_ids` 经 `asset_resolver.resolve_many()`
   进 `namespace.runtime_inputs`。
2. **逻辑引用解析**：
   - 遍历 `task.required_inputs`，匹配 §3.2 正则的字符串按逻辑引用处理：
     `binding = output_bindings.resolve(run_id, step_id, output_name, attempt=self.run.attempt)`，
     将 `binding.asset_id` 追加进本次请求的输入集合与 `namespace.runtime_inputs`。
   - 遍历 `task.arguments`（来自 `task.constraints["arguments"]`，即 planner 写入的
     `asset_id` 等）：值为逻辑引用时**原地替换为物理 asset_id**，工具收到的仍是物理 ID，
     工具代码不变。
3. **校验顺序**：逻辑引用的 `step_id` 必须是当前任务的传递闭包依赖
   （`task.depends_on` 的闭包）或本 run 内已成功步骤，否则视为非法引用，直接失败。
4. **失败语义**：`OutputBindingNotFoundError` / `OutputBindingConflictError` /
   非法引用 → 记录 `metadata["binding_resolution_error"]` 并使任务失败
   （与现有 `asset_resolution_error` 的处理方式一致，但明确为错误而非告警）；
   **禁止**回退到 `session.current_asset_id` 或 `plan.input_asset_ids`。
5. **计划期校验**：`runtime/plans.py::validate_runtime_plan()` 扩展——
   逻辑引用只允许指向 `depends_on` 闭包内的 step，且 `output_name` 必须出现在该 step 的
   `expected_outputs` 中；物理 asset ID 继续走现有 `validate_plan()` 校验。

### 7.2 不改动的层

- `TaskRunner` / `TaskScheduler`：不接触 Binding（Scheduler 仅新增 §9 的 skip 级联）。
- `AssetResolver`：继续只按 asset_id 解析。
- `graph.py::RuntimeV2Controller._request_factory()`：继续委托
  `build_execution_request()`；同时修复 B11.2.0 P2-1（合并而非覆盖
  `request.metadata`），因为 Binding 解析错误需要经 metadata 传递。

## 8. Retry / Attempt 语义

### 8.1 冻结决策

1. **Binding 唯一键包含 attempt**：新 Attempt 产生的 Binding 永不覆盖旧 Attempt。
2. **Retry Run 不继承父 Run 输出**：`_create_retry_run()`
   （`runtime/context.py:1703`）已经清空 `assets` / `executions` / `artifacts`
   并新建 `run(attempt=parent+1)`；B11.2.1 沿用该语义——retry 从头执行计划，
   父 Attempt 的 Binding 留在 `.analysis_runs/{parent_run_id}.json` 中只读可审计，
   但子 Run 的 `resolve()` 只在子 Run 自身 Registry 内查找。
   理由：复用父输出需要跨 run 资产快照恢复与“哪些步骤可信复用”的判定，
   属于独立批次的工作量；强行继承会把未验证的旧数据混入新 Attempt，
   违反“缺失 Binding 时明确失败”的原则。
3. **Retry Run 的 Registry 必须清空**：`_create_retry_run()` 中显式重建
   `OutputBindingRegistry`，防止子 Run 复用父 Run 的任何 Binding。
4. **SQLite dedup 语义**：`register_sqlite_result()` 命中 dedup 时返回已有资产 ID；
   该资产仍会以**当前** `(run_id, step_id, output_name, attempt, execution_id)`
   注册 Binding。即：物理资产可复用，血缘必须指向当前 Attempt 的执行。
5. **旧 Attempt 输出防误用**：下游解析只查当前 run 的 Registry（含当前 attempt 精确匹配）；
   旧 Attempt 的输出在新 Run 中不可达，除非同一步骤重新执行并重新绑定。
6. **同一 run 内同步骤二次执行**（如 needs_revision 后重跑）：Binding 唯一键含 attempt，
   同 attempt 内重复执行同一输出名且 asset_id 不同 → `OutputBindingConflictError`，
   执行失败显式暴露，不静默覆盖。

### 8.2 血缘字段

Binding 同时记录 `execution_id`（生产者）与下游任务的解析结果会进入
`ExecutionResult.input_asset_ids`；B11.2.2 将据此验证
“输入资产 == 上游 Binding 资产 && evidence.execution_id == binding.execution_id”。

## 9. 失败传播规则

### 9.1 状态定义（冻结）

| 状态 | 含义 |
| --- | --- |
| `failed` | 实际执行过且出错（含 Binding 解析失败、冲突失败） |
| `skipped` | 因传递闭包内上游 `failed`/`skipped` 而确定不执行 |
| `blocked` | 上游仍在运行、结果未定（保持现状语义） |

### 9.2 级联规则

1. `TaskScheduler` 新增 `skip_dependents(task_id)`：把 `task_id` 的传递闭包内所有
   `pending` 任务标记为 `skipped`，并写入 `task.error = "upstream_failed"`（或等价标记）。
2. `TaskRunner._finish_step()` 在 `result.status in {"failed", "cancelled"}` 时调用
   `scheduler.skip_dependents(task_id)`，使 scheduler 状态机在失败后立即收敛，
   而不是留下一批永远 pending 的任务。
3. `AnalysisRuntime.execute_next_task()` 中 `all(... in {"succeeded","failed","skipped","cancelled"})`
   的收敛判断（`context.py`）已覆盖 `skipped`，无需改动。
4. **本批次只实现 scheduler/runner 级联**；`run.status` 维持现有“失败即 failed”策略，
   partial-success 的 run 级语义留给 Golden E2E 批次验证后决定。

## 10. 兼容性策略

1. `session.current_asset_id` **保留赋值**（`langgraph_agent.py` 旧链路、
   `tool_python_repl` 输入、UI 显示依赖），但：
   - V2 计划执行路径（`build_execution_request` 及之后）不再读取它作为输入真源；
   - `langgraph_agent.py:1147` 的旧 python_repl 路径在本批次不动。
2. 旧快照兼容：`snapshot()` 版本升为 2；`_restore()` 对缺
   `output_bindings` 键的旧快照默认空 Registry。
3. 无 Binding 的旧执行路径：单步骤 file/SQLite 链路（`prepare_file_analysis` /
   `prepare_sqlite_analysis` 生成的计划）在新机制下自动获得 Binding
   （工具注册输出时即绑定），不需要额外迁移；任何“缺失 Binding”场景一律显式失败。
4. `expected_outputs` 命名统一为裸名称后，历史 run 归档中的 `{step_id}:output`
   不做迁移——归档是只读历史，血缘重建只对新执行生效。

## 13. Golden E2E 验收计划（B11.2.3 的输入）

新增 `tests/test_runtime_golden_e2e.py` 场景（本批次只验收设计，不实施）：

1. **文件链路**：CSV load → group_aggregate → sort → top_n；每个下游步骤的
   `asset_id` 参数在计划里写成逻辑引用，执行后断言：
   - 每步 `ExecutionResult.output_asset_ids` 非空；
   - 下游输入 = 上游 Binding 资产（不是源 CSV）；
   - `session.current_asset_id` 不参与解析。
2. **多输出**：一个步骤产生 2 个命名输出，两个下游步骤分别消费其一。
3. **失败传播**：中间步骤注入失败 → 下游 skipped，run 收敛为 failed。
4. **Retry**：对中间步骤发起 retry run → 新 attempt 产生新 Binding；父 run 归档中
   旧 Binding 保持原值；子 run 下游消费的是新资产。
5. **SQLite 链路**：`run_sqlite_query` → `run_analysis_operation` 消费查询输出资产
   （经 Binding 而非 `current_asset_id`），dedup 命中时断言 Binding 的
   `execution_id` 属于当前 Attempt。

### 15.2 批次验收门槛（B11.2.1 整体）

1. 单个 Step 可产生一个命名 DataAsset；单个 Step 可产生多个命名 DataAsset。
2. 多个下游 Step 可消费同一 Binding；下游可正确解析上游逻辑输出名称。
3. `ExecutionResult` 能记录真实输出 Asset IDs。
4. V2 计划执行不再依赖 `session.current_asset_id` 做权威传递。
5. Retry 不覆盖历史 Attempt 的 Binding；SQLite dedup 不混淆 Execution 血缘。
6. 原有文件分析与 SQLite 单步骤链路不回归。
7. 缺失 Binding 时返回明确错误，不静默使用错误资产。
8. `git diff --check` 通过，相关测试通过。
