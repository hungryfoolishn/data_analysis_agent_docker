# M2.7.1: Runtime V2 SQLite DataAsset 消费链路检查

## 1. 检查范围与结论

本检查基于当前分支提交 `533e8bf fix(runtime): harden sqlite asset registration`。
本阶段只新增设计检查文档，不实现 SnapshotStore，不修改 Runtime 核心逻辑。

核心结论：

- Runtime V2 目前有 Task、Plan、Execution、Artifact 的元数据链路，但没有统一的
  Asset Resolver，也没有按 `input_asset_ids` 恢复 DataFrame 的消费接口。
- M2.6 注册的 SQLite DataAsset 已经具备身份、provenance、content hash、task
  input 关联和持久化能力，但没有持久化 DataFrame 数据本体。
- Runtime 重启后可以通过 `.analysis_runtime.json` 恢复 `DataAsset`、
  `AnalysisTask`、`ExecutionResult`、`RuntimeArtifact` 的元数据，但恢复不了
  SQLite 查询结果数据本体。
- 现有 `RuntimeArtifact` 是执行输出模型，不适合承载输入快照。
- 现有 `DataCache` 使用 pickle，且语义是临时缓存，不适合作为可信 SnapshotStore。
- 当前 `analysis` 环境没有安装 `pyarrow` 或 `fastparquet`，Parquet 不能作为
  M2.7.2 的默认实现前提。
- M2.7.2 应新增独立 SnapshotStore，并把快照引用写入 `DataAsset.source_metadata`，
  不复用 `DataAsset.location` 表示 SQLite 数据库路径。

## 2. 当前真实调用链

### 2.1 FileDataSource 到 DataFrame 的现有链路

文件数据的现行链路集中在：

- `langgraph_langchain/tools/tool_load_data.py`
- `langgraph_langchain/data/sources.py`
- `langgraph_langchain/data/cache.py`
- `langgraph_langchain/runtime/context.py`

实际顺序：

1. `load_data` tool 接收 `file_path` 和可选 `sheet_name`。
2. `_resolve_load_path()` 将路径限制在 session workspace 内。
3. 构造 `FileDataSource(path, sheet_name=...)`。
4. 调用 `FileDataSource.scan_schema()` 读取 schema 和估算行数。
5. 如果行数超过 `MAX_IN_MEMORY_ROWS`，构造 `SamplingSpec`。
6. 构造 `DataCache(workspace_dir / ".data_cache")`。
7. `cache_key()` 使用 source hash、adapter version、sheet/sampling 参数生成 key。
8. cache miss 时调用 `FileDataSource.materialize()` 或 `source.sample()`。
9. DataFrame 写入 `session.ns["df"]`。
10. `register_session_dataframe()` 调用
    `AnalysisRuntime.register_dataframe()`。
11. `DataAsset.from_dataframe()` 创建文件来源 asset，`location` 保存真实文件路径。
12. asset ID 追加到 `AnalysisTask.input_asset_ids`。
13. `_persist()` 持久化 Runtime 元数据。

该链路的关键问题是：`session.ns["df"]` 是会话内存状态；Runtime V2 的
`TaskExecutionRequest` 本身不会根据 `input_asset_ids` 重新解析 DataFrame。

### 2.2 Runtime V2 Task 执行链路

主要模块：

- `langgraph_langchain/runtime/context.py`
- `langgraph_langchain/runtime/runner.py`
- `langgraph_langchain/runtime/executor.py`
- `langgraph_langchain/execution/task_models.py`
- `langgraph_langchain/execution/structured_executor.py`
- `langgraph_langchain/execution/python_task_executor.py`
- `langgraph_langchain/execution/react_executor.py`

实际顺序：

1. `AnalysisRuntime.propose_plan()` 或
   `AnalysisRuntime.initialize_plan()` 生成/校验 `AnalysisPlan`。
2. `validate_plan()` 校验 method、`input_asset_ids` 和
   `RuntimePlanStep.required_inputs`。
3. `TaskScheduler.from_plan()` 将 `AnalysisPlan` 转成 `AnalysisTask`。
4. `analysis_tasks_from_plan()` 会把 plan 级别的 `input_asset_ids`
   赋给每个 `AnalysisTask.input_asset_ids`。
5. `AnalysisRuntime.build_execution_request()` 构造 `TaskExecutionRequest`。
6. `TaskExecutionRequest.input_asset_ids` 只是 `self.task.input_asset_ids`
   的拷贝，没有资产解析。
7. `TaskRunner.execute_next()` 取 ready task、调用 request factory、执行 executor。
8. `TaskExecutor` 根据 `task.executor_type` 分发到 structured / react / python。
9. `build_execution_result()` 把 `request.input_asset_ids`
   写入 `ExecutionResult.input_asset_ids`。
10. `AnalysisRuntime.execute_next_task()` 调用
    `record_execution_result()`，并 `_persist()`。

因此，Execution 记录的是“输入资产 ID 清单”，不是“已恢复的数据”。

### 2.3 Python 执行链路

`PythonTaskExecutor` 会把 `TaskExecutionRequest` 转成
`PythonExecutionRequest`：

- `code`
- `workspace_dir`
- `source_path`
- `namespace`
- `input_asset_ids`
- `timeout_seconds`
- `max_output_chars`

`IsolatedPythonExecutor` 会把 `namespace` 通过 fork 或 pickle 传给子进程，
但 `input_asset_ids` 只是请求字段，不会转换成 DataFrame。

当前 Python 代码主要依赖：

- `SOURCE_PATH`
- `session.ns["df"]` 或 request namespace 中已经存在的 DataFrame
- `load_csv()`

这些都不是 Runtime V2 的 DataAsset resolver。

## 3. DataAsset 与 M2.6 现状

`langgraph_langchain/data/assets.py` 中的 `DataAsset` 字段：

- `asset_id`
- `name`
- `source_type`
- `location: Optional[str]`
- `content_hash`
- `sheet_name`
- `schema_snapshot`
- `grain`
- `source_metadata`
- `created_at`

SQLite 查询来源由 `DataAsset.from_sqlite_query()` 创建：

- `source_type = "sqlite"`
- `location = None`
- `content_hash = hash_dataframe(dataframe)`
- `source_metadata` 保存：
  - `source_identity`
  - `query_fingerprint`
  - `query_type`
  - `table_name`
  - `selected_columns`
  - `row_count`
  - `truncated`

`AnalysisRuntime.register_sqlite_result()` 当前行为：

1. 校验 `BoundedReadResult` 和 SQLite provenance。
2. 创建或复用 SQLite DataAsset。
3. 将 asset ID 关联到 `task.input_asset_ids`。
4. `_persist()` 持久化。
5. 新增 asset 或新增 task 关联失败时回滚内存状态。
6. 复用 asset 时不会重新保存 DataFrame，因为没有 SnapshotStore。

`SQLiteReadMetadata` 已经保留：

- `database_path`
- `source_identity`
- `query_type`
- `table_name`
- `query_sha256`
- `selected_columns`
- `returned_row_count`
- `requested_row_limit`
- `truncated`
- `execution_duration_seconds`

其中 `database_path` 只存在于 M2.5 读取元数据中；M2.6 的 DataAsset
`source_metadata` 不保存数据库路径、原始 SQL 或原始参数。

## 4. Runtime 持久化与恢复

`AnalysisRuntime.snapshot()` 会序列化：

- `task`
- `run`
- `assets`
- `executions`
- `artifacts`
- `findings`
- `metric_definitions`
- `assumptions`
- `verifications`
- `evidence`
- `evaluations`

`_persist()` 的顺序：

1. 在 workspace 中写临时 JSON。
2. `os.replace()` 原子替换 `.analysis_runtime.json`。
3. 写 run history archive。
4. best-effort 写入 `SQLiteMetadataStore`。

`_restore()` 只从 `.analysis_runtime.json` 读取并用 Pydantic
`model_validate()` 恢复：

- `AnalysisTask`
- `AnalysisRun`
- `DataAsset`
- `ExecutionResult`
- `RuntimeArtifact`
- 其他 Runtime 元数据

Runtime 重启后，SQLite DataAsset 的身份、查询指纹、列、行数、truncated、
content hash 都可以恢复；但 DataFrame 本体当前无法恢复。

## 5. 关键问题回答

### A. 当前 Runtime V2 是否已有统一输入资产消费接口？

没有。

`register_dataframe()` 和 `register_sqlite_result()` 是注册接口。
`build_execution_request()` 只复制 `task.input_asset_ids`。
`TaskExecutionRequest`、`PythonExecutionRequest`、`ExecutionResult`
都只有 `input_asset_ids` 元数据字段，没有按 asset ID 恢复 DataFrame 的入口。

### B. SQLite DataAsset 注册后，能否通过 task.input_asset_ids 找到对应数据？

只能找到元数据。

`task.input_asset_ids -> runtime.assets[asset_id]` 可以得到
`DataAsset.source_metadata`、`schema_snapshot` 和 `content_hash`。
但没有 snapshot reference，也没有 snapshot loader，因此拿不到 DataFrame。

### C. DataFrame 数据本体目前是否持久化？

SQLite 查询结果 DataFrame 没有持久化。

Runtime 持久化的 `.analysis_runtime.json`、run history 和
`SQLiteMetadataStore` 只保存 asset 元数据，不保存 DataFrame。

文件资产看起来“可恢复”，是因为原始文件仍存在于磁盘上；这不是 DataFrame
快照持久化。SQLite 查询结果不能重新读原始数据库替代，因为查询结果可能在注册后
随数据库变化。

### D. 当前 Artifact 存储能否安全承载输入快照？

不建议复用 `RuntimeArtifact`。

理由：

- `RuntimeArtifact` 表示 execution output，具有 `execution_id`、
  `step_id`、`output_artifact_ids` 等输出语义。
- `register_artifact()` 生成 URL 和 workspace-relative path，主要面向
  图表、表格、报告、代码等用户可见产物。
- 把注册前输入快照注册为 Artifact 会混淆 input asset 与 output artifact。
- `RuntimeArtifact.input_asset_ids` 表达的是 artifact 的输入血缘，而不是
  artifact 本身可以反序列化为输入数据。
- Artifact 存储没有 SnapshotStore 需要的格式、hash、原子恢复和不可变快照语义。

结论：需要独立 SnapshotStore。可以在 DataAsset 的 `source_metadata`
中保存 snapshot reference，但不能让 `DataAsset.location` 伪装成 SQLite
数据库路径。

### E. 如何保证注册时的查询结果与后续分析使用的数据一致？

M2.7.2 应引入双层校验：

1. `snapshot_hash`：对快照物理文件或 snapshot container 做哈希，加载前验证
   快照未被篡改或截断。
2. `DataAsset.content_hash`：快照恢复为 DataFrame 后，重新计算
   `hash_dataframe()` 并与注册时的 content hash 比较。

两者都通过才允许进入分析执行。快照损坏时必须显式失败，不允许静默重新执行 SQL。

### F. 如何处理 truncated、snapshot_hash、缺失快照和持久化失败？

建议语义：

- `truncated=True` 表示 M2.5 读取受控截断，快照只能代表实际返回行，不代表
  数据库全集。
- `truncated` 必须进入 snapshot metadata 和 DataAsset source metadata，并在
  resolver 返回结果中继续暴露。
- `snapshot_hash` 是快照物理完整性校验值。
- `content_hash` 是 DataFrame 逻辑内容校验值。
- 快照缺失抛出明确的 snapshot missing error。
- 快照哈希不匹配抛出 integrity error。
- 快照格式不支持抛出 format error。
- 不允许因快照缺失或损坏而 fallback 重新执行 SQL。
- 快照写入成功、DataAsset 元数据持久化失败时，清理本次新建快照。
- 复用已有快照时，不能因一次注册或关联失败删除已有快照。
- task 关联持久化失败时，回滚新增 task 关联，但保留已有 asset 和快照。

### G. 如何以最小代码改动复用现有 FileDataSource 分析路径？

不建议让 SQLite 快照假装成 FileDataSource。

最小集成点是 Runtime V2 request construction 和 executor 输入准备：

1. 新增独立 `SnapshotStore`。
2. 新增 `AssetResolver`。
3. `AnalysisRuntime` 持有 SnapshotStore / AssetResolver。
4. 在 `build_execution_request()` 或其后的 request preparation 阶段解析
   `task.input_asset_ids`。
5. 将 resolved inputs 以显式 asset ID 映射交给 executor。
6. 继续由现有 `TaskRunner`、`TaskExecutor` 和 `build_execution_result()`
   记录 Execution。
7. 不改变 `FileDataSource` 的现有文件链路。

对 Python executor，可以在 request preparation 阶段把 resolved DataFrame
注入 `namespace`，但应使用明确的多资产映射，例如：

```python
{
    "runtime_inputs": {
        "<asset_id>": <ResolvedAsset>
    }
}
```

对 structured tool executor，不应强制所有既有 tool 立即接受 DataFrame；
M2.7.4 可先从 Python executor 或一个新的 data-consuming tool 路径打通，
不重写现有分析工具。

## 6. SnapshotStore 结论与依赖检查

在当前 `analysis` Conda 环境检查：

```text
pandas 2.3.2
numpy 2.2.6
pyarrow: missing
fastparquet: missing
```

因此：

- Parquet 是长期优先格式，但当前不能假设已可用。
- 如果 M2.7.2 选择 Parquet，必须先把 `pyarrow` 加入明确依赖，并补充安装/测试说明。
- 如果不新增依赖，可考虑 SQLite snapshot file + JSON schema sidecar，或
  CSV + schema sidecar；但必须解决 dtype 恢复、NULL、日期、Decimal 和
  content hash 稳定性。
- 不应使用 `DataCache` 现有 pickle 作为 SnapshotStore。
- 不应把 DataFrame 内容写入 Runtime SQLite 元数据表。
- 不应把 DataFrame JSON 序列化塞进 `.analysis_runtime.json`。

`DataCache` 当前使用：

- `DataFrame.to_pickle()`
- `pd.read_pickle()`
- `.pkl` 物理文件
- `.json` cache entry

它没有跨进程可信反序列化边界，也不具备不可变 snapshot 的失败语义，因此不能
承载 M2.7 的查询结果快照。

## 7. Asset Resolver 最小接口设计

建议保持小接口，不重构 Runtime：

```python
@dataclass(frozen=True)
class ResolvedAsset:
    asset_id: str
    dataframe: pd.DataFrame
    asset: DataAsset
    snapshot: SnapshotReference
    truncated: bool
    warnings: tuple[str, ...]


class SnapshotStore:
    def save(self, dataframe: pd.DataFrame, metadata: dict[str, Any]) -> SnapshotReference: ...
    def load(self, reference: SnapshotReference) -> pd.DataFrame: ...
    def exists(self, reference: SnapshotReference) -> bool: ...


class AssetResolver:
    def resolve(self, asset_id: str) -> ResolvedAsset: ...
    def resolve_many(self, asset_ids: Sequence[str]) -> dict[str, ResolvedAsset]: ...
    def resolve_task_inputs(self, task: AnalysisTask) -> dict[str, ResolvedAsset]: ...
```

错误类别可以最小化为：

- `AssetNotFoundError`
- `SnapshotReferenceError`
- `SnapshotNotFoundError`
- `SnapshotIntegrityError`
- `SnapshotFormatError`
- `SnapshotLoadError`

`resolve_many()` 必须保留输入 ID 顺序，但返回以 asset ID 为 key 的映射。
不要让下游只依赖列表位置猜测资产角色。

Resolver 返回的 `ResolvedAsset` 必须携带：

- `truncated`
- `query_fingerprint`
- `source_identity`
- `row_count`
- `selected_columns`
- `content_hash`

这样下游分析可以在不读取原始数据库路径的情况下理解数据来源和限制。

## 8. Runtime V2 集成位置

M2.7.4 建议按以下顺序接入：

1. `AnalysisRuntime` 增加 SnapshotStore 和 AssetResolver 组装点。
2. `register_sqlite_result()` 先保存快照，再注册 DataAsset。
3. DataAsset `source_metadata` 写入 snapshot reference。
4. `AnalysisRuntime.build_execution_request()` 或 request preparation 阶段
   调用 `AssetResolver.resolve_task_inputs(task)`。
5. 将 resolved inputs 提供给现有 executor。
6. `ExecutionResult.input_asset_ids` 继续使用现有
   `build_execution_result()` 逻辑。
7. resolver 失败时让 executor 返回 failed ExecutionResult，不允许跳过或
   fallback 到 SQL 重执行。

不要在 `AssetResolver.resolve()` 内部重新执行 SQL。

## 9. 快照生命周期与失败回滚

M2.7.2 建议流程：

1. 生成 `snapshot_id`。
2. 将 DataFrame 写入临时文件。
3. flush/fsync 并完成本地完整性检查。
4. `os.replace()` 原子替换到 final snapshot path。
5. 计算 `snapshot_hash`。
6. 在 DataAsset `source_metadata` 中写入 snapshot reference。
7. 注册 DataAsset。
8. `_persist()` 保存 Runtime 元数据。
9. 元数据注册失败时，只删除本次新建快照。
10. 复用 DataAsset 时，不删除已有快照。
11. task 关联持久化失败时，只回滚新增关联。

快照引用至少包括：

```json
{
  "snapshot_id": "snap_...",
  "snapshot_format": "parquet|sqlite|csv",
  "snapshot_location": "<workspace-relative or store-relative reference>",
  "snapshot_hash": "<sha256>",
  "snapshot_hash_type": "sha256",
  "row_count": 0,
  "column_count": 0,
  "created_at": "<utc iso8601>"
}
```

`snapshot_location` 不应使用绝对用户路径或原始 SQLite 数据库路径。
SnapshotStore 内部可以基于 workspace / store root 解析相对引用。

## 12. 风险

1. **Parquet 依赖缺失**：当前环境没有 pyarrow/fastparquet，M2.7.2 需要先做
   依赖决策。
2. **dtype round-trip**：CSV 会丢失或改变 dtype；SQLite snapshot 需要显式
   schema 映射；Parquet 最适合但依赖当前不可用。
3. **pickle 风险**：不能把 SnapshotStore 建立在不可信 pickle 反序列化上。
4. **快照膨胀**：有界读取已有行数和字节限制，但 SnapshotStore 仍需要大小上限。
5. **孤儿快照**：注册失败时必须只清理本次新快照，不能误删复用快照。
6. **多个输入映射**：plan/task 目前只有 asset ID 列表，没有角色或参数名映射；
   M2.7.4 需要避免靠列表位置猜测。
7. **SQLite 数据漂移**：绝对不能通过重新执行 SQL 隐式刷新快照，否则会破坏
   M2.6 content hash 和 provenance。
8. **Artifact 语义污染**：不要把输入快照注册为 RuntimeArtifact。
