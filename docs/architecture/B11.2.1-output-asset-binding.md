## 2. 核心实现说明

### 2.1 Canonical execution_id（v3 §5.2）
- 唯一创建点：`AnalysisRuntime.build_execution_request()` 生成 `request.execution_id`。
- 传递链：request → executor 注入 `arguments["execution_id"]` → `SessionExecutionRecorder(execution_id=...)` → 资产 `source_metadata["execution_id"]` → `ExecutionResult.execution_id` → `OutputAssetBinding.execution_id`。
- `record_execution_result()`：canonical 结果只按 execution_id 匹配既有记录（同步骤二次执行不再被误合并）；legacy 工具记录走收养路径；不一致时改判 failed（`ExecutionIdMismatch`），工具侧记录保留。
- 兜底：工具未声明 `execution_id` 字段时不注入，`execution_id_source="legacy"`，行为与基线一致。

### 2.2 Binding 单点写入（v3 §5.4）
- Binding 只在 `record_execution_result()` 写入，先整批预校验（输出名 ∈ expected_outputs、资产已注册、provenance 一致、无键冲突）再 `register_many()` all-or-nothing；任何违规将结果改判 failed 且不写任何 Binding。
- 多输出：命名映射为绑定真源；未命名单值仅在 `len(expected_outputs)==1` 时补名，否则 `UnnamedMultiOutput` 失败；禁止下标映射。

### 2.3 输入解析（v3 §7）
- `build_execution_request()` 产出 `ResolvedTaskInputs`：物理资产 + 逻辑引用（`{step_id}.{output_name}`，仅识别已知 Step ID，歧义报错）→ 物理 asset_id；`arguments` 中逻辑引用原地替换；`parameters_json` 内引用同样改写。
- 缺失 Binding / 非依赖闭包引用 → `BindingResolutionError` → 任务失败、工具不执行、下游级联 skipped、不回退 `session.current_asset_id`。
- 计划期（`validate_runtime_plan`）与执行期使用同一分类器；`initialize_plan` 不再对未分型 plan 直接调用 `validate_plan`（否则逻辑引用被误拒）。

### 2.4 Registry 生命周期（v3 §4/§8）
- Registry 属于当前 `AnalysisRun`（内存内权威 + run snapshot v2 持久化 + `.analysis_runs/` 归档）。
- Retry Run 重建空 Registry；父 Attempt Binding 只存在于父归档；resolve 精确匹配 `(run_id, step_id, output_name, attempt)`。
- `_restore()` 孤儿清理：丢弃没有对应 succeeded 执行记录的 Binding。

### 2.5 SQLite dedup（v3 §8.1）
- `register_sqlite_result()` dedup 返回旧资产 ID；工具 JSON 声明该 ID；Binding 以当前 `(run_id, step_id, output_name, attempt)` + 当前 canonical execution_id 注册；provenance 一致性校验对 sqlite 资产豁免（以 `_sqlite_provenance_matches` 语义为准）。
- load_data 同文件重读命中 `register_dataframe` 去重（返回无 execution_id 元数据的既有资产）时，回退规则第二分支绑定该复用资产（同一去重原则），仍记当前 execution_id。

### 2.6 失败传播（v3 §9）
- failed（真实执行失败，含契约失败）／skipped（闭包内下游级联）／blocked（上游运行中）。
- `skip_dependents()` 仅对 failed/cancelled 根任务生效；`stop_on_failure` 默认行为不变；`execute_next` 在全部任务终态且存在失败时判 failed。
- 契约失败发生在 runner 标记成功之后：`demote_to_failed()` 显式降级 + 级联 skip。

## 3. 实施中的关键决策（对 v3 设计的落地澄清）

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| D1 | 绑定模型放 `schemas.py`（而非 `runtime/models.py`） | `runtime/__init__` 急切导入 context→runner→`execution.task_models`；task_models 需要绑定模型类型构造 `TaskExecutionRequest`，放 runtime 包内必然循环。schemas 是无 runtime 依赖的契约层 |
| D2 | canonical 结果只按 execution_id 查既有记录 | 旧 step+tool 兜底会把同步骤二次执行误并成一条执行；mismatch 场景改由 legacy 记录存在性判定 |
| D3 | 同 id 合并时以 Runtime 终局判定为准（stdout 取 executor 结果） | 同 canonical id 本就是同一执行节点；executor 的 stdout（工具完整 JSON 输出）比 recorder 文本更完整；mismatch 场景两条记录都保留 |
| D4 | `initialize_plan` 移除裸 `validate_plan` 前置调用 | 裸调用会先用物理资产校验拒绝逻辑引用；分型后 `validate_runtime_plan` 内部完成同等校验 |
| D5 | load_data 去重回退第二分支 | e2e 中 load_data 重读会话初始化已登记的同文件 → `register_dataframe` 去重返回旧资产；按 §8.1 去重原则绑定复用资产并记当前 execution_id；多候选时显式失败 |

## 5. 未覆盖场景 / 已知边界

1. `python_repl` 与 React 执行器路径不产生命名输出绑定（`output_assets` 为空；契约允许）。
2. Golden E2E（多输出多消费者、中步 retry、SQLite 链路场景）按计划属 B11.2.3。
3. Evidence Lineage Validator 属 B11.2.2；本批次只保证 Binding/ExecutionResult/Evidence 共用 canonical execution_id 与 resolved inputs。
4. runner `run()` 中 `max_steps` 与失败并存的收敛细节沿用基线（仅新增 skip 级联与终态 failed 判定）。
5. 存量归档（`.analysis_runs/`）中的历史 Binding 不做迁移；血缘重建仅对新执行生效。
