# B8.9 — Acquisition Version History & Lineage Review

Date: 2026-11-15
Branch: `codex/phase1-m2.4-sqlite-schema`
Base: `5e218a7 fix(data): harden acquisition contract and asset consistency`

## 1. Version semantics (verified / defined)

| Concept | Storage | Notes |
| --- | --- | --- |
| fetched_at | `FetchResult.fetch_metadata`, asset metadata, history record | UTC ISO; never conflated with observation period |
| observation_period | `FetchResult.observation_period`, asset metadata, history record | Derived from the normalized frame only |
| release_date | asset metadata / history record | `None` unless the adapter provides one; never inferred |
| revision | asset metadata / history record | `None` unless upstream provides it; change detection does not depend on it |
| content version | `content_version` label (`v1`, `v2`, …) | Deterministic sequence over distinct `content_hash` values per dataset |
| content hash | `FetchResult.content_hash`, `DataAsset.content_hash`, history record | Identity of content; repeat acquisition with unchanged content never creates a new version |

Change detection is content-hash based: `version_changed` is true only when the
previous successful acquisition has a different `content_hash`. A repeat
acquisition of identical content returns the same asset and records a new
acquisition event without a new content version.

## 2. AcquisitionHistory hardening (`langgraph_langchain/data/acquisition.py`)

- **Atomic writes**: temp file in the history directory + `fsync` +
  `os.replace`; a crash can no longer leave a partially written file.
- **Corruption detection**: invalid JSON / non-list / non-dict entries raise
  `AcquisitionHistoryCorruptionError` instead of being silently reset (which
  previously erased version history).
- **Schema version**: every record carries `schema_version: 1`; old records
  remain readable (queries tolerate missing fields).
- **Safe filenames**: dataset ids are validated (`^[A-Za-z0-9_.-]+$`) before
  being used as file names; traversal like `../x` is rejected.
- **In-process concurrency**: writes are serialized with a lock; atomic replace
  makes each reader see either the old or the new complete file. Multi-process
  single-writer boundary unchanged (documented in B8.8).
- **Failure vs. version**: fetch failures are recorded only as adapter health
  state; they never create history entries, so a failed acquisition can not be
  mistaken for a version or overwrite the previous version record.
- Records now also store `request_parameters` and `source_url` for lineage.

## 3. Read-only query capabilities (no implicit re-acquisition)

`AcquisitionHistory` now answers:

- `versions(dataset_id)` — all acquisition records, oldest first.
- `content_versions(dataset_id)` — distinct content versions, oldest first.
- `latest(dataset_id)` — latest acquisition record (existing).
- `find_by_asset_id(asset_id, dataset_id=None)` — maps a `DataAsset` id back to
  its acquisition record (asset id ↔ version lineage).

All queries are read-only; history lookups never trigger fetching and never
mutate registered assets.

## 4. DataAsset ↔ version lineage

The lineage chain is verified end to end:

```
FetchResult → AcquisitionHistory (asset_id, content_hash, content_version,
fetched_at, observation_period, release_date, revision)
           → SnapshotStore (snapshot_reference in asset metadata)
           → DataAsset.source_metadata (source_id, dataset_id, content_hash,
             fetched_at, observation_period, release_date, revision, quality_report)
           → Runtime Binding → Evidence → Verified Report
```

Evidence-level tracing of `source_id` / `dataset_id` / `content_hash` /
`fetched_at` / `observation_period` / `release_date` / `revision` is provided by
the B8.1 asset metadata contract (unknown values stay `None`); the history side
now allows the reverse lookup from a registered asset id to its acquisition
record. No second lineage system was introduced.

## 5. Tests (`tests/test_acquisition_history.py`, offline)

- atomic record write (no leftover temp file, schema version present);
- repeat content → no version change, same `content_version`;
- changed content → `version_changed=True`, `v1 → v2`, distinct content versions;
- missing upstream revision with changed content still detected via hash;
- failed acquisition → no history entry, previous version intact, health updated;
- process restart → history recoverable from disk;
- corrupted history → `AcquisitionHistoryCorruptionError` on read and write;
- unsafe dataset ids rejected;
- latest / versions / content_versions / find_by_asset_id queries.

## 7. Remaining issues

- P2: cross-process concurrent writes to the same history file are outside the
  documented single-writer runtime boundary; atomic replace prevents partial
  files but a last-writer-wins race remains possible. Revisit only if a
  multi-process acquisition deployment is actually introduced.
- P3: `content_version` labels are derived from distinct content hashes, so
  history-file deletion/rebuild could renumber labels; identity remains the
  content hash.
