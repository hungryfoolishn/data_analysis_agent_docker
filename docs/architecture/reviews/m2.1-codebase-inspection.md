# M2.1 Codebase Inspection

## 1. Executive Summary

DeepAnalyze already has reusable domain-neutral building blocks for file-backed
analysis: a `DataSource` interface, `DataAsset` metadata, deterministic
sampling/caching, runtime asset registration, execution records, verification,
and evidence collection.

However, it does **not** yet have a user-data database adapter. The only SQLite
use today is `SQLiteMetadataStore`, which persists Runtime metadata. It is not a
user-data source adapter and should not be reused as one.

For M2, the safest path is to extend the existing domain-neutral data layer with
a SQLite `DatabaseDataSource`, while keeping connection/security/bounds inside
that adapter. The adapter should return a `QueryResultDataSource` /
`DataAsset` for each governed query. Runtime and tool integration should remain
separate.

## 3. DataSource Review

### 3.1 Existing Contract

Status: `EXISTS_AND_VERIFIED`

`langgraph_langchain/data/sources.py` defines an abstract `DataSource`:

```python
class DataSource(ABC):
    source_type: str = "unknown"
    adapter_version: str = "1"

    @abstractmethod
    def scan_schema(self) -> SourceScan: ...

    @abstractmethod
    def preview(self, rows: int = 5) -> pd.DataFrame: ...

    @abstractmethod
    def estimate_rows(self) -> int: ...

    @abstractmethod
    def materialize(...) -> pd.DataFrame: ...

    def sample(self, spec: SamplingSpec) -> tuple[pd.DataFrame, SamplingMetadata]:
        return sample_dataframe(self.materialize(), spec)
```

This is a real data source contract, not just a dataclass.

### 3.2 File Path

Status: `EXISTS_AND_VERIFIED`

`FileDataSource` supports:

- CSV
- Excel `.xlsx` / `.xls`
- Parquet

It handles:

- Encoding detection for CSV.
- Schema scanning with `SchemaSnapshot.from_dataframe()`.
- Hashing with `hash_file()`.
- Row estimation.
- Preview and materialization.
- Deterministic sampling.
- Chunked CSV iteration.

### 3.3 Runtime Usage

Status: `EXISTS_AND_VERIFIED`

`langgraph_langchain/tools/tool_load_data.py` is the main file-loading entry
point. It:

1. Validates the tool stage.
2. Resolves the file path inside the session workspace with
   `_resolve_load_path()`.
3. Instantiates `FileDataSource`.
4. Calls `scan_schema()`.
5. Applies deterministic sampling for large files.
6. Uses `DataCache` with a source-hash/adapter-version/parameter cache key.
7. Registers the dataframe as a runtime asset through
   `register_session_dataframe()`.
8. Records execution through `record_session_execution()`.

### 3.4 Source Registry

Status: `NOT_FOUND`

There is no data source registry analogous to
`langgraph_langchain/tools/registry.py`. `FileDataSource` is instantiated
directly by `tool_load_data.py`.

For M2, this is acceptable. A database adapter can be constructed directly by a
future database tool or service. A general source registry can be added later if
multiple database types are introduced.

## 4. DataAsset Review

### 4.1 DataAsset Contract

Status: `EXISTS_AND_VERIFIED`

`langgraph_langchain/data/assets.py` defines `DataAsset` with:

- `asset_id`
- `name`
- `source_type`
- `location`
- `content_hash`
- `sheet_name`
- `schema_snapshot`
- `grain`
- `source_metadata`
- `created_at`

`SchemaSnapshot` records:

- Row count.
- Column count.
- Column names/dtypes/nullability/null counts/unique counts.
- Candidate keys.
- Time columns.
- Observation timestamp.

### 4.2 Runtime Registration

Status: `EXISTS_AND_VERIFIED`

`AnalysisRuntime.register_dataframe()` in
`langgraph_langchain/runtime/context.py` converts a dataframe into a `DataAsset`
using `DataAsset.from_dataframe()`.

It deduplicates by:

```python
existing.location == asset.location
and existing.content_hash == asset.content_hash
and existing.sheet_name == asset.sheet_name
```

It stores the asset in `AnalysisRuntime.assets` and appends the asset id to
`AnalysisTask.input_asset_ids`.

### 4.3 QueryResultDataSource

Status: `EXISTS_NOT_IN_MAIN_PATH`

`langgraph_langchain/data/sources.py` also defines
`QueryResultDataSource(MemoryDataSource)`. It is exported from
`langgraph_langchain.data`.

However, it is not currently used in the main file-analysis path. It is only
referenced by tests and package exports.

This is still the right shape for M2.6: a governed query result can be wrapped
as a `QueryResultDataSource` and converted into a `DataAsset`.

### 4.4 Gap

`DataAsset.from_dataframe()` currently requires a `source_path`. That is natural
for files, but not for SQL query results. M2.6 should add a database-specific
asset registration path or extend the contract so a query result can be
registered without pretending to be a file.

standard-library `sqlite3` is available, but currently used only by
`SQLiteMetadataStore`.

## 11. M2 Implementation Decisions

### M2.2 — SQLite Fixture Builder

**Decision:** add a deterministic test-only fixture builder.

Reuse:

- `pytest tmp_path`
- Python `sqlite3`
- Existing test conventions

Suggested location:

```text
tests/fixtures/phase1/golden/database/golden_sqlite.py
```

Responsibilities:

- Create a temporary SQLite database.
- Create deterministic schema and rows.
- Expose connection parameters/path.
- Clean up temporary files.

Do not:

- check in a binary SQLite file;
- depend on external services;
- use Runtime metadata tables;
- create Golden manifests in M2.2.

### M2.3 — Read-only Connection

**Decision:** create a database-layer connection wrapper.

Suggested location:

```text
langgraph_langchain/data/database.py
```

Responsibilities:

- Open SQLite with read-only URI where possible.
- Enforce timeout.
- Prevent mutation through SQLite authorizer/URI/policy.
- Close connections deterministically.
- Translate low-level errors into database-layer errors.

Do not place connection policy in the SQL tool.

### M2.4 — Schema Introspection

**Decision:** implement introspection in the same database adapter module.

Responsibilities:

- List accessible tables.
- Return columns, declared types, nullability where available, and primary keys.
- Return stable schema metadata suitable for `SchemaSnapshot` conversion later.
- Avoid exposing raw connection objects.

### M2.5 — Bounded SQL Execution

**Decision:** implement bounded execution inside the database adapter.

Responsibilities:

- Accept SQL text and bounded execution options.
- Enforce timeout.
- Enforce row limit.
- Enforce result-size limit.
- Reject unsafe statements.
- Return structured result metadata plus dataframe.
- Record enough metadata for future evidence, but do not create Evidence in M2.

### M2.6 — QueryResult → DataAsset

**Decision:** extend the existing data-asset path rather than create a parallel
asset model.

Preferred approach:

1. Wrap query result dataframe in `QueryResultDataSource`.
2. Add a database-aware `DataAsset` construction helper.
3. Add `AnalysisRuntime.register_query_result()` or extend
   `register_dataframe()` with explicit query-result metadata.

Requirements:

- Preserve SQL text, database path/identifier, row count, and bounded-execution
  metadata.
- Do not invent a fake source file path without documentation.
- Reuse `SchemaSnapshot.from_dataframe()`.
- Keep runtime deduplication semantics explicit.

### M2.7 — Adapter Tests

**Decision:** add focused tests without Runtime integration.

Suggested files:

```text
tests/data/test_database_connection.py
tests/data/test_database_introspection.py
tests/data/test_database_readonly.py
tests/data/test_database_execution.py
tests/data/test_database_limits.py
tests/fixtures/phase1/golden/database/golden_sqlite.py
```

Tests must cover:

- fixture determinism;
- connection success/failure;
- schema introspection;
- normal SELECT;
- unsafe write rejection;
- PRAGMA/attach restrictions;
- timeout;
- row limit;
- result-size limit;
- query error;
- connection cleanup;
- `QueryResultDataSource` behavior;
- `DataAsset` conversion.

Runtime/tool/planner/evidence integration is not in M2.7.

## 13. Risks and Open Questions

### Risks

1. **Overloading `DataSource`.** The current interface is read-only dataframe
   oriented. Database connection lifecycle may not fit cleanly without an
   explicit context manager or separate connection class.
2. **Fake source paths.** `DataAsset.from_dataframe()` requires `source_path`;
   using a fake path for query results would weaken provenance.
3. **SQL safety by string matching alone.** Prefix checking is insufficient for
   SQLite.
4. **Resource leakage.** Connections, temporary files, and cursors need explicit
   cleanup.
5. **Silent truncation.** Row/result-size limits should be recorded, not hidden.
6. **Mixing metadata and user data.** `SQLiteMetadataStore` must not be reused as
   a user-data adapter.

### Open Questions

1. Should the M2 public API be context-managed
   (`with DatabaseDataSource(...)`) or factory-created with explicit `close()`?
   Recommended: context manager plus deterministic close.
2. Should row-limit truncation raise or return truncated data with metadata?
   Recommended: return truncated data with explicit truncation metadata.
3. Should query results be cached in M2? Recommended: defer until bounded
   execution is stable.
4. Should `DataAsset.location` hold the database URI, logical database id, or
   query id? Recommended: logical database id plus query metadata, not raw
   credentials.
5. Should unsafe SQL return a structured error or raise? Recommended: adapter
   raises typed error; future tool converts it to user-facing failure.
