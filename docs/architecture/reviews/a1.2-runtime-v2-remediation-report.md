## 5. A1.2-1 Cancellation: Propagation Chain and Evidence

Propagation chain: POST /sessions/{id}/cancel sets the API cancel event -> session.cancel_event -> three layers:

1. Graph level (_run_runtime_v2_graph_stream): checked before the graph starts, raced against every stream event (asyncio.wait FIRST_COMPLETED), checked again before report building and before the final completed state. After cancellation the producer stops pulling new graph nodes, so no further task can start.
2. Scheduler level: on cancel, remaining pending/running scheduler tasks are marked cancelled; the runtime outcome derives status "cancelled"; the run status is persisted as "cancelled" via set_run_status (V1-parity semantics; step-level records use the persisted RuntimePlanStep contract, matching V1 behavior).
3. Python worker level: PythonTaskExecutor forwards the cancel event into IsolatedPythonExecutor.execute, which terminates the worker process group (SIGTERM then SIGKILL) and returns status "cancelled" -- not a generic failure.

Test evidence (test_runtime_v2_cancellation.py):

- Cancel before graph start: no task executes; run/outcome cancelled; repeated cancel requests are idempotent.
- Cancel during a sleeping python task: the worker is terminated (execution duration well under the 10s timeout), the second task never runs, run cancelled.
- Cancel racing task completion: the task may finish, but the session ends cancelled, never completed.
- PythonTaskExecutor forwards the event and terminates a real spinning worker process in under 5 seconds.

Measured cancel response: the sleeping-worker test completes in about 1s of wall clock for a 3s task (0.4s cancel delay + poll interval + termination). No SLA is claimed beyond the test bounds.

## 6. A1.2-2 SSE Token Streaming: Protocol and Evidence

V1 event contract (audited, unchanged): raw on_chat_model_stream token chunks, tool start/end progress messages, artifact flush, completed/error/cancelled.

V2 implementation: ReactTaskExecutor gained an optional token_callback. When present and the agent supports astream_events, the executor streams the agent graph exactly once, forwarding token deltas via loop.call_soon_threadsafe into the stream loop (thread-safe bridge from the worker thread), and keeps the final assistant message as the task result. The blocking invoke path is retained as fallback (agent_runner or non-streaming agents).

Event mapping (V2 vs V1):

- Token delta: restored for react tasks.
- Task preview: preserved for structured/python tasks; suppressed for tasks whose tokens were already streamed (no duplicate output).
- Tool start/result: V2 graph-level events are per-task previews; V1 per-tool events remain V1-only (documented design difference, not a regression).
- Artifact flush: preserved. Error: preserved (failed task message). Cancelled: preserved (cancel branch). Completed: preserved (only after verified report).

Tests (test_runtime_v2_sse_streaming.py): incremental token order, single agent execution (no duplicate tool runs), preview suppression for streamed tasks, preview retention for python tasks, unit contract of ReactTaskExecutor, and the error path (stream failure becomes a task failure, never a completed session).

## 8. A1.2-4 Rollback Semantics Documentation

The _run_runtime_v2_graph_stream docstring previously claimed the caller falls back to the legacy ReAct stream. It now documents the actual policy: default strict mode hard-stops on any V2 failure; fallback requires RUNTIME_V2_FALLBACK_ENABLED=1 plus RUNTIME_V2_STRICT_MODE=0 and applies only to infrastructure failures; config rollback affects only new sessions; V2 plan progress is not replayed by V1; drain active V2 sessions before rollback. No runtime behavior changed in this WP (docstring-only diff verified).

## 9. Blocking Baseline Defects Found and Fixed

Both defects existed at the A1.1-audited baseline HEAD 6cc265b and were verified by direct probes before fixing. Both crash the production entry.

P0-1: run_analysis_stream called log_runtime_route(..., session_id=...), but the function signature (from commit 59d9c21) does not accept session_id. Every session start raised TypeError before any analysis ran. Fix: log_runtime_route now accepts and logs session_id (runtime_route.py). Discovered by the first API-level V1 probe.

P0-2: AnalysisRuntime(plan_first=True) always stores a default fallback plan. When prepare_file_analysis fails (for example, an invalid planner goal), the V2 stream still found that stored plan and initialize_plan raised PlanExecutionValidationError outside any handler, crashing the stream instead of hard-stopping. Fix: plan initialization is guarded in _run_runtime_v2_graph_stream; failures yield "Runtime V2 failed: structured plan could not be initialized", set run status failed with error_code "runtime_plan_invalid", and stop (strict semantics, no fallback).

Additional pre-existing defect found and fixed while implementing WP2: with the installed LangGraph version, controller.graph.astream yields node-nested updates ({"execute_task": {...}}), so the previous loop's update.get("result") / update.get("action") were always None -- per-task previews, failure handling, and cancelled-result detection never fired in the V2 stream. The loop now unwraps the node state (flat dicts remain supported).
