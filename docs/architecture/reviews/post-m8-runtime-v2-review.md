## 1. Executive decision

**Not ready to enable Runtime V2 as the product default.**

Runtime V2 can be enabled explicitly for CI, development, or controlled evaluation. It should not become the product default until the P0 upload-path/security issues and the main-path integration gaps below are fixed.

Recommended target policy before re-review:

```bash
RUNTIME_V2_ENABLED=true       # only after P0/P1 closure
RUNTIME_V2_FALLBACK_ENABLED=false
RUNTIME_V2_STRICT_MODE=true
```

No runtime behavior or default configuration was changed in this B9 review.

## 4. Actual Runtime V2 call path

The real API/UI path is not yet the B4-B8 module-by-module path. It is currently:

```text
User upload
  -> POST /workspace/upload or POST /v1/files
     -> api_server_langgraph.py: upload_file_openai / workspace_upload

Analysis request
  -> POST /v1/chat/completions or POST /analysis/tasks
     -> _run_analysis_stream()
     -> _Session initialization
        -> AnalysisRuntime(..., plan_first=True)
        -> runtime/plans.py default_analysis_plan()

Runtime route
  -> langgraph_agent.run_analysis_stream()
  -> _RUNTIME_V2_ENABLED
  -> _run_runtime_v2_graph_stream()

Plan restore and validation
  -> AnalysisPlan.model_validate(runtime.run.plan)
  -> AnalysisRuntime.initialize_plan()

Execution
  -> runtime.build_execution_controller()
  -> TaskRunner / TaskExecutor
  -> StructuredTaskExecutor / ReactTaskExecutor / PythonTaskExecutor
  -> AnalysisRuntime.build_execution_request()
     -> AssetResolver when task.input_asset_ids exists
     -> runtime_inputs / runtime_input_metadata namespace injection

Assets / artifacts
  -> register_session_dataframe() for file loading
  -> register_session_artifact() for Python output
  -> SnapshotStore only for SQLite result registration paths

Report
  -> tools/tool_finish_report.py
  -> runtime/report_validator.validate_report()
  -> legacy Finding / EvidenceItem model
```

B4-B8 modules exist and are tested, but the production API path does not yet call all of them.

## 6. Session, Task, Execution, and lifecycle review

Current relationships:

- API session state is persisted in `WORKSPACE_DIR/.sessions.json`.
- API tasks are persisted in `WORKSPACE_DIR/.analysis_tasks.json`.
- Runtime metadata is persisted per session in `.analysis_runtime.json`.
- Historical run snapshots are written under `.analysis_runs/`.
- SQLite snapshots are stored under the session workspace `.data_snapshots/`.
- Runtime metadata is additionally mirrored to `WORKSPACE_DIR/.analysis_metadata.sqlite`.

Observed strengths:

- Runtime run, plan, steps, executions, assets, and artifacts have stable IDs and are serialized.
- Runtime restart can restore DataAsset metadata, tasks, executions, and artifacts.
- Snapshot references and data files are under the mounted workspace volume.
- Task idempotency keys prevent duplicate API task creation.
- Asset resolution and snapshot integrity are tested across restart.

Observed gaps:

- API task status does not distinguish completed, partial success, failed, and cancelled in a consistent lifecycle. `_background_analysis_task()` sets `completed` after the stream generator returns even when Runtime V2 reported a failed or fallback result.
- API task status has `queued`, `running`, `completed`, `failed`, `cancelled`, and `cancel_requested`, but Runtime run status uses a different state set and does not expose `partial_success`.
- On backend restart, tasks in `queued`, `running`, or `cancel_requested` are marked failed and marked not recoverable. Runtime metadata and snapshots may remain, but the API task itself is not resumed.
- There is no single owner for the end-to-end state machine across API task, Runtime run, plan step, execution, evidence, and report.
- Evidence and report persistence are split between legacy `Finding` / `EvidenceItem` and B6/B7 models; the B6/B7 records are not persisted by the API path.

## 7. Error, timeout, cancellation, and partial success review

### Error handling

Strong points:

- Runtime task failures are represented as failed `ExecutionResult` records.
- Snapshot and SQL failures do not create successful assets or evidence.
- The legacy report validator blocks unsupported numbers in `finish_report`.
- B5 tests cover that business failures do not fallback.

Gaps:

- Error classes are not uniformly translated into stable API error codes.
- B5 route policy is not used by the actual Runtime V2 path, so strict mode is not enforced in the real route.
- Some API exceptions include local filesystem paths; these should be minimized.

### Timeouts

Current coverage:

- SQLite bounded queries have a progress-handler deadline.
- Python execution has wall-time timeout and process-group termination.
- LLM requests have configurable request timeout.

Gaps:

- General Planner has no timeout.
- B7 report building/validation has no timeout.
- API background tasks do not impose an end-to-end analysis deadline independent of tool timeouts.
- Excel/Parquet/file loading does not have a universal execution deadline.

### Cancellation

- Legacy `/sessions/{session_id}/cancel` sets an asyncio event.
- Legacy Python REPL accepts that event.
- Runtime V2 graph and `PythonTaskExecutor` do not accept the API cancellation event.
- Background API tasks can be cancelled through asyncio cancellation, but the explicit cancel endpoint only sets an event that the Runtime V2 path does not inspect.

This is a productization blocker for long-running analyses.

### Partial success

- Runtime currently represents tasks as succeeded/failed and runs as completed/failed.
- B7 `AnalysisReport` supports `partial_success`, but it is not wired to API response semantics.
- The API task lifecycle does not expose partial success.

## 8. Security and resource boundaries

### 8.1 File input

Findings:

- Upload size is checked after `await file.read()` has loaded the entire upload into memory. A very large request can still cause memory pressure before the 100 MB check.
- `/v1/files` constructs `WORKSPACE_DIR / f"{file_id}_{file.filename}"`.
- `/workspace/upload` constructs `session_workspace / file.filename`.
- Neither upload endpoint sanitizes `file.filename` to a basename or rejects path separators before writing.
- There is no server-side upload format allowlist; Streamlit has a client-side `type=` restriction only.
- File changes are detected in the B3 file AssetResolver only when the asset is registered with a content hash. The legacy `load_data` path does not use that resolver contract.

This is a **P0** security issue: crafted upload names can escape the intended directory and overwrite files.

### 8.2 SQLite

Strong points:

- `SQLiteDataSource` opens `mode=ro`, sets `PRAGMA query_only=ON`, and uses an authorizer.
- Multi-statement SQL is rejected.
- Queries use bound parameters.
- Execution has progress-handler timeout, row limit, result-size estimate, and truncation metadata.
- Result registration uses SnapshotStore with physical and logical hash checks.
- SQL failures do not create assets.

Limitations:

- The SQL Tool is not exposed through the API/tool registry.
- Table and column allowlisting is enforced for table reads, but arbitrary SQL still reads any table or column visible to SQLite. That is acceptable for a controlled read-only SQL tool, but should be documented.
- Error normalization is good in Resolver, but lower layers can still include paths in server logs.

### 8.3 Python Executor

Current protections:

- Child process separation.
- Service environment variables are cleared in the worker.
- File audit hook restricts opens to workspace and trusted read roots.
- `.env` opens are blocked.
- Wall-clock timeout with process-group termination.
- Output and line-count guardrails.
- Workspace artifact discovery.

Gaps:

- This is process isolation, not a container or OS security sandbox.
- Network access is not blocked.
- Subprocess execution is not explicitly blocked.
- Memory limit is optional and is not set by the Runtime V2 Python executor.
- CPU limits are not independently enforced.
- The child can read allowed site-packages and workspace data.
- Pickle is used for namespace transfer; this is acceptable only because both sides are trusted service code, but it is not a security boundary.

Therefore Python execution is suitable for trusted/controlled local use, not for hostile multi-tenant input.

### 8.4 Multi-user isolation

Current deployment is effectively single-token, shared-workspace-root, not multi-tenant.

- `/workspace/files/{filename:path}` can resolve files anywhere under the global workspace root, including another session directory.
- `/workspace/files` without `session_id` lists global root files.
- API authorization is disabled when `API_AUTH_TOKEN` is empty.
- Docker Compose defaults `API_AUTH_TOKEN` to empty.
- There is no per-user identity model or per-asset authorization check.

This must be documented as a single-user/local deployment boundary, or fixed before multi-user deployment.

## 9. Runtime route and configuration review

Current defaults:

- `RUNTIME_V2_ENABLED=false`
- `RUNTIME_V2_FALLBACK_ENABLED=false`
- `RUNTIME_V2_STRICT_MODE` exists only in `runtime_route.py`; it is not in `config.py`

Actual API behavior:

- `_RUNTIME_V2_ENABLED` is used by `langgraph_agent.run_analysis_stream()`.
- `_RUNTIME_V2_FALLBACK_ENABLED` is used by `_run_runtime_v2_graph_stream()`.
- `RuntimeSelectionPolicy`, `decide_runtime_route()`, and `log_runtime_route()` are not called there.
- Therefore B5 policy is tested, but strict-mode enforcement is not active in the production route.

Also, Docker Compose does not pass `RUNTIME_V2_ENABLED`, `RUNTIME_V2_FALLBACK_ENABLED`, or `RUNTIME_V2_STRICT_MODE` to the container, so operators cannot set them through the documented compose environment without editing Compose.

## 10. Docker, dependency, and persistence review

Static deployment findings:

- `requirements.txt` includes `pyarrow>=15.0.0`, so Parquet SnapshotStore is declared.
- Docker uses a prebuilt base image `telebi-telebi-base:latest`; reproducibility depends on that image.
- Entrypoint starts as root, chowns mounted workspace directories, then drops to `telebi`.
- FastAPI and Streamlit can run in one container; health check probes backend port 8888.
- Compose mounts `workspace/` and `temp_uploads/`, so Runtime metadata and snapshots are persistent.
- Runtime metadata is written under the session workspace; snapshots are under session `.data_snapshots/`.
- Entrypoint handles SIGINT/SIGTERM and cleans up child processes.
- No CPU/memory limits are configured in Compose.
- No backup/restore procedure is documented.
- No image build or live upload was executed during this B9 review.

## 13. Findings

Severity definitions:

- **P0**: security or data-integrity issue that blocks any shared/exposed deployment and must be fixed before default switch.
- **P1**: blocker for enabling Runtime V2 as product default.
- **P2**: important quality/reliability gap for follow-up.
- **P3**: non-blocking improvement.

### P0

| ID | Finding | Location | Impact | Recommended fix |
| --- | --- | --- | --- | --- |
| B9-P0-01 | Upload filename is used directly in path construction and is not sanitized to a basename. | `api_server_langgraph.py:1011`, `api_server_langgraph.py:1036`; also `webui/app.py:927` for local temp path | Crafted `filename` values can traverse directories, overwrite Runtime metadata/snapshots, or write outside intended upload areas. | Generate server-side filenames, use `Path(name).name`, reject separators and NUL, resolve and enforce containment, and refuse existing target overwrite. |
| B9-P0-02 | API authentication is disabled when `API_AUTH_TOKEN` is empty, and Compose defaults it to empty. | `security.py:verify_bearer_token`, `config.py:130`, `docker-compose.yml` | A mapped service can expose upload, analysis, file download, session deletion, and cancellation without authentication. | Require a non-empty token for non-local startup or bind localhost by default; add startup readiness/security check and test. |
| B9-P0-03 | Workspace download/list endpoints expose global workspace contents rather than a single authorized session. | `api_server_langgraph.py:/workspace/files`, `/workspace/files/{filename:path}` | With missing or shared auth, one caller can enumerate/read another session's uploads, artifacts, Runtime metadata, or snapshots. | Scope file routes to an authorized session; enforce per-session authorization; never expose global workspace listing by default. |

### P1

| ID | Finding | Location | Impact | Recommended fix |
| --- | --- | --- | --- | --- |
| B9-P1-01 | B4 General Planner and validator are not called by API/UI. | `runtime/general_planner.py`; `runtime/plans.py:default_analysis_plan()` | Production still uses the old default plan; B4 does not improve real usage. | Introduce planner entry point and require `validate_general_plan()` before Runtime execution. |

| B9-P1-03 | B6 SQL Evidence and B7 AnalysisReport are not connected to `finish_report` or API responses. | `evidence/sqlite.py`; `runtime/analysis_report.py`; `tools/tool_finish_report.py` | New evidence/report contracts remain offline modules. | Persist/query evidence records and route final report through B7 validator or extend legacy validator with equivalent checks. |

## 14. Runtime V2 switch decision

### Decision: **Not ready**

Reasons:

1. P0 upload path traversal and default-unauthenticated/global file exposure must be fixed first.
2. B4 General Planner, B6 SQL Tool/Evidence, and B7 AnalysisReport are not integrated into the real API/UI path.
3. AssetResolver is not exercised by the default file analysis plan.
4. B5 strict-mode route policy is not wired into the real route.
5. User cancellation is not propagated through Runtime V2.
6. API task lifecycle does not reliably distinguish failed, partial success, and completed.
7. Docker deployment and restart behavior were not executed in B9.

### Conditions for re-review

Before a follow-up switch review, complete at minimum:

1. Fix all P0 upload/auth/session data-boundary issues.
2. Wire the General Planner and validator into the real analysis entry point.
3. Register or expose SQLite SQL Tool and require result asset registration.
4. Wire SQL Evidence and one canonical report validation path.
5. Populate task/plan `input_asset_ids` for file and SQLite assets so AssetResolver is mandatory.
6. Replace direct route flags with `RuntimeSelectionPolicy` and emit route decisions.
7. Propagate cancellation and enforce partial-success semantics.
8. Add Docker build/start/upload/analysis/restart verification.
9. Add multi-session isolation and cancellation tests.

## 15. Next recommended phase

Split work into small, independently accepted phases rather than one broad refactor:

1. **B10 Security Hotfix**  
   Fix upload path traversal, auth requirements, session-scoped file access, upload streaming/format allowlist. Add security tests.
2. **B11 Production Chain Integration**  
   Wire General Planner, AssetResolver-backed inputs, SQLite SQL Tool, SQL Evidence, and report validation into API/UI.
3. **B12 Lifecycle and Cancellation**  
   Unify API/Runtime statuses, partial success, cancellation propagation, and route logging.
4. **B13 Deployment Verification**  
   Docker build, health check, live file and SQLite analysis, restart recovery, resource limits, backup runbook.
5. **B14 Switch Review**  
   Re-run P0/P1 checklist and decide whether product default can change.
