# B4.2.0 General Planner 现状检查与扩展设计

Status: B4.2.0 design complete（documentation-only；HEAD `1e6349c`）
Scope: 只读检查 + 扩展设计。未修改业务代码、未切换默认路由、未触碰用户工作区。

## 1. 当前 Planner 架构（真实调用链）

```
prepare_file_analysis（runtime/analysis_workflow.py:103）
  → register_file_asset（FileDataSource.scan_schema → SchemaSnapshot）
  → DeterministicAnalysisPlanner().plan（runtime/general_planner.py:341）
      输入：goal: str、input_asset_ids、asset_columns（列名集合）
  → general_plan_to_runtime_plan（analysis_workflow.py:51）
  → runtime.initialize_plan（context.py）
      → validate_runtime_plan（runtime/plans.py，物理 ID/逻辑引用分型）
      → TaskScheduler.from_plan
```

生产调用方：仅 `analysis_workflow.py:115`（`prepare_file_analysis`，即 API 会话初始化路径）。
测试调用方：`tests/test_general_planner.py`、`tests/test_runtime_golden_e2e.py`。
**LLM 参与情况**：`general_planner.py` / `analysis_workflow.py` 无任何 LLM 导入（rg 证实）。当前事实上的"LLM 规划"只存在于 Legacy ReAct 的隐式工具选择（`langgraph_agent.py` 主循环），V2 路径的规划完全确定性。

## 2. 当前 Planner 能力清单

### 2.1 输入 / 输出结构

| 项 | 现状 | 位置 |
| --- | --- | --- |
| Planner 输入 | `goal: str` + `input_asset_ids: list[str]` + `asset_columns: Mapping[str, list[str]]`（仅列名） | `general_planner.py:341`、`analysis_workflow.py:112-119` |
| Planner 输出 | `PlannerResult{plan: GeneralAnalysisPlan, clarification_questions, unsupported_reason}` | `general_planner.py:76` |
| 步骤结构 | `GeneralPlanStep{step_id(pattern step_[0-9a-f]{32}), operation, input_refs(min 1), parameters, expected_output, depends_on, rationale}` | `general_planner.py:59` |
| 计划结构 | `GeneralAnalysisPlan{plan_id, user_goal, input_asset_ids(min 1), steps(min 1)}` | `general_planner.py:69` |

### 2.2 operation 白名单（`PLAN_OPERATIONS`，general_planner.py:15）

`inspect / select_columns / filter / group_aggregate / sort / trend / detect_anomalies / correlation / data_quality / summarize`（10 个，全部单输入单输出，output ∈ {dataframe, metric}）。
与 toDo.md Phase 1A 八类能力的对应：描述统计→summarize、分组比较→group_aggregate、趋势→trend、异常→detect_anomalies、相关→correlation、TopN/排名→sort、质量→data_quality；**比率计算无专用 operation**（需 group_aggregate/filter 组合或新增）。
执行实现：`runtime/analysis_operations.py::_EXECUTORS`（与白名单一一对应）。

### 2.3 参数定义与校验（三层）

1. `_valid_parameters(operation, parameters)`（general_planner.py:82）：逐 operation 的必填/类型/枚举校验（如 group_aggregate 的 group_by/metric/agg∈{sum,mean,count,min,max}）。
2. `validate_general_plan(plan, asset_columns)`（:245）：白名单、input 数量、input_refs ⊆ 初始资产、depends_on 无前向引用、expected_output 与 operation 匹配、`_parameter_columns` 列存在性。
3. Runtime 层：`validate_runtime_plan`（plans.py）——计划期分型校验（含 parameters_json、依赖闭包、输出声明）+ 参数 schema 校验。

### 2.4 依赖 / 输入引用 / 多输出

- **依赖**：`depends_on` 只表达执行顺序；`validate_general_plan` 要求依赖必须先出现（无前向引用），但**步骤间无数据传递**——`output_by_step` 仅登记 `f"{step_id}:output"` 用于依赖存在性检查。
- **输入引用**：`input_refs` 必须属于 `plan.input_asset_ids`（:267-272）——**上游步骤输出不能作为下游输入**。即 GeneralPlan 层无法表达"下游消费上游输出"；当前确定性 Planner 也只生成"两步同源"计划（inspect + 单操作，均引用主资产）。
- **多输出**：`expected_output` 为单值 Literal，不支持命名多输出（Runtime 层 B11.2.1 已支持，Planner 层未跟上）。

### 2.5 意图识别（无 LLM）

`_operation_for_goal`（:142）：正则关键词匹配（中英混合）选择单一 operation 并抽取参数（如 group by/agg/metric、top N、filter gt/lt）。匹配失败返回 None → `DeterministicAnalysisPlanner.plan` 抛 `PlannerClarificationError`（澄清问题）或 `PlanValidationError`。

## 3. Data Understanding 能力清单（真实存在的数据）

| 数据上下文 | 当前是否存在 | 来源 | 是否可注入 Planner |
| --- | --- | --- | --- |
| 列名 | 是 | `SchemaSnapshot.columns[].name`（data/assets.py:71） | **可直接注入**（已注入，asset_columns） |
| 数据类型 | 是 | `ColumnSpec.dtype` | 可注入（需扩展 asset_columns → schema 对象） |
| 行数 | 是 | `SchemaSnapshot.row_count` + `SourceScan.estimated_rows`（sources.py:16） | 可注入 |
| 缺失率 | 间接 | `ColumnSpec.null_count`（缺失率 = null_count/row_count 可计算） | 可注入（结构化） |
| 数值统计 | 否（schema 层无；`eda_profile` 工具产出**文本报告+图表**且耦合 `session.ns["filter_business_metrics"]`，非机器可读、不持久化） | `tools/tool_eda_profile.py`；运行期可由 `analysis_operations._summarize/_data_quality` 计算 | **不可直接注入**——需新增结构化 Data Profile（建议复用 analysis_operations 的确定性统计） |
| 类别分布 | 否（同上） | 同上 | 不可直接注入（同上） |
| 时间列识别 | 是 | `SchemaSnapshot.time_columns`（dtype 启发式） | 可注入 |
| 唯一值/重复值 | 列级唯一值：`ColumnSpec.unique_count`；候选键：`candidate_keys`；表级重复：无（`data_quality` 运行期计算） | assets.py:73-105 | 唯一值可注入；表级重复不可 |

**结论**：Schema 层（列名/dtype/行数/缺失数/唯一值/时间列/候选键）已是结构化且随资产持久化，可直接作为 PlannerInput；数值/类别统计缺少结构化载体——但 `analysis_operations` 已有确定性实现，可零风险复用生成 `DataProfile`，无需新增分析逻辑。

## 4. 当前缺口（对照 B4.2 目标链路）

1. **无 LLM 规划**：自然语言 → 计划依赖正则关键词，复杂/组合问题（如"按地区分析近三年趋势并找异常"需要 trend+anomaly 两步）无法生成多步计划（`_operation_for_goal` 只返回单 operation）。
2. **步骤间数据流不可表达**：`GeneralPlanStep.input_refs` 只接受初始资产（§2.4），下游消费上游输出的链式计划在 Planner 层无法构建（Runtime 层 B11.2.1 已支持逻辑引用，两层能力不齐）。
3. **无多输出命名**：Planner 层无命名输出概念。
4. **Data Profile 缺失**：Planner 只见列名，不见缺失率/数值统计/类别分布——无法做"数据感知"的参数填充（如自动选数值列、识别高缺失列并披露）。
5. **调用点时序问题**：`prepare_file_analysis` 在 `_Session.__init__`（同步、无 LLM 客户端）中执行规划；LLM Planner 的接入点必须重新安排（见 §8 决策 DD-2）。
6. **比率计算**缺专用 operation（toDo.md 八类之一）。
7. **澄清语义已有但未贯通**：`PlannerClarificationError` 存在，`PlannerResult.clarification_questions` 字段存在但 `prepare_file_analysis` 未消费（直接异常上抛）。

## 5. 扩展架构（不另起平行体系）

```
User Question + SchemaSnapshot + DataProfile
  → PlannerInput（新，结构化上下文）
  → PlannerRouter：
      ① LLMPlanner（新）：白名单约束的结构化输出
      ② fallback：DeterministicAnalysisPlanner（现有，零改动语义）
      ③ clarification / unsupported：显式返回，不静默改写意图
  → GeneralAnalysisPlan v2（步骤间可引用上游输出）
  → validate_general_plan v2（扩展 input_refs 校验）
  → general_plan_to_runtime_plan v2（上游引用 → `step_x.output` 逻辑引用）
  → validate_runtime_plan（现有，复用）
  → initialize_plan → Runtime V2（Scheduler/Binding/Evidence/Report 全部现有链路）
```

### 5.1 PlannerInput（统一输入）

```python
class PlannerAssetContext(BaseModel):
    asset_id: str
    schema_snapshot: SchemaSnapshot        # 复用 data/assets.py
    profile: DataProfile | None            # 新增，见 §5.4

class PlannerInput(BaseModel):
    question: str
    assets: list[PlannerAssetContext]      # 输入 Asset + Schema + Profile
    session_context: dict[str, Any] = {}   # 会话必要上下文（如澄清历史），最小化
```

### 5.2 LLM Planner（新模块 `runtime/llm_planner.py`）

职责边界（冻结）：
- 输入 PlannerInput，输出 `GeneralAnalysisPlan v2`（Pydantic 解析，非法 JSON/超白名单 → 返回结构化失败而非异常上抛）；
- **不执行任何数据分析**；不生成 Python/SQL 作为执行方案（system prompt 固化"只能从 PLAN_OPERATIONS 白名单选择 operation"）；
- LLM 客户端由调用方注入（`planner_fn: Callable[[PlannerInput], str]`），便于 fake 测试与无 LLM 环境降级；
- Prompt 内容 = operation 契约（PLAN_OPERATIONS + `_valid_parameters` 规则的文本化）+ Schema/Profile JSON + 用户问题 + 澄清规范。

### 5.3 GeneralAnalysisPlan v2（结构化计划契约）

- `GeneralPlanStep.input_refs` 扩展：允许 `plan.input_asset_ids` 成员或 `<先前 step_id>.output`；
- `validate_general_plan` v2：input_refs 校验扩展为"初始资产 ∪ 前序步骤输出引用"，依赖闭包与引用一致性一并校验（与 B11.2.1 Runtime 逻辑引用语义对齐，语法复用 §3.2 已知 Step ID 规则）；
- `general_plan_to_runtime_plan` v2：上游引用转换为 `required_inputs=["step_x.output"]` + `parameters.asset_id="step_x.output"`（逻辑引用），由 B11.2.1 的 `build_execution_request` 解析为物理资产——**Runtime 侧零新增**；
- 多输出暂不扩展（Runtime 已支持命名输出，Planner 层等首批八类能力需要时再开，避免过早抽象）。

### 5.4 DataProfile（新增结构化画像，复用确定性实现）

```python
class ColumnProfile(BaseModel):
    name: str; dtype: str; missing_rate: float; unique_count: int | None
    numeric_summary: dict[str, float] | None   # mean/std/min/max（复用 _summarize 语义）
    top_categories: list[tuple[str, int]] | None

class DataProfile(BaseModel):
    row_count: int; duplicate_rows: int | None
    columns: list[ColumnProfile]
    # 由 analysis_operations 的确定性实现生成（新增 build_data_profile(frame)），
    # 在 register_file_asset 时计算并随 Asset 持久化（source_metadata["profile"]）
```

### 5.5 Validator 复用方案

不新建校验器：`validate_general_plan` v2（扩展引用校验）→ `general_plan_to_runtime_plan` → `validate_runtime_plan`（现有）双层保持；LLM 计划与确定性计划走**同一条校验链**，杜绝入口分叉（B11.2.1.1 P1-2 的教训）。

### 5.6 Fallback / Clarification 策略（冻结）

| 场景 | 行为 |
| --- | --- |
| LLM 输出解析失败 / operation 越界 | 记录 unsupported_reason → 尝试确定性 Planner |
| 确定性 Planner 能忠实匹配用户意图（`_operation_for_goal` 命中且校验通过） | 采用确定性计划（兜底） |
| 确定性 Planner 亦无法匹配 | 抛 `PlannerClarificationError` → `PlannerResult.clarification_questions` 返回给会话层（澄清 UI/API），**不得静默改写用户需求** |
| LLM 计划校验失败（列不存在/闭包外引用等） | 一次自修复重试（携带校验错误回喂）→ 仍失败则走 fallback/clarification |
| LLM 不可用（无客户端/超时） | 直接确定性兜底 + unsupported_reason 标记 `llm_unavailable` |

### 5.7 Runtime 接入

全部经现有链路：`general_plan_to_runtime_plan v2 → validate_runtime_plan → initialize_plan → Scheduler → OutputAssetBinding → Evidence → Report Validation`。禁止绕过任何一环（B11.2.1.1 已固化入口一致性）。

## 6. 结构化计划契约（汇总）

- Planner 层：`GeneralPlanStep`/`GeneralAnalysisPlan` v2（引用扩展）+ `PlannerInput`/`PlannerAssetContext`/`DataProfile`/`ColumnProfile`（新增）。
- LLM 输出契约：JSON 符合 `GeneralAnalysisPlan` schema（白名单 operation + 引用规则），Pydantic 强校验。
- Runtime 层契约：不变（`validate_runtime_plan` / `ResolvedTaskInputs` / Binding）。

## 7. 测试策略（真实调用链优先）

| 测试 | 验证点 | 链路 |
| --- | --- | --- |
| LLM 结构化输出测试 | fake planner_fn 输出合法/非法 JSON → 解析与失败分类 | llm_planner 单测 |
| operation 白名单测试 | LLM 输出越界 operation → 拒绝 → fallback | llm_planner + validate_general_plan |
| 参数校验测试 | 各 operation 必填/类型/枚举错误 → 拒绝 | `_valid_parameters` + runtime 双层 |
| DAG/依赖校验测试 | 前向引用、环、闭包外引用（`step_x.output`）→ 拒绝 | validate_general_plan v2 + validate_runtime_plan |
| Schema 感知规划测试 | 给定 schema，LLM 生成计划的列引用全部真实存在；错误列名被拒 | PlannerInput 注入链 |
| Data Profile 感知规划测试 | 高缺失列参与质量步骤、数值列自动填充 metric | build_data_profile + PlannerInput |
| 确定性兜底测试 | LLM 不可用/解析失败 → 确定性计划结果与现行为一致（回归保护） | fallback 编排 |
| 澄清问题测试 | 意图不明 → clarification_questions 非空、不产生计划 | PlannerResult 契约 |
| 非法计划拒绝执行测试 | 校验失败的计划不会进入 initialize_plan/执行 | 端到端编排 |
| Runtime V2 计划接入测试 | LLM 计划（含上游输出引用）经 general_plan_to_runtime_plan v2 → initialize_plan → execute_next_task 全链路，Binding/Evidence/Report 断言 | 复用 `tests/runtime_v2/test_runtime_e2e.py` 模式 |

## 8. 文件修改范围建议

| 文件 | 变更 |
| --- | --- |
| `runtime/general_planner.py` | v2 模型（引用扩展）、`validate_general_plan` 扩展、PlannerInput/DataProfile 模型（或独立文件） |
| `runtime/llm_planner.py`（新） | LLMPlanner + fallback 编排 + clarification 契约 |
| `runtime/analysis_operations.py` | 新增 `build_data_profile(frame)`（复用现有确定性统计） |
| `runtime/analysis_workflow.py` | `prepare_file_analysis` 注入 profile；planner 选择编排（确定性调用点调整见 DD-2） |
| `langgraph_agent.py::run_analysis_stream` | V2 分支下用已注入的 LLM 客户端执行 LLM Planner（DD-2 方案 B） |
| `tests/test_general_planner.py` 等 | v2 回归 + 新测试矩阵 |

**设计决策（需评审确认）**：
- **DD-1**：DataProfile 在资产注册时计算并持久化（source_metadata["profile"]）——代价是注册耗时略增，收益是规划/澄清/报告均可复用。
- **DD-2**：LLM Planner 调用点。方案 A：保持在 `_Session.__init__`（需在 init 注入 LLM 客户端，改动面大）；**方案 B（推荐）**：`prepare_file_analysis` 拆为"注册 + Schema/Profile 准备"（init 时）与"规划"（`run_analysis_stream` V2 分支内、LLM 客户端可用处），确定性 Planner 仍可在 init 时先行生成兜底计划，LLM 计划在校验通过后替换。方案 B 保持无 LLM 环境行为完全不变。
- **DD-3**：`ratio` 专用 operation 是否本批次新增——建议 B4.2.1 先以 group_aggregate+filter 组合覆盖，ratio operation 独立小批次（避免范围膨胀）。
