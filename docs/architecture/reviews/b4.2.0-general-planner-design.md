## 4. 当前缺口

1. 无 LLM 规划（正则只能选单 operation，无法生成"趋势+异常"类多步组合计划）。
2. GeneralPlan 层步骤间数据流不可表达（`input_refs` 仅初始资产，`validate_general_plan`:267 强制）——Runtime 层 B11.2.1 已支持逻辑引用，两层不齐。
3. 无输出命名（`expected_output` 是类型 Literal 而非输出名；转换层固定 `expected_outputs=["output"]`）。
4. 无 DataProfile（数值/类别/质量统计无结构化载体）。
5. 调用点时序：`prepare_file_analysis` 在 `_Session.__init__` 同步执行，无 LLM 客户端（DD-2 已冻结解决）。
6. 比率无专用 operation（DD-3：组合覆盖，独立小批次）。
7. 澄清字段存在但未贯通到会话/API。

## 6. 冻结约束 A：DataProfile 契约

### 6.1 生命周期

```
Asset Registration（register_file_asset / register_dataframe）
       |  失败 → 核心输入失败，阻止后续分析（现状语义不变）
       v
Schema Extraction（FileDataSource.scan_schema，已支持）
       |
       v
DataProfile Generation（build_data_profile(frame)，B4.2.1 实现）
       |  失败 → profile unavailable，Asset 仍可用（降级规划），不回滚注册
       v
Persist Asset + Profile（DataAsset.source_metadata["profile"]）
       |  _persist 失败 → 现有注册回滚语义不变
       v
Runtime V2 Planning（PlannerInput.assets[].profile，缺失时降级）
```

### 6.2 绑定与版本

DataProfile 绑定字段（写入 `source_metadata["profile"]`）：

```python
class DataProfileMeta(BaseModel):
    asset_id: str                      # 所属资产
    data_version: str                  # = DataAsset.content_hash（文件资产的数据版本标识；
                                       #   sqlite 资产将来用 snapshot_id，本期不涉及）
    profile_version: str               # Profile 模型版本（语义变更必须递增）
    generator_version: str             # build_data_profile 实现版本
    generated_at: str                  # UTC ISO
    row_count: int
    column_count: int
    columns: list[ColumnProfile]       # 见 §6.3
    duplicate_rows: int | None         # 计算失败/超限时为 None，并记录原因
```

- **版本判定规则**：复用 Profile 前必须校验 `data_version == asset.content_hash` 且 `profile_version` 与当前实现兼容；不匹配 → 视为过期（§6.4），不得静默使用。
- 优先复用现有 `DataAsset.source_metadata` 机制（B11.2.1 sqlite 快照引用同模式），**不建立第二套资产注册系统**。

### 6.3 内容与限制（首批）

| 类别 | 字段 | 限制 |
| --- | --- | --- |
| 数值列 | count/mean/std/min/max/median/p25/p75 | 数值列数上限 20（按方差贡献或字典序截断，记录 truncated 标记） |
| 类别列 | distinct_count、top_values（Top-K=10）、frequency | Top-K 上限 10；distinct 上限内 |
| 时间列 | min_time/max_time/range | 仅 dtype 为时间语义的列 |
| 数据质量 | missing_ratio（列级）、duplicate_rows（表级） | duplicate 计算成本超限时 None + 原因 |
| 键摘要 | candidate_keys（复用 SchemaSnapshot） | — |

禁止写入：完整 DataFrame、原始数据行、无界类别列表。Profile 序列化大小上限 64KB，超限截断并标记 `truncated=true`。

### 6.4 失败语义（冻结）

| 场景 | 语义 |
| --- | --- |
| Asset 注册失败 | 核心输入失败，阻止后续分析（现状不变） |
| Profile 生成失败 | Asset/Schema 仍可用 → 降级规划（PlannerInput.profile=None），记录 `profile_unavailable` + 原因 |
| Profile 过期（data_version 不匹配） | 重新生成；重算失败则降级并记录 `profile_stale`，不得静默使用旧 Profile |
| Profile 不完整 | 携带可用字段 + `missing` 原因列表；Planner 对缺失段做无 Profile 假设 |

DataProfile 是**辅助规划上下文，非硬依赖**：无 Profile 时 LLM/确定性 Planner 均可运行（Schema 层信息始终可用）。

## 7. 冻结约束 B：DD-2 LLM Planner 调用生命周期

**采用方案 B：LLM Planner 仅在 Runtime V2 路径中调用。**

```
run_analysis_stream（langgraph_agent.py:1793）
  → decide_runtime_route（:1841）
     ├─ legacy_v1 → ReAct Agent（行为零改动；不调用 LLM Planner）
     └─ runtime_v2
          → V2 分支内（LLM 客户端已在 run_analysis_stream 构建，:1898 ChatOpenAI）
             → Resolve Asset + Load DataProfile（PlannerInput 组装）
             → LLM Planner（planner_fn 注入）
             → GeneralAnalysisPlan v2
             → validate_general_plan v2
             → general_plan_to_runtime_plan v2
             → validate_runtime_plan
             → initialize_plan（替换 init 时确定性兜底计划）
             → Scheduler（后续链路全部现有）
```

**隔离规则（9 条，冻结）**：
1. 不在 `_Session.__init__` 调用 LLM。
2. 不在文件注册过程中调用 LLM。
3. 不在 Legacy 路径调用 LLM Planner。
4. 不改变 Legacy ReAct 工具选择行为。
5. `RUNTIME_V2_ENABLED=0` 时现有 Legacy 行为不变（确定性兜底计划在 init 生成，供 Legacy 会话观察/续跑使用，与现状一致）。
6. `RUNTIME_V2_ENABLED=1` 且 LLM 不可用 → 确定性 Planner（fallback_planned）。
7. 不改变默认路由开关。
8. 不改变既有基础设施失败回退策略（`run_analysis_stream:1668` 分支）。
9. **LLM Planner 异常不得导致请求静默转 Legacy**——规划失败映射为 §9 状态（needs_clarification/planning_failed）并向用户显式呈现，与 B11.2.1 的"不静默回退"契约一致。

**调用时机/输入/输出/观测**：时机 = 路由决策为 V2 后、`initialize_plan` 前；输入 = `PlannerInput`（question + PlannerAssetContext[asset_id/schema/profile] + session_context）；输出 = `PlanningOutcome{status: planned|fallback_planned|needs_clarification|planning_failed, plan?, clarification_questions?, reason_code?}`；观测 = `session.runtime_route_decision` 旁新增 `session.planning_outcome` + 结构化日志 `planning_outcome status=... reason=...`（兼容现有 metrics 语义，不改 API 协议）。

## 8. 冻结约束 C：Plan v2 前序输出引用契约

### 8.1 真实代码事实（输出命名核对）

| 事实 | 位置 |
| --- | --- |
| Runtime 逻辑引用语法 = `{step_id}.{output_name}`，且 `output_name ∈ 生产步骤 expected_outputs` | `plans.py:303`（validate_runtime_plan）；`context.py::_resolve_task_inputs` |
| OutputBindingRegistry 键 = `(run_id, step_id, output_name, attempt)` | `runtime/output_bindings.py` |
| `general_plan_to_runtime_plan` 目前固定 `expected_outputs=["output"]` | `analysis_workflow.py:75` |
| `GeneralPlanStep.expected_output` 是**类型** Literal（dataframe/metric/chart），非输出名，转换层未消费其值 | `general_planner.py:64` |

**结论**：Runtime 支持任意 output_name（经 expected_outputs 声明），但当前转换层只发 `output`。评审示例中的 `step_001.aggregate_result` 需要最小适配（见 §8.3），不伪称已支持。

### 8.2 引用规则（10 条，冻结）

`GeneralPlanStep.input_refs` 条目允许两种形态：
1. **初始资产引用**：∈ `GeneralAnalysisPlan.input_asset_ids`；
2. **前序输出引用**：`{producer_step_id}.{output_name}`，且必须满足：

| # | 规则 |
| --- | --- |
| 1 | 只能引用已定义的初始资产或**前序** Step 输出（按 steps 列表顺序） |
| 2 | 不允许引用自身输出 |
| 3 | 不允许前向引用（引用的 producer 必须在当前 step 之前定义） |
| 4 | 不允许循环依赖（depends_on + 引用联合判定，等价于 DAG 校验） |
| 5 | 不允许未知 Step |
| 6 | `output_name` 必须等于生产者 Step 声明的 `output_name`（§8.3） |
| 7 | 不允许引用不存在的输出 |
| 8 | 步骤顺序与 `depends_on` 一致（depends_on ⊆ 已出现步骤且与引用关系不矛盾） |
| 9 | 转换后必须通过 `validate_runtime_plan`（第二层校验，不绕过） |
| 10 | v1 计划（全部引用初始资产、expected_output 为类型）继续有效 |

### 8.3 输出命名：基于真实代码的最小适配

**GeneralPlanStep v2 新增字段**：

```python
class GeneralPlanStep(BaseModel):
    ...
    output_name: str = Field(default="output", pattern=r"^[a-z][a-z0-9_]{0,63}$")
```

**映射规则（GeneralPlan → RuntimePlan，无损害转换）**：
- `general_plan_to_runtime_plan` 的 `expected_outputs` 由固定 `["output"]` 改为 `[step.output_name]`；
- 上游引用 `input_refs` 中的 `{producer_step_id}.{output_name}` 原样转为 RuntimePlanStep 的 `required_inputs` 与 `parameters.asset_id` 逻辑引用——由 B11.2.1 `build_execution_request` 解析为物理资产，**Runtime 层零新增**；
- v1 兼容：未指定 `output_name` 的旧计划默认 `"output"`，引用形态 `{step_id}.output` 与现状完全一致；
- `expected_output`（类型 Literal）保留，仅用于 `validate_general_plan` 与 `PLAN_OPERATIONS["output"]` 的类型一致性检查（现状语义不变）。

**契约示例（评审示例的合法 v2 形态）**：

```yaml
step_001: {operation: group_aggregate, input_refs: [asset_123], output_name: aggregate_result,  expected_output: dataframe}
step_002: {operation: sort,           input_refs: [step_001.aggregate_result], output_name: sorted_result, expected_output: dataframe, depends_on: [step_001]}
step_003: {operation: summarize,      input_refs: [step_002.sorted_result],    output_name: summary_result, expected_output: metric,   depends_on: [step_002]}
```

### 8.4 拓扑与顺序约束

- steps 列表顺序即计划顺序；`depends_on` 与前序输出引用必须指向列表中更早的步骤；
- `validate_general_plan` v2 在现有"依赖不得前向"检查上增加"引用不得前向/自引用/环"；
- 转换后 `validate_runtime_plan` 的依赖闭包校验（B11.2.1）自然复验，双层防线。

## 9. 冻结约束 D：Fallback / Clarification 状态机

### 9.1 状态定义（冻结）

| 状态 | 含义 |
| --- | --- |
| `planned` | LLM 或确定性 Planner 成功生成通过校验的计划 |
| `fallback_planned` | LLM 不可用或输出无效，确定性 Planner **忠实匹配原意**并成功生成计划 |
| `needs_clarification` | 当前数据或能力无法忠实完成用户目标，需要用户补充信息 |
| `planning_failed` | 不可恢复的规划错误 |

### 9.2 状态转移

```
PlannerInput
   → LLM 可用？
      ├─ 否 ──────────────→ 确定性 Planner ─成功→ fallback_planned（reason=llm_unavailable）
      │                        └─ 失败→ needs_clarification / planning_failed
      └─ 是 → LLMPlanner
            ├─ 输出非法（≤2 次修复重试，携带校验错误）→ 仍非法 → 确定性兜底（同上分支）
            ├─ 计划非法（校验链拒绝，不绕过）→ 确定性兜底（重新完整校验）
            ├─ 计划合法 → planned
            └─ 意图不可实现（如要求利润率但无利润字段）→ needs_clarification
                 （禁止改写为其他统计，如销售额）
不可恢复异常（任何环节）→ planning_failed（保留错误分类与日志）
```

### 9.3 处理原则（冻结）

1. LLM 不可用 → 确定性 Planner，成功标记 `fallback_planned`，记录 `llm_unavailable`。
2. LLM 输出格式非法 → 允许**有限次数**（≤2）修复重试；仍非法才进入确定性 Fallback；不得无限重试。
3. LLM 生成非法计划 → 校验链拒绝（不绕过 `validate_general_plan`/`validate_runtime_plan`）；允许确定性 Fallback，但必须**重新完整校验**。
4. 用户目标无法实现（数据缺字段/能力不支持）→ `needs_clarification`，禁止自动改写问题。
5. 不可恢复异常 → `planning_failed` + 可诊断错误分类。
6. 状态传播：`PlanningOutcome` 写入 `session.planning_outcome` + 结构化日志；API/SSE 层以现有结构兼容透传（text 提示 + 现有 metrics），**不大规模修改 API 响应协议**。
