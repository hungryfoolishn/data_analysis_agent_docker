# B10.1 Security Fix

Status: complete
Baseline: `6db551f1694926418ce5ebd513dcac8badb51112`
Scope: B10 upload validation and concurrency boundary only.
B11 was not started.

## Original issues

1. **Parquet footer check was incorrect.**
   `Parquet` validation read the header, seeked a handle to the end, then opened
   another handle and read from the beginning. The footer check therefore read
   the file header again and could not detect a bad or missing footer.

2. **Upload semaphore covered only streaming.**
   Content validation and atomic replace occurred after releasing the upload
   semaphore, so concurrent uploads could bypass the intended resource limit
   during validation and finalization.

3. **B10 documentation had stale regression numbers.**
   The hardening report recorded an earlier test result rather than the actual
   complete verification command and result.

## Fix

### Parquet validation

`_validate_upload_file()` now:

1. opens the file once;
2. reads the first four bytes;
3. seeks to the end with the same handle;
4. rejects files shorter than eight bytes;
5. seeks back four bytes from end;
6. reads the real footer;
7. requires both header and footer to be `PAR1`.

All handles are managed with context managers. No new dependency was added.

### Concurrency boundary

Both `/v1/files` and `/workspace/upload` now execute the full upload lifecycle
inside `_upload_semaphore`:

```text
acquire semaphore
  -> stream upload
  -> enforce byte limit
  -> fsync temp file
  -> validate declared file structure
  -> atomic replace to final path
  -> cleanup temp file
release semaphore
```

Validation failure now occurs while holding the semaphore and cannot leave a
formal destination file.
