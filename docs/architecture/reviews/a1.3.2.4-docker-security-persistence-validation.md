**N1 Limitation (P2)**: Docker bridge does NOT block outbound public internet by default. The container can reach public IPs. The task book states:
> 如果 Docker 环境不能实现可靠的出站网络控制：记录限制。提供部署层替代方案。不得宣称 Worker 网络隔离 PASS。

**Recorded limitation**: Docker Compose bridge network does not provide outbound egress filtering. For production deployment, recommend network policy enforcement at the Docker network level (e.g., iptables rules, network ACLs) or use a dedicated egress proxy.

**N2/N3 Assessment**: Host services and other containers on different networks are NOT reachable. Internal isolation is adequate.

**N4 Assessment**: The fake LLM server (inside the container at localhost:9999) is accessible. In production this would be the real LLM API endpoint.

#### E2: Unknown Evidence State

**Result: PASS (with limitation)**

Evidence entries carry `verification_status` field:
- 10 entries: `verification_status = "verified"` (V2 runtime_verified evidence)
- 36 entries: `verification_status = None` (V1 agent evidence without explicit verification)

The system distinguishes between verified and unverified evidence. Evidence without verification status is not treated as verified.

#### E4: Corrupted Evidence

**Result: PARTIAL PASS**

The system stores `content_hash` on DataAssets and evidence provenance. The evidence persistence layer enforces:
```python
if validation_status == "verified" and output_asset.content_hash is None:
    raise SqliteEvidenceError("verified evidence requires output content hash")
```

However, **no automatic content_hash re-verification is performed when serving artifacts after restart**. If a parquet file were corrupted post-restart, the system would serve it without checking the stored hash.

**Recorded limitation (P2)**: content_hash is written at creation time but not re-verified on read. An integrity check on restore would improve robustness.

#### E5: Evidence Re-verification

**Result: NOT IMPLEMENTED**

After container restart, evidence retains its pre-restart `verification_status`. There is no re-verification pipeline that recomputes content hashes or re-validates evidence chains post-restart.

**Assessment**: Persistence success ≠ re-verification success. The system preserves evidence state but does not actively re-verify it. This is a known limitation, not a regression.

### P2 Limitations (non-blocking)
1. **N1 public internet**: Container CAN access public internet (Docker bridge default). Record as deployment-level gap; recommend network ACL/egress proxy for production.
2. **E4 content_hash not re-verified on read**: Hash stored at creation but not checked on restore/serve.
3. **E5 no evidence re-verification pipeline**: Evidence status preserved but not actively re-validated post-restart.

### NOT BLOCKING B10.3
These limitations do not affect the B10.3 unlock condition. They are Docker deployment hardening items that should be addressed in a production deployment review, not in the current code freeze scope.

## 5. Gate Decision

**A1.3.2.4 = PASS WITH P2 LIMITATIONS**

The security boundary is adequate for the A1.3.2 validation scope. The three P2 limitations (N1 public internet, E4 no hash re-verify, E5 no re-verification) are deployment-level concerns that should be tracked for production hardening but do not block the current phase.
