## 2. Restore entry points

The only production restore entry for `DataAsset` state is `AnalysisRuntime.__init__` → `AnalysisRuntime._restore()` in `langgraph_langchain/runtime/context.py:2139`. API/session code loads the runtime by constructing `AnalysisRuntime`; no second production deserializer of `.analysis_runtime.json` was found.

`snapshot()` serializes `self.assets`, canonical-free legacy `self.evidence`, executions, artifacts, verifications, findings and other run metadata into `.analysis_runtime.json`; `_persist()` writes a temp file and atomically replaces it. `EvidenceRegistry` is constructed with live references to `self.assets`, `self.artifacts`, and the execution lookup, so restore must update these mappings in place.

## 3. DataAsset lifecycle

### Creation

- File-backed assets: `register_dataframe()` calls `DataAsset.from_dataframe()`, which records the absolute `location` and computes `content_hash = hash_file(resolved)` when the file exists (`langgraph_langchain/data/assets.py:218`).
- SQLite query output: `register_sqlite_result()` computes `hash_dataframe(dataframe)`, saves a `SnapshotReference`, and constructs an asset with no filesystem `location`.
- Adapter output: `register_fetch_result()` similarly saves a snapshot-backed `DataAsset` with `content_hash = result.content_hash`.
- SQLite database source: `DataAsset.from_sqlite_database()` hashes the database file bytes.

The current file hash is streaming SHA-256 (`data/assets.py:25`); DataFrame hash is canonical and includes schema, row order and values (`data/assets.py:181`).

### Restore

`_restore()` calls `DataAsset.model_validate(item)` and inserts the result into `self.assets`. It does not recompute a file or snapshot fingerprint. This is P0-1. Although `AssetResolver._resolve_file_asset()` later rejects a changed file when `content_hash` exists, restored metadata and evidence can still declare the old object trustworthy before an explicit later resolve. Snapshot-backed assets are only rechecked when they are actually resolved; restore itself does not establish trust.

The existing hash is not sufficient for SQLite database semantics if WAL/SHM are present. For this package, SQLite query outputs use immutable DataFrame snapshots and can be verified through `SnapshotStore`; raw SQLite database assets should be marked UNVERIFIABLE unless a stable checkpoint/snapshot contract exists. Ordinary `mtime` comparison is not accepted as cryptographic integrity.

## 4. Evidence lifecycle

Two evidence layers exist.

1. Canonical evidence: tools create `OperationEvidence` or `SqliteQueryEvidence`, adapt it to `CanonicalEvidence`, and call `AnalysisRuntime.register_canonical_evidence()`. `EvidenceRegistry.register()` validates references and sets `reference_validated`. After successful execution, `record_execution()` calls `_verify_canonical_evidence_for_execution()`, which invokes `verify_canonical_evidence()` and may set `verified` or `failed`.
2. Legacy evidence: `EvidenceItem` objects are stored in `self.evidence` and persisted. A persisted `verification_status="verified"` is accepted verbatim by `_restore()`.

A critical additional finding is that `snapshot()` does not serialize `EvidenceRegistry._records`. Consequently, canonical evidence records created before restore disappear from the registry. Post-restore report building using `build_verified_report()` has no canonical evidence unless it is newly registered. This is a restore-trust failure in addition to P0-2: the persisted JSON cannot be used to restore canonical evidence directly because that state was never persisted.

Legacy evidence has no independently recomputable content contract. Its linked `VerificationResult` may exist, but that result is itself persisted and cannot prove current asset content. Therefore restored legacy `verified` status must be downgraded; it must not be treated as current VERIFIED trust.

## 5. Report trust

Runtime V2 builds reports only from `EvidenceRegistry.list(statuses={"verified"})` (`context.py:505`). Runtime V1's report validator accepts `EvidenceItem.verification_status == "verified"`. Thus stale/missing assets or downgraded evidence must not retain that status. Historical report text remains immutable; current trust should be reflected by removing failed/unverifiable evidence from current verified evidence rather than rewriting historical findings.

## 6. Current defects and reproducibility

### P0-1: Restored file-backed DataAsset is accepted without hash validation

Reproduction outline:

1. Create a runtime and register a real CSV/Parquet file.
2. Persist runtime state.
3. Change the file bytes.
4. Construct a new `AnalysisRuntime` for the same session/question.
5. Observe that restore succeeds and the asset metadata is available without a restore-time integrity check or propagated trust state.

### P0-2: Restored evidence trust is inherited from JSON

Reproduction outline:

1. Persist an `EvidenceItem` with `verification_status="verified"`.
2. Modify or remove its referenced file.
3. Restore the runtime.
4. The old `verified` status survives even though current asset integrity cannot be established.

### P1: Canonical evidence registry is not persisted

After restore, canonical evidence IDs in tool result payloads no longer resolve in `EvidenceRegistry`. This breaks current evidence traceability and cannot be repaired by simply trusting legacy JSON.

## 7. Compatibility and dependency notes

- Existing serialized `DataAsset` fields must remain compatible. Adding trust state under `source_metadata["restore_integrity"]` avoids a schema migration.
- Legacy snapshots without `content_hash` must restore metadata but mark the asset `UNVERIFIABLE`; they must not be silently promoted to trusted.
- `EvidenceRegistry` captures live mappings; any restore code must mutate mappings in place.
- No circular imports are required. Asset validation can stay in `AnalysisRuntime` and use existing `hash_file`, `hash_dataframe`, and `SnapshotStore.load()`.
- `AssetResolver` already performs file hash checks for file-backed assets and `SnapshotStore.load()` checks snapshot hashes. Restore validation must reuse these algorithms, not invent a second format.

## 8. Concurrency and file stability risks

A file can change while it is being hashed. A plain hash result cannot prove stability in that interval. Restore verification must fail closed for unstable reads (for example, using file metadata before/after an open-stream hash). A matching hash is VERIFIED only when stability checks pass. Snapshot-backed DataFrame validation is performed after loading the snapshot and hashing the in-memory frame.

## 9. Proposed scope

- Add a deterministic restore-time verifier for file-backed and snapshot-backed assets.
- Store asset restore state in `source_metadata["restore_integrity"]`.
- Persist canonical evidence records as a backward-compatible `canonical_evidence` key in the runtime snapshot and restore them into `EvidenceRegistry`.
- Revalidate restored canonical evidence through the existing `EvidenceRegistry.verify()` path.
- Downgrade persisted legacy evidence status based on current asset trust; create deterministic restore verification records.
- Expose failed/stale asset limitations in current report trust derivation without rewriting historical reports.
