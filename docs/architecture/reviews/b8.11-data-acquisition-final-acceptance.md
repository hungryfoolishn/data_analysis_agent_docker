## 2. Core architecture & data flow (unchanged shape, hardened internals)

```
DatasetCatalog → AdapterRegistry → Adapter.fetch (rate limit, cache, bounded retry)
  → FetchResult (provenance + quality_report + content_hash)
  → AcquisitionService.acquire/refresh
      ├─ AcquisitionHistory (atomic, corruption-safe, content_version)
      ├─ health tracker (quality ≠ health)
      └─ runtime.register_fetch_result
          → SnapshotStore (atomic parquet, hash-verified)
          → DataAsset (full provenance metadata)
          → AssetResolver (restore by asset_id)
          → Runtime V2 plan/step → Binding → Evidence (verified)
          → Verified Report (discloses input + output assets)
```

No new lineage system, no second registration path, no Runtime rewrite.

## 4. AcquisitionHistory ↔ DataAsset version relations

- content identity = `content_hash`; `content_version` (`v1`, `v2`, …) is a
  deterministic label over the distinct content-hash sequence.
- repeat acquisition of identical content → same asset, no version change.
- content change → new asset + `version_changed=True` + next `content_version`.
- `AcquisitionHistory.find_by_asset_id(asset_id)` maps a registered asset back
  to its acquisition record; asset metadata carries the forward lineage
  (`source_id`, `dataset_id`, `content_hash`, `fetched_at`,
  `observation_period`, `release_date`, `revision` — unknown stays `None`).

## 5. SnapshotStore recovery

- save is atomic (temp file + rename), hash-verified, rejects existing ids.
- `AssetResolver.resolve` restores data by `snapshot_reference` in asset
  metadata; dedup candidates with lost snapshots are never returned (B8.8).
- failures during registration roll back asset + task link + snapshot; previous
  versions stay restorable (tested).

## 6. Quality vs. Health boundary

Quality = data trustworthiness (gaps, duplicates, invalid values, empty data).
Health = source reachability (timeouts, 429, 5xx, auth). Quality warnings never
touch health; health failures never fabricate data or versions. See B8.10 doc.

## 7. Rate limit / retry

Rate limit guards upstream requests only (cache hits excluded, `refresh`
included, thread-safe). Retry policy is error-class aware: request/quality/auth
fail fast, 429 honors capped Retry-After, transient errors use bounded backoff
with a hard `max_retries`. See B8.10 doc.

## 8. Runtime V2 / Binding / Evidence / Report integration

- acquired DataAssets enter the runtime through `register_fetch_result` (same
  asset/task-link mechanism as file and SQLite assets).
- Runtime V2 plans bind the acquired asset as required input; the scripted
  full-chain tests consume it through the real executor path.
- verified Evidence references the input asset (`input_asset_ids`) and the
  registered output asset; the verified report's findings reference both.

## 9. B9/B10 reusable interface (frozen contract)

B9 Macro Pack may consume:
- `AdapterRegistry` / `DatasetCatalog` (`from_registry`), including NBS
  (`nbs_gdp`, `nbs_cpi`) and FRED/BLS/BEA datasets with `unit`/`frequency`.
- `FetchRequest(dataset_id, start, end, parameters)` + `refresh`.
- `AcquisitionService.acquire/refresh` → `AcquisitionOutcome`
  (`.asset`, `.version_changed`, `.previous_content_hash`, `.fetch_result`).
- `DataAsset.source_metadata` provenance (observation_period / release_date /
  revision semantics) and `AcquisitionHistory` read-only queries
  (`versions`, `content_versions`, `latest`, `find_by_asset_id`).
- `AssetResolver.resolve(asset_id)` for dataframe access.

B10 Financial Pack may consume SEC assets with raw period/unit semantics
(filing_event frequency, USD units, form/accession preserved; distinct revisions
stay distinct rows). B8 performs no domain transformation (no GDP deflators, no
CPI YoY, no financial ratios) — that belongs to B9/B10.
