- Date: 2026-11-20
- Project: DeepAnalyze / data_analysis_agent
- Stage: A1.4.2.0
- Baseline branch: `codex/a1.3.3-canary-readiness`
- HEAD before this documentation commit: `cdaa4737fab50dcc77801fc82a2821cea2ff8b05`
- Audit mode: read-only code/configuration/runtime-boundary audit; no implementation changes
- Verification classes:
  - CODE-AUDIT: repository code was traced.
  - CONFIG-AUDIT: compose/Dockerfile/runtime container metadata was read.
  - RUNTIME-PROBE: non-destructive probes were executed in `deepanalyze-a132-test`, not production.
  - NOT VERIFIED: items requiring a dedicated implementation/E2E environment.

## 1. Executive conclusion

Current Python execution is **process isolation**, not a container sandbox or OS-level security boundary. `IsolatedPythonExecutor` creates a child Python process inside the existing API container. It inherits the API process's mount namespace, network namespace, PID namespace, Linux user identity and container security posture. Existing controls improve reliability and reduce accidental access, but they do not enforce a security boundary against deliberately malicious Python code.

Key residual risks:

1. In fork mode, inherited parent memory can expose module globals containing secrets.
2. `subprocess`, `ctypes`, or OS-level primitives can bypass the Python file audit hook.
3. The V1 regex blacklist is not a security control and can be bypassed by dynamic imports/reflection.
4. Production container has no cap-drop, no-new-privileges, seccomp profile, read-only root filesystem or CPU/memory/PID limits.
5. Production workers have unrestricted network egress.
6. Artifact handling does not yet reject symlink/path-confusion outputs independently at the parent boundary.

Therefore the current system must be classified as **bounded process execution**, not a secure multi-tenant sandbox.

### 4.3 Cancellation path

```text
POST /sessions/{session_id}/cancel
  -> api_server_langgraph.py:1378 cancel_session
  -> sets _ACTIVE_CANCELS[session_id]
  -> run_analysis_stream propagates session.cancel_event
  -> V1 checks at stream/event boundaries
  -> V2 controller receives cancel_event_provider
  -> IsolatedPythonExecutor polls cancel_event every 0.1s
  -> os.setsid() worker group receives SIGTERM
  -> 5s grace -> SIGKILL -> 2s wait
```

Tests in `tests/test_isolated_python_executor.py` and `tests/runtime_v2/test_a132_linux_worker_validation.py` prove normal timeout/cancel and ordinary subprocess child termination. They do not prove that a double-forked `setsid` descendant cannot survive.

## 7. Findings

### F1 — P0: Fork memory can expose parent module globals

- Location: `langgraph_langchain/execution/python_executor.py:229-256`, `69-74`
- The fork start method deliberately retains unpicklable namespace objects and inherits the whole parent address space.
- Runtime probe showed a simulated secret stored as a parent module global was visible through inherited `sys.modules` object state.
- Direct `os.environ` cleanup does not remove copied Python heap content.
- Impact: LLM keys, internal tokens and connection configuration can leak to untrusted analysis code.
- Required target: separate container image/process with explicit allow-listed inputs and no parent service secrets.

### F2 — P0: Python file audit hook is bypassable

- Location: `langgraph_langchain/execution/python_executor.py:91-121,184`
- The hook only intercepts Python `open()` events.
- Runtime probe showed `subprocess.run(["id"])` succeeded as uid 999 after `importlib.import_module("subprocess")`.
- Consequence: worker can use subprocess/native modules to access container files and other session data permitted by uid 999.
- Required target: mount namespace with only job-scoped read/write paths; deny sensitive host paths independently of Python language controls.

### F3 — P1: Regex blacklist is not a security control

- Location: `langgraph_langchain/langgraph_agent.py:1071-1096`
- Covers a small literal pattern set; omits `importlib`, `getattr`, `ctypes`, `mmap`, `signal`, `socket`, `os.exec*`, etc.
- Only V1 calls it; V2 `PythonTaskExecutor` does not apply regex filtering.
- Impact: false assurance, inconsistent V1/V2 behavior.
- Required target: remove it as security dependency and enforce OS/container boundaries.

### F4 — P1: Production container lacks resource limits

- Location: `docker-compose.yml:1-49`; production `docker inspect`
- No CPU, memory, swap or PID limits are configured.
- Worker-level RLIMIT_AS is not populated by either V1 or V2 path.
- Impact: runaway code, process explosion, disk/CPU exhaustion can affect the main service.

### F5 — P1: Production egress is unrestricted

- Location: production container network metadata and host DOCKER-USER rules
- No observed default-deny egress for `172.31.0.0/16`.
- Worker can connect to API localhost and potentially databases, internal services and public endpoints.
- Required target: default deny, explicit allow-list, IPv4/IPv6/DNS/proxy validation.

### F6 — P1: Production container lacks container security hardening

- Location: `docker-compose.yml`, production `docker inspect`
- No cap-drop, no-new-privileges, seccomp profile, read-only rootfs, or user-namespace hardening.
- Entrypoint does drop to uid 999, but that is not a capability/file/network isolation boundary.

### F7 — P2: Artifact validation is incomplete

- Locations:
  - `python_executor.py:157-205` diffs workspace files and checks size.
  - `langgraph_agent.py:1620-1630` builds parent-side path from worker-supplied `relative_path`.
  - `runtime/context.py:1114-1141` resolves path and hashes it.
- The parent does not independently enforce a per-job output directory, regular-file policy, symlink rejection, MIME/type policy or cross-session path policy.
- A symlink created inside a workspace can point to another session file under the same `/app/workspace` parent and still be resolved/hashable by `register_artifact`.

### F8 — P2: Parent/container crash can leak temporary state files

- Location: `python_executor.py:238-242,186-192,289-324`
- State file lives inside session workspace.
- Normal timeout/cancel/result paths delete it, but a parent crash, container kill or power loss can leave `.python_state_*.pkl` behind.

## 8. Not verified in this stage

The following require A1.4.2 implementation and an isolated acceptance environment:

1. Real per-job container mount enforcement.
2. Real per-job default-deny network policy, IPv6 and DNS behavior.
3. Container lifecycle cancellation under adversarial double-fork descendants.
4. Resource ceiling behavior under CPU, memory, PID and storage pressure.
5. Kernel/runtime escape resistance beyond Docker configuration review.
6. Production rollback behavior of the future worker dispatcher.
