## 3. Implementation

### Approach: iptables DOCKER-USER chain

DOCKER-USER is the Docker-sanctioned chain for user-defined container filtering. It is evaluated first in the FORWARD chain and only affects Docker container traffic (not host traffic).

### Rules added

`
iptables -I DOCKER-USER 1 -m state --state ESTABLISHED,RELATED -j RETURN
iptables -I DOCKER-USER 2 -s 192.168.48.0/20 -d 192.168.48.0/20 -j RETURN
iptables -I DOCKER-USER 3 -s 192.168.48.0/20 -j REJECT --reject-with icmp-admin-prohibited
`

Rule 1: Allow return traffic for inbound API connections.
Rule 2: Allow traffic within the test network (Docker internal DNS resolution, container-to-gateway).
Rule 3: REJECT all other outbound from the test container subnet.

### Scoping

Rules are scoped to source 192.168.48.0/20 (da-a132_default network). This is a dedicated Docker network for the A1.3.2/A1.3.3 test project. No other containers share this subnet.

### Rollback

Remove rule 3 to restore original behavior:
`
iptables -D DOCKER-USER -s 192.168.48.0/20 -j REJECT --reject-with icmp-admin-prohibited
`

## 8. IPv6 Assessment

The Docker bridge network (da-a132_default) does not have IPv6 enabled:
- Container /proc/net/if_inet6: only ::1 on loopback
- No global IPv6 address assigned
- IPv6 egress: Network is unreachable

No IPv6 bypass path exists. If IPv6 were enabled on the Docker network in the future, ip6tables DOCKER-USER rules would need to be added for equivalent isolation.

## 9. DNS Behavior

Docker internal DNS (127.0.0.11):
- Internal Docker container names: resolved by Docker daemon (within the network) - unaffected by egress block
- External domain names: Docker daemon forwards to upstream DNS from the HOST. The DNS response returns to the container via Docker internal mechanism. TCP connections to resolved IPs are blocked.

The observed DNS_FAIL for external domains (www.baidu.com, ragflow-server) is expected: either DNS resolution times out (because the Docker daemon cannot forward due to network conditions) or the TCP connection fails even if DNS resolves. Either way, the connection is blocked.

## 10. Remaining Limitations

1. **Host-level iptables rules**: These rules exist on the Docker host and are not persisted across host reboots (unless saved with iptables-persistent). For production, they should be managed by a proper network policy controller or Docker network configuration.
2. **No real LLM egress**: The current block prevents outbound connections to api.deepseek.com. For A1.3.3.5 (real LLM test), temporary rules allowing the LLM API endpoint will need to be added.
3. **Single container architecture**: API and Worker share the same network namespace. The isolation applies to the entire container. For finer-grained Worker isolation, a separate Worker container would be needed (architectural change).
