# B8.11.1 — Acquisition Transaction Consistency Fix

Date: 2026-11-15
Branch: `codex/phase1-m2.4-sqlite-schema`
Base: `b682196 docs(macro): add macro pack acceptance and freeze` (includes B8.11 `692e30f`)

## 1. Background & original risk

`AcquisitionService.acquire` executed:

```
Adapter.fetch → runtime.register_fetch_result (snapshot + DataAsset + persist)
             → AcquisitionHistory.record
```

If the final `AcquisitionHistory.record` failed, the snapshot, DataAsset, and
task linkage were already committed while no history event existed, and the
call raised — an apparently failed acquisition with real state changes. This
was the last P1 consistency risk before freezing B8.

## 2. Resource ownership audit (performed before designing the fix)

| Resource | Ownership | Compensation rule |
| --- | --- | --- |
| Snapshot (this acquisition) | created by `register_fetch_result`; rolled back internally on registration failure | after `asset_registered`, never deleted (may already be shared) |
| DataAsset (this acquisition, newly created) | registered + linked to task + persisted | after `asset_registered`, never deleted |
| DataAsset (dedup reuse) | existing asset returned for same `dataset_id + content_hash` | never touched by compensation |
| History event | append-only, atomic per file | idempotent per `transaction_id` |
| Shared snapshots / assets referenced by other tasks or Evidence | — | never treated as temporary resources |

`register_fetch_result` already rolls back (snapshot + asset + task link +
persist) on its own failure, so scenarios B/C need no external compensation.

## 3. Fixed flow (saga with journal)

```
STARTED (journal)
  → fetch (fail ⇒ ABANDONED, no resources exist)
  → runtime.register_fetch_result (fail ⇒ internal rollback + ABANDONED)
  → ASSET_REGISTERED (journal; snapshot + asset committed, may be shared)
  → history.record (fail ⇒ stays ASSET_REGISTERED = recoverable; acquire raises)
  → COMPLETED (journal)
```

Implementation (`langgraph_langchain/data/acquisition.py`):

- `AcquisitionTransactionLog` — per-transaction journal under
  `<history_dir>/transactions/acqtx_<32hex>.json`, atomic writes, corruption
  detection, states `started → asset_registered → completed` plus terminal
  `abandoned`. Active states: `started`, `asset_registered`.
- Every committed history entry carries its `transaction_id`.
- `AcquisitionHistory.record` is **idempotent per `transaction_id`** (a repeat
  recovery cannot duplicate the event).
- `AcquisitionService.recover_pending_transactions()` (idempotent saga
  recovery, runs automatically at service construction):
  - `started` → `abandoned` (crash before registration; no resource exists);
  - `asset_registered` → the **only safe compensation** is the idempotent
    commit of the missing history event, then finalize. Committed history is
    never rolled back; shared assets/snapshots are never deleted.
  - Recovery failures are aggregated and raised (`AcquisitionTransactionError`)
    — no silent swallowing.
- Query visibility: journal files live outside the per-dataset history files;
  pending/abandoned transactions never appear in `history()/versions()/
  content_versions()/latest()`.

### Guarantees & non-goals

- Same acquisition is uniquely identified by `transaction_id`; retries do not
  duplicate content versions (asset dedup) or history events (idempotent
  record).
- Crash between history write and journal finalization is repaired by the same
  idempotent recovery.
- Not a distributed/ACID transaction across components; it is a recoverable
  compensation (saga) with an explicit journal — stated as such.

## 4. Asset ID history query semantics (B8.11.1-B)

Concepts kept distinct: **DataAsset** (content asset) ≠ **content version**
(distinct `content_hash`, `v1/v2/...`) ≠ **acquisition event** (one fetch).

- `find_by_asset_id(asset_id)` → **latest committed acquisition event** for the
  asset (documented; repeated acquisitions of identical content return the most
  recent event).
- `find_acquisitions_by_asset_id(asset_id)` → **all** committed acquisition
  events for the asset, oldest first (stable `fetched_at` + file order).
- Pending/abandoned transactions are invisible to all history queries.

## 5. Real runtime operation integration (B8.11.1-C)

`tests/test_b8_runtime_operation.py` drives the production chain without the
scripted mini-tool:

```
AcquisitionService → register_fetch_result → DataAsset → AssetResolver
  → DeterministicAnalysisPlanner (GeneralAnalysisPlan, production planner)
  → _run_runtime_v2_graph_stream (Runtime V2 scheduler + StructuredTaskExecutor)
  → real run_analysis_operation (production tool registry)
  → ExecutionResult → OutputBinding → Canonical Evidence → Verified Report
```

Verified in-test: explicit asset binding (no `session.current_asset_id`
fallback), resolver restore, real tool invoked, canonical execution id through
execution record/output binding/evidence, output asset registered, evidence
verified referencing input+output assets, report findings referencing both.
The transport is injected (offline); LLM planning is the injected boundary —
the production deterministic planner builds the plan.

## 8. Remaining issues

- P2: the transaction journal is per-process-recovered (service construction);
  a multi-process deployment would need external coordination (unchanged
  single-writer boundary).
- P2: recovery of `asset_registered` transactions writes history from journal
  payload; if the runtime workspace itself was deleted, the journal reports the
  history write failure and keeps the transaction pending for manual handling
  (explicitly exposed, never auto-deleted).

No P0/P1 remain.

## 9. B8 final freeze conclusion

**B8 (Data Acquisition Platform) is formally frozen** after B8.11.1:

- the last P1 consistency risk is fixed with recoverable saga semantics;
- acquisition events / content versions / assets are queryable with explicit
  semantics;
- the real runtime operation entry consumes acquired assets end to end;
- B8, B6, and macro regressions pass; the only full-suite failures are the
  documented pre-existing dashboard baseline failures.

Allowed after freeze: P0/P1 data-consistency/security fixes, compatibility and
regression fixes for existing adapters. Not allowed: domain semantics in the
acquisition layer, new sources without need, Runtime V2 restructuring, bypassing
DataAsset/AssetResolver/Binding/Evidence. B9 Macro Domain Pack is the next
development stage and consumes the frozen B8 interfaces.
