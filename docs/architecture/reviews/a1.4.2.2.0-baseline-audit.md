## 3. Worker Contract Audit

### 3.1 WorkerJob (`job_contract.py:171-258`) — portable

| Field | Type | Notes |
|---|---|---|
| `schema_version` | `Literal["worker_job.v1"]` | versioned |
| `job_id` | str (regex-validated) | path-safe |
| `session_id/task_id/execution_id/correlation_id` | optional str | validated |
| `code` | str, 1..512000 chars | redacted in repr/log-safe payload |
| `workspace_dir` | str (absolute host path, validated) | **process backend detail**; container mapping must translate, not treat as mount request (docstring states this) |
| `source_path` | str | absolute backend path; same mapping rule |
| `namespace` | `dict[str, JsonValue]` | **closed recursive JSON type** (`job_contract.py:23-34`) — no arbitrary objects |

| `output_policy` | ArtifactPolicy | relative `output_dir`, extension allow-list, size/count limits |
| `execution_options` | WorkerExecutionOptions | timeout ≤3600s, `allow_network` (intent-only), `environment` dict with forbidden-key markers (`API_KEY/SECRET/TOKEN/PASSWORD/...`) rejected at `job_contract.py:149-158` |

### 3.2 ProcessWorkerJob (`job_contract.py:259-269`) — process-only

Overrides `namespace: dict[str, Any]`. Built by `build_process_worker_job` from `PythonExecutionRequest`. It carries live fork-inherited objects (modules, closures, DataFrames). Its own docstring states it "is not accepted by a container backend; A1.4.2.2 must replace it with an explicit artifact-based state mechanism."

### 3.3 WorkerResult (`worker_backend.py:58-72`) — portable

JSON-safe: status/stdout/stderr (≤100k each)/exit_code/duration_ms/artifacts/error.

### 3.4 ProcessWorkerResult (`worker_backend.py:93-107`) — process-only

Extends WorkerResult with `namespace_updates: dict[str, Any]` (live/pickled objects). Runtime consumers: `langgraph_agent.py:1163` and `python_task_executor.py:132-136`.

## 4. Serialization Boundary Audit

**There is currently no real serialization at the dispatcher/backend boundary.** The dispatcher receives and passes object references. The only serialization points:

1. `ProcessWorkerBackend.execute` converts `WorkerJob -> PythonExecutionRequest` (`worker_backend.py:180-196`) — still in-process, namespace objects passed by reference (`job.namespace` is the live fork namespace).
2. `IsolatedPythonExecutor.execute` (`python_executor.py:250-276`):
   - fork mode (default on Linux): `_fork_namespace` keeps **all** non-reserved values without pickling; `prepared.model_dump()` is passed as `mp.Process` args (fork inherits memory).
   - spawn mode: `_serializable_namespace` keeps only pickle-safe values.
3. Child → parent result: dict via `mp.Queue` (JSON-safe fields) + namespace_updates via a pickle state file (`.python_state_*.pkl`, written by child, unpickled by parent, then unlinked). Artifacts collection excludes dot-prefixed paths (`python_executor.py:198`), so the state file is not collected as an artifact.

**Conclusion:** cross-container execution requires a real serialization boundary in the Docker backend: JSON job envelope in / JSON result out, artifact files in/out. Pickle must not become the container trust protocol.

## 5. namespace Investigation (final determination)

Creation/flow (grep evidence):

```text
V1 _Session.ns            -> langgraph_agent.py:1131 (request.namespace)
V2 task namespace         -> python_task_executor.py:92 (request.namespace or task.constraints)
build_process_worker_job  -> job_contract.py:288 (namespace=request.namespace)
ProcessWorkerBackend      -> worker_backend.py:199 (namespace=job.namespace into PythonExecutionRequest)
IsolatedPythonExecutor    -> python_executor.py:172-185 (namespace = helpers + request.namespace; exec(code, namespace))
namespace_updates         -> python_executor.py:56-66 (_serializable_namespace, pickle-filtered) -> back to callers
```

- The namespace carries live analysis objects; cancellation, stdout capture and artifacts do NOT depend on it (cancellation uses the parent-side event; stdout via redirect; artifacts via workspace diff).
- The namespace is a **Process Backend internal implementation that leaks into ProcessWorkerJob**. The portable WorkerJob keeps `dict[str, JsonValue]` and is safe.
- Docker Backend must accept only the base `WorkerJob`; a container worker cannot use the fork namespace. State continuity across container jobs requires an artifact-based state mechanism (e.g., input artifact manifest of pickled/parquet state files transferred by the trusted manager), which is out of scope for this phase.

## 6. Artifact Flow Audit

- **Input**: `ArtifactReference` paths are relative and validated; however the current process backend passes only `artifact_id` values into `PythonExecutionRequest.input_asset_ids` — the executor does not fetch them; the runtime pre-stages files in the session workspace. For Docker, input must be physically staged by the trusted manager (RO mount or copy-in).
- **Output**: workspace file diff (mtime+size) collected by the child (`python_executor.py:190-205`), dotfiles excluded, oversized artifacts deleted and raise. Parent-side validation (`worker_backend.py:293-334`): symlink rejection, resolve-escape rejection, size metadata match, size limit, extension allow-list, sha256 computed.
- **Cleanup**: child kills on timeout/cancel with killpg SIGTERM→SIGKILL; state file unlinked on all paths. Workspace cleanup is session-level (out of scope here).

## 7. Environment & Secret Exposure

- Child clears `os.environ` and installs only validated `request.environment` (`python_executor.py:228-236`); forbidden key markers rejected in contract validation.
- In fork mode the child still inherits **parent memory** — module-level secrets, clients and cached credentials are reachable by untrusted code. Environment cleaning is application-level; it is NOT equivalent to container isolation. This is the core motivation for A1.4.2.2.

## 8. Docker/Compose & Image Baseline

- `docker-compose.yml`: single `api` service, image `deepanalyze:latest`, no worker service, no worker container wiring.
- `Dockerfile`: base `telebi-telebi-base:latest` (unpinned, `:latest`), `USER root`, conda env creation at build, requirements installed unpinned (no lockfile), no image digest pinning, no SBOM/scanning. Adequate for the API container today; NOT adequate as an untrusted-worker image policy.
- Dockerfile `tini` present (PID 1 signal handling precedent exists).
