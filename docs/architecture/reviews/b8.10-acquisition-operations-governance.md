# B8.10 — Acquisition Operations Governance Review

Date: 2026-11-15
Branch: `codex/phase1-m2.4-sqlite-schema`
Base: `ad8d029 feat(data): strengthen acquisition version history and lineage`

## 1. Quality vs. Health boundary (enforced + tested)

- **Data quality** (`QualityReport`) describes the returned data (missing
  columns, empty frame, null columns, invalid times, duplicate periods,
  undeclared units, observation gaps). It never mutates adapter health.
- **Adapter health** (`AdapterHealthTracker`) describes source reachability
  (timeouts, 429, 5xx, auth rejection). It is updated only by acquisition
  success/failure, never by data-quality warnings.

Test `test_quality_and_health_are_independent` proves a monthly data gap
produces a quality **warning** while the adapter stays **healthy**.

## 2. QualityReport policy (verified)

- `issues` → `failed`; `warnings` → `warning`; otherwise `passed`. Warnings are
  never auto-upgraded to errors (`test_quality_report_keeps_evidence_and_does_not_upgrade_warnings`).
- Every issue/warning is a self-describing message (detection basis), e.g.
  `Missing required columns: …`, `Duplicate time values found`,
  `observation gaps for frequency monthly: 2026-02 (+…)`.
- `detect_observation_gaps` works on the normalized frame's declared frequency
  (annual/quarterly/monthly/weekly/daily); period labels that are not real
  timestamps (e.g. BLS `M01`) are skipped instead of misjudged. Quarterly and
  annual release intervals are not misjudged as gaps because the expected range
  is derived from observed first/last periods only.
- Empty/missing values are never auto-filled with 0: invalid numeric values are
  dropped during normalization (documented adapter behavior), which is visible
  through row counts and content hashes.

## 3. AdapterHealthTracker state machine (B8.10)

- `unknown` → no observation yet.
- one transient failure → `degraded`.
- `failure_threshold` (default 2) consecutive failures → `failing`.
- authentication failure (`error_type="auth"`) → `failing` immediately.
- any successful fetch → `healthy` (resets counters and auth flag).
- updates serialized with a lock; state intentionally process-local (describes
  "now", not history).

## 4. Rate limit & retry policy (B8.10)

- Rate limiting moved to the **upstream request path**: cache hits no longer
  consume the interval; `refresh=True` bypasses the cache and still enforces
  the limit (`test_refresh_bypasses_cache_but_still_respects_rate_limit`).
- Concurrent callers are serialized by a lock; N distinct concurrent requests
  are spaced by the declared interval
  (`test_rate_limit_is_thread_safe_under_concurrent_fetches`).
- Error classes: `AdapterRequestError` (bad request, fail fast),
  `AdapterQualityError` (fail fast), `AdapterAuthError` (HTTP 401/403 — **never
  retried**), `AdapterRateLimitError` (HTTP 429 — retries honor a bounded
  `Retry-After`), `AdapterTemporaryError` (5xx/network — bounded exponential
  backoff, hard `max_retries` limit).
- `retry_after_cap_seconds` (5s) bounds Retry-After waits — no unbounded
  waiting; retries are bounded by `max_retries` (default 2).

## 5. Credential & log safety (verified)

- `register_fetch_result` provenance stores only user request parameters;
  adapter-level credentials (e.g. FRED `api_key`) never enter request
  parameters, cache keys (`cache_key` hashes the normalized request), history
  records, or snapshots.
- `_http_get` error messages contain the request path with the query string
  stripped, so query-passed credentials are never logged
  (`test_http_get_classifies_errors_without_leaking_query_params`).
- No adapter logs request URLs at all; tests/fixtures use placeholder keys only.

## 6. Failure recovery semantics (defined + tested)

| Situation | Retry? | Old data | Behavior |
| --- | --- | --- | --- |
| Network error / 5xx | bounded retries | preserved | `AdapterTemporaryError` after limit; health degraded/failing |
| HTTP 429 | bounded, honors Retry-After (capped) | preserved | same as above |
| Auth failure | never | preserved | immediate failure, health `failing` |
| Empty response | no | preserved | `AdapterQualityError` ("Fetched dataset is empty"), not auto-filled |
| Data format change | no | preserved | quality issues / normalize errors surface; no silent coercion |
| SnapshotStore write failure | no | preserved | `register_fetch_result` rolls back asset/link/persist; previous version restorable (`test_snapshot_write_failure_rolls_back_registration`) |
| DataAsset registration failure | no | preserved | same rollback path (B8.1 transaction) |
| AcquisitionHistory write failure | no | preserved | atomic write + corruption detection (B8.9); failed acquisition never writes a version record |

Stale data is never silently presented as fresh: cache entries carry TTL and
`refresh` forces a new fetch; history records distinguish acquisition events
from content versions.
