# B11.2.0 Runtime Output Propagation Inspection

Status: complete (documentation-only inspection)
Baseline: `86adc0119231da0256ae540a191192bf1c1bcbb0`
Scope: Runtime V2 output propagation, step-to-step data transfer, scheduler input dynamics, retry output reuse.
Constraint honored: no business code, tests, runtime behavior, Scheduler/TaskRunner, routing, Golden expectations, or Docker config was modified. This report is the only change.

## 1. Current Runtime V2 execution chain

The real chain observed at this baseline is:

1. Plan steps become `RuntimePlanStep` objects with `required_inputs` and `expected_outputs`
   (`langgraph_langchain/runtime/models.py`, `RuntimePlanStep`).
2. `analysis_tasks_from_plan()` converts each step into an `AnalysisTask`
   (`langgraph_langchain/runtime/scheduler.py`). Every task receives the same
   `plan.input_asset_ids` list; `required_inputs` and `expected_outputs` are copied as plain
   string lists and are not resolved into asset IDs.
3. `TaskRunner.execute_next()` picks a ready task and calls `request_factory(task)`
   (`langgraph_langchain/runtime/runner.py`). `next_task()` / `is_ready()` consider only task
   status and `depends_on` status (`scheduler.py`, `TaskScheduler.is_ready()`).
4. `RuntimeV2Controller._request_factory()` builds the request
   (`langgraph_langchain/runtime/graph.py`). With `analysis_runtime` present it calls
   `AnalysisRuntime.build_execution_request(task)`
   (`langgraph_langchain/runtime/context.py`). That resolves `task.input_asset_ids` into
   `namespace.runtime_inputs` / `runtime_input_metadata`. Then the controller overwrites
   `request.metadata` with skill metadata.
5. A structured executor invokes the tool (`langgraph_langchain/execution/structured_executor.py`).
   For `run_analysis_operation` the tool resolves an asset ID, computes the dataframe,
   registers a new DataAsset and artifact, records evidence, sets
   `session.current_asset_id = asset.asset_id`, and returns JSON containing
   `output_asset_id` (`langgraph_langchain/tools/tool_analysis_operation.py`,
   `run_analysis_operation`; same pattern in `tool_sqlite_query.py` and `tool_load_data.py`).
6. The executor extracts only artifact IDs from the tool output via
   `extract_artifact_ids()` (`langgraph_langchain/execution/task_models.py`) and stores them in
   `ExecutionResult.output_artifact_ids`. `ExecutionResult` has no `output_asset_ids` field
   (`langgraph_langchain/runtime/models.py`, `ExecutionResult`).
7. Evidence is collected from the tool-side registration, not from an output binding on the
   result.

## 2. Answers to the eight core questions

### Q1. Is `expected_outputs` a logical name or an actual Asset ID?

Logical name only. `RuntimePlanStep.expected_outputs` is `list[str]`
(`models.py:38`), populated with values such as `step_id:output`
(`runtime/analysis_workflow.py:75`), `query_result_asset`
(`runtime/sqlite_workflow.py:189`), or `analysis_output`
(`runtime/plans.py:104`). Nothing at this baseline maps these strings to real
DataAsset IDs.

### Q2. Can one step produce multiple Output Assets?

The data model does not prevent multiple logical output names, but the current
tool contract returns exactly one `output_asset_id` and registers exactly one
output DataAsset. Artifacts (charts, reports) can be several, but there is no
mechanism that records "this step produced asset X as output `grouped_data`
and asset Y as output `summary`". Multiple data outputs are therefore not
supported as first-class, named outputs.

### Q3. How does a downstream step reference the upstream output?

It does not do so structurally. Downstream referencing relies on one of:

- `session.current_asset_id`, a mutable field set by
  `run_analysis_operation`, `tool_sqlite_query`, and `tool_load_data`;
- the plan-level `input_asset_ids` copied identically into every task by
  `analysis_tasks_from_plan()`.

`required_inputs` strings such as `step_1.grouped_data` are never resolved to
physical asset IDs during request building.

### Q4. Does the Scheduler support dynamic inputs?

No. `TaskScheduler` validates dependency topology and orders tasks by status
only (`scheduler.py`, `is_ready()`, `ready_tasks()`, `blocked_tasks()`). It has
no knowledge of DataAssets, output bindings, or data readiness. A task becomes
ready purely when its dependencies have status `succeeded`.

### Q5. Can `TaskRunner` inject real Asset IDs before execution?

There is an injection point: `request_factory(task)` in
`TaskRunner.execute_next()` and the default
`AnalysisRuntime.build_execution_request()`, which resolves
`task.input_asset_ids` into `namespace.runtime_inputs`. However, this only
resolves pre-assigned asset IDs. There is no formal output-binding protocol that
lets the runner inject "the asset produced by dependency step N" automatically.

### Q6. Does `ExecutionResult` save real Output Asset IDs?

No. `ExecutionResult.output_artifact_ids` holds artifact IDs extracted from the
tool JSON (`task_models.py:extract_artifact_ids`,
`runtime/models.py:100`). The real `output_asset_id` exists only inside the
tool's JSON payload and in the tool-registered DataAsset/evidence, not as a
typed field on the result.

### Q7. When upstream fails, is downstream skipped?

No. `TaskRunner` marks the failed task failed and, with the default
`stop_on_failure=True`, stops the run
(`runner.py`, `run()`). Without stop-on-failure, downstream tasks simply remain
`pending` and are reported by `blocked_tasks()`; the runner does not call
`mark_skipped()` on dependents. `TaskScheduler.mark_skipped()` exists
(`scheduler.py:366`) but is not invoked by this propagation path.

### Q8. Can retry reuse old outputs?

Retry is run-level, not task-level: `_create_retry_run()`
(`context.py:1709`) creates a new `AnalysisRun` with
`parent_run_id`, `retry_of_step_id`, and `attempt + 1`, and clears runtime
assets/executions. Because there is no attempt-scoped output binding, the
runtime cannot deterministically state whether an old attempt's asset was
reused, must be recomputed, or must be invalidated. The SQLite dedup path can
return an existing asset registered under an older `execution_id`
(`context.py`, `register_sqlite_result()`), which is acceptable for identical
provenance but must be made explicit under retry/attempt semantics.

## 3. Findings

### P1-1: Output transfer relies on implicit mutable global state

- `session.current_asset_id` is written by `run_analysis_operation`
  (`tool_analysis_operation.py:120`), `tool_sqlite_query`
  (`tool_sqlite_query.py:117`), and `tool_load_data`
  (`tool_load_data.py:158`).
- `analysis_tasks_from_plan()` gives every task the same
  `plan.input_asset_ids` (`scheduler.py:77`).
- There is no durable mapping from `(run_id, step_id, output_name)` to
  `asset_id`.

Consequence: multi-step propagation is order-dependent and side-channel
dependent, cannot express multiple outputs, and cannot support parallel or
dynamic downstream consumption safely.

### P1-2: `ExecutionResult` cannot answer "which DataAssets did this execution produce"

`ExecutionResult` stores only `output_artifact_ids` (`models.py:100`).
Downstream steps, evidence validation, and report lineage cannot reconstruct
step-to-asset lineage from the result alone.

### P2-1: Controller metadata overwrite can drop diagnostics

`RuntimeV2Controller._request_factory()` builds a request via
`build_execution_request()` (which may set
`metadata["asset_resolution_error"]`) and then assigns
`request.metadata = metadata` (`graph.py:151`), discarding anything the runtime
put there.

### P2-2: `required_inputs` semantics are ambiguous

Depending on the workflow, `required_inputs` is filled with asset IDs
(`sqlite_workflow.py:188`, `analysis_workflow.py:74`) or is expected to carry
logical step-output names. Nothing validates which domain a value belongs to.

### P2-3: Downstream tasks are not skipped on upstream failure

They remain `pending` and are surfaced as blocked; with the default runner
configuration the whole run stops. This is a defined behavior today, but
B11.2 must decide explicitly whether dependents should be marked `skipped`.

### P2-4: SQLite dedup reuses assets registered under older executions

`register_sqlite_result()` returns an existing asset with identical content
hash and provenance. This is correct for deterministic re-reads but interacts
with attempt semantics: a retry that intentionally re-executes the same query
must not silently inherit the parent attempt's execution context in evidence
lineage.

### P2-5: `expected_outputs` naming is inconsistent

Producers use three different conventions (`{step_id}:output`,
`query_result_asset`, `analysis_output`). Any binding protocol must define one
canonical output-name namespace.

## 4. Current capability boundary

What works today:

- single-step file and SQLite chains, driven by tool-registered DataAssets and
  `session.current_asset_id`;
- multi-task plans where all tasks share the plan-level input assets;
- status-only dependency scheduling with deterministic topological order;
- artifact extraction and evidence registration per execution.

What does not work yet:

- a downstream step referencing a named upstream output (`step_1.grouped_data`)
  resolved to its real Asset ID;
- a step producing and registering multiple named data outputs;
- dynamic input resolution at scheduling time based on upstream results;
- attempt-scoped output isolation across retries;
- reconstructing step-level DataAsset lineage purely from `ExecutionResult`.

## 5. B11.2.1 design suggestion (not implemented in B11.2.0)

Introduce an explicit `OutputAssetBinding` with at least:

- `run_id`
- `step_id`
- `output_name`
- `asset_id`
- `execution_id`
- `attempt`
- `created_at`

Design constraints:

1. `session.current_asset_id` must not be the authoritative transfer state.
   It may remain a UI/legacy convenience, but binding lookup must be the
   source of truth.
2. Logical references such as `step_1.grouped_data` must be distinct from
   physical Asset IDs; request building resolves logical references through
   the binding registry for the current `run_id`/`attempt`.
3. One step may register multiple bindings with distinct `output_name`s;
   multiple downstream tasks may consume the same binding.
4. Retry must isolate old attempt outputs: bindings are immutable per
   `(run_id, step_id, output_name, attempt)`; a retry attempt creates new
   bindings and never overwrites the parent attempt's records. SQLite dedup
   may still reuse identical assets, but the binding must record the current
   attempt's `execution_id`.
5. `ExecutionResult` should gain `output_asset_ids` (or reference bindings) so
   evidence and reports can validate step-to-asset lineage without parsing
   tool stdout.

## 6. B11.2.2 evidence lineage acceptance scope

Evidence work after B11.2.1 should verify, without extending runtime features:

- evidence `execution_id` matches the binding's `execution_id`;
- evidence input assets match the task's resolved logical inputs;
- evidence output assets match the step's registered bindings;
- report claims can rebuild the chain
  `asset -> binding -> execution -> step -> run/attempt`;
- legacy paths without bindings do not silently pass as fully bound lineage.

## 7. B11.2.3 file Runtime E2E test scope

End-to-end validation should use file-runtime chains and cover:

- CSV load -> `group_aggregate` -> `sort` -> `top_n`, where each downstream
  step consumes the real upstream Asset ID resolved through bindings;
- a step producing two named outputs consumed by two downstream steps;
- upstream failure propagation (explicit skip-or-block decision assertion);
- retry of a mid-chain step producing new attempt-scoped bindings while the
  parent attempt's outputs remain queryable;
- SQLite query step followed by an analysis step consuming the query output
  asset via binding rather than `session.current_asset_id`.
