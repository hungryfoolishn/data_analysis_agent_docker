# A1.4.2.2 — Docker Worker Architecture Design

Status: design document (nothing in this file is implemented).
Basis: A1.4.2.2.0 baseline audit at HEAD `4d322cc`.

## 1. Target Architecture

```text
Runtime V1 ─┐
            ├── WorkerDispatcher  (unchanged contract: WorkerJob + CancellationHandle -> WorkerResult)
Runtime V2 ─┘        │
                     ▼
        DockerWorkerBackend (explicit opt-in only)
                     │  JSON job envelope (no pickle, no live objects)
                     ▼
        Trusted Container Manager (host-side component)
                     │  docker engine API over local socket
                     ▼
        Docker Runtime
                     ▼
        Worker Container (untrusted, one container per job)
          ├── input artifacts: read-only mount
          ├── output artifacts: job-specific writable dir
          ├── network: deny (IPv4/IPv6/DNS)
          ├── resources: cpu/mem/pids/disk limits
          └── no secrets, no docker socket, no host mounts
```

Key principle: the `WorkerJob` base contract is the container protocol; `ProcessWorkerJob` never crosses the container boundary.

## 2. Container Manager & Docker Socket Boundary

Options considered:

| Option | Docker socket holder | Verdict |
|---|---|---|
| A. API process direct Docker SDK | API process | Rejected for production: API compromise = host compromise; socket reachable from the largest attack surface. |
| B. Trusted Container Manager service | dedicated host-side process | **Recommended MVP** for single-host deployment. API talks to it over a local authenticated channel; it is the only component that may create/stop/remove containers. |
| C. Local IPC privileged launcher | launcher invoked over restricted IPC | Deferred: stronger privilege separation, higher complexity; revisit for multi-host. |
| D. External worker service | external service | Deferred: operational overhead beyond current single-host deployment. |

**Recommended MVP (Option B, in-process manager module, host-side):**

```text
API (untrusted-adjacent)
  └── WorkerDispatcher
        └── DockerWorkerBackend
              └── ContainerManager (host-side, only component allowed to use the engine API)
                    └── docker engine (local socket / named pipe)
```

For the current single-host deployment, `ContainerManager` may run inside the API process **provided**:

1. It is the only module importing the docker engine client.
2. It validates every job envelope before any container creation (fail closed).
3. All container lifecycle operations are logged with job_id + container_id.
4. The worker container itself never receives the socket (enforced by not mounting it; verified by S10 test).

## 3. Job Envelope & Result Protocol

Docker path uses the base `WorkerJob` serialized with `model_dump(mode="json")` written to the input mount as `job.json`:

```text
job.json (schema_version=worker_job.v1)
├── job_id, session_id, task_id, execution_id, correlation_id
├── code (read by worker entrypoint)
├── input_artifacts[]   (relative to /workspace/input)
├── output_policy       (relative to /workspace/output)
└── execution_options   (timeout, limits; environment allow-list)
```

Container path mapping (manager-side translation, never job-controlled):

```text
job.workspace_dir (host absolute)  ->  /workspace (container)
job.source_path (host absolute)    ->  /workspace/input/<basename> (container, read-only)
ArtifactReference.relative_path    ->  /workspace/input/<relative_path>
output_policy.output_dir           ->  /workspace/output/<output_dir>
```

Result: worker writes `result.json` into the output dir (same JSON schema as `WorkerResult` minus job_id which the manager sets); manager reads it, validates artifacts host-side (reuse `ProcessWorkerBackend._validate_artifacts` logic semantics: symlink/escape/size/extension/sha256), then removes the container.

Protocol rules:

- JSON only between manager and container. No pickle, no arbitrary objects.
- Payload/code size limits inherited from WorkerJob validation.
- `namespace` continuity: NOT supported via container memory. Two policies (choose at A1.4.2.2.2):
  - stateless-per-job (default), or
  - state handoff via explicit state artifacts transferred by the manager (host-trusted pickle of session state files, produced by the *previous trusted* process run — never unpickled inside the worker from untrusted output without policy).
- Unknown/extra fields: worker entrypoint fails closed (extra="forbid" semantics).

## 4. Container Lifecycle

```text
SUBMIT -> VALIDATE (fail closed) -> ALLOCATE (limits) -> CREATE -> START
      -> EXECUTE (job.json) -> [success|failure|cancel|timeout]
      -> COLLECT result.json -> VALIDATE ARTIFACTS (host-side)
      -> REMOVE CONTAINER -> CLEANUP -> RETURN RESULT
```

Failure/cleanup rules:

| Stage | Failure behavior |
|---|---|
| Validate | fail closed, no container |
| Create/Start | remove partial container |
| Execute | result/error collected if possible |
| Cancel | stop (graceful, t=10s) -> kill -> rm; only then return CANCELLED |
| Timeout | same as cancel; TIMED_OUT status |
| Collect | invalid/missing result.json -> FAILED + ARTIFACT_VALIDATION; quarantine output dir |
| Cleanup failure | record + reconciliation scan (orphan containers by job_id label removed on next tick/startup) |

Idempotency: `job_id` used as container name suffix + label; duplicate create for the same job_id is rejected. Container labels: `deepanalyze.job_id`, `deepanalyze.session_id`.

Reconciliation: on backend health check / manager start, list containers with the job label, remove any not tracked by an active dispatch (orphan cleanup). Host restart handled by the same scan.

## 5. Cancellation & Timeout Contract

- Parent-side `CancellationHandle` (dispatcher contract) is observed by the backend thread; backend calls manager stop.
- Sequence: `docker stop -t 10` (tini forwards SIGTERM) -> if running after timeout, `docker kill` -> `docker rm`. API returns CANCELLED only after container is confirmed removed; if confirmation fails, return CANCELLED with a warning detail and schedule reconciliation — the job state notes "container removal pending" rather than silently claiming success.
- Child processes inside the container are contained by the container PID namespace + `pids-limit`; kill of the namespace reaps children. `docker kill` is the fallback when graceful stop fails.
- Cancellation before create: skip container entirely. During create/start: remove partial container. During collect: still validate artifacts before accepting results.

## 6. Filesystem Isolation (design)

```text
/                      read-only rootfs
/tmp                   tmpfs, size-limited (e.g. 256m)
/workspace/input       bind mount RO (job-specific staged dir)
/workspace/output      bind mount RW (job-specific dir)
/workspace/.tmp        tmpfs or output-local
```

- No host sensitive mounts: no docker socket, no `.env`, no SSH, no git credentials, no host `/etc`, `/proc`, `/sys`, no home directories.
- `--read-only` rootfs; tmpfs for /tmp; non-root user (uid fixed, e.g. 10001).
- Mount propagation: rprivate (default) — no shared/master propagation.
- Input files staged by the manager into a job-specific host dir (copy, not the original upload path), so the container cannot modify original uploads; output published only after host-side validation.
- Symlink/hardlink escape: handled by read-only input + validated output collection (host-side check rejects non-regular files and escape paths, mirroring `_validate_artifacts`).

## 7. Network Isolation (design)

- Default: `--network none` for the worker container (denies IPv4, IPv6, DNS, container discovery, host gateway access in one mechanism).
- `allow_network=true` in the future must map to an explicit egress allow-list policy (dedicated network + proxy), never to default bridge; out of MVP scope.
- Loopback risk with `network none`: no interfaces beyond loopback inside the namespace; host services (even on 0.0.0.0) are unreachable without a network path.
- Compose/API and worker never share a network namespace for the worker (worker is not attached to the API's compose network).
- Proxy env: worker receives no proxy variables (environment allow-list only), and with no network interfaces a proxy is moot; S08 test still verifies.

## 8. Secret Isolation (design)

- Worker container environment: explicit allow-list from `WorkerExecutionOptions.environment` only (contract already rejects secret-marker keys).
- No `env_file`, no inherited API env, no mounted secret files.
- Layered defense statement: application-level env cleaning (`os.environ.clear()` in the process executor) and container isolation are different protection layers; container isolation is the enforceable one for untrusted code. Fork memory inheritance (the current residual risk) is eliminated by per-job container execution.

## 9. Resource Limits (design, container-enforced)

| Resource | Enforcement |
|---|---|
| CPU | `--cpus` (e.g. 2.0 default, configurable) |
| Memory | `--memory` + `--memory-swap` = same value (no swap) |
| PIDs | `--pids-limit` (e.g. 128) |
| Disk/output | output dir quota via manager-side validation (max_artifact_bytes/max_files) + tmpfs size limit |
| Stdout/stderr | collected from result.json, already length-bounded by contract |
| Concurrency | manager-level semaphore (global + per-session) |
| Execution time | job timeout -> stop/kill |

Application-level limits (max_output_chars etc.) remain in the contract; container-enforced limits are the authoritative ones for isolation claims.

## 10. Worker Image & Supply Chain (design)

- Dedicated `Dockerfile.worker`: minimal base (python:3.11-slim or equivalent pinned digest), non-root user, pinned dependencies (lockfile), no conda, no runtime package install, no network tools beyond stdlib.
- Image referenced by digest, tag policy: `deepanalyze-worker:<version>` with digest recorded at deploy.
- Build-time: reproducible build, SBOM generation, vulnerability scanning, no secrets in build context.
- Runtime: no privileged mode, `--cap-drop=ALL`, no added capabilities, `--security-opt no-new-privileges`.
- Update/rollback: version pinning in deployment config; rollback = redeploy previous digest.

## 11. V1/V2 Compatibility & Rollback

- Selection remains explicit: `WORKER_BACKEND` env (validated names only) or constructor injection; default process. No silent fallback: Docker failure -> FAILED + BACKEND_UNAVAILABLE/BACKEND_UNSUPPORTED (+ retryable flag), never process fallback.
- V1/V2 code paths unchanged; they consume `WorkerResult`/`ProcessWorkerResult` via the dispatcher. Docker path returns base `WorkerResult` (no namespace_updates) — V1/V2 session state handling must treat missing namespace_updates as "no state change" (already the case: `python_task_executor.py:132-136` checks isinstance).
- Rollback: set `WORKER_BACKEND=process` (or unset) and restart API; containers are removed by reconciliation on next manager start.
- `RUNTIME_V2_ENABLED` default remains unchanged; Docker backend default remains disabled.

## 12. Explicit Non-Goals (this design phase)

- No implementation, no image build, no container creation, no socket access.
- No change to Process Backend default status.
- No B11 contract or Evidence changes.
