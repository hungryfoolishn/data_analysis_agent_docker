# A1.4.2 — Python Worker Isolation Architecture

- Date: 2026-11-20
- Status: A1.4.2.0 recommended architecture
- Recommendation: **Option B — per-job Docker worker container**
- Non-goal in A1.4.2.0: implement Docker changes or alter production routing

## 1. Design goals

1. Untrusted Python code must not affect the API process, host, other sessions, main code or official artifact store.
2. Filesystem, network, secret, process and resource boundaries must be enforced outside the Python language.
3. Existing V1/V2 public behavior, cancellation and timeout semantics must remain compatible.
4. Job identity must not be used directly as a filesystem path.
5. Worker outputs must be validated by the parent before entering runtime state.
6. The design must be practical for a single-host personal/small-team deployment.
7. There must be a rollback path to the existing process executor if the dispatcher fails.

## 2. Options compared

### Option A — Enhanced current process isolation

Continue using `IsolatedPythonExecutor`, but strengthen audit hooks, RLIMITs, process-group termination, output checks and path restrictions.

| Area | Assessment |
|---|---|
| Strength | Small code change; preserves synchronous result/state semantics |
| Strength | Existing cancellation tests continue to apply |
| Weakness | Worker still shares API mount/network/PID namespace and uid |
| Weakness | Cannot prevent subprocess/native bypass of Python controls |
| Weakness | Fork still copies parent memory; secrets remain exposed |
| Security result | Reliability improvement, not a secure sandbox |

Option A is not accepted as the final isolation architecture.

### Option B — Per-job Docker worker container

The main service dispatches one Python execution job to a disposable worker container.

| Area | Assessment |
|---|---|
| Strength | Separate mount, network, PID and process identity boundary |
| Strength | Can remove code/config/secret mounts and inject only job inputs |
| Strength | Container PID namespace makes container stop authoritative for descendants |
| Strength | Independent CPU/memory/PID/storage/network controls |
| Strength | Compatible with existing Docker single-host deployment |
| Weakness | Docker shares the host kernel; not equivalent to a hardware virtual machine |
| Weakness | Adds image/container lifecycle and start latency |
| Weakness | Requires robust dispatcher, cleanup and rollback design |

Option B provides the best risk reduction for the current deployment scale.

### Option C — gVisor / Kata / Firecracker or other strong sandbox runtime

| Area | Assessment |
|---|---|
| Strength | Stronger kernel/RISC isolation or VM boundary |
| Weakness | Additional runtime, host prerequisites and operational complexity |
| Weakness | Potential incompatibility with Python data libraries, native packages, GPU or local tooling |
| Weakness | Startup/memory overhead may be significant |
| Fit | Not justified as the first iteration for the current personal/small-team deployment |

Option C may be revisited only if Option B acceptance tests demonstrate an escape or if a true hostile multi-tenant requirement is introduced.

## 3. Recommended architecture

```
API/Runtime V1/V2
        |
        v
Worker Job Contract
        |
        v
Worker Dispatcher (main service)
        |
        +-- create per-job input/output temp dirs
        +-- write job manifest without secrets
        +-- run one worker container
        |
        v
Isolated Worker Container
  - non-root runtime user
  - read-only worker image/rootfs
  - read-only input mount
  - writable job output mount
  - ephemeral /tmp
  - no Docker socket
  - no API/LLM/DB secret env
  - no application code volume
  - default-deny network
  - cap-drop ALL + explicit minimal additions
  - no-new-privileges + seccomp
  - CPU/memory/PID/time limits
        |
        v
Worker writes only /output
        |
        v
Parent Artifact Validator
  - validates path/type/size/symlink/content
  - copies approved output into session/runtime store
        |
        v
Runtime result / Artifact registry
```

### 3.1 Component responsibilities

**Main service/Runtime**

- performs authorization and runtime selection;
- constructs the Job Contract;
- creates job IDs and job directories;
- writes code and input manifest;
- dispatches and supervises container;
- validates and copies output;
- records execution/artifact metadata;
- maps worker failures to existing V1/V2 statuses.

**Dispatcher**

- owns container lifecycle and concurrency limits;
- enforces timeout and cancellation;
- captures logs/exit status;
- guarantees best-effort cleanup and records cleanup failures;
- never allows job code to choose host paths or Docker parameters.

**Worker**

- executes only the job manifest code;
- reads only mounted input;
- writes only mounted output;
- cannot access Docker socket, main service secrets, source code volume or sibling sessions;
- returns a structured result through the controlled output channel, not through arbitrary host state.

## 4. Job Contract

```json
{
  "job_id": "job_<opaque-random-id>",
  "session_id": "session_reference",
  "execution_id": "execution_reference",
  "code": "python source",
  "input_assets": [
    {"input_name": "source", "container_path": "/input/source", "asset_id": "..."}
  ],
  "resource_limits": {
    "timeout_seconds": 60,
    "memory_bytes": 1073741824,
    "cpu_quota": 1,
    "pids_limit": 128,
    "max_output_bytes": 104857600
  },
  "output_policy": {
    "output_dir": "/output",
    "allowed_types": ["csv", "json", "png", "parquet"],
    "max_files": 100
  }
}
```

Rules:

1. `job_id` is opaque and never concatenated into a host path without server-side validation.
2. The dispatcher generates and validates all host/container paths.
3. Inputs are read-only. Inputs are copied/symlink-mounted individually, not the whole workspace tree.
4. The worker receives no API key, database URL, auth token or unrelated environment.
5. Parent-side helper functions are not injected into the worker.
6. Session state crossing jobs must be explicit, serializable and validated.
7. The worker cannot alter resource limits or output policy.

## 5. Filesystem contract

Target worker mounts:

| Path | Policy | Purpose |
|---|---|---|
| Worker application/library image | read-only | execute Python and dependencies |
| `/input/<input_name>` | read-only | job input only |
| `/output` | controlled write | job output only |
| `/tmp` or dedicated temp | ephemeral, job-scoped | scratch space |
| Host code/config/workspace/artifact store | absent | prevent access/tampering |

Validation and cleanup:

- output entries must resolve under `/output`;
- reject symlinks and non-regular files unless explicitly approved;
- enforce file count, size and type/extension policy;
- copy approved files to the parent's session output area;
- hash copied file after copy, not merely the source;
- delete failed/cancelled job output after preserving required diagnostics;
- startup/start teardown removes stale job directories owned by the dispatcher;
- cleanup failures must be logged and visible to operations.

This closes the current symlink/sibling-session artifact risk at an OS boundary.

## 6. Network contract

Default policy:

- default deny IPv4 and IPv6 egress;
- no route to public internet by default;
- no access to host services by default;
- no access to unrelated containers or databases;
- no proxy environment variables are inherited.

Allowed exceptions must be explicit and minimal. Preferred order:

1. No network at all for pure local analysis.
2. A tightly scoped internal analysis service, if needed.
3. Main-service-mediated external calls, not direct worker internet access.
4. Direct LLM access only if a documented business need exists, with dedicated credentials and narrow policy.

Validation must cover IPv4, IPv6, DNS, proxy env absence, unauthorized container/database access and policy persistence after restart. Docker `internal: true` alone is not accepted as complete egress proof.

## 7. Secret isolation

Requirements:

- worker image contains no production `.env`;
- worker environment contains only Matplotlib/job-scoped variables unless explicitly allow-listed;
- no Python object transfer from API memory;
- prefer `spawn`-like clean process/container startup over fork inheritance;
- no database URL, LLM API key, auth token or internal service token in the job manifest;
- if a future feature requires credentials, issue a short-lived, narrowly scoped token from the main service.

## 8. Resource limits

Per worker/container:

| Limit | Initial target | Notes |
|---|---:|---|
| Timeout | from existing `PythonExecutionRequest.timeout_seconds` | must remain visible to dispatcher |
| CPU | 1.0 initially | tune with E2E benchmarks |
| Memory | 1-2 GiB initially | must be less than host/API capacity |
| Memory swap | equal to memory or disabled | avoid swap amplification |
| PID | 64-128 | catch fork loops |
| Output size | preserve current `max_artifact_bytes` | reject early |
| Output files | bounded | prevent directory/file spam |
| Log size | bounded | prevent log exhaustion |

The worker should also retain OS-level RLIMITs as defense in depth, but they are not a substitute for container limits.

## 9. Cancellation contract

```
User cancel
 -> API sets runtime cancellation
 -> dispatcher observes cancellation
 -> docker stop -t 5 worker
 -> if still running: docker kill
 -> wait for container exit
 -> inspect cleanup/output directory
 -> remove job dirs
 -> report cancelled
```

Rules:

1. Container stop/kill is authoritative; no reliance on Python cooperative checks for final termination.
2. Worker should still handle SIGTERM for fast graceful shutdown.
3. All descendants are expected to die with the container PID namespace; acceptance must prove it.
4. Timeout and cancellation use the same lifecycle path.
5. Cleanup failure changes execution metadata but must never silently leave a running worker.
6. Repeated cancel is idempotent.

## 10. Artifact Transfer Contract

```
Worker /output
 -> dispatcher verifies container exited
 -> validator validates path, regular file, no symlink, size, count, type
 -> optionally scans/rejects executable or policy-violating content
 -> copies to session output staging
 -> hashes copied bytes
 -> runtime.register_artifact(staged copy)
 -> only registered copy is exposed as official artifact
```

The worker never writes directly to the official workspace/artifact registry. The parent does not trust the worker's reported path, file type or size.

## 11. Concurrency and startup latency

Initial implementation should use **one container per execution**, synchronized with existing semantics, because it is easiest to reason about isolation and cleanup.

Latency mitigations, in order:

1. Keep a prebuilt minimal worker image local.
2. Pre-create an ephemeral root filesystem template if necessary.
3. Use a bounded warm pool only after basic per-job isolation is accepted.
4. If a pool is introduced, every checkout must reset mounts, temp files, environment, network state and worker memory. Pool reuse cannot retain Python objects or files between jobs.

Concurrency limit must be derived from host CPU/memory/PID capacity and should not exceed the existing agent semaphore.

## 12. Failure and recovery

| Failure | Required behavior |
|---|---|
| Container create failure | return existing `failed` result, no partial artifact registration |
| Container start failure | same as create failure; clean job dirs |
| Worker exit nonzero | return failed result with bounded stderr/log |
| Timeout | stop/kill container, return `timed_out` |
| Cancel | stop/kill container, return `cancelled` |
| Worker crash | return failed, validate any already-copied output? No—discard unless output contract explicitly allows partial results |
| Cleanup failure | mark cleanup_failed, never leak active container silently |
| Dispatcher unavailable | keep current executor disabled for new jobs or fail closed; no silent fallback to unsafe process path |
| Parent crash | orphan policy uses container labels and startup reaper to identify/remove stale job containers |

## 13. Rollback strategy

- Preserve the existing `IsolatedPythonExecutor` implementation until the container dispatcher passes E2E.
- Add a backend selection flag; default remains current behavior until acceptance completes.
- Run V1/V2 golden tests with both backends.
- On dispatcher failure, rollback only affects newly started sessions; drain active jobs first.
- Do not silently fall back from secure worker container to legacy process executor.

## 14. Explicit answers to architecture questions

1. Current worker is a child process, not a container.
2. API and worker share the PID namespace.
3. API and worker share the Network namespace.
4. Worker cannot read environment after cleanup, but fork memory can expose module globals.
5. Worker cannot access Docker Socket in current production/test containers.
6. Worker can access files permitted to uid 999 by bypassing the Python audit hook.
7. Worker may access other session files through the shared workspace mount when bypassing audit hook.
8. Worker can access public/internal networks in production.
9. Worker may reach database services if network routing permits; no deny policy exists in production.
10. Worker can create child processes.
11. Normal same-group subprocess trees are killed; detached double-fork trees are not proven killed.
12. Normal parent timeout/cancel removes state files; parent/container crash can leak them.
13. Artifact hash is computed after worker returns, but independent artifact validation is incomplete.
14. RLIMIT_AS exists in code but callers do not set `max_memory_mb`; production container limits are absent.
15. Existing tests prove stdout/error transfer, timeout, cancel, simple child cleanup and direct `open()` denial.
16. Real Docker acceptance must prove mount, network, secret, resource and container-lifecycle behavior.
17. gVisor/Kata is not required for the current deployment scale.
18. Option B is sufficient as the next architecture.
19. Use a prebuilt image initially; consider a bounded warm pool only after per-job isolation is proven.
20. A warm pool must be strictly reset between jobs; if reset guarantees cannot be tested, do not use it.
