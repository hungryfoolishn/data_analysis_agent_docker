# A1.4.2 — Python Worker Isolation Implementation Roadmap

- Date: 2026-11-20
- Status: A1.4.2.0 design baseline
- Starting point: A1.4.2.0 Gate A = PASS WITH LIMITATIONS
- Rule: do not begin the next stage until its predecessor's Gate passes.

## 0. Guiding constraints

1. Keep `RUNTIME_V2_ENABLED` default unchanged unless a later task explicitly changes it.
2. Preserve V1 and V2 compatibility; do not introduce a parallel authority for execution results.
3. Do not mount Docker socket into workers.
4. Do not inject API/LLM/database secrets into worker jobs.
5. Do not use the Python regex blacklist as the security boundary.
6. Adversarial tests run only in isolated Docker environments.
7. Every stage has a rollback path and does not alter existing behavior until switched on for tests.

## A1.4.2.1 — Worker Job Contract and Dispatcher

### Scope

- Define `WorkerJob` / `WorkerJobResult` models.
- Create a dispatcher interface behind the existing `IsolatedPythonExecutor` usage boundary.
- Generate opaque job IDs and job-specific input/output directories.
- Add backend selection, initially defaulting to current process executor.
- Preserve V1/V2 result, timeout, cancellation and artifact status mapping.
- Add structured logs/metrics for dispatch, container id, timeout, cancellation and cleanup.

### Deliverables

1. Job Contract schema and validation.
2. Dispatcher abstraction with process and container backend.
3. Backend selection flag and feature tests.
4. Unit tests for contract validation, path generation and status mapping.

### Gate

- Job Contract tests pass.
- Existing process backend remains default.
- No Docker/production configuration changes yet.
- V1/V2 smoke tests unchanged.

## A1.4.2.2 — Independent Worker Container

### Scope

- Build minimal worker image containing Python and analysis dependencies only.
- Remove API code/config/secret mounts from worker.
- Implement non-root runtime user.
- Configure read-only rootfs/image, cap-drop, no-new-privileges and curated seccomp.
- Add no-new-privileges and no Docker socket policy.
- Keep no network or a scoped test network during this stage.

### Deliverables

1. `Dockerfile.worker` or equivalent build target.
2. Worker entrypoint that reads only a job manifest.
3. Dispatcher container-create/stop/remove implementation.
4. Configuration audit script/tests for live container settings.

### Gate

- CS-1 to CS-7 from the acceptance matrix pass.
- Worker cannot see API code, `.env`, secrets, Docker socket or sibling sessions.
- No production compose changes.

## A1.4.2.3 — Filesystem and Artifact Isolation

### Scope

- Mount each required input read-only under a generated input path.
- Mount generated output directory as the only writable analysis path.
- Implement per-job ephemeral temp.
- Implement parent-side artifact validator.
- Reject path traversal, symlink, non-regular file, wrong type, excessive count/size.
- Copy approved outputs into session/runtime output staging before registration.
- Add stale job/container/directory cleanup handling.

### Deliverables

1. Input/output mount policy.
2. Artifact validator and copy-to-approved-store logic.
3. Cleanup/reaper implementation.
4. Adversarial filesystem/artifact tests.

### Gate

- FS-1 to FS-7 pass.
- T2, T3, T7 and T10 negative tests pass.
- Existing artifact metadata and Evidence paths remain compatible.

## A1.4.2.4 — Network and Secret Isolation

### Scope

- Default deny IPv4 and IPv6 worker egress.
- Add explicit allow-list only for a proven business need.
- Remove all proxy variables from worker environment.
- Audit DNS and service discovery behavior.
- Ensure no API/LLM/DB credentials are present in image, env, job manifest or address space.
- Prefer main-service-mediated external calls.

### Deliverables

1. Worker network policy and compose/runtime configuration.
2. Secret scanning/allow-list tests.
3. IPv4/IPv6/DNS/proxy positive and negative tests.

### Gate

- NET-1 to NET-6 pass.
- T4 and T8 negative tests pass.
- Production worker business functionality remains sufficient without broad egress.

## A1.4.2.5 — Resource and Cancellation Hardening

### Scope

- Enforce CPU, memory, swap, PID, storage, output and log limits.
- Integrate timeout and cancellation with container stop/kill.
- Track all descendants through container PID namespace.
- Make cleanup failures visible.
- Add concurrency ceiling and bounded job queue behavior.
- Test worker/container crash and stale cleanup.

### Deliverables

1. Resource policy wired into dispatcher.
2. Cancellation lifecycle tests.
3. Crash/orphan cleanup tests.
4. Concurrency and scheduler tests.

### Gate

- RC-1 to RC-8 pass.
- T6 and T9 tests pass.
- No orphan worker/container remains after cancellation/timeout.

## A1.4.2.6 — Security Attack Test Suite

### Scope

- Execute all T1-T10 acceptance matrix cases.
- Use isolated Docker Compose project and dedicated test services.
- Include dynamic import/reflection, subprocess, ctypes if available, symlink, path traversal, fork loop, memory pressure, network bypass, secret scan and detached process tests.
- Capture command, expected result, actual result and evidence ID.

### Deliverables

1. Automated security acceptance suite.
2. Evidence report with every matrix row marked PASS/FAIL/NOT RUN.
3. Findings list and remediation decisions.

### Gate

- All planned security cases are executed; every required case passes.
- Any failure is either fixed and retested or the stage is explicitly BLOCKED.

## A1.4.2.7 — Runtime E2E and Rollback

### Scope

- Run V1 and explicitly enabled V2 E2E flows.
- Test CSV, Excel, Parquet and SQLite workflows.
- Verify artifacts, Evidence lineage, reports and user-facing status.
- Test failure, timeout, cancellation, container crash and cleanup.
- Verify rollback/legacy backend and safe drain behavior.
- Confirm `RUNTIME_V2_ENABLED` default is unchanged.

### Deliverables

1. E2E regression report.
2. Rollback procedure and evidence.
3. Performance/startup latency baseline.

### Gate

- RT-1 to RT-7 pass.
- No B11 frozen contract regression.
- Rollback tested before any production enablement discussion.

## A1.4.2.8 — Final Security Review

### Scope

- Re-read threat model against implemented code/config.
- Independently inspect container runtime metadata and test evidence.
- Validate no scope creep into unrelated B11 or dashboard work.
- Reassess P0/P1/P2 residual risks.
- Produce final acceptance with PASS, PASS WITH LIMITATIONS or BLOCKED.

### Deliverables

1. Final implementation review.
2. Updated threat model/residual-risk register.
3. Production readiness decision and rollout constraints.

### Gate

- No unresolved P0/P1 architecture or implementation issue.
- Documentation, code and observed runtime behavior agree.
- Production enablement remains a separate, explicit decision.
