# A1.4.1 Restore Integrity Design

- Design date: 2026-11-19
- Baseline: `e44f3cd` (A1.4.1 baseline audit)
- Target: `AnalysisRuntime` restore, `EvidenceRegistry`, and focused restore tests
- Non-goals: Worker isolation, Docker/network changes, TLS, real-LLM tests, B8/B10/B11 expansion, or V1/V2 rearchitecture

## 1. Trust chain

The restored trust chain is explicit and fail-closed:

```text
runtime state restore
  -> asset metadata validation
  -> file/snapshot content verification
  -> DataAsset trust state
  -> canonical evidence rehydration and revalidation
  -> legacy evidence trust downgrade/revalidation
  -> current report trust
```

A missing check or verification exception results in a non-VERIFIED state. No restoration path treats persisted `verified` alone as current proof.

## 2. DataAsset restore states

The following serializable states are stored under `DataAsset.source_metadata["restore_integrity"]`:

| State | Meaning |
|---|---|
| `VERIFIED` | Expected hash existed, current content was read successfully, stability checks passed, and the recomputed digest matched. |
| `STALE` | Underlying content was readable but did not match the recorded fingerprint. |
| `UNVERIFIABLE` | There was no expected hash, no supported content representation, or the representation cannot prove current integrity. |
| `MISSING` | The referenced file or snapshot did not exist. |
| `VALIDATION_FAILED` | Reference was invalid, read/hash failed, was unstable, or an unexpected verifier exception occurred. |

No new top-level `DataAsset` field is introduced. The metadata payload is backward compatible with old snapshots and new assets:

```json
{
  "status": "VERIFIED",
  "reason": null,
  "algorithm": "sha256:file-stream-v1"
}
```

For non-verified states the reason is a stable, non-localized code and human-readable message is not required. `UNVERIFIABLE` is never mapped to `VERIFIED`.

## 3. Asset verification contract

### File-backed assets

- `location` must be an absolute path and a regular file; otherwise the result is `MISSING` or `VALIDATION_FAILED`.
- `content_hash` must be a present SHA-256 string; absence is `UNVERIFIABLE`.
- Hashing reuses `hash_file()` (streaming SHA-256).
- Before and after reading the stream, file metadata is compared. A size, inode, or nanosecond mtime change during hashing yields `VALIDATION_FAILED`; it is not accepted as a verified read. The metadata check is a stability guard, not a substitute for cryptographic verification.
- `sqlite_database` assets are additionally `UNVERIFIABLE` when `-wal` or `-shm` sidecars exist, because hashing only the main database file cannot represent uncheckpointed state. If no sidecars exist, normal file verification applies.

### Snapshot-backed assets

- `source_metadata.snapshot_reference` is validated with the existing `SnapshotReference` model.
- `SnapshotStore.load()` remains the only loader. It validates snapshot integrity and restores a DataFrame.
- `hash_dataframe(restored)` is compared with `DataAsset.content_hash`. Missing expected hash is `UNVERIFIABLE`.
- Snapshot not-found maps to `MISSING`; snapshot integrity mismatch maps to `STALE`; malformed reference or verifier exceptions map to `VALIDATION_FAILED`.

### Unsupported assets

An asset with neither a file location nor snapshot reference is `UNVERIFIABLE`. Restore does not guess a content identity from source metadata, name, or schema.

## 4. Canonical evidence persistence and restore

`snapshot()` adds a backward-compatible `canonical_evidence` array containing `CanonicalEvidence.model_dump(mode="json")` records. This closes the current loss of registry records across process restore.

`EvidenceRegistry` gains:

- `records()` — a read-only ordering for serialization.
- `restore_record()` — insert one persisted record into the registry with its trust status reset to `unverified`. It does not raise on stale/invalid references; revalidation will record the failure.

Restored canonical evidence is then validated by the existing `AnalysisRuntime.verify_canonical_evidence()` implementation. The content validator is extended to reject evidence that references an asset whose current restore state is not `VERIFIED`. For SQLite evidence, a persisted `source_metadata.content_hash` must match the referenced output asset's current `content_hash`.

Allowed outcomes are only:

- `verified` — all existing registry references and the new asset-trust/content checks pass.
- `failed` — any reference, asset state, content metadata, or content-validator check fails.

No restored record remains implicitly trusted because its JSON said `verified`.

## 5. Legacy evidence trust

`EvidenceItem` has no independently recomputable calculation contract. Therefore:

1. The persisted `verification_status` is never preserved as proof on restore.
2. If any referenced asset is `MISSING`, `STALE`, or `VALIDATION_FAILED`, the evidence becomes `failed`.
3. If any referenced asset is `UNVERIFIABLE`, if source asset IDs are missing/unknown, or there is no recomputable evidence contract, the evidence becomes `unverified`.
4. A legacy record previously marked `failed` remains failed unless current checks could genuinely verify it; current legacy evidence cannot be independently re-verified, so it is never promoted.
5. Each result is recorded as a deterministic `VerificationResult` with `evidence_id`, `check_type="custom"`, and a deterministic verification ID. Re-restoring replaces the previous restore verification record rather than duplicating it.

This downgrading preserves metadata for human inspection while preventing report validators from consuming stale `verified` status.

## 6. Report trust

- Runtime V2 continues to build current reports only from canonical records currently marked `verified`. Failed/downgraded records are excluded.
- `build_verified_report()` appends a limitation note for each current asset in a non-VERIFIED restore state. Historical persisted report text is not rewritten.
- Runtime V1's existing validator sees the downgraded legacy statuses and therefore will not accept unsupported numbers as verified after restore.
- If canonical evidence cannot be restored and verified, no current verified claim is fabricated from an old report string.

## 7. Compatibility and rollback

- The runtime snapshot version remains `2`; the new `canonical_evidence` key is optional on read. Old snapshots restore with canonical registry empty and legacy evidence downgraded.
- `DataAsset` serialization is unchanged except for additive `source_metadata["restore_integrity"]`; existing consumers that ignore metadata remain compatible.
- `EvidenceRegistry.register()` semantics and duplicate handling remain unchanged.
- No API response schema is deliberately changed; additive metadata may appear in detailed runtime payloads.
- Rollback is a code-level revert of this work package. Old snapshots written by the new version restore under the previous implementation because all fields are additive and old fields are unchanged.

## 8. Implementation boundaries

Production changes are limited to:

- `langgraph_langchain/data/assets.py`: stable file hash helper.
- `langgraph_langchain/evidence/registry.py`: record export and restore insertion.
- `langgraph_langchain/runtime/context.py`: restore asset verification, canonical persistence/revalidation, legacy downgrade, report limitation.
- `tests/runtime_v2/test_restore_integrity.py`: restore contract tests.

No changes are made to Docker configuration, network policy, Runtime V2 default flags, or B11 frozen contracts.

## 9. Acceptance gates

The implementation is accepted only when the new restore tests and focused regressions pass, including:

1. Asset integrity tests above.
2. Canonical and legacy evidence trust tests.
3. Existing restore/evidence/runtime regressions.
4. At least one V1 report validation check and one V2 verified-report check.
5. A clean tree with path-scoped commits and no force/amend operations.
