# A1.4.2.2.0 — Docker Worker Readiness Plan (master)

Phase: A1.4.2.2.0 — readiness audit & implementation plan. This document is the master plan; architecture detail lives in `a1.4.2.2-docker-worker-architecture.md`, roadmap in `a1.4.2.2-docker-worker-implementation-roadmap.md`, security in the threat model and acceptance matrix.

## 1. Core Question

Can the A1.4.2.1 Worker Contract / Dispatcher / Backend design support a safe, controlled, verifiable standalone Docker Worker container?

## 2. Answer (audit conclusion)

**Yes, with bounded adaptation inside the new Docker backend — no contract rewrite required.**

- The portable `WorkerJob` (JSON-safe namespace, validated artifact refs, versioned schema) is container-ready as the job protocol.
- The `WorkerBackend` protocol (`execute(job, cancellation) -> WorkerResult`, `cancel`, `health_check`) can host a real container backend without touching V1/V2 or the dispatcher.
- Gaps to close inside the Docker backend (not blockers): real JSON serialization boundary (F1), host-path -> container-path translation for `workspace_dir`/`source_path` (F2), namespace/state continuity policy (F3), container-enforced network/resource limits (F4, resource design).

## 3. Readiness Verdicts

| Component | Verdict |
|---|---|
| `WorkerJob` (base) | CONTAINER_READY (as job envelope; path fields need manager-side translation) |
| `ProcessWorkerJob` | NOT_CONTAINER_READY (process-only; documented as such; excluded from container boundary) |
| `WorkerResult` | CONTAINER_READY |
| `ProcessWorkerResult` | Process-only (namespace_updates); container path returns base `WorkerResult` |
| `WorkerDispatcher` | Ready (contract unchanged; no fallback exists) |
| `ProcessWorkerBackend` | Ready (unchanged, remains default) |
| `DockerWorkerBackend` | NOT_IMPLEMENTED (fail-closed stub; implementation starts at A1.4.2.2.1) |
| Artifact flow | CONTAINER_READY_WITH_ADAPTER (input staging + host-side validation reuse) |
| Cancellation | CONTAINER_READY_WITH_ADAPTER (stop/kill/rm sequence; cgroup-level kill) |

## 4. A1.4.2.2.1 Recommendation

**RECOMMENDED** — proceed to A1.4.2.2.1 (Docker Worker Container Foundation) after user confirmation, with the roadmap phases .1–.7 and the security acceptance matrix as the execution contract.

## 5. Standing Constraints (inherited, still binding)

```text
Process Backend remains the default execution backend.
Docker Backend is not enabled in production.
No Docker production execution path exists today (no production wiring of WORKER_BACKEND).
No Runtime V2 default routing change.
RUNTIME_V2_ENABLED default unchanged.
No silent fallback from Docker to process.
```

## 6. Risks Accepted / Deferred

- Namespace continuity across container jobs: deferred to state-handoff policy decision at A1.4.2.2.2 (stateless-per-job default).
- Kernel-level container escape risk: accepted residual, mitigated by hardening profile + patch cadence; reviewed again at A1.4.2.2.7.
