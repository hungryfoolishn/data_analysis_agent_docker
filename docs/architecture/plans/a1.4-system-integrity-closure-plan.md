## 2. Risk Re-confirmation on Current HEAD

### P0-1: Session Restore Trust Chain

**Code location**: langgraph_langchain/runtime/context.py:2139 _restore()

Current behavior:
`python
restored_assets = {
    item[asset_id]: DataAsset.model_validate(item)

DataAsset JSON is deserialized with stored content_hash without re-computing the actual file hash. Evidence is deserialized with stored erification_status without re-executing the verifier. A file modified between persist and restore would be used silently.

### P1-1: Python Sandbox Regex Bypass

**Code location**: langgraph_langchain/langgraph_agent.py:1072 _DANGEROUS_PATTERNS

The regex blacklist matches os.system, subprocess, val, xec, __import__ etc. Bypassable via getattr(os, chr(115)+chr(121)+chr(115)+chr(116)+chr(101)+chr(109))(...) or importlib.import_module(...).

The IsolatedPythonExecutor (execution/python_executor.py) provides process isolation with os.setsid(), resource.setrlimit, timeout with SIGTERM->SIGKILL. This is process-level isolation, not OS-level sandboxing. Container network namespace is shared with API.

**Affected files**:
- langgraph_langchain/langgraph_agent.py (_DANGEROUS_PATTERNS, run_code)
- langgraph_langchain/execution/python_executor.py (IsolatedPythonExecutor)
- Dockerfile / docker-compose.yml (security config)

## 5. Data Migration Risk

**Session JSON format**: The current .state.json format stores DataAsset as model_dump(mode=json). Adding integrity validation on restore does NOT change the JSON format. Old sessions remain compatible because:
- content_hash field already exists in DataAsset
- verification_status already exists in EvidenceItem
- New validation only ADDS checks, does NOT change serialization

**Risk**: Old sessions with files that have been legitimately modified (e.g., data update) will now FAIL restore validation. Mitigation: provide clear error message and allow re-upload. This is the intended fail-closed behavior.

**Schema version**: No schema change required. Validation is logic added to the restore path.

---

## 6. Compatibility Strategy

1. **Old sessions without content_hash**: DataAsset.content_hash is Optional. If missing on restore, log warning and skip hash check (do not block). This preserves compatibility with very old sessions.

2. **Old Evidence without verification metadata**: EvidenceItem.validation_status defaults to unverified. Restore re-verification will attempt to verify; if it fails, the status is set to failed (not left as verified).

3. **SnapshotStore**: Already has integrity check on load. No change needed.

4. **AssetResolver**: No change needed. The resolver reads DataAsset from RuntimeContext.assets which will have been validated on restore.

5. **tool_load_data.py**: No change needed in A1.4.1. The restore validation happens at RuntimeContext level, not at tool level.
