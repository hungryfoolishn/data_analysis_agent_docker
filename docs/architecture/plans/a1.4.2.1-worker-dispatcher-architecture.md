# A1.4.2.1 — Worker Dispatcher Architecture

## 1. Scope

A1.4.2.1 introduces a unified Worker Job Contract, a Worker Backend interface, and a
`WorkerDispatcher`, and routes both V1 and Runtime V2 Python execution through a
Process Backend. Docker production isolation is explicitly out of scope for this
phase (A1.4.2.2).

## 2. Job Contract (`langgraph_langchain/execution/job_contract.py`)

Core types:

- `ArtifactReference` — validated relative artifact path (rejects absolute paths,
  `..` segments, and empty segments).
- `ArtifactPolicy` — extension allow-list. Default policy permits a broad set of
  analysis file extensions for backward compatibility with existing V1/V2 behavior.
- `WorkerExecutionOptions` — timeout (default 60s, maximum 3600s) and related knobs.
- `WorkerJob` — the portable, serializable, JSON-safe job contract.
- `ProcessWorkerJob` — a process-only compatibility extension of `WorkerJob`.
- `build_process_worker_job(request)` — adapts the existing
  `PythonExecutionRequest` into a process-only job.
- `new_job_id()` — job id generator.

### 2.1 Process-only namespace field

`ProcessWorkerJob.namespace` is deliberately typed `dict[str, Any]`. This is a
process-only compatibility field, not a portable contract field: the current
`IsolatedPythonExecutor` fork model depends on parent-process memory, and V1/V2
namespaces contain modules, classes, closures, and DataFrame objects that cannot be
serialized to JSON. The Docker backend does not accept a process-only namespace.

## 3. Backend Interface (`langgraph_langchain/execution/worker_backend.py`)

Core types:

- `WorkerStatus`, `WorkerErrorCode`, `WorkerError`, `WorkerResult`,
  `ProcessWorkerResult`, `BackendHealth`, `BackendCapabilities`.
- `UnsupportedBackendError`, `BackendUnavailableError`, `CancellationHandle`.
- `WorkerBackend` — abstract interface.
- `ProcessWorkerBackend` — wraps the existing `IsolatedPythonExecutor`; it does not
  reimplement execution.
- `DockerWorkerBackend` — a fail-closed stub.

### 3.1 Process Backend capabilities

```text
supports_cancellation        = true
supports_timeout             = true
supports_network_isolation   = false
supports_filesystem_isolation = false
supports_resource_limits     = false
supports_container_isolation = false
```

The Process Backend is NOT a security sandbox. It preserves the pre-existing
fork-inherited-memory execution model.

### 3.2 Docker Backend stub

The `DockerWorkerBackend` stub is fail-closed:

- It never creates containers and never touches the Docker socket.
- `execute()` / `cancel()` raise `UnsupportedBackendError`.
- `health()` reports `not_implemented`.
- All capabilities are `false`.

## 4. Dispatcher (`langgraph_langchain/execution/worker_dispatcher.py`)

Core types: `WorkerDispatcher`, `WorkerValidationError`, `DuplicateJobError`,
`JobState`; plus `DEFAULT_WORKER_BACKEND = "process"`, `create_worker_backend(name)`,
and `worker_backend_from_env(env)`.

Key behaviors:

- The default backend is `process`. There is no implicit fallback; selecting an
  invalid backend raises, and selecting the Docker backend yields a FAILED result
  with `BACKEND_UNSUPPORTED` rather than a fallback to process.
- In-memory job state machine: `VALIDATING -> QUEUED -> RUNNING -> final`.
- Duplicate submission of an active job id raises `DuplicateJobError`.
- `cancel()` is idempotent; cancellation before dispatch returns CANCELLED.
- A backend result whose `job_id` mismatches is converted to FAILED + `INTERNAL`.
- Cancellation arriving after completion does not rewrite a succeeded result to
  cancelled. This preserves the A1.3 race contract: the task may remain succeeded
  while the overall runtime is marked cancelled by the upper layer.

## 5. Runtime Integration

- Runtime V2: `PythonTaskExecutor` now routes through
  `WorkerDispatcher(ProcessWorkerBackend())` by default. Explicit injection of a
  legacy executor preserves the old raw path as a compatibility path. Artifacts are
  read via `getattr(result, "raw_artifacts", [])` because pre-dispatch cancellation
  returns a plain `WorkerResult` without the `raw_artifacts` property.
- V1: `_Session.run_code` constructs a `PythonExecutionRequest`, builds a
  process-only job, dispatches it, applies `ProcessWorkerResult.namespace_updates`,
  and preserves the original timeout / cancelled / failed output semantics.

Runtime V2 default routing (`RUNTIME_V2_ENABLED`) is unchanged.

### 5.1 Current call chains

```text
V1: api_server_langgraph.py
  -> langgraph_agent.py (RuntimeSelectionPolicy -> V1 ReAct)
  -> tool_python_repl.py
  -> langgraph_agent.py _Session.run_code
  -> WorkerDispatcher(ProcessWorkerBackend())
  -> IsolatedPythonExecutor

V2: api_server_langgraph.py
  -> langgraph_agent.py (RuntimeSelectionPolicy -> V2)
  -> _run_runtime_v2_graph_stream
  -> PythonTaskExecutor
  -> WorkerDispatcher(ProcessWorkerBackend())
  -> IsolatedPythonExecutor
```

## 6. Security Boundary Statement

Process Backend remains the default execution backend.

Docker Backend is not enabled in production.

No Docker production execution path was introduced.

No Runtime V2 default routing change was made.

The existing Worker process model is still not a production-grade security sandbox.
Fork-inherited memory and shared namespace risks remain unresolved until the later
container-isolation phase (A1.4.2.2).

## 7. A1.4.2.2 Boundary

A1.4.2.1 completion does NOT mean:

- Docker Worker is implemented.
- Worker has container isolation.
- The Python sandbox security problem is solved.

A1.4.2.2 must implement a real container backend behind `WorkerBackend`, reject the
process-only namespace, and re-run the full cancellation / timeout / artifact /
parity matrix against the container path.
