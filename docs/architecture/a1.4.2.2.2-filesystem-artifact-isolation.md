# A1.4.2.2.2 — Filesystem & Artifact Isolation Architecture

## Outcome

Each Docker Worker job receives a manager-owned, uniquely named filesystem workspace. User code cannot mutate staged inputs through normal paths, publish hidden or unsafe names, escape the output boundary through traversal or symlinks, or retain artifacts after job completion.

## Workspace Layout

```text
/tmp/deepanalyze-worker-jobs/<job_id>/
  manifest.json
  input/
  output/
  tmp/
  collected/
```

The root is created by `ContainerManager.create_workspace`. The manager writes an atomic manifest containing job identity and SHA-256 hashes for staged inputs. Creation is one-shot.

## Identity and Ownership

- Workspace identity is `(manager_root, job_id, manifest)`.
- `cleanup_workspace(job_id)` refuses a missing manifest, mismatched job ID, symlinked root, or path escaping the managed root.
- Cleanup deletes only the managed job root; unrelated workspaces are preserved.

## Input Isolation

- Authorized `job.workspace_dir` paths are joined through `safe_workspace_join`.
- Inputs are copied, not hardlinked, into `input/`.
- Staged input files are mode `0440`, owned by `root:10001`; `input/` is mode `0550`.
- Containers mount `/workspace/input` read-only.
- `verify_input_integrity` re-hashes staged files before output publication.

## Output Isolation

- Containers receive `/workspace/output` writable and use it as working directory.
- `collect_output_files` reads Docker archives and rejects symlink, link, and non-regular-file members.
- `publish_artifacts` is all-or-nothing:
  1. validate names, sizes, hashes, duplicates, and total quota;
  2. write temporary files;
  3. atomically `os.replace` into `collected/`;
  4. roll back temporary paths on any failure.

Published artifacts exclude unsafe names, dotfiles, duplicate names, and mismatched content.

## Worker Entry Point

The worker reads `/workspace/input/job.json`, executes in `/workspace/output`, and sets `TMPDIR=/workspace/tmp` when writable. If the tmp mount is absent or read-only, it degrades to the container temporary directory rather than crashing.

## Backend Flow

`DockerWorkerBackend._execute` performs:

1. create one-shot workspace;
2. stage authorized inputs;
3. execute container;
4. verify input integrity;
5. collect declared output bytes;
6. publish atomically;
7. clean workspace.

A pre-container failure also cleans the job workspace.

## Platform Boundary

- No production default backend change.
- No Runtime API contract change.
- No Evidence or B11 contract change.
- Artifact metadata remains the Worker Result artifact list; there is no parallel Evidence store.
