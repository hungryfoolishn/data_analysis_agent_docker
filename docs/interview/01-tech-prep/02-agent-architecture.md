# 技术资料 2：Agent 架构（岗位核心，重点投入）

## 1. Agent Loop 的本质

剥掉所有框架，Agent = **一个让 LLM 反复"决策 → 调工具 → 看结果"的 while 循环**。所有 Agent 框架（LangGraph、AutoGen、OpenAI Agents SDK）都是给这个循环加了工程化外壳。面试里说清这句话，比背十个框架名词有说服力。

### 主要模式（Anthropic《Building Effective Agents》的分类）

| 模式 | 一句话解释 | 适用场景 |
|---|---|---|
| Prompt chaining | 拆成固定串行步骤，步间可加校验 | 流程可预测（如"先分析→再改→再测"） |
| Routing | 先分类再分流到不同处理链 | 用户意图差异大 |
| Parallelization | 多个子任务并发跑，结果汇总 | 多文件批量分析 |
| Orchestrator-workers | 一个主 Agent 动态拆任务给子 Agent | 复杂任务，Claude Code 的 subagent 就是这个 |
| Evaluator-optimizer | 生成→评估→再生成循环 | 有明确质量标准的场景 |
| ReAct 自由循环 | 模型自己决定调什么工具、调几轮 | **编码 Agent 的主体就是它** |

**要点**：Coding Agent ≠ 纯自由循环。工程上通常是"自由循环为骨架 + 关键节点结构化"（比如：改代码前强制先跑相关测试的编排约束）。

## 2. 上下文工程（Coding Agent 最难的工程问题）

Coding Agent 跑一个真实任务，几十次工具调用后上下文轻松爆掉。处理策略按朴素到精巧排列：

1. **工具结果截断**：grep 结果只回前 N 行，写文件成功只回 "OK"。这是性价比最高的手段——大多数 token 浪费在冗长的工具输出上。
2. **滑动窗口 + 摘要压缩**：超过阈值时，把最早的 N 轮对话用 LLM 压缩成一段摘要（保留：任务目标、已完成的步骤、重要发现、当前卡点），替换原消息。
3. **结构化记忆**：Agent 维护一份 `todo.md` / 计划文件，每步后更新；上下文里始终注入最新计划。Claude Code 的 TodoWrite 工具就是这个思路——**把"状态"外化到文件，而不是依赖对话历史**。
4. **子 Agent 隔离**：把大搜索/大分析任务丢给 subagent，主 Agent 只收回一段结论。子 Agent 的几十轮调用完全不占主上下文。
5. **按需重读**：旧文件内容被截断后，依赖"需要时重新 read_file"——所以工具设计上读文件要便宜。

**必读**：Anthropic 的《Claude Code: Best practices for agentic coding》和官方博客对上下文管理的描述；以及社区对 Claude Code `/compact` 机制的分析文章。

## 3. 拆解 Claude Code / OpenCode（面试前必做）

### Claude Code 值得记住的设计

- **工具集极简且正交**：Read / Write / Edit / Bash / Grep / Glob / WebFetch / TodoWrite / Task(subagent) 等，不到 15 个工具打天下。工具少 = 模型选择成本低的提示词工程难度低。
- **Edit 用"精确旧文本→新文本"而非行号**：避免了"模型数错行号"这一类错误，天然自带并发修改冲突检测。
- **权限分级**：只读工具默认放行，写文件/执行命令需用户确认或配置白名单。
- **Bash 输出截断 + 后台任务**：长输出截断，可转后台。
- **subagent（Task 工具）**：独立上下文跑搜索类任务，只回结论。
- **MCP（Model Context Protocol）**：把"接入外部工具/数据"标准化为协议，第三方 server 声明自己的 tools/resources/prompts。**这是当前工具生态最重要的协议趋势，面试必提**。

## 4. 多 Agent 协作

- **为什么需要**：单 Agent 上下文有限 + 串行慢。子 Agent 并行搜索/并行改不同模块。
- **关键难点**：任务描述要自包含（子 Agent 看不到主对话）；结果要压缩回传；写文件类任务的冲突协调（不同子 Agent 改同一文件会打架）。
- **务实观点**：Coding Agent 的主战场仍是单 Agent + 子 Agent 只做只读任务。面试不要吹"多 Agent 集群"，讲清边界更成熟。

## 5. 框架选型观点（面试会问"你用什么框架"）

| 选项 | 适合 | 我的观点 |
|---|---|---|
| 裸写循环 | 学习、可控性要求高、自定义强 | **demo 必须裸写**，证明懂原理 |
| LangChain | 快速原型、RAG 组件全 | 抽象层多，复杂 Agent 里经常在跟抽象搏斗 |
| LangGraph | 有状态、多步流程、需要 checkpoint | 图编排适合审计要求高的流程 |
| OpenAI Agents SDK / Anthropic SDK 原生 | 生产级、轻量 | 官方 SDK 越来越够用，趋势是"轻框架" |
| 自研薄层 | 长期维护的内部平台 | 内部工具团队最终都会走向自研薄层 + MCP |

**建议口径**：原型用框架快速验证，生产自研薄层（自己控制 loop、上下文、权限），通过 MCP 接入生态。这套观点很符合"内部平台团队"的实际。

## 自查问题参考答案

### 1. 白板写一个支持并行 tool_calls 的 agent loop

```python
def agent_loop(client, model, messages, tools, execute, max_steps=20):
    for _ in range(max_steps):
        resp = client.chat.completions.create(
            model=model, messages=messages, tools=tools)
        msg = resp.choices[0].message
        messages.append(msg.model_dump())
        if not msg.tool_calls:
            return msg.content
        # 并行执行本响应里的所有 tool_calls
        results = execute_parallel(msg.tool_calls, execute)   # 线程池/asyncio
        for tc, result in zip(msg.tool_calls, results):
            messages.append({"role": "tool", "tool_call_id": tc.id, "content": result})
    raise RuntimeError("max steps exceeded")
```

口头补两句才算完整：
- **并行执行要用线程/asyncio**（工具多是 IO 型），但**写操作要串行或加锁**——两个并行 write 改同一个文件会互相覆盖；
- 结果必须按 tool_call_id 一一对应回传，顺序不能乱。

追问"并行有什么风险"时答：文件写冲突、shell 命令相互干扰（并行跑测试可能抢端口）、上下文同时涌入大量结果撞预算。所以务实做法是**只读工具并行、写工具串行**。

### 2. 你的 Agent 上下文爆了，五种压缩策略的适用场景和代价分别是什么？

| 策略 | 适用场景 | 代价/风险 |
|---|---|---|
| 工具结果截断 | 一切场景的第一道防线 | 模型可能错过被截断部分的信息；截断提示语让它知道去缩小范围重查 |
| 滑动窗口 + 摘要压缩 | 长对话、多步任务 | 摘要会丢细节；摘要本身要花一次 LLM 调用（延迟+成本）；关键约束可能被摘要稀释 |
| 结构化记忆（todo/计划文件外化） | 多任务、跨多轮的计划型工作 | 模型要记得更新文件（靠提示词约束）；文件会占上下文（但比原始历史小得多） |
| 子 Agent 隔离 | 大规模搜索/分析，结果可压缩成一段结论 | 任务描述要自包含；子 Agent 上下文传递成本；不适合需要逐步反馈的写操作 |
| 按需重读（旧内容被截后重新读） | 与截断配套的兜底 | 多一轮工具调用（延迟）；要求读文件便宜、工具描述鼓励重读 |

回答框架："没有万能策略，按成本从低到高组合使用；最容易被忽略的是外化状态——把'对话里的记忆'变成'文件里的记忆'。"

### 3. Claude Code 的 Edit 工具为什么用"旧文本匹配"而不是行号？有什么缺点？

为什么：
- 模型数行号不可靠，尤其是 Agent 自己刚改过文件、行号已经漂移之后——行号方案在多轮编辑里错误率会滚雪球；
- "复述要替换的原文"强迫模型先读后改，形成天然的读写一致性校验；
- 唯一性检查（旧文本在文件中出现次数必须为 1）把"改错位置"从静默破坏变成显式报错。

缺点：
- old_text 需要完整复述，大段替换 token 开销比行号大；
- 模型复述不精确（空格/缩进/换行符差异）会报"找不到"，需要重试；
- 需要配套机制：报错信息引导先 read_file、模糊匹配 fallback、或要求带上更多上下文使匹配唯一。

demo 的 `tools.py` 里 `edit_file` 就是这个设计的实现，`count == 0` 和 `count > 1` 两种失败都有明确报错。

### 4. MCP 是什么？解决什么问题？

MCP（Model Context Protocol）是 Anthropic 推的开放协议，把"给 LLM 接入工具和数据"标准化：一个 MCP server 声明自己提供哪些 tools / resources / prompts，任何支持 MCP 的客户端（Claude Code、IDE 等）都能发现并调用，不需要为每个客户端写一遍集成。

解决的核心问题是 **M×N 集成爆炸**：M 个 AI 应用 × N 个数据源/工具，原来要写 M×N 个适配器；有了协议就是 M + N 个实现。

与"直接在代码里注册工具"对比：
- **多了**：跨应用复用（写一次 server，Claude Code / 自研 Agent 都能用）、生态接入（数据库、内部系统的现成 server）、进程隔离与权限边界；
- **少了**：进程内调用的性能（走 JSON-RPC）、细粒度的进程内状态共享、调试简单性。

面试加分口径："内部平台自研 Agent 时，把工具实现收敛成 MCP server 是合理投资——同一个 server 既能接我们的自研工具，也能直接被开发者在 Claude Code 里用，等于工具层顺便开放给了生态。"

### 5. 什么任务适合丢给 subagent？什么不适合？

适合：
- **只读的大搜索**："全库找出所有调用 X 接口的地方并总结模式"——几十轮 grep/read 的调用细节对主任务无价值，只要结论；
- **独立可并行的分析**：多模块并行调研；
- **会产生大量中间输出的验证**：跑全量测试并归因失败用例。

不适合：
- **写操作为主的任务**：subagent 改文件时主 Agent 失去了过程可见性，冲突和错误难协调；多 subagent 改同一文件会互相覆盖；
- **需要与用户反复交互确认的任务**：子 Agent 没有用户的会话上下文；
- **强依赖主对话历史语义的任务**：任务描述必须自包含，如果"自包含"本身要把半本对话史塞进去，成本还不如主 Agent 自己做。

一句话总结："subagent 用来隔离上下文消耗大的只读工作，不用来隔离责任大的写操作。"

### 6. 如果模型反复调用同一个工具陷入循环，你的 Agent 怎么处理？

分层处理：
1. **检测**：记录最近 N 次工具调用（名称+参数 hash），发现同调用连续出现 ≥ 3 次即判定疑似循环；
2. **软干预**：向上下文注入一条系统级提示："你已重复调用同一工具多次且结果相同，请停止重试，改变策略或汇报障碍"——多数循环这样就能打破；
3. **硬保护**：max_steps 上限（demo 里是 30 步）兜底，触顶时优雅退出并汇报已完成的部分，而不是报错崩掉；
4. **根因修复**：循环通常暴露设计问题——工具报错信息不够可操作（模型不知道怎么改参数）、工具描述有歧义、或任务本身不可行（文件根本不存在但模型不信邪）。把高频循环模式记下来，回头改工具层的报错文案，比在循环检测上堆逻辑更治本。

追问"为什么不直接失败退出"：软干预优先，因为很多"循环"其实是模型在修正参数的重试（第二次参数改对了），一刀切退出会误伤自愈过程。
