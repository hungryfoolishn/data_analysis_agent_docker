# 技术资料 4：存量代码重构自动化（职责 3）

## 1. 问题定位：银行存量代码重构难在哪

- **语言老、规模大**：Java 老版本（Java 6/8）、大量存储过程、XML 配置、可能还有 COBOL 遗留。
- **测试基础不均**：核心系统有测试但覆盖率参差；老模块改动"牵一发动全身"。
- **业务逻辑埋在代码里**：没有文档，规则散落在代码和数据库触发器中。
- **不敢动**：金融系统对正确性要求极高，一次大版本重构失败是生产事故。

所以 AI 重构工具的定位不是"自动改完"，而是**"AI 提出方案 + 自动验证 + 人最终决策"的半自动流水线**。面试把这个定位讲对，就是最大的业务成熟度信号。

## 2. 重构流水线设计（背下来，面试直接用）

```
圈定范围 → 理解与规划 → 生成变更 → 静态验证 → 测试验证 → 人工审查 → 灰度合入
```

每一步的关键设计：

1. **圈定范围**：从依赖图出发，先算"影响面"——只圈出直接/间接依赖的模块，禁止越界修改。
2. **理解与规划**：LLM 读代码 + 知识库检索，产出重构方案（改哪些文件、每个文件改成什么样、风险点），方案先给人过目。
3. **生成变更**：小步提交，一次只做一类变换（如"把这个类拆成三个"），禁止混合多个重构意图。
4. **静态验证**：AST diff 确认只改了预期范围、编译通过、lint 通过。
5. **测试验证**：跑受影响模块的单测；没有测试的老模块，**先让 AI 给现状代码补"表征测试"（characterization test），锁定现有行为后再重构**——这是处理无测试遗留代码的标准打法。
6. **人工审查**：AI 生成结构化 diff 说明（为什么改、改了什么、验证结果），人审查后合入。
7. **灰度合入**：先改一个非核心模块跑通全流程，建立信心后扩大。

## 3. 变更生成的技术路线

| 路线 | 做法 | 适用 |
|---|---|---|
| 确定性 codemod | 用 AST 变换脚本做机械变换（如 API 改名） | 变换规则完全明确，**优先用，别用 LLM** |
| LLM + AST 定位 | tree-sitter 定位目标代码块 → LLM 重写该块 → AST 校验结构合法 → 原位替换 | 语义性重构（拆方法、改设计模式） |
| 纯 LLM 生成整文件 | 模型重写整个文件 | 大文件易丢内容，不推荐，仅小文件 |

**核心原则：能用确定性代码做的不要用 LLM，LLM 只负责语义决策。** AST 校验是安全网：LLM 输出的代码先 parse 成功、再和原代码 diff，异常就打回重试。

## 4. 验证闭环（面试必问"怎么证明没改坏"）

分层验证，从便宜到贵：

1. **语法/结构**：AST parse 通过、diff 范围符合预期。
2. **编译**：Java 项目 javac / mvn compile。
3. **静态分析**：SpotBugs、SonarQube（银行一般都有现成接入）。
4. **测试**：单测 → 集成测试；覆盖率变化报告（重构后覆盖率不应下降）。
5. **行为等价性**：表征测试 + 关键路径回归；更进一步可以对老新代码做**差分测试**（同一输入跑两版对比输出）——金融计算场景特别适用（对账、计息逻辑重构时用新旧双跑比对）。
6. **可观测兜底**：灰度上线后对比新旧版本的业务指标（如计算结果分布）。

## 5. 大规模批量变更策略

- **金丝雀顺序**：1 个文件 → 1 个模块 → 1 个子系统，每级稳定后再扩大。
- **自动化工作流**：批量任务拆成工单队列，每个工单 = 一处变更 + 自动验证 + 人工审批，失败自动隔离不阻塞队列。
- **回滚**：每步独立 git commit，出问题 revert 单个 commit。
- **进度可观测**：批量重构的看板（完成率、失败原因分布、人工审查积压）——内部工具的用户是领导 + 开发者，看板决定项目能不能继续拿资源。

## 6. 和职责 2（落档）的协同

重构前用知识库评估影响面，重构过程中产生的"新结构、新接口"自动回流知识库——**重构和落档是一体两面**：落档让重构安全，重构让落档保持新鲜。面试把这两个职责串起来讲，展示系统性思考。

## 7. 学习资源

- 《Working Effectively with Legacy Code》（Michael Feathers）——表征测试、接缝（seam）概念，存量代码圣经
- 《Refactoring》（Martin Fowler）——重构手法分类，LLM 重构提示词可以直接引用这些"手法"作为任务模板
- OpenRewrite（大规模 Java 重构的开源框架，银行 Java 场景高度相关）: https://docs.openrewrite.org/
- JetBrains 的结构化搜索替换、Google 的 Tricorder 大规模静态分析论文（了解大规模变更的工程实践）

## 自查问题参考答案

### 1. 没有 Git 历史文档、没有测试的老模块，你的重构第一步是什么？

**第一步是补表征测试（characterization test），锁定现状行为**，而不是急着改代码：
- 给现状代码写测试，**期望值由实际运行结果生成**（"它现在输出什么就断言什么"），包括看起来像 bug 的行为——因为下游可能已经依赖了这个行为；
- 补不上测试的路径（依赖外部系统），先建测试替身（mock/stub）或用差分记录（录制真实输入输出）；
- 表征测试绿了才有重构的"安全网"。

同时做两件事：用知识库/依赖图圈出模块的影响面（谁依赖它）；和业务方确认哪些行为是"故意的"哪些是"已知 bug 可以修"——**"修 bug"和"重构"绝不能混在一次变更里**，否则测试失败时无法归因。

这个答案的出处是《Working Effectively with Legacy Code》，面试说出书名增加可信度。

### 2. LLM 重写了一个方法，你做哪几层检查才敢替换进源码？

从便宜到贵的五层，全过才落盘：
1. **AST 层**：新代码能被 tree-sitter/编译器 parse（拦截语法错误）；AST diff 确认方法签名按预期变化、没有意外增删其他节点；
2. **范围层**：文本 diff 只落在本方法边界内，没有"顺手"改到别的代码；
3. **语义静态层**：编译通过 + 静态分析无新增告警（空指针、资源泄漏类）；
4. **测试层**：该方法的表征测试 + 所在模块单测通过；覆盖率不降；
5. **审查层**：结构化 diff 说明（为什么改、风险点）给人过目——工具输出"可审查的变更"而不是"黑盒替换"。

任何一层失败 → 错误信息回传给 LLM 重试（限次数），仍失败则该工单隔离转人工。核心原则：**验证是确定性代码做的，LLM 的"我觉得没问题"不算数**。

### 3. 什么场景必须用确定性 codemod 而不是 LLM？举两个例子。

判据：**变换规则可以完全形式化时，用 codemod——便宜、100% 一致、可重放**。例子：

1. **API 迁移改名**：`OldClient.query()` → `NewClient.search()`，200 个调用点。tree-sitter 找到所有调用节点 → 机械替换 → AST 校验。LLM 做这事反而危险：它会"聪明地"顺手改参数顺序或重新格式化，制造不必要的 diff 噪音。
2. **日志框架替换**：log4j 的 `logger.info("x" + var)` → slf4j 占位符 `logger.info("x {}", var)`。模式固定（字符串拼接 → 占位符），纯语法变换。

反例（必须 LLM）：拆分 500 行的上帝方法、把回调风格改成响应式风格——变换规则写不出来，需要语义理解。

中间态（混合）：LLM 生成变换规则/草稿，codemod 引擎执行批量替换——"LLM 出主意，确定性代码动手"。

### 4. 批量重构 200 个文件的 API 迁移，怎么设计流程保证安全和进度可视？

**流程设计（工单队列模式）**：
1. codemod 预处理：机械可判定的调用点直接批量替换（占大头）；
2. LLM 处理剩余复杂点：每个文件/调用点 = 一个工单；
3. 每个工单独立流水线：生成变更 → AST/编译/测试验证 → **独立 git commit**（信息里带工单号和验证结果摘要）→ 人工审批入主干；
4. 失败自动隔离：验证不过的工单标红挂起，**不阻塞队列**，人工介入后重跑。

**安全设计**：
- 金丝雀顺序：先 1 个非核心文件 → 1 个低风险模块 → 全量，每级观察后再扩大；
- 单 commit 粒度 = 单工单，出问题 `git revert` 单个提交，不牵连已完成部分；
- 全程审计日志：谁、何时、哪个工单、验证结果、审批人——银行合规刚需。

**进度可视**：
- 看板四列：待处理 / 已完成 / 验证失败 / 人工待审，实时统计各列数量和占比；
- 汇报层指标：完成率、自动通过率（衡量变换规则成熟度）、失败原因 Top5（指导下一步优化）、预计剩余工时（按当前吞吐线性外推）；
- 这块别小看：**内部工具项目能不能继续拿资源，取决于领导能不能一眼看懂进度和风险**。

### 5. 金融计算逻辑重构，除了单测还能用什么手段验证等价性？

- **差分测试（新旧双跑比对）**：同一批真实输入（脱敏后的历史交易数据）分别跑新旧实现，逐笔比对输出。金融场景特别适用因为：输入输出是结构化数字、历史数据天然是现成测试集、容差可配置（浮点比较定精度阈值，如对账分差 ≤ 0.01 元）。
- **影子运行（shadow run）**：新逻辑在旁路挂一段时间，真实流量同时进新旧两版，只记录不生效，比对生产数据的持续一致性——比离线差分更接近真实分布。
- **统计校验**：全量对账（金额合计、笔数、按维度的分布）新旧两版必须一致；单个用例一致但合计不一致能暴露数据依赖类 bug。
- **性质测试（property-based testing，hypothesis 库）**：不写具体用例，而是断言数学性质——如"计息函数对任意本金满足单调性""拆分-合并等价性"，自动生成上千组输入验证。
- **回归期对账兜底**：灰度上线后新旧并行出账 N 天，用现有对账体系日常校验。

面试要点：先说差分测试这个主力手段，再补影子运行和统计校验展示深度，最后点一句"金融场景的优势是历史数据即测试集"。
