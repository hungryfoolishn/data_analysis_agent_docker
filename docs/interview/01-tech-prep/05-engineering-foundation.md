# 技术资料 5：工程底座（容易被忽视但必问）

## 1. Python 工程能力（岗位硬要求）

### 必须熟练

- **asyncio**：Agent 要并发跑多个工具调用（并行读文件、并发 subagent）。核心概念：event loop、`asyncio.gather`、`Semaphore` 限流、`asyncio.wait_for` 超时。知道什么时候**不用** async（CPU 密集的 AST 解析用进程池 `ProcessPoolExecutor`）。
- **类型注解**：全量 type hints + `mypy`/`pyright` 检查。工具层的 JSON Schema 和 Pydantic 模型是主要接口契约，Pydantic 必须会用（tool 参数校验、配置管理）。
- **测试**：pytest + fixture；LLM 应用特有测试方式见下节。
- **打包与工程化**：pyproject.toml、uv（新一代包管理，面试提加分）、pre-commit（ruff + mypy + pytest）。

### LLM 应用的测试策略（面试亮点）

| 层 | 测什么 | 方法 |
|---|---|---|
| 工具层 | 工具本身正确性 | 纯单元测试，不涉及 LLM |
| 循环层 | agent loop 逻辑 | **mock LLM 返回预置的 tool_calls 序列**，验证流程正确 |
| 端到端 | 真实任务完成率 | 小型 evals 集：几十个任务 + 期望结果，跑分 |
| 质量回归 | 换模型/改 prompt 后有没有变差 | evals 基线对比 |

**关键词 evals**：Anthropic、OpenAI 都强调"Agent 开发=开发+评测闭环"。面试说出"我们给 Agent 建了任务级评测集，改 prompt 跑基线对比"，立刻与 90% 候选人拉开差距。

## 2. 沙箱与安全（银行背景必考）

### 为什么关键

Agent 会执行模型生成的代码和 shell 命令、读内部代码库。银行环境数据敏感、合规要求高（等保、数据不出域）。

### 防护分层

1. **权限分级**：只读工具放行；写文件、执行命令需确认或白名单（Claude Code 的 allowlist 模式）。
2. **路径限制**：所有文件操作限制在工作目录内，符号链接逃逸要防（`resolve()` 后校验前缀）。
3. **命令执行隔离**：
   - 容器方案：Docker 容器内执行、只读挂载源码、输出回传（生产标准做法）；
   - Windows 环境可用受限用户 + Job Object；预算充裕直接上 **microVM（Firecracker）**；
   - 网络隔离：执行环境默认断网或只允许代理出口。
4. **数据安全**：代码发给外部 LLM API = 数据出域。银行内网方案必须支持私有化模型（vLLM 部署 Qwen/DeepSeek）或经审批的专有云。**面试主动提"数据不出域"和 vLLM，证明理解银行合规。**
5. **审计**：所有工具调用留痕（谁、何时、执行了什么、结果摘要），可回放——银行审计刚需。

## 3. 可观测性与成本

- **Trace**：每次会话完整记录消息流、工具调用、token 用量。可用 Langfuse（开源、可私有化）或自建。排障和审计都靠它。
- **Token 成本统计**：按团队/项目聚合成本，内部平台要向领导证明 ROI——**成本看板和效率提升报告是这类团队的存在价值证明**。
- **缓存**：prompt caching（Anthropic/OpenAI 支持）缓存系统提示词 + 长文件，成本可降数倍；本地 embedding 结果持久化避免重复计算。

## 4. 模型私有化部署（内网场景常识）

- **vLLM**：主流推理框架，OpenAI 兼容 API，`pip install vllm` 起服务，Agent 代码无感切换。
- 量化：AWQ/GPTQ，单卡跑 32B 级别模型。
- Tool calling 支持：部署时确认模型模板支持 function calling（Qwen 系列支持好）。
- 取舍：本地模型能力弱于 Claude/GPT 旗舰 → 工具设计和上下文工程要更"喂到嘴边"（更清晰的工具描述、更小的任务粒度）。

## 5. 文档处理（落档的输入源）

存量资产不止代码：需求文档、设计文档（Word/PDF）、数据库设计（DDL）、接口文档。落档工具要能统一解析：

- `python-docx` / `pdfplumber` / `unstructured`（一站式解析 Word/PDF/HTML）
- 表格类：`openpyxl`
- 解析后统一转 Markdown 入知识库，保留标题层级方便切块

## 自查问题参考答案

### 1. mock LLM 写一个 agent loop 的单元测试，怎么设计？

核心思路：**把 LLM 客户端 mock 成"按剧本返回响应的演员"**，让循环逻辑变成确定性测试。demo 的 `test_agent_loop.py` 就是完整实现，设计要素：

1. **假客户端对象**：接口对齐 `openai.OpenAI`（`client.chat.completions.create(...)`），`create` 每次被调用就从预置剧本里 pop 一个响应——剧本是 `FakeMessage(content=..., tool_calls=[...])` 序列；
2. **FakeToolCall**：构造带 `id` 和 `function.name/arguments` 的对象，模拟模型要调用某工具；
3. **断言重点**（测的是工程逻辑，不是模型智能）：
   - 工具结果以 `role=tool` 且 `tool_call_id` 正确回传；
   - 工具执行异常被转为错误消息回传而不是抛出（自愈路径）；
   - 无效工具名返回"无效调用"错误；
   - `confirm` 拒绝后写入不落盘（权限路径）；
   - 达到 `max_steps` 优雅退出。
4. **confirm 也 mock**（自动放行/一律拒绝两种），让权限逻辑可测。

边界说清：mock 测试保证**工程正确性**，模型行为质量交给 evals（见第 5 题）——两层各管一段，面试把这层边界说清楚是亮点。

### 2. Agent 生成的代码要执行，你的隔离方案分几层？

纵深防御五层：
1. **静态层**：执行前先过 AST parse 和静态检查，明显恶意的模式（网络外发、删除操作）模式匹配拦截；
2. **进程层**：最小权限用户运行、资源限额（CPU/内存/时长），demo 的 `run_shell` 有超时即最简版；
3. **容器层（生产标准）**：Docker 容器执行，源码只读挂载，输出目录白名单可写，网络默认断开或只允许代理出口；
4. **数据层**：容器内无凭证、无数据库连接串；需要查库时通过受控的中间服务代理，且带行级权限；
5. **审计层**：所有执行留痕（命令、输入输出摘要、触发会话），可回放可追责。

面试要点：先承认"demo 用人工确认兜底"，再给生产五层——展示你分得清 demo 级和生产级的差距，这比吹自己 demo 多安全更成熟。

### 3. 为什么银行内网要用 vLLM？部署 Qwen 时要注意什么？

为什么 vLLM：
- **OpenAI 兼容 API**：`client = OpenAI(base_url="http://内网vllm:8000/v1")`，Agent 代码从云端 API 切到内网 vLLM 一行不用改——这对"代码不能出域"的银行是关键工程价值；
- 吞吐优化成熟：PagedAttention、continuous batching、张量并行，多人共用一台推理机时吞吐比裸 transformers 高数倍；
- 量化支持（AWQ/GPTQ）让单卡跑 32B 级模型成为可能。

部署 Qwen 要注意：
- **function calling 模板**：启动 vLLM 时 `--enable-auto-tool-choice --tool-call-parser hermes`（按模型文档选 parser），不配对 tool calling 会静默降级成文本输出——部署后必须用一个 tool calling 冒烟用例实测；
- 上下文长度配置：`--max-model-len` 要按 Agent 场景开够（32K 起步），并确认显存装得下 KV cache；
- 量化取舍：AWQ 32B 大多数编码任务可用，但复杂重构推理会弱于全精度，关键场景留全精度实例；
- 版本匹配：vLLM 版本要支持所选 Qwen 版本的架构，别用太老的 vLLM。

### 4. 怎么向领导证明这个工具团队的 ROI？说出至少三个指标。

指标（至少备齐五个，面试说三个）：
1. **采纳率**：AI 建议被开发者接受的比率（代码补全采纳率、Agent 方案采纳率）——最直接的"工具有没有用"信号；
2. **任务一次完成率**：交给 Agent 的任务中不需要人工返工的比例——质量信号；
3. **节省工时**：抽样任务人工基线耗时 vs 工具辅助耗时（如"存量接口文档化：人工 2 天/模块 → 工具 2 小时/模块 + 1 小时审核"），换算成 FTE 成本；
4. **token 成本趋势**：单位任务成本随优化的下降曲线——证明团队在收敛成本而非烧钱；
5. **留存信号**：AI 参与的代码"活过一周"的比例——防"采纳率虚高"（开发者用了但随后全删）。

呈现方式比指标本身更重要：
- 用**团队/项目维度聚合的看板**持续展示，而不是一次性 PPT；
- 讲**具体故事**："上周 X 项目核心系统迁移，工具完成了 60% 的机械改动，省了约 15 人天"——一个故事胜过十张图；
- 定期（季度）报告效率基线变化，把工具价值锚定在业务交付提速上。

### 5. evals 是什么？给 coding agent 建 evals 集大概包含什么？

evals = 把"模型/Agent 的效果"变成**可重复跑分的评测集**，让每次改 prompt、换模型、改工具设计后都能客观对比有没有变差——Agent 开发的"单元测试 + 回归基线"。

coding agent 的 evals 集包含：
1. **任务集**：50-100 个真实场景任务，按类型分层——bug 修复（给定失败测试，修到通过）、功能新增（在指定模块加函数并过测）、代码解释/落档（生成的文档要点对照人工标注）、重构（行为等价验证）。来源：真实使用日志脱敏入库，避免人工造题失真；
2. **期望产物与判定器**：每个任务带自动判定脚本——代码类跑测试断言（最客观）、文档类关键词/要点覆盖检查、交互类用规则判断（如"是否触发了确认"）；
3. **执行环境**：容器化的沙箱项目（受控的代码库副本 + 测试套件），跑分可并发可复现；
4. **基线与报告**：每个模型/prompt 版本的分数记录，对比报告自动生成（总分 + 分类型得分 + 失败案例归因）；
5. **防污染**：任务定期轮换补充（防止版本迭代过拟合到固定题目）。

面试加分句："demo 阶段可以没有 evals，但生产第一优先级就是建它——没有 evals 的 Agent 迭代是凭感觉开车。我的 demo 里 `test_agent_loop.py` 是工程层的 mock 测试，evals 是它上面的质量层，两层互补。"
