# 设计决策文档：为什么这么设计

> 面试场景演练文档。每个决策按"决策 → 为什么 → 代价/取舍 → 追问预演"组织。
> 能对每一条脱稿讲 2 分钟，这份 demo 就完成了使命。

---

## 决策 1：手写 Agent Loop，不用 LangChain / LangGraph

**决策**：核心循环是 `agent.py` 里约 60 行的 for 循环。

**为什么**：
- Agent Loop 的本质就是"LLM 决策 → 执行工具 → 结果回传 → 再决策"，写出来才能证明真懂原理；用框架封装等于把这个考察点藏起来了。
- 编码 Agent 需要精细控制：工具执行顺序、上下文压缩时机、权限确认时机、步数上限。框架的抽象层反而碍事（LangChain 的复杂 Agent 常见"和抽象搏斗"的体验）。
- 面试语境下：内部工具团队最终都会走向自研薄层 + MCP，裸写能力是招聘硬需求。

**取舍/代价**：失去框架的开箱即用（重试、回调、可观测性要自己搭）。demo 里我留了 hook 机制（`agent.on("on_tool", ...)`）作为可观测性的最小实现，生产版会换成 OpenTelemetry trace。

**追问预演**：
- "那生产环境你会用框架吗？" → 答：原型期用框架快速验证选型，确定架构后自研薄层，工具接入走 MCP。理由是编码工具的生命周期长，框架版本迭代风险不可控。
- "你说的循环和 LangGraph 的图编排什么关系？" → LangGraph 把循环拓扑显式化为图，适合流程确定、要 checkpoint 审计的场景；编码 Agent 主体是模型自由决策，硬套图反而别扭，但"改前先测"这类强约束可以用图表达。

## 决策 2：工具集 6 个，极简正交

**决策**：list_dir / read_file / write_file / edit_file / run_shell / grep，就这 6 个。

**为什么**：
- 每个工具都是模型的选择点，工具越多，选错的概率越高，工具描述的提示词工程成本越高。Claude Code 也是十几个工具打天下。
- 这 6 个覆盖了读（list/read/grep）写（write/edit）执行（shell）三类，正交不重叠。
- 刻意**没有**做的：专门的知识库检索工具（demo 规模 grep 足够；生产版会加 MCP 形式的 code search tool）、git 工具（shell 里跑 `git` 命令即可，没必要单独封装）。

**取舍/代价**：能力上限受限（没有 LSP 精确跳转、没有 AST 工具）。这是"规模决定能力"的取舍：demo 和单人使用场景下 6 个够；接入百万行 Java 库时必须加符号检索和依赖图工具。

**追问预演**："如果加第 7 个工具你加什么？" → "AST 查询工具（列出某类的所有方法/找调用点），因为 grep 对结构性问题无能为力，比如'找出所有没写单测的 public 方法'。"

## 决策 3：路径安全——所有文件操作限制在 workdir 内

**为什么**：LLM 不可信任。模型可能生成 `../../../etc/passwd` 这样的路径（未必是恶意，可能就是幻觉）。`tools.py` 的 `_safe_path` 用 `resolve()` 解析真实路径后校验前缀，同时防住了符号链接逃逸。

**为什么这么较真**：面试的公司是银行背景。数据边界是这类内部工具能否立项的前提——"Agent 只能看授权目录"必须是硬约束而不是软提示。系统提示词里写"不要访问工作目录外的文件"是**提示层防护，必须叠加代码层强制**，两层缺一不可。

**追问预演**："run_shell 能执行任意命令，路径限制不就形同虚设？" → 承认这是 demo 的已知边界：shell 是最大攻击面。生产方案：容器执行（只读挂载 + 网络隔离）、命令黑/白名单、敏感命令（git push、curl 外发）强制审批。demo 用人工确认兜底。

## 决策 4：edit_file 用"精确旧文本替换"，不用行号

**为什么**：对齐 Claude Code 的 Edit 设计。模型数行号经常出错（尤其是自己刚改过文件、行号已漂移之后），而"复述要替换的原文"会强迫模型先读再改，形成天然的读写一致校验。同时 `count != 1` 的唯一性检查把"改错位置"直接变成报错而不是静默破坏。

**取舍/代价**：大段替换时 old_text 要完整复述，token 开销比行号大；模型复述不精确时报"old_text 未找到"，需要重试。缓解：系统提示词强制"修改前先 read_file"，报错信息明确引导（"请先用 read_file 获取精确原文"）。

**追问预演**："频繁报 old_text 找不到怎么办？" → "第一，报错信息里做模糊匹配提示（找出最相似的行段帮助模型定位）；第二，重试 2 次仍失败就要求模型换 write_file 整写；第三，观察失败率，如果特定文件编码/换行符问题就做归一化预处理。"

## 决策 5：上下文三级压缩，而不是一上来就摘要

**为什么**：压缩策略要按成本从低到高启用——截断旧工具输出几乎零成本且收益最大（大部分 token 浪费在冗长工具输出）；LLM 摘要每次都跑又慢又花钱还可能丢关键细节。所以 `context_manager.py` 的顺序是：① 工具结果入库前截断（tools.py 第一道）→ ② 超预算先截旧工具结果 → ③ 压缩最早任务描述 → ④ 保底丢弃中间消息。

**关键取舍**：demo 用规则版摘要（截断保头尾），生产版第 ③ 级应换成 LLM 摘要（保留任务目标、已完成步骤、当前卡点），并外化 `todo.md`——把状态放文件里比放对话里可靠。

**追问预演**："压缩把模型刚写的代码计划压没了怎么办？" → "两个防御：一是压缩永远保留最近 6 条消息（KEEP_RECENT），正在进行的工作不会被压；二是关键决策应该外化到 todo/计划文件，压缩只伤对话历史不伤工作产物。这也是为什么 Claude Code 有 TodoWrite 工具。"

## 决策 6：token 估算用启发式而不是精确 tokenizer

**为什么**：压缩决策只需要"量级正确"（比如 20K 预算在 22K 时触发），启发式（CJK 1 字 1 token + 其他 4 字符 1 token）误差 ±20% 完全够用，且省掉 tiktoken 依赖和与具体模型 tokenizer 绑定的问题——银行场景模型可能是 DeepSeek 也可能是本地 Qwen，tokenizer 各不相同，**估算反而比精确更可移植**。

**取舍**：预算值本身要留 20% 余量补偿估算误差（demo 的 24K 预算对应 32K 上下文模型）。

## 决策 7：工具执行异常不中断循环，回传给模型自愈

**为什么**：`agent.py` 里工具异常被捕获后转成 JSON error 回传。Agent 的健壮性恰恰体现在错误恢复：文件不存在 → 模型改用 grep 找正确文件名；测试失败 → 模型读错误输出修代码。直接 raise 会让一次可自愈的失败变成整个任务中断。

**边界**：这也依赖系统提示词里的守则 4（"工具报错先修正参数重试，不要盲目重试"）来防模型陷入"同一错误无限重试"。配合 max_steps 硬上限双保险。

## 决策 8：危险操作人工确认（confirm 回调注入）

**为什么**：写文件、编辑、执行 shell 前回调 `terminal_confirm`。设计成**注入的回调**而非硬编码终端交互，是为了：a) 单元测试可以注入自动放行的 confirm；b) 生产版可以换成 Web UI 弹窗或审批服务，Agent 逻辑零改动。这体现了工具层对"人机协同模式"的可替换设计。

**追问预演**："每次都确认太烦，效率呢？" → "确认策略分级：读操作免确认；写工作目录内文件白名单免确认；shell 按命令前缀白名单（pytest/git status 免确认，rm/curl 必确认）；风险操作永远人工。这是 Claude Code allowlist 的同款思路。"

## 决策 9：测试策略——mock LLM 验证循环逻辑

**为什么**：见 `test_agent_loop.py`。Agent 的单元测试难点是 LLM 不可预测，所以把 LLM mock 成"预置 tool_calls 序列的脚本"，就能确定性验证：工具被正确调用、参数正确传递、错误结果正确回传、最终回答正常返回。端到端质量交给 evals 任务集（当前任务 + 期望产出 + 自动判定），demo 规模没建 evals 集，但这是生产第一优先级。

**追问预演**："mock 测试覆盖不了模型行为变化，怎么评估？" → "对，mock 只保工程正确性，模型质量要靠 evals：攒几十个真实任务（修 bug、加函数、写文档），自动跑分（文件 diff 是否符合预期、测试是否通过），换模型/改 prompt 后跑基线对比防回归。"

## 决策 10：温度 0.2 + max_steps 30

**为什么**：编码任务要求可复现和稳定，低温减少"自由发挥"；max_steps 防失控——失控的 Agent 循环烧的是真金白银的 token（曾有社区案例单任务烧掉几十美元），硬上限是底线保护。达上限时优雅退出并汇报进度，而不是报错崩掉。
