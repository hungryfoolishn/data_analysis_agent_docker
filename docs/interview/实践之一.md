我建议把 Codebase Understanding（代码库理解） 当成智能代码生成 Agent 的一个独立核心子系统来设计，而不是简单地理解为「给 AI 配一个代码搜索工具」。

它实际上解决一个非常关键的问题：

> 当用户提出一个修改需求时，AI 如何在一个陌生、复杂、可能有几十万行代码的项目中，准确找到相关代码，理解代码之间的关系，判断修改影响范围，并为后续代码生成提供可靠的上下文？

例如：

用户提出：

> 在用户登录功能中增加失败次数限制，连续失败 5 次锁定账户。

一个普通代码生成 AI 可能直接搜索 `login`，找到一个函数就开始修改。

一个具备 Codebase Understanding 能力的 Agent，应该先回答：

1. 登录入口在哪里？
2. 登录业务逻辑在哪里？
3. 用户模型在哪里？
4. 密码验证逻辑在哪里？
5. 登录失败次数是否已经存在？
6. 数据库如何更新用户状态？
7. 哪些 API 调用了登录功能？
8. 哪些测试需要同步修改？
9. 修改登录逻辑会影响哪些其他功能？

这就是代码库理解系统需要完成的事情。

下面给出一套可以真正落地的设计方案。

# 一、先确定 Codebase Understanding 的整体架构

我建议分成六个核心模块。

## Codebase Understanding 架构

① Repository Scanner

项目扫描、文件发现、语言识别、目录结构

② Code Parser

Tree-sitter / AST / 符号提取

③ Symbol & Relationship Index

函数、类、变量、引用、调用、依赖关系

④ Code Retrieval

文本搜索、符号搜索、语义搜索、关系检索

⑤ Context Builder

上下文组装、相关代码选择、Token 预算

⑥ Impact Analyzer

修改影响分析、依赖分析、测试关联、风险评估

输出：Repository Context

提供给 Planner、Code Generator、Validator 使用

注意：这是逻辑架构，不意味着必须部署六个独立服务。初期完全可以实现为一个 Python Package。

# 二、六个模块具体怎么做？

## M1：Repository Scanner —— 项目扫描

第一步实施

首先需要让 Agent 知道项目里有什么。

假设用户提供一个 Git 仓库：

```
my-project/
├── app/
│   ├── main.py
│   ├── auth/
│   │   ├── login.py
│   │   └── user.py
│   ├── database/
│   │   └── models.py
│   └── services/
│       └── auth_service.py
├── tests/
│   ├── test_login.py
│   └── test_user.py
├── requirements.txt
└── README.md
```

Scanner 需要收集：

| 信息      | 示例                   |
| ------- | -------------------- |
| 文件路径    | app/auth/login.py    |
| 文件类型    | Python               |
| 文件大小    | 10KB                 |
| 所属目录    | app/auth             |
| 是否测试文件  | False                |
| 是否配置文件  | False                |
| Git 状态  | Modified / Untracked |
| 文件 Hash | SHA256               |

建议同时识别：

- 编程语言
- 项目框架
- 包管理器
- 项目入口
- 测试框架
- 配置文件
- Git 仓库状态

技术选型：

- `os.scandir` / `pathlib`：文件扫描。
- `pathspec`：处理 `.gitignore` 规则。
- `gitpython` 或 Git CLI：获取 Git 信息。
- `ripgrep`：快速文本检索。

这里有一个重要原则：

不要把所有文件都扫描进代码索引。

例如：

```
排除：
.git/
.venv/
node_modules/
__pycache__/
dist/
build/
```

对于 PDF、图片、二进制文件，也不应该作为源代码解析。

M1 的输出：Repository Manifest。

它是整个代码理解系统的基础资产。

## M2：Code Parser —— 代码结构解析

这是之前讨论的 Tree-sitter 和 AST 的实际应用。

扫描完文件后，需要理解每个文件的结构。

例如：

```
# auth_service.pyclass AuthService:    def login(self, username, password):        user = self.get_user(username)        if user is None:            return False        return self.verify_password(user, password)    def get_user(self, username):        pass    def verify_password(self, user, password):        pass
```

解析之后，得到：

```
File: auth_service.py

Class:
  AuthService

Methods:
  login(username, password)
  get_user(username)
  verify_password(user, password)
```

每个符号都应该有自己的唯一 ID。

例如：

```
{
  "symbol_id": "sym_001",
  "name": "login",
  "qualified_name": "AuthService.login",
  "symbol_type": "method",
  "file_path": "auth_service.py",
  "start_line": 5,
  "end_line": 12,
  "parameters": [
    "username",
    "password"
  ]
}
```

建议建立统一的符号类型：

| Symbol 类型 | 说明 |
| --------- | -- |
| Module    | 模块 |
| Class     | 类  |
| Function  | 函数 |
| Method    | 方法 |
| Variable  | 变量 |
| Import    | 导入 |
| Constant  | 常量 |

技术选型：

- Tree-sitter：统一多语言解析。
- Python AST：Python 深度分析。
- 后续根据需求接入 Java、TypeScript 等语言解析器。

这里要特别注意：

不要只保存解析后的 AST，还要保存原始文件的行号、字节范围和代码位置。

因为后面 AI 要修改代码时，需要知道准确的代码范围。

另外，语法解析不代表语义理解。对于动态语言中的反射、动态导入、运行时装饰器等情况，必须允许索引结果标记为不确定。

## M3：Symbol & Relationship Index —— 符号和关系索引

核心能力

这是整个系统最重要的模块之一。

M2 解决的是：

> 项目里有哪些函数、类？

M3 解决的是：

> 这些函数、类之间有什么关系？

例如：

```
# main.pyfrom auth_service import AuthServiceservice = AuthService()service.login("admin", "123456")
```

```
# auth_service.pyclass AuthService:    def login(self, username, password):        user = self.get_user(username)        return self.verify_password(user, password)    def get_user(self, username):        pass    def verify_password(self, user, password):        pass
```

我们需要建立类似这样的关系：

## 函数调用关系图

main.py

`main()`

CALLS

auth_service.py

`AuthService.login()`

CALLS

get_user()

CALLS

verify_password()

建议第一阶段建立以下关系：

| 关系         | 含义       | 示例                         |
| ---------- | -------- | -------------------------- |
| CONTAINS   | 文件包含类/函数 | 文件 → 函数                    |
| DEFINES    | 模块定义符号   | 模块 → 类                     |
| IMPORTS    | 模块导入模块   | main → auth_service        |
| CALLS      | 函数调用函数   | login → get_user           |
| REFERENCES | 符号被引用    | login → AuthService        |
| INHERITS   | 类继承      | Admin → User               |
| IMPLEMENTS | 类实现接口    | UserService → IUserService |

注意，`CALLS` 和 `REFERENCES` 不一样。

例如：

```
user = get_user()
```

这里是调用关系。

而：

```
handler = get_user
```

这里是函数引用，不一定发生函数调用。

### 数据如何存储？

初期不建议直接上 Neo4j 这样的图数据库。

使用 SQLite 就可以。

可以设计两张核心表：

symbols 表

```
CREATE TABLE symbols (
    symbol_id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    qualified_name TEXT,
    symbol_type TEXT,
    file_path TEXT,
    start_line INTEGER,
    end_line INTEGER
);
```

symbol_relations 表

```
CREATE TABLE symbol_relations (
    source_symbol_id TEXT,
    target_symbol_id TEXT,
    relation_type TEXT,
    confidence REAL,
    evidence TEXT
);
```

这里的 `confidence` 和 `evidence` 很重要。

例如，Tree-sitter 发现：

```
self.get_user(username)
```

可以确定这是一个方法调用表达式，但不一定能仅靠语法确定它指向哪个类的方法。

因此：

- 确定的关系：高置信度。
- LSP 确认的关系：高置信度。
- 静态推断的关系：标记为推断。
- 无法解析的关系：保留未知，不要强行建立关系。

关系最好还保存调用位置、解析方式和索引版本，以便后续验证和更新。

## M4：Code Retrieval —— 代码检索

面向 Agent 的检索入口

前面三个模块已经建立了项目的基础信息。

但 AI 真正工作时，不能每次把所有信息都读取出来。

需要一个统一的代码检索引擎。

我建议采用四种检索方式。

| 检索方式 | 技术                        | 适合场景         |
| ---- | ------------------------- | ------------ |
| 文本检索 | ripgrep                   | 搜索关键词、配置、异常  |
| 符号检索 | Symbol Index              | 搜索函数、类、方法    |
| 语义检索 | Embedding + Vector Search | 根据自然语言找相关代码  |
| 关系检索 | Relationship Index + LSP  | 查调用者、被调用者、引用 |

例如用户提出：

> 增加登录失败次数限制。

系统可以执行：

第一步：语义检索

找到：

```
auth/login.py
auth/auth_service.py
auth/security.py
```

第二步：符号检索

定位：

```
AuthService.login()
AuthService.verify_password()
```

第三步：关系检索

找到：

```
main.py -> AuthService.login()
login() -> verify_password()
login() -> get_user()
```

第四步：文本检索

搜索：

```
failed_attempts
account_locked
login_attempts
```

确认项目是否已经存在相关实现。

最终形成一个相关代码候选集合。

### 是否需要向量数据库？

需要视情况而定。

我建议不要一开始就使用向量数据库。

初期可以：

- SQLite FTS5：关键词和符号文本搜索。
- Tree-sitter：结构化定位。
- SQLite 关系表：代码关联。
- LSP：按需进行语义查询。

等代码量增大、自然语言检索效果成为瓶颈时，再增加向量检索。

而且代码向量化时，不建议简单地每 500 个 Token 切一块。

更合理的粒度是：

- 一个函数一个 Chunk。
- 一个类一个 Chunk。
- 一个模块一个 Chunk。
- 必要时对超长函数分块，同时保留父级符号 ID。

这样能够保留代码的结构信息。

## M5：Context Builder —— 上下文构建

直接影响生成质量

这是 Codebase Understanding 与 LLM 连接的关键环节。

检索出 20 个相关文件，并不意味着应该把 20 个文件全部交给 LLM。

Context Builder 需要决定：

- 哪些代码必须提供？
- 哪些代码可以只提供摘要？
- 哪些代码只需要提供接口？
- 哪些代码应该排除？
- 如何控制 Token 消耗？

例如：

用户提出登录失败锁定账户。

系统检索到了：

```
auth/login.py
auth/auth_service.py
auth/user.py
database/models.py
database/session.py
api/auth.py
tests/test_login.py
tests/test_user.py
utils/logger.py
```

可以采用这样的上下文策略：

| 内容                | 处理方式    | 原因        |
| ----------------- | ------- | --------- |
| login()           | 完整代码    | 核心修改目标    |
| verify_password() | 完整代码    | 核心业务逻辑    |
| User 模型           | 完整定义    | 需要增加或使用字段 |
| 数据库操作             | 完整相关方法  | 需要更新用户状态  |
| API 登录入口          | 接口与调用代码 | 了解入口      |
| 登录测试              | 完整相关测试  | 修改测试      |
| 日志工具              | 接口摘要    | 可能不需要深入   |

建议 Context Builder 输出结构化结果：

```
{
  "task": "增加登录失败次数限制",
  "target_symbols": [
    "AuthService.login",
    "AuthService.verify_password"
  ],
  "related_files": [
    "auth/login.py",
    "database/models.py",
    "tests/test_login.py"
  ],
  "dependencies": [
    "User",
    "DatabaseSession"
  ],
  "context": {
    "primary_code": [],
    "related_code": [],
    "interfaces": [],
    "tests": []
  },
  "token_budget": 12000
}
```

注意：这里的 `token_budget` 只是示例值，实际应该根据所用模型的上下文窗口、任务复杂度和生成需求动态分配。

### Context Builder 最重要的设计原则

我建议建立三层上下文：

P0：直接修改上下文

目标函数、目标类、直接相关的数据模型和接口。

必须准确

P1：依赖上下文

调用者、被调用者、依赖模块、相关配置。

建议提供

P2：背景上下文

README、项目规范、架构文档、相似实现。

按需提供

这样可以避免 AI 把大量无关代码带入上下文。

## M6：Impact Analyzer —— 修改影响分析

降低修改风险

这一层是很多简单代码生成工具容易忽略的。

例如：

你准备修改：

```
AuthService.login()
```

但它可能被以下地方调用：

```
api/auth.py
admin/login.py
mobile/auth.py
tests/test_login.py
```

如果只修改登录函数，而忽略其他调用方，就可能产生兼容性问题。

Impact Analyzer 应该做以下事情：

1. 查询目标函数的所有调用者。
2. 查询目标函数依赖的函数。
3. 查询关联的数据模型。
4. 查询相关 API 和接口。
5. 查询相关测试。
6. 判断修改是否影响公共接口。
7. 生成修改风险清单。

例如：

```
{
  "target": "AuthService.login",
  "impact": [
    {
      "file": "api/auth.py",
      "reason": "调用登录方法",
      "risk": "medium"
    },
    {
      "file": "admin/login.py",
      "reason": "调用登录方法",
      "risk": "medium"
    },
    {
      "file": "tests/test_login.py",
      "reason": "相关测试",
      "risk": "high"
    }
  ],
  "recommendations": [
    "检查登录接口返回值兼容性",
    "增加连续失败测试",
    "增加账户锁定测试",
    "验证锁定后的登录行为"
  ]
}
```

这里要区分两个方向：

- 正向依赖：目标函数调用了谁？
- 反向依赖：谁调用了目标函数？

修改影响分析通常尤其关注反向依赖。

但需要强调：静态调用图不可能保证覆盖所有运行时关系。动态调用、反射、插件注册、事件回调等，都可能让调用关系不完整。因此最终需要结合测试、类型检查和运行时验证。

# 三、六个模块之间如何协同工作？

前面介绍的是模块，现在把它们串起来，看看一次真实的 AI 代码修改任务如何执行。

假设用户提出：

> 在用户登录时增加失败次数限制，连续失败 5 次锁定账户。

完整执行过程可以设计为：

## 一次代码修改任务的执行流程

1. 接收用户需求

   将自然语言转化为任务目标和约束。
2. Scanner

   检查仓库、项目结构、语言、入口和 Git 状态。
3. Parser

   解析相关文件，提取函数、类、参数、代码范围。
4. Index

   建立符号索引、调用关系和模块依赖。
5. Retriever

   根据任务检索登录逻辑、用户模型、数据库操作和测试。
6. Context Builder

   选择相关代码，生成有限 Token 的上下文包。
7. Impact Analyzer

   分析调用者、关联接口、测试以及潜在影响。
8. Planner

   制定具体修改计划，明确修改哪些文件、为什么修改。
9. Code Generator

   根据上下文执行代码修改。
10. Validator

    运行测试、类型检查、Lint，并检查修改是否符合原始需求。

这里还有一个重要设计：

Codebase Understanding 不应该只在代码生成之前运行一次。

代码修改之后，应该重新扫描变更文件、更新符号索引和关系索引，并对修改前后的依赖关系进行比较。

否则 Agent 可能一直使用过期的代码上下文。

# 五、真正落地：建议分五个阶段实施

我不建议六个模块一次性全部开发。因为一旦同时做语法解析、跨文件语义分析、向量检索和影响分析，很难判断问题出在哪里。

建议先做一个能工作的 MVP，再逐步增强。

## Codebase Understanding 实施路线图

Phase 1：项目扫描与结构解析

P0

建立项目文件清单、Tree-sitter 解析、符号提取。

- Repository Scanner
- Code Parser
- Repository Manifest
- Symbol Index

# 六、还有三个容易忽略的工程问题

这三个问题决定你的系统能不能从 Demo 变成真正可用的工程系统。

## 1. 索引如何保持最新？

假设：

1. 系统扫描了 1000 个文件。
2. 建立了符号索引。
3. 用户修改了其中 3 个文件。
4. Agent 再次执行检索。

如果不更新索引，检索结果可能已经过期。

建议建立文件级索引状态：

```
{
  "file_path": "auth/login.py",
  "content_hash": "sha256:xxx",
  "parser_version": "1.0",
  "index_version": 12,
  "last_indexed_at": "2026-11-09T10:00:00",
  "status": "valid"
}
```

通过 Git Diff 或文件 Hash 判断哪些文件需要重新解析。

注意：如果一个文件发生变化，不一定只需要更新这个文件。例如它的公开接口发生变化，依赖它的模块也可能需要重新分析。

## 2. 如何确保代码理解准确？

不能只以「能找到代码」作为验收标准。

我建议建立一个 Golden Dataset（标准测试集）。

例如准备 20 个真实代码理解任务：

| 测试项      | 预期结果    |
| -------- | ------- |
| 找到指定函数定义 | 正确文件和行号 |
| 找到指定类    | 正确类定义   |
| 找到函数调用者  | 完整引用集合  |
| 找到函数依赖   | 正确被调用函数 |
| 找到相关测试   | 正确测试文件  |
| 分析跨文件依赖  | 正确模块关系  |
| 修改后更新索引  | 不返回过期结果 |

建议重点统计：

- Symbol Extraction Precision / Recall
- Reference Resolution Precision / Recall
- Retrieval Recall\@K
- Context Token Efficiency
- Impact Analysis Coverage
- Index Freshness

特别是 Reference Resolution Precision，不能为了追求召回率而把不确定的调用关系都当成真实关系。

## 3. 不要让 LLM 负责所有代码理解

这一点非常重要。

我建议采用：

| 工作     | 由谁负责         |
| ------ | ------------ |
| 文件扫描   | 确定性程序        |
| 语法解析   | Tree-sitter  |
| 符号提取   | Parser       |
| 引用解析   | LSP + 静态分析   |
| 文本搜索   | ripgrep      |
| 关系查询   | Index        |
| 自然语言理解 | LLM          |
| 任务规划   | LLM          |
| 上下文筛选  | 检索算法 + LLM   |
| 代码修改   | LLM + 编辑工具   |
| 修改验证   | 测试、Lint、类型检查 |

核心原则：能用确定性程序解决的问题，不要交给 LLM 猜测。

# 八、我的最终建议：先把什么做好？

如果让我负责这个项目的技术方案，我会把下面四项作为第一阶段的核心交付：

## 第一阶段必须交付的能力

1\. Repository Manifest

必做

能够完整了解一个代码仓库有哪些文件、语言、目录和入口。

2\. Symbol Index

必做

能够准确定位函数、类、方法、参数及代码范围。

3\. Relationship Index

必做

能够分析函数调用、模块依赖、引用关系。

4\. Context Builder

必做

能够根据自然语言需求，提取最相关的代码上下文。

这四项做好之后，你就拥有了一个初步的 Codebase Understanding Engine。

再加入 LSP 和 Impact Analyzer，就能进一步提高复杂项目中的代码理解能力。

有一个架构上的建议：把 Codebase Understanding 做成独立的基础设施，向上提供标准接口，而不是将其写死在某一个代码生成 Agent 中。

未来无论是 Python Agent、Java Agent，还是多语言代码生成 Agent，都可以复用这套能力。

下一步最有价值的是把 Phase 1 拆成可执行的技术规格、SQLite Schema、接口定义和测试验收标准。
