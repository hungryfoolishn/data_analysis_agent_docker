# 面试问答预演：问题 + 参考回答 + 追问链

> 用法：不要背答案。每题先自己说 1-2 分钟，再对照参考回答找差距，
> 最后练追问链——被追问三层后还能自洽才算过关。

---

## 第一部分：技术设计题

### Q1. 设计一个内部 coding agent，工具集怎么定义？

**参考回答（60 秒版）**：
工具集按"读、写、执行"三类定义，保持极简正交——每个工具都是模型的选择点，越少越准。最小集是：`read_file`（分页读）、`grep`（文本/正则搜索）、`glob`（文件名匹配）、`edit_file`（精确旧文本替换）、`write_file`（新建）、`run_shell`（跑测试和 git）。在此基础上按规模加：符号索引查询（结构性问题如"谁调用了这个函数"，grep 回答不了）、AST 查询。安全上分级：只读工具免确认，写操作白名单，shell 按命令前缀分级，危险命令永远人工确认。

**追问链**：
1. "为什么 edit 用旧文本匹配不用行号？" → 模型数行号常错，尤其自己改过文件行号漂移后；复述原文强制先读后改，天然一致性校验。缺点是 token 稍多、复述不精确要重试，用模糊匹配提示缓解。
2. "工具多了会怎样？有什么量化感受？" → 工具超过 15-20 个后模型会开始选错工具、传错参数，工具描述的提示词工程成本超线性增长。我的原则是发现两个工具 70% 重叠就合并。
3. "怎么评测工具集设计得好不好？" → 看任务失败归因：统计 evals 失败案例里多少是"选错工具/参数错"，占比高说明工具设计有问题而不是模型问题。

### Q2. LLM 生成的代码怎么保证质量？

**参考回答**：
分层验证，从便宜到贵：① 语法层——AST parse 通过、diff 范围符合预期（防止改到无关代码）；② 编译/静态检查；③ 测试——只跑受影响模块的单测，依赖图算影响面；④ 行为层——无测试的老代码先补表征测试锁定现状再改；金融计算类重构用新旧双跑差分比对。核心思想是**不信任、必验证**：模型输出永远过完整验证流水线才落库，验证是确定性代码做的，不靠另一个 LLM 判断。

**追问链**：
1. "没有测试的遗留模块怎么办？" → 先让 AI 为现状代码写表征测试（characterization test），锁定当前行为（包括 bug 行为），重构后表征测试不变才算成功。这是《Working Effectively with Legacy Code》的标准打法。
2. "验证流水线本身误报/漏报怎么办？" → 漏报靠金丝雀灰度兜底：先改非核心模块，观察一周再扩大。误报记录归因，持续收紧检查规则。
3. "模型生成的测试也是错的怎么办？" → 表征测试的期望值由"实际运行现状代码"生成而不是模型拍脑袋；新功能的测试则要人审测试意图，工具辅助但不全自动。

### Q3. 百万行代码库怎么做 RAG？

**参考回答**：
先纠正一个常见误区：代码检索不能只靠向量。我设计三路混合：① 符号检索——grep + 符号索引（ctags/tree-sitter 提取），代码标识符是强信号；② 向量检索——AST 按函数切块后 embedding，处理"对账逻辑在哪"这类语义查询；③ 结构检索——调用图/依赖图，回答变更影响。查询路由：先符号后向量，代码查询大多命中符号层。索引工程：首次全量分批并行 embedding，文件监听增量更新，向量库银行场景首选 pgvector（复用现有 PG 和权限体系）。

**追问链**：
1. "为什么按函数切块？" → 函数是完整语义单元，固定行数切割会把方法腰斩，检索命中也读不通。超长函数递归细分并保留 `file:class.method` 路径上下文。
2. "百万行首次索引多久？怎么加速？" → tree-sitter 解析本身每秒几十万行，瓶颈在 embedding API；分批并发 + 本地 embedding 模型（BGE）+ 增量机制让后续更新秒级。
3. "多项目权限怎么隔离？" → 检索层带项目/模块过滤条件，索引时打标，查询时按用户权限收窄——银行场景这一条是一票否决项。

### Q4. 怎么评估这个工具的效果？

**参考回答**：
两层指标。工程层用 evals：攒 50-100 个真实任务（修 bug、加功能、写文档），自动跑分（产物 diff 是否符合预期、测试是否通过），改 prompt/换模型后跑基线对比防回归。业务层看采纳与效率：代码建议采纳率、任务一次完成率、开发者调研的节省工时、token 成本趋势。内部平台还要向管理层证明 ROI——成本看板 + 每季度效率报告是团队存在价值的证据。

**追问链**：
1. "evals 任务从哪来？" → 从真实使用日志里挑高频任务类型脱敏后入库，避免人工造题失真。
2. "采纳率会不会被讨好性使用污染？" → 会，所以要看留存信号：AI 改的代码是否活过一周、是否被后续重构。

### Q5. 存量 Java 代码重构，Python 工具怎么介入？

**参考回答**：
Python 是工具层不是重构对象。用 tree-sitter 的 Python binding 解析 Java（它支持 100+ 语言），做三件事：AST 切块喂给 LLM 理解；定位精确代码位置（带行列号的节点）；验证模型输出（parse 校验结构合法、diff 校验范围）。重构流水线：影响面分析（依赖图）→ 方案人审 → 小步生成 → 静态+测试验证 → 灰度合入。能用确定性 codemod 的不用 LLM（如 API 改名），LLM 只负责语义决策。

**追问链**：
1. "tree-sitter 不做类型分析，怎么办？" → 分层：tree-sitter 做快而糙的第一层，精确引用用 LSP（Eclipse JDT LS）做第二层，重构验证由编译器和测试兜底。
2. "200 个文件的批量迁移怎么管？" → 工单队列：每个工单=一处变更+自动验证+人审批，失败自动隔离不阻塞队列，每步独立 commit 可单独 revert，配看板管进度。

## 第二部分：业务与动机题

### Q6. 你了解银行核心系统改造吗？这个工具能帮上什么？

**参考回答**：
背景是信创国产化：银行核心系统从集中式架构（大机/IOE）向分布式架构迁移，存量 Java 系统体量大、文档缺、不敢动。AI 工具的价值点：迁移时 API 映射和代码翻译提效；改造前的存量资产落档（接口文档、数据流、业务规则提取）降低理解成本；改造中的大规模 codemod + 自动验证保证质量。海外交付团队还需要标准化工具复制能力——一套工具链多国项目复用。

**要点**：说到"海外"时自然衔接——长亮的东南亚交付同样需要这套工具，说明你理解岗位的完整价值场景。

### Q7. 为什么想做内部工具而不是业务开发？

**参考回答方向**（结合自己真实经历组织）：
- 亲手感受过开发痛点：接手无文档的存量代码时，理解成本占总工作量一半以上——这个岗位是在系统性地解决我亲身经历的问题。
- 技术匹配：LLM 应用 + 工程化能力正好落在这个交叉点。
- 平台思维：内部工具的用户是几百个开发者，杠杆率高，一个提效 20% 的工具等于给公司多了几十个工程师的产能。

### Q8. 如果工具上线后开发者不用，怎么办？

**参考回答**：
先归因：是能力不行（任务完成率低）、还是体验差（太慢/太麻烦）、还是没场景（和现有工作流脱节）。对策不同：能力问题补 evals 迭代；体验问题优化延迟和确认频率（这提醒我 confirm 分级不能一刀切）；场景问题要把工具嵌进现有流程（IDE 插件/CI 集成）而不是让人"多开一个窗口"。推广策略：找 2-3 个种子团队共创，用他们的真实任务打磨，成功案例再横向推。**内部工具的死法是"领导要的、没人用"，活法是"种子用户离不开"**。

## 第三部分：压力/开放题

### Q9. 模型上下文不够长，任务做不完，怎么办？

**参考回答**：
四板斧按顺序上：① 工具结果截断——最大浪费源，grep 只回前 40 条、读文件分页；② 滑动窗口压缩——旧工具结果和对话摘要化，保留最近几轮原文；③ 状态外化——计划/todo 写文件，上下文只注入最新版，压缩不伤工作产物；④ 子 Agent 隔离——大搜索任务丢给独立上下文的 subagent，主 Agent 只收回结论。我的 demo 里实现了 ①②③，见 `context_manager.py`。

### Q10. 你有什么想问我们的？（反问环节，提前准备）

**推荐问的问题**（每个都传递"我已在认真思考这个岗位"）：
1. "目前团队内部开发用什么辅助工具？自建还是基于开源改？"——判断起点和改造空间。
2. "目标代码库主要什么语言、什么规模、测试覆盖率怎么样？"——直接决定技术方案（Java 百万行无测试 vs Python 有测试，方案完全不同）。
3. "落档的知识库未来主要给 AI 用还是给人用？"——决定 RAG 设计方向（给 AI 用重结构化检索，给人用重可读性）。
4. "重构的验证标准公司现在有什么基础？CI/单测覆盖率现状？"——判断验证闭环能不能落地。
5. "这个岗位在组织的定位：效能平台团队还是某个交付线的配套？"——判断资源和空间。

**不要问**的：薪资福利细节（留到 offer 阶段）、"加班多吗"（可以问节奏但要包装成"项目节奏和交付压力"）。

## 第四部分：口头表达建议

1. **每个回答先给结论再展开**："我的方案是 X，三个理由……"，不要上来就铺垫背景。
2. **主动引用自己 demo 里的具体实现**："我在 demo 里就是这么做的，edit_file 的唯一性校验就是防这个"——真实感是最大加分项。
3. **承认边界**：被问住的题，说清"这块我了解到的程度是 X，没实践过的是 Y，我的推断是 Z"，比硬编强十倍。
4. **业务锚点反复回扣**：聊技术时自然带一句"这在银行场景要注意数据不出域/审计留痕"，两三次就够，多了刻意。
