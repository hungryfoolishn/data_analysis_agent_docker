# 项目优化路线图（分层 + 2~4 周执行版）

## 文档目的

基于 `.claude/project_critical_evaluation.md` 的批判性结论，给出一版面向落地执行的优化路线图。

核心原则只有一句话：

**先证明系统“真的可靠”，再继续扩展系统“看起来很完整”。**

也就是说，当前优化顺序应当优先围绕：

1. 分析可信度
2. Agent 收敛稳定性
3. 可复核与工程治理
4. 产品化与行业化增强

---

## 一、当前问题分层总结

### 1. L1：分析可信度不足（最高优先级）

当前系统已经具备较强的：
- 自动 EDA
- 图表生成
- 报告组织
- 分析过程说明

但仍然存在关键缺口：
- 更擅长描述现象，不够擅长解释原因和支持决策
- 容易产出“像洞察”的总结，但不一定具备业务决策价值
- 业务口径不够显式，容易误解字段语义、时间窗口、分母和去重逻辑
- 面对多表、脏数据、半结构化数据时，结论稳定性未被证明

### 2. L2：Agent 收敛稳定性仍依赖大量工程约束

当前系统稳定性更多是由：
- prompt 约束
- validator
- 运行时 guardrails
- 步数限制
- 输出格式限制

共同“硬控”出来的。

这说明：
- 系统对模型行为比较敏感
- 一旦模型版本、输出风格、任务复杂度变化，容易退化
- 当前测试通过代表已有进步，但不等于复杂真实任务下稳定

### 3. L3：可复核性和工程治理还不够强

系统离“放心交付”还差几类底座能力：
- 结论与证据的追踪映射
- 更完整的可观测性
- 更明确的错误分类与恢复策略
- workspace / 文件生命周期治理
- session 清理与资源回收
- 成本与吞吐治理

### 4. L4：产品定位和行业护城河尚未收敛

当前系统容易落入中间态：
- 对普通业务用户偏复杂
- 对高级分析师又不够可信
- 对开发者很有研究价值，但未完全形成可规模化交付形态

未来真正的壁垒不在 UI，而在：
- 分析可信度
- 稳定性
- 可复核性
- 行业知识与口径沉淀
- 真实业务数据流接入能力

---

## 二、总体优化原则

### 原则 1：先修“错得很像对”的问题

当前最危险的不是失败，而是：

**系统给出了流畅、完整、像样的结论，但这些结论并不一定足够可信。**

因此第一优先级必须是降低“伪洞察”的概率。

### 原则 2：先补底座，再加功能

不优先做：
- UI 包装
- 表层交互增强
- 额外展示型能力堆叠

优先做：
- 证据绑定
- 口径声明
- validator
- 收敛状态机
- tracing / observability

### 原则 3：把“能跑”升级成“可证明地稳定”

优化目标不应是“多做几个 demo 能跑通”，而应是：
- 更高成功率
- 更低错误结论率
- 更清晰失败类型
- 更稳定恢复策略
- 更强跨数据集泛化能力

---

## 三、分层优化路线图

## 第 1 层：分析可信度层（最先优化）

### 目标
让系统输出的结论具备最基本的“可信分析”特征，而不是只会组织一份像分析报告的文本。

### 核心建设项

#### 1. 结论-证据绑定机制
每一个最终结论都必须能追溯到：
- 使用了哪些字段
- 哪些过滤条件
- 哪些统计结果
- 哪些图表或中间分析结果

建议输出结构从“自由报告”升级为“结构化 findings + 报告生成”。

#### 2. 业务口径显式声明
系统在输出结论前，需要显式声明：
- 时间窗口
- 指标定义
- 分母来源
- 去重规则
- 缺失值处理方式
- 关键字段语义假设

#### 3. 结论类型分层
对输出内容区分：
- 事实型结论
- 推断型结论
- 建议型结论
- 待确认项

避免系统把“观察到的相关性”直接包装成“业务原因”。

#### 4. 分析前 schema 理解步骤
在真正分析前，先完成：
- 字段类型理解
- 主键候选识别
- 时间字段识别
- 金额/计数/类别字段识别
- 多表关联合理性初判
- 可疑字段标注

#### 5. 分析结果 validator
重点校验：
- 是否存在无证据结论
- 是否过度解释字段语义
- 是否把相关性说成因果
- 是否遗漏样本限制条件
- 是否在样本很小的情况下做强结论

### 这一层的优先交付物
- findings schema
- conclusion-evidence trace 数据结构
- metric definition / assumption block
- insight validator
- schema understanding pre-check

### 成功标准
- 最终报告中的核心结论都能找到证据来源
- 模型不能轻易“脑补业务含义”
- 业务口径不再隐式存在于推理里，而是显式输出
- “看起来很像洞察”的错误结论明显下降

---

## 第 2 层：Agent 收敛稳定性层（然后做）

### 目标
让系统从“偶尔跑通”走向“多数情况下都能稳定跑通”。

### 核心建设项

#### 1. 分析状态机化
把分析过程规范为有限阶段：
1. 数据理解
2. 数据质量检查
3. 基础 EDA
4. 定向深挖
5. 结论整理
6. 报告生成

减少 agent 的自由跳转和无效往返。

#### 2. 失败分类体系
对失败做明确 taxonomy：
- 数据理解失败
- 字段语义不明确
- 工具执行失败
- 代码运行失败
- 推理偏航
- 报告生成失败
- 超时 / 长 session 中断

#### 3. 分类型恢复策略
不是统一重试，而是：
- 代码报错 → 修复后重试当前步骤
- 字段语义不清 → 输出待确认，不强推断
- 数据质量差 → 自动降级分析范围
- 结果不收敛 → 提前结束并报告局限性

#### 4. 稳定性 benchmark 集
建立固定回归数据集，至少覆盖：
- 单表干净数据
- 单表脏数据
- 多表关联数据
- 时间序列数据
- 半结构化字段
- 行业场景样例

#### 5. 核心稳定性指标
需要持续跟踪：
- 任务成功率
- 中断率
- 平均步数
- 平均耗时
- 重试率
- 空结论率
- 高风险结论率

### 这一层的优先交付物
- agent state machine
- failure taxonomy
- recovery strategy matrix
- benchmark dataset
- regression 稳定性报告

### 成功标准
- 同类任务成功率更稳定
- 失败后能更自然地恢复或降级
- 长 session 和复杂数据下退化幅度受控
- 模型变化对系统表现的冲击更可观测

---

## 第 3 层：可复核与工程治理层（再然后）

### 目标
让系统结果可审查、问题可定位、资源可治理。

### 核心建设项

#### 1. 全链路可追踪
建立 request / session / run / artifact 的关联链路，能回答：
- 用户问了什么
- 系统分析了哪些数据
- 中间执行了哪些步骤
- 生成了哪些图和文件
- 最终哪个结论对应哪些证据

#### 2. 结构化日志与 tracing
补齐：
- 每阶段耗时
- token 消耗
- 工具调用统计
- 失败位置
- 重试原因
- 结束原因

#### 3. 文件与 workspace 生命周期治理
补齐：
- 文件 TTL
- 任务取消后的清理
- 长 session 的回收策略
- 过期产物清理
- 残留临时文件治理

#### 4. 用户可理解的错误系统
避免统一“分析失败”，而改成：
- 数据格式不符合要求
- 字段含义不明确
- 分析未收敛
- 运行超时
- 结果可信度不足
- 文件已失效

#### 5. 成本与吞吐治理
补齐：
- 轻重任务分级
- 不同阶段模型路径优化
- 无效循环限制
- 重复分析缓存 / 避免重复计算

### 这一层的优先交付物
- trace IDs 体系
- structured log schema
- artifact lineage
- workspace cleanup policy
- user-facing error taxonomy

### 成功标准
- 能快速定位失败在哪一层
- 能知道某条结论是如何得出的
- workspace 不再越跑越脏
- 成本和耗时趋势具备可分析性

---

## 第 4 层：产品化与行业化层（最后强化）

### 目标
在底层可信度和稳定性建立后，再逐步收敛产品形态和行业能力。

### 核心建设项

#### 1. 明确目标用户
先选一个主用户群：
- 数据分析师
- 业务运营
- 内部技术团队
- 垂直行业客户

#### 2. 行业分析模板
沉淀：
- 常见指标定义
- 常见分析路径
- 常见异常解释模板
- 行业报告框架

#### 3. 交互收敛
对非技术用户隐藏：
- session_id
- workspace
- 工具细节
- 中间运行机制

强化：
- 结论
- 证据
- 建议行动
- 风险提示

#### 4. 接入真实业务数据流
逐步从“上传文件分析”扩展到：
- 数据库
- BI / 报表源
- 内部数据接口
- 周期化分析任务

### 成功标准
- 产品形态不再摇摆
- 特定场景下有明显优于通用 AI 的表现
- 开始形成“稳定 + 行业化”的差异化优势

---

## 四、建议的执行顺序

### 最先优化什么

**最先优化：第 1 层，分析可信度。**

如果当前只能先投入一个方向，就先做：
1. 结论必须绑定证据
2. 业务口径必须显式声明
3. 高风险结论必须过 validator

原因很简单：

- 错误但流畅的答案，比失败更危险
- 不可信的系统，后面做再多产品包装都没有意义
- 可信度是稳定性、可复核性、商业化的共同底座

### 然后做什么

**然后：第 2 层，Agent 收敛稳定性。**

优先顺序：
1. 状态机化
2. 失败分类
3. 恢复策略矩阵
4. benchmark 回归集

### 再然后做什么

**再然后：第 3 层，可复核与工程治理。**

优先顺序：
1. trace / lineage
2. structured logging
3. lifecycle cleanup
4. 错误反馈分层
5. 成本治理

### 最后强化什么

**最后：第 4 层，产品化与行业化。**

---

## 五、未来 2~4 周执行版 Roadmap

下面给出一版务实的短周期执行建议，目标不是一次做完所有事，而是用 2~4 周把系统从“像产品”推向“更可信的系统”。

---

## Week 1：先把“结论可信度底座”立起来

### 目标
把“没有证据的漂亮结论”先压下去。

### 本周重点

#### A. 定义 findings 结构
建议将分析输出拆成两层：
- machine-readable findings
- human-readable report

findings 至少包含：
- finding_id
- statement
- evidence
- related_fields
- filters
- confidence
- assumption
- risk_level

#### B. 改造最终报告生成链路
要求报告只能基于 findings 生成，不能绕过 findings 直接自由总结。

#### C. 增加口径声明块
在最终输出中强制包含：
- 时间范围
- 去重逻辑
- 指标定义
- 关键假设
- 数据限制

#### D. 增加高风险结论 validator
先拦截最危险的几类问题：
- 无证据结论
- 因果化表达
- 过度解释业务字段
- 忽略样本限制

### 本周预期结果
- 系统报告更“克制”
- 幻觉型结论下降
- 用户更容易知道结论从哪来

---

## Week 2：把 Agent 路径从“自由发挥”改成“可控收敛”\n
### 目标
让执行过程更稳定，不靠运气。

### 本周重点

#### A. 固化状态机
至少先定清：
- schema 理解
- 数据质量检查
- EDA
- 深挖
- 结论整理
- 报告生成

#### B. 失败分类落地
对日志和运行结果引入统一 failure_code。

#### C. 分类型恢复策略
先处理最常见的 3 类：
- python 执行失败
- 字段意义不明确
- 长步骤不收敛

#### D. 建第一版 benchmark 集
至少做 5~10 个固定样例，覆盖：
- 干净单表
- 脏单表
- 多表
- 时间序列
- 字段歧义

### 本周预期结果
- 同类任务跑法更一致
- 失败更可解释
- 回归验证开始具备基准

---

## Week 3：补可复核与可观测性

### 目标
让“怎么得出这个结论的”可以被追踪。

### 本周重点

#### A. 建立 conclusion → evidence → artifact 链路
至少能串起来：
- 哪个结论
- 对应哪个 finding
- 来源于哪个图/统计/中间结果

#### B. 补 structured logs
统一记录：
- session_id / run_id
- 阶段名
- 耗时
- 工具调用
- 失败码
- token / 成本估计

#### C. 建 workspace 生命周期策略
- 产物命名规范
- TTL
- 清理机制
- 取消任务后的回收策略

#### D. 改错误提示文案
先让用户能区分：
- 数据问题
- 系统问题
- 超时问题
- 可信度不足问题

### 本周预期结果
- 运维和调试效率明显提升
- 用户更能理解失败原因
- 结果可信链条开始成型

---

## Week 4：小范围行业化增强 + 目标用户收敛

### 目标
在底层稳定之后，开始做“可落地场景”而不是泛泛展示。

### 本周重点

#### A. 选一个主用户画像
建议只选一个主方向，不并行发散。

#### B. 选一个行业或业务域做模板化
例如：
- 电商运营分析
- 销售漏斗分析
- 用户留存分析
- 财务结构分析

#### C. 沉淀领域口径
把常见指标和分析问题固化为模板。

#### D. 收敛交互表达
技术细节继续保留在底层，但对用户主界面尽量只暴露：
- 核心结论
- 支撑证据
- 建议动作
- 风险提示

### 本周预期结果
- 开始出现可复用的场景模板
- 项目方向更聚焦
- 逐步形成差异化能力，而不是泛化 demo

## 七、给技术负责人的一句执行建议

如果接下来只能盯住一条主线，不要盯“功能数”，要盯下面四个指标：

1. 分析正确率
2. 收敛成功率
3. 可复核性
4. 目标用户聚焦度

这四项提升了，项目会越来越像真正的智能分析系统。

如果这四项不提升，而只是继续堆展示能力，项目很容易停留在：

**体验像产品，能力像 demo。**

---

## 八、最终建议

当前阶段的正确顺序应该是：

**先可信度，后稳定性；先底座，后包装；先证明可靠，再放大体验。**

具体顺序：

1. 先做分析可信度底座
2. 然后做 agent 收敛稳定性
3. 再做可复核与工程治理
4. 最后做产品化与行业化增强

这是当前最稳、也最符合项目阶段的优化路径。
