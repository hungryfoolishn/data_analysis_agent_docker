# 解释性分析与决策分析薄弱问题及优化方案

## 问题

### 2.1 描述性分析强，解释性分析和决策性分析还弱

现在系统更擅长：
- 看分布
- 看趋势
- 看分组差异
- 找异常

但真正高价值的业务分析经常要求：
- 为什么发生
- 哪些因素是主驱动
- 哪个结论可以指导行动
- 哪些判断只是相关性，哪些接近因果

如果这部分没有更硬的方法学支撑，系统就容易输出“像洞察的总结”，但未必是可以直接用于业务决策的洞察。

---

## 优化方向总纲

核心不是让 agent “多说原因”，而是把“解释”和“决策”从文风问题，改成方法学问题。

要把系统从：

**自动发现现象并写报告**

升级成：

**先做结构化解释与证据分级，再生成可复核、可行动、但不过度因果化的分析报告**

---

## 一、需要补的 4 层能力

### 1. 从“描述”升级到“归因候选”

对每个重要发现，不能停在“发现了什么”，而要继续回答：
- 是谁贡献了变化
- 是量变还是结构变
- 是全局性变化还是局部群体变化
- 是一次性异常还是持续性变化

建议把每个重要发现都强制走这套模板：

```text
现象
→ 影响范围
→ 贡献拆解
→ 候选驱动因素
→ 证据强度
→ 待验证假设
→ 可执行建议
```

### 2. 从“相关描述”升级到“驱动拆解”

解释性分析不能只写“可能与 X 有关”，而要固定做几类拆解：

#### A. 构成拆解
适合收入、订单、转化、成本等指标。

例如收入下降时，优先拆：
- 用户数变了？
- 转化率变了？
- 客单价变了？
- 某渠道/区域/产品结构变了？

#### B. 分群贡献拆解
适合找“是谁拉动/拖累了结果”。

例如整体 GMV 下滑时，要回答：
- 哪些 region / channel / product segment 贡献了主要跌幅
- 贡献占比多少
- 是头部组驱动，还是普遍下滑

#### C. 时间窗口拆解
适合区分趋势、波动、事件冲击。

例如：
- 长期趋势是否真的变差
- 只是最近一期异常，还是连续多个周期下滑
- 同比和环比是否一致
- 异常点是否集中在活动期/节假日/版本变更后

#### D. 异常解释框架
异常不能只报数值，要至少判断：
- 数据问题可能性
- 小样本噪声可能性
- 真实业务事件可能性

### 3. 从“解释像因果”升级到“证据分级”

建议强制区分三类表述：

#### 一级：事实描述
例如：
- North 区域 Q3 revenue 占比 42%，高于 South 的 27%。

#### 二级：相关线索
例如：
- Revenue 下滑与 orders 同期下降同时出现，二者方向一致，可作为线索。

#### 三级：接近因果的判断
只有满足更强条件时才允许：
- 时间先后明确
- 分组对照存在
- 机制上说得通
- 替代解释被部分排除

否则必须使用：
- 可能
- 疑似
- 需要进一步验证
- 不能仅据此认定为直接原因

#### 建议做证据等级标注

```text
证据等级：
- A：直接数据事实
- B：稳定相关关系 / 多切片一致
- C：合理假设，待验证
```

### 4. 从“建议生成”升级到“建议与证据绑定”

没有满足证据门槛，就不给强行动建议，只给验证建议或观察建议。

建议分三类输出：

#### A. 立即行动建议
仅当：
- 影响大
- 证据强
- 风险明确
- 可操作对象清楚

#### B. 验证型建议
当证据中等时，输出：
- 还应看什么切片
- 还应补什么数据
- 还应做什么对照分析

#### C. 观察型建议
当只是弱信号时，输出：
- 持续监测
- 建立预警阈值
- 下一周期复核

## 二、现有项目最值得补的 5 个后端能力

### 1. 增加“指标变化解释器”

建议新增 deterministic helper，例如：

```python
explain_metric_change(
    df,
    metric="revenue",
    time_col="date",
    dims=["region", "channel", "product"],
    compare="mom" | "qoq" | "yoy"
)
```

先输出结构化结果，再让 LLM 生成自然语言：

```python
{
  "metric": "revenue",
  "change": -0.12,
  "period": "2025-08 vs 2025-07",
  "top_positive_contributors": [...],
  "top_negative_contributors": [...],
  "mix_shift_signals": [...],
  "confidence": "medium",
  "hypotheses": [...],
  "recommended_checks": [...]
}
```

### 2. 增加“候选驱动因素排序”

不要让 agent 自由拍脑袋决定“主驱动”。

建议对候选因素按以下维度打分：
- 解释力：能解释多少变化量
- 稳定性：多个时间窗口/分组下是否一致
- 覆盖度：影响局部还是整体
- 先后关系：是否发生在结果变化之前
- 数据质量：该字段缺失是否严重

输出形态建议：

```text
Potential drivers ranked:
1. channel mix shift — evidence medium-high
2. order volume decline in East — evidence medium
3. discount policy change — hypothesis only
```

### 3. 增加“建议生成必须绑定证据”

recommendations 不能从空气里长出来。

规则建议：
- 证据不足时，不生成行动建议
- 只生成验证建议或观察建议
- 行动建议必须能回指到具体证据、分组、时间窗口或贡献拆解结果

### 4. 增加“业务口径检查”

在解释前先做口径确认：
- 指标定义是否明确
- 时间粒度是否统一
- 分母是否一致
- 去重规则是否明确
- 是否存在退款/取消/补录等影响口径的字段

如果未确认，应自动降级措辞：

```text
以下解释基于当前字段语义推断，因缺少明确业务口径定义，相关结论仅作为探索性线索。
```

### 5. 增加“反事实 / 对照意识”

先不必直接做真正因果推断，但至少让系统学会问：
- 排除某个大客户/大区后，结论还成立吗？
- 只看新用户/老用户时，结论还成立吗？
- 换一个时间窗口后，趋势还存在吗？
- 控制某个关键维度后，相关关系还存在吗？

这是最轻量但很有价值的“准因果意识”。

## 三、最务实的三阶段优化路径

### 第一阶段：先补“解释框架”，不要急着补复杂算法

优先补：
1. 指标变化拆解
2. 分群贡献排序
3. 证据等级标注
4. 建议与证据绑定
5. 相关不等于因果的强制表达

这一阶段最适合当前项目状态，收益最高。

### 第二阶段：补“准因果分析”能力

在第一阶段稳定后，再加：
- 分层比较
- 控制变量式切片分析
- before/after 事件窗口分析
- cohort 分析
- 留存/漏斗驱动分析
- 简单回归 / 敏感性分析

注意这仍然是辅助解释，不是自动宣称因果。

### 第三阶段：做行业化解释模板

例如：
- 电商：流量 → 转化 → 客单价 → 履约
- SaaS：线索 → 激活 → 留存 → 扩张
- 内容平台：曝光 → 点击 → 停留 → 转化
- 销售：线索 → 商机 → 赢单率 → 客单价

一旦有行业模板，解释性分析能力会显著强于通用 EDA。

## 四、对当前项目最建议先改的地方

### 1. 在 agent 主链路里新增“解释任务”

不只做：
- profile
- compare
- trend
- anomaly

还要补：
- explain_change
- rank_drivers
- assess_confidence
- generate_actionable_recommendations

### 2. 让 `finish_report` 不只审格式，还审解释质量

如果报告里出现“原因 / 驱动 / 导致 / 根因”等词，必须至少满足之一：
- 有贡献拆解结果
- 有多窗口一致性
- 有分层验证
- 有明确不确定性说明

否则拒绝。

### 3. 新增 deterministic 测试

重点不是测模型会不会“说得漂亮”，而是测系统有没有逼它按正确框架说。

建议新增测试：
- 有总指标波动时，是否触发贡献拆解
- 有分组维度时，是否输出 top contributors / laggards
- 有驱动判断时，是否标注 evidence level
- 证据不足时，是否将 action recommendation 降级为 validation recommendation
- 相关结论是否自动附带非因果提醒

---

## 最终一句话

最关键的优化，不是让系统更会写“像分析师的话”，而是让它先产出**结构化解释、候选驱动排序、证据等级与建议边界**，再去生成报告。这样它输出的才更接近真正可复核、可决策、但不过度自信的业务分析结论。
